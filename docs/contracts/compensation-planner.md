# 보상 계획기 설계 (평가 프로토콜 §8.2 시연 B)

상태: **구현 전 제안·팀 검토용.** 코드는 없다. E② 승인된 쓰기가 12/18 전에 없으면 시연 B는 이 문서까지다(프로토콜 §8.2). 작성: 2026-11-06 · 최민준. E② 입력·회차 순서는 이동찬 합의가 필요하다.

## 1. 하는 일과 하지 않는 일

- **하는 일:** 승인된 쓰기 기록에서 "새로 만든 자원"을 골라 회차 끝에 역순으로 지우는 계획을 만들고, 러너의 상태 차이로 결과 칸을 정한다.
- **보상은 생성 → 삭제뿐이다.** 수정·삭제·동작형 POST는 되돌리지 않고 기록만 남긴다.
- **회차 사이 원복이 아니다.** 회차 사이 원복은 새 컨테이너가 한다(NE14). 보상을 원복 기능으로 세지 않는다.
- **상태 변경을 자동 판별한다고 주장하지 않는다.** 생성이라는 분류는 응답 신호로 고른 후보이고, 지우기 전에 §4의 근거로 다시 거른다.
- **근거가 부족하면 지우지 않는다.** 잘못 지우면 원래 자원이 사라지므로, 놓치는 쪽을 택한다.
- **앱별 값을 코드에 넣지 않는다.** 경로·테이블 대응은 설정으로만 받는다.

## 2. 입력 (E② 소유, 필드 제안)

승인된 쓰기 시도 하나당 기록 하나다. 형식과 저장 위치는 E② 담당이 정한다. 계획기에 필요한 것은 아래다.

| 필드 | 뜻 | 민감도 |
|---|---|---|
| `attempt_id`, `sequence` | E② 시도 ID와 실행 내 순번. 역순 정렬과 계측기 행 대조에 쓴다 | 비민감 |
| `approval_ref` | 이 쓰기를 허용한 승인 참조 | 비민감 |
| `session_ref` | 요청에 쓴 보호 세션 참조. 보상도 같은 세션으로 한다 | 참조만, 값 없음 |
| `method`, `origin`, `raw_target` | 실제 전달한 요청 | 경로·쿼리에 값이 들어갈 수 있어 서버 내부 전용 |
| `outcome` | 신뢰 결과 5상태(`policy_denied`·`not_sent`·`send_attempted`·`response_received`·`outcome_unknown`) | 비민감 |
| `status` | 대상 응답 상태 코드 | 비민감 |
| `location` | 응답 `Location` 값 | 서버 내부 전용 |
| `body_id` | 응답 본문에서 뽑은 자원 id. `id_field` 설정이 있을 때만 | 서버 내부 전용 |

서버 내부 전용 값은 전달 JSON·LLM 입력·공유 로그·근거 파일에 넣지 않는다(절대규칙 2). 근거 파일에는 건수와 분류, 시도 ID만 남긴다.

## 3. 분류

위에서부터 처음 맞는 줄로 정한다.

| 조건 | 분류 | 계획 |
|---|---|---|
| `outcome`이 `policy_denied`·`not_sent` | 없음 | 대상이 바뀌지 않았으므로 칸에 넣지 않는다 |
| `outcome`이 `response_received`가 아님 | `record_only` | 결과를 모르면 지우지 않는다 |
| `method`가 POST가 아님 | `record_only` | |
| `status`가 2xx가 아님 | `record_only` | 생성 여부를 모른다 |
| `status`가 201이고 `location`이 같은 origin | `create_strong` | `location` 경로를 지운다 |
| `status`가 2xx이고 `body_id`가 있고 대상 경로 규칙을 설정이 허용 | `create_weak` | `<POST 경로>/<id>`를 지운다. §4의 사전 GET이 필수다 |
| 그 밖 | `record_only` | 동작형 POST를 생성으로 읽지 않는다 |

- `location`은 다른 origin이거나 파싱할 수 없으면 신호로 쓰지 않는다.
- `body_id`는 정수 또는 영숫자·`-`·`_`만 받는다. 경로 조립에 그 밖의 문자를 쓰지 않는다.
- `<POST 경로>`는 `raw_target`의 경로 부분만 쓴다. 쿼리·fragment는 뺀다.
- 이 표는 응답 신호만 본다. `create_strong`·`create_weak`도 §4의 근거가 없으면 지우지 않는다.

## 4. 계획과 실행

### 지우기 전 근거

2xx 응답, 사전 GET, 1회 승인은 신규 생성의 근거가 아니다. POST가 기존 자원을 갱신하고 그 id를 돌려주면(upsert) 응답만으로는 구분되지 않고, 그대로 지우면 원래 자원이 사라진다. 그래서 러너가 **보상 직전 상태 사본**을 떠서 pre와 비교하고(§6), 아래를 모두 만족하는 자원만 삭제 후보로 삼는다.

- 경로→테이블 설정(§5)으로 테이블을 정할 수 있다.
- 자원 id가 정수다(`location` 마지막 구간 또는 `body_id`).
- pre → 보상 직전 차이의 그 테이블 `added_ids`에 그 id가 있다. `added_ids`가 null이면(정수 키 없음, 스키마 변경) 부재 증거가 아니므로 통과가 아니다.

못 맞추면 지우지 않는다. 그 id가 `changed_ids`에 있으면 기존 자원을 바꾼 것으로 보고 `record_only`로 둔다. 나머지는 판단불가다(§5).

### 실행

후보를 `sequence` 역순으로 처리한다. 자원 하나마다 아래를 한다.

1. **승인:** 그 기록 하나에 묶인 1회 승인을 받는다. 메서드 DELETE, 정확한 대상, 같은 세션, 이번 실행 안에서만 유효하다. 다른 자원에 다시 쓸 수 없고, 쓰기 승인 범위를 넓히지 않는다.
2. **사전 GET:** 같은 세션으로 조회한다. 2xx가 아니면 지우지 않는다(`precheck_failed`). 대상을 지울 수 있는 상태인지 보는 단계이고 신규 생성의 근거가 아니다.
3. **DELETE:** E²를 통과해 한 번 보낸다. 재시도하지 않는다. 리다이렉트를 따르지 않는다.
4. **사후 GET:** 같은 세션으로 조회한다. 401·403을 뺀 4xx면 `deleted`, 그 밖(2xx·401·403·5xx·전송 실패)은 `delete_unconfirmed`다. 앱마다 없는 자원에 주는 코드가 달라서 404로 좁히지 않는다(11/06 실측: Juice Shop v15는 주소·카드 400, 장바구니 항목 404). 401·403은 세션이 끊긴 것일 수 있어 확인으로 치지 않는다.

사전·사후 GET도 부작용이 없다고 가정하지 않는다. 결과 판정은 §5의 상태 차이가 하고, 이 단계 결과는 판정 입력이 아니라 기록이다.

## 5. 결과 칸 (러너, 프로토콜 §8.2 표)

칸은 러너의 상태 차이로 정한다. 기록과 상태 차이를 잇는 설정이 필요하다.

- 설정 `compensation.table_by_path`: POST 경로 → SQLite 테이블(앱별 값). 지우려면 이 설정이 있어야 한다.
- 자원 키: (테이블, 정수 id).
- `before`는 pre → 보상 직전 차이, `after`는 pre → post 차이다. 둘 다 `state_diff` 출력이고 같은 컨테이너끼리 비교한다.

| 칸 | 조건 |
|---|---|
| 복구됨 | `before.added_ids`에 있었고, 보상을 시도했고, `after`의 `added_ids`·`changed_ids`·`removed_ids` 어디에도 없음 |
| 복구 실패 | `before.added_ids`에 있었고, 보상을 시도했고, `after`의 `added_ids`·`changed_ids`·`removed_ids` 중 하나에 남음 |
| 기록만 | `record_only`로 분류됨. 또는 `before.changed_ids`에 있어 기존 자원을 바꾼 것으로 보고 지우지 않음 |
| 놓침 | `after.added_ids`에 있고, 어떤 기록과도 이어지지 않고, 그 테이블로 이어지는 기록 중 id를 못 정한 것이 없음 |
| 판단불가 | 경로→테이블 설정 없음, id가 정수가 아님, `added_ids`가 null, 응답은 2xx인데 `before`에 없음, 상태 차이를 못 잼. 지우지 않는다 |

- **복구율 분모는 복구됨 + 복구 실패뿐이다.** 처음부터 저장되지 않은 자원은 보상이 지운 게 아니므로 분모에 넣지 않는다.
- **`기존 자원 삭제(기대 0)` 행을 따로 둔다.** 보상 대상이 `after.removed_ids`에 있으면 pre에 있던 자원을 지운 사고다. 복구 실패로 세고 이 행에도 건수를 올린다.
- 복구됨이어도 `sqlite_sequence`는 남는다. "내용은 원복, 흔적은 남음"으로 `sequence_changed`를 같이 보고한다.
- `changed_ids`·`removed_ids`처럼 기록만으로 끝나는 변화는 건수만 보고한다.
- 놓침은 id를 못 정한 기록이 있는 테이블에서 세지 않는다. 그 기록이 만든 행과 구분되지 않아서 놓침으로 부풀기 때문이다. 그 테이블의 건수는 판단불가로 올린다.
- 메모리 저장은 경로별 변화 건수만 있어서 자원 단위 칸에 넣지 않고, 지우지도 않는다.
- 판단불가를 복구됨이나 놓침으로 옮기지 않는다(절대규칙 5). 앱 하나에서 잰 복구율을 일반화하지 않는다.

## 6. 회차 순서 (합의 필요)

보상은 엔진이 아닌 주체의 쓰기라서 격리 구간의 귀속과 부딪힌다. 제안은 아래다.

1. 시연 B 회차는 성능 비교표에 넣지 않는다. 표를 따로 만든다.
2. 순서: 예산 종료 → 엔진 신규 작업 차단·drain → **구간 감시 닫음** → **보상 직전 상태 사본** → 삭제 후보 확정 → **보상(E² 통과, 계측기 봉인 전)** → 계측기 봉인 → post 상태 사본.
3. 구간을 먼저 닫는 이유는 사본이 대상 pause를 쓰고 Docker 이벤트를 만들기 때문이다(§8.2). 엔진 귀속은 구간을 닫을 때까지로 한다.
   엔진 차단·drain은 지금 계측기 봉인(USR1)이 함께 한다. 봉인 뒤에는 보상도 503을 받으므로 시연 B에서는 계측기를 두 단계로 나눈다. 먼저 엔진 요청을 막고 drain한 뒤 보상 시도만 통과시키고, 보상이 끝나면 최종 봉인한다. 러너·계측기 변경은 최민준 몫이고 §9-4 판단 뒤에 구현한다.
4. 계측기 행은 E² 시도 ID로 엔진 요청과 보상 요청을 가른다. 메서드별 건수(§8.1)와 엔진 요청 수에 보상 요청을 섞지 않는다.
5. 보상 뒤 새로 생긴 해결 기록은 엔진 귀속으로 세지 않는다. 그 회차의 해결 귀속은 쓰지 않는 쪽을 제안한다.

## 9. 열린 것

1. **승인 기록 형식과 응답 신호 전달**(이동찬): `location`·`body_id`를 E²가 신뢰 결과로 넘길 수 있는지. 프록시는 응답 전체를 상한까지 읽고 `ResponseComplete`를 정한다(`e2proxy/execution.go`). 그래서 값은 볼 수 있지만 결과 구조에는 아직 없다. 남은 것은 필드 추가와, 근거 파일·감사 기록으로 새지 않는 서버 내부 전달 경로다. 응답이 불완전하면 신호를 쓰지 않는다.
2. **약한 신호는 필요하다(11/06 실측, 1회용 Juice Shop v15, 일반 계정).** 주소·카드 POST는 201 + `Location`이지만 장바구니 항목 POST는 200 + `Location` 없음 + 본문 정수 id다. `Location`만 쓰면 장바구니 항목이 전부 기록만으로 남는다. 본문 id를 어느 필드에서 읽을지(`id_field`)는 앱별 설정이다. 세 경우 모두 사전 GET 200, DELETE 200이었다. 피드백 POST는 캡차가 필요해 재지 못했다.
3. **회차 순서**(§6, 이동찬·최민준): 러너·계측기 쪽은 두 단계 봉인으로 가능하다. 이동찬 확인이 필요한 것은 보상 요청이 E²를 지나 같은 보호 세션과 별도 시도 ID를 받는 경로, 그리고 엔진이 그 시도 ID를 흉내 낼 수 없다는 점이다.
4. **쓰기 승인 일정:** 쓰기 IDOR은 12/04에 판단한다. 그때 승인된 쓰기가 없으면 §7 구현은 하지 않고 이 문서로 끝낸다.
