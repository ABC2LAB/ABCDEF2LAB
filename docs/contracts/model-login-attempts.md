# 모델 로그인 시도 기록 계약 (v1)

상태: 계약 초안(최민준 작성, 이동찬 리뷰). 2026-11-26 사용자 결정을 따른다.
- 탐색·진단 모두 모델이 직접 로그인한다.
- 모델이 비밀번호와 세션 토큰을 보는 것을 허용한다.
- 모델의 성공한 로그인을 기록해 E③(증거 판정) 확정 단계 로그인에 다시 쓴다. 그래서 로그인 설정 9칸은 없앤다.

이 문서는 프로그램이 **어떤 요청을 로그인 시도로 보는지**와 **시도마다 무엇을 남기는지**를 정한다. E③ 로그인 재사용(이동찬)은 이 기록만 읽어 로그인 방법을 배운다.

## 0. 기존 결정과의 관계·효력 조건

이 계약은 아래 기존 결정과 반대 방향이다. 2026-11-26 사용자 결정으로 그것들을 대체한다.

- [계정 로그인 결정안](../account-login-decision.md)
  - 결정 3: 로그인은 프로그램의 인증 준비가 하고, 로그인 설정 칸을 둔다.
  - 결정 4: 세션은 지침 줄로 준다.
  - '하지 않는 것' 가운데 "모델이 비밀번호를 입력하는 로그인, 모델이 로그인 설정을 만드는 것".
  - S09 "프로그램이 모델 입력에 비밀번호를 넣는 일은 없다".
- CLAUDE.md 절대규칙 2의 옛 문장 "비밀번호는 어떤 계정이든 모델에 넣지 않는다". 이 문장은 2026-11-26에 이미 개정됐다. 지금 규칙 2는 등록 계정의 아이디·비밀번호를 모델 입력에 넣을 수 있고, 제품 기록은 가리지 않는다(DLP 폐기).
- E②의 "모델 요청 속 등록 비밀번호 거부"([비밀번호 응답 보호](password-response-protection.md), 사용자 결정 2026-11-23).

효력 조건은 다음과 같다.
- 이 계약은 지금 dev에서 효력이 없다. 기록 칸·판정 규칙의 합의만 먼저 한다.
- 모델 로그인 구현 PR은 그 PR이 바꾸는 동작을 설명하는 계약을 같은 PR에서 고친다: 계정 로그인 결정안(결정 3·4·'하지 않는 것'), [비밀번호 응답 보호](password-response-protection.md), [탐색 경계](exploration-boundary.md) §8과 수용시험 S09. 개발 계획·동의 문장·그 밖의 문서는 문서 PR에서 고친다(사용자 순서 2026-11-26: 모델 로그인 11/30, 문서 12/5). 절대규칙 2는 이미 개정됐다.
- E② 실행 허용을 바꾸는 부분(모델 요청 속 비밀번호 거부 삭제, 탐색 경계 로그인 예외)은 계정 로그인 결정안의 규칙대로 이동찬 또는 윤재상 승인 없이 머지하지 않는다.
- **계정 분류 폐지의 담당·순서**(#963 경준 리뷰 P2-A):
  - 서버가 회차 계정을 고를 때 `시험 계정` 표시를 보지 않는 것은 모델 로그인 PR(최민준)이 한다(`runAccounts`).
  - 표시·해제 API(`mark-test`·`unmark`)와 계정 분류 화면은 이경준 화면 PR에서 같이 걷는다. 그 전까지 서버는 이 API를 받되 결속에 쓰지 않는다.
  - 회차별 계정 동의(`external_test_accounts`)는 설치 동의 PR(#965)이 대신한다.
  - 대상에 로그인 방식(로그인 설정 9칸)이 없으면 계정을 결속하지 않는 조건은 9칸 폐지 PR(§7)까지 그대로다.
  - 그래서 그 전까지 이 계약의 "등록 계정"은 **자격이 저장되고 대상에 로그인 방식이 있는, 그 회차에 결속된 계정**이다. 결속되지 않은 계정은 `account_label`도 §2-2 쓰기 예외도 받지 않는다.

외부 모델 회차에서는 프로그램이 탐색 목표에 넣은 등록 계정 비밀번호도 제공자로 간다. 11/23 갱신은 대상 응답에 비친 비밀번호까지만 다뤘다. 그래서 **모델 로그인 구현 PR은 설치 단위 외부 전송 동의(#965, 이경준)가 먼저 들어간 뒤에만 머지한다**(#963 동찬 리뷰 P1).
- #965의 설치 동의 문장은 등록 계정의 아이디·비밀번호와 대상이 발급한 세션을 가리지 않고 외부 모델 제공자에게 보낸다는 것을 담는다. 동의가 없는 설치의 외부 모델 점검은 시작하지 않는다(`external_transfer_consent_required`).
- 그래서 모델 로그인 PR은 동의 문장을 따로 고치지 않는다. 옛 회차별 동의(11/23 문장, "로그인 비밀번호는 프로그램이 입력하며 모델에 넣지 않습니다")만 있는 설치는 #965 규칙대로 새 동의 전까지 외부 모델 점검이 시작되지 않는다.
- 로컬 모델 회차는 외부 전송이 없어 이 조건과 상관없다.

## 1. 범위

- 탐색 단계는 탐색 경계를, 진단 단계는 E②(실제 전송 통제)를 지난다. 두 단계의 모델 요청이 모두 대상이다. 확정 단계의 프로그램 로그인(E③ 재사용)도 같은 칸으로 남긴다(`actor: program`).
- 판정·기록은 프로그램이 한다. 모델이 "로그인했다"고 쓴 글은 근거가 아니다(절대규칙 4).
- 대상 앱의 로그인 경로·필드 이름·쿠키 이름을 코드에 넣지 않는다. 아래 규칙은 요청·응답의 모양만 본다.
- 아이디 제한은 없다. 등록 계정이 아닌 아이디(기본 계정 시험 등)도 로그인 시도로 보고 같은 칸·같은 실패 상한을 적용한다. 다만 §2-2 탐색 예외는 등록 계정 쌍에만 있고, 등록 밖 아이디 로그인은 쓰기 승인 범위로만 나간다.
- **등록 계정**은 대상에 등록된 계정(라벨·아이디·비밀번호) 목록이다. 프로그램은 계정을 따로 분류하지 않는다(절대규칙 2, 시험 계정만 등록하라는 공지는 사용자 책임). 아래에서 "등록 계정과 같다"는 그 목록의 아이디·비밀번호와 값이 같다는 뜻이다.

## 2. 로그인 시도로 보는 요청

두 가지를 따로 정한다(#963 동찬 리뷰 P1).
- **로그인 시도 기록**(§2-1): 무엇을 기록하고 연속 실패를 셀지. 넓게 잡는다.
- **쓰기 예외 허용**(§2-2): 쓰기 승인이 없는 회차에서 로그인 POST만 보내 주는 조건. 좁게 잡는다. 요청 모양만으로는 로그인과 비밀번호 바꾸기·가입을 안전하게 가를 수 없기 때문이다.

둘 다 보내기 전에 요청만 보고 정한다.

### 2-1. 로그인 시도 기록

요청이 아래이면 로그인 시도로 기록한다.

- **본문 로그인**: 메서드가 `POST`이고, 본문이 아래 형식 중 하나이며, 아래 규칙으로 **비밀번호 칸**이 정확히 하나 정해진다.
  - 본문 형식은 `application/x-www-form-urlencoded`, `application/json`(객체), `multipart/form-data`(파일 부분 없음)다.
  - 칸 순서는 요청 바이트에 나온 순서다(폼은 본문 순서, JSON은 키가 나온 순서).
  - **끝 조각**은 칸 이름을 `.`·`[`·`]`·`_`·`-`와 소문자→대문자 경계로 나눈 마지막 조각이다. 이름 비교는 대소문자를 무시한다.
  - **비밀번호 후보**는 다음 둘의 합집합이다.
    - 값이 등록 계정 비밀번호와 정확히 같은 칸
    - 칸 이름 전체나 나눈 조각 가운데 하나가 `password`·`passwd`·`passphrase`·`pass`·`pwd`인 칸(예: `password`, `user[password]`, `loginPassword`, `user.pwd`, `oldPassword`, `newPassword`, `passwordConfirm`). 끝 조각만 보면 가입의 `passwordConfirm`(끝 조각 `confirm`)을 놓쳐 후보가 하나로 남는다(구현에서 찾음).
  - 비밀번호 후보가 **정확히 하나**일 때만 그 칸이 비밀번호 칸이다. 둘 이상이면 로그인 시도가 아니다. 예: 비밀번호 바꾸기 `oldPassword`·`newPassword`, 가입 `password`·`passwordConfirm`.
  - **아이디 칸**은 비밀번호 칸과 `fields_from_response`(§3, CSRF 토큰 같은 칸)를 뺀 문자열 칸 가운데 아래 순서로 처음 맞는 하나다. 없으면 아이디 칸 없음으로 남긴다.
    1. 값이 등록 계정 아이디와 정확히 같은 칸
    2. 칸 이름 전체가 `username`·`user`·`login`·`email`·`mail`·`account`·`id` 가운데 하나인 칸(예: NodeGoat `userName`)
    3. 끝 조각이 `username`·`user`·`login`·`email`·`mail`·`account` 가운데 하나인 칸. `id`는 끝 조각으로는 보지 않는다(`csrf_id` 같은 칸을 잡지 않게).
  - 본문 상한은 이 판정을 위해 따로 두지 않는다. 경계·E②의 요청 본문 상한을 그대로 쓴다.

이것은 로그인 시도로 보지 않는다.
- 세션 쿠키나 토큰만 단 요청
- 비밀번호 후보가 없거나 둘 이상인 본문
- **Basic 인증**(`Authorization: Basic …`): v1은 다루지 않는다. Basic 자격은 로그인 뒤 일반 요청에도 매번 붙고, 응답이 새 세션을 주지 않아 §4 성공 규칙과 맞지 않는다(#963 동찬 리뷰 P1). Basic을 단 요청은 기존 메서드·쓰기 범위 검사를 그대로 받는다. §7 열린 것.

### 2-2. 탐색의 쓰기 예외 (팀 합의 2026-11-26: 세션 기준)

쓰기 승인 없는 탐색(`read_only`)에서 로그인 POST만 보내 주는 규칙이다. **진단 단계(E②)와 확정 단계(E③)의 로그인은 예외 없이 지금처럼 쓰기 승인 범위를 따른다.** 로그인 화면이나 주소 이름으로 로그인인지 판별하지 않는다. 대신 계정별 로그인 상태로 예외를 켜고 끈다.

**계정별 상태(예외용)** — 등록 계정 라벨마다 하나. 탐색 경계가 회차 메모리에 든다.
- `로그인 안 됨`: 처음 상태. 예외가 켜져 있다.
- `확인 중`: 예외 POST를 보냈고 판정 전이다.
- `로그인됨`: 예외가 꺼져 있다.

**예외로 보내는 요청** — 아래를 모두 채워야 한다.
- 그 계정 상태가 `로그인 안 됨`이다.
- §2-1의 본문 로그인이다(비밀번호 후보 정확히 하나).
- 아이디 칸과 비밀번호 칸의 값이 같은 등록 계정 하나의 아이디·비밀번호 쌍과 정확히 같다.
- 파일 부분이 없고, 승인 origin·경로 범위 안이며, 제외 경로·위험 경로 단어 검사를 지난다.
- 그 아이디가 §5 연속 실패 상한에 닿지 않았다.

**상태가 바뀌는 때**
- 예외 POST를 보내면 `확인 중`이 된다. 판정 전까지 그 계정의 다른 예외 POST는 보내지 않는다(한 번에 하나). 그 요청만 고정 사유 `login_verification_pending`으로 실패하고 탐색은 계속한다.
- 실패가 분명하면 `로그인 안 됨`으로 돌리고 §5 연속 실패에 센다. 분명한 실패는 다음 셋이다.
  - 400 이상(401·403 포함)
  - 로그인 화면으로 돌아감(§4 `login_form_returned`)
  - 세션이 없음(`session_source: none`): 응답이 새 세션을 주지 않았고, 로그인 요청에 실려 간 세션 쿠키(이어진 세션)도 없다. 로그인 전부터 받은 세션 쿠키를 로그인 뒤에도 그대로 쓰는 앱(세션 고정)은 `continued`라 여기에 들지 않고, 성공 여부는 대조(§4)로 가린다(#963 재상 봇 리뷰).
- §4 성공 기준(`authenticated_contrast`)이 서면 `로그인됨`이 된다.
- 실패가 분명하지 않은데 대조도 세우지 못하면(`unconfirmed`) 예외용 상태는 안전하게 `로그인됨`으로 쳐서 예외를 끈다. 화면 계정 상태(§4 표)는 그대로 `unconfirmed`다.
- 보냈는지·응답을 모르는 예외 POST(`result_unknown`)도 예외를 끈다(`로그인됨`). 결과 불명 쓰기는 자동으로 다시 보내지 않는다.
- 다른 경계 규칙(범위·제외 경로·예산 등)으로 예외 POST를 보내지 못하면 상태는 보내기 전으로 되돌린다.
- **세션 만료**: 성공 판정에 쓴 대조 URL(질의 값까지 같은 URL)을 지금 세션으로 다시 열었을 때 '막힘'(401·403이거나 로그인 화면 경로로 리다이렉트, §4 용어)이면 `로그인 안 됨`으로 돌려 다시 로그인을 허용하고 `session_ended`를 남긴다. 다른 URL이 막히거나 로그인 화면으로 가는 것만으로는 만료로 보지 않고 기록도 하지 않는다(§4와 같은 기준).

**`로그인됨`일 때** 예외는 꺼진다. 그 뒤 POST는 원래 규칙(회차의 쓰기 승인 범위)을 따른다. 승인이 없으면 그 요청만 보내지 않고 사유를 기록한다. 승인 알림은 띄우지 않고 탐색은 계속한다.

**계정별 분리**: 예외 상태는 계정마다 따로다. 브라우저 문맥(쿠키 저장소)도 계정마다 따로 둔다. 한 계정의 로그인 세션이 다른 계정 상태를 바꾸지 않는다.

**남는 위험(받아들임)** — 아래 둘은 이 규칙으로 구별하지 못한다. 시험 계정만 등록하라는 공지 범위(절대규칙 2, 사용자 책임)에서 받아들이고, 보고서 '한계' 항목 후보로 표시한다.
- 로그인 안 된 상태에서 아이디·비밀번호 한 번으로 계정을 바꾸는 요청(공개 탈퇴·계정 삭제 화면 등). 위험 경로 단어 검사에 걸리지 않는 경로면 예외로 나갈 수 있다.
- 로그인 제출에 다른 효과가 같이 붙는 경우(로그인하면서 설정을 바꾸는 폼 등).

**로그인 기록(§3)** 은 예외로 보낸 탐색 로그인뿐 아니라, 쓰기 승인 범위로 보낸 진단 단계 로그인 성공도 남긴다(E③ 재사용 §6과 배운 방법 §6-1이 이를 읽는다).

## 3. 시도마다 남기는 칸

기록 이름은 `jindo.login-attempt/v1`이고, 한 시도가 한 행이다. **비밀번호 값, 세션 값(쿠키 값·토큰), 우리 통제 비밀은 넣지 않는다.** 대상 응답 본문도 넣지 않는다. 이것들은 가림 대상이라서가 아니라 로그인 방법을 배우는 데 필요 없어서 넣지 않는다(DLP 폐기 뒤에도 기록을 작게 둔다).

| 칸 | 뜻 |
|---|---|
| `attempt_ref` | 이 기록의 시도 참조(회차 안에서 유일) |
| `run_ref`·`stage` | 회차, 단계(`exploration`·`diagnosis`·`confirmation`) |
| `actor` | `model`(모델 요청) 또는 `program`(E③ 재사용 로그인) |
| `transport_ref` | 경계 기록 순번(탐색) 또는 E② `call_ref`·`attempt_id`(진단·확정). 경계·E② 기록과 잇는 열쇠다 |
| `at` | 보낸 시각(UTC) |
| `account_label` | 아이디가 등록 계정과 같으면 그 계정 라벨, 아니면 빈 값 |
| `identifier` | 아이디 원문(256바이트까지). 아이디 칸이 없으면 빈 값. 제품 기록은 내부 담당자만 보므로 가리지 않는다(절대규칙 2, DLP 폐기) |
| `password_registered` | 비밀번호 값이 그 계정의 등록 비밀번호와 같은지(참·거짓). 값 자체는 남기지 않는다 |
| `method`·`path` | 메서드, 이 origin 기준 경로(질의 값 없음) |
| `query_keys` | 질의 키 이름 |
| `format` | `form`·`json`·`multipart` |
| `write_exception` | 쓰기 승인 없이 §2-2 탐색 예외로 보냈는지(참·거짓) |
| `identifier_field`·`password_field` | 아이디·비밀번호 칸 이름. JSON은 점 경로(`user.email`)로 남긴다 |
| `other_fields` | 나머지 본문 칸 이름(32개·64바이트까지, 값 없음) |
| `fields_from_response` | 비밀번호 칸 말고 값이 같은 회차에서 앞서 받은 대상 응답에 그대로 있던 칸 이름. CSRF 토큰처럼 로그인 화면에서 먼저 받아야 하는 칸을 배우는 데 쓴다 |
| `status` | 응답 상태. 응답이 없으면 0 |
| `transport` | `sent`(응답 받음)·`not_sent`(보내기 전 거부)·`result_unknown`(보냈는지·응답을 모름) |
| `refusal` | `not_sent`일 때 고정 사유(예: `login_attempts_exhausted`). 그 밖에는 빈 값 |
| `redirect_path` | 같은 origin으로 리다이렉트하면 그 경로, 아니면 빈 값 |
| `login_form_returned` | 로그인 응답이 로그인 화면을 다시 준 신호(§4) |
| `session_source` | 이 시도의 세션 자리. `set_cookie`(응답이 새로 준 쿠키 이름 목록), `json_field`(점 경로), `header`(헤더 이름), `continued`(응답은 새 세션을 주지 않았지만 로그인 요청에 실려 간 세션 쿠키가 있음 — 세션 고정 앱), `none`(둘 다 없음) |
| `session_names` | 위 자리의 이름들(쿠키 이름·점 경로·헤더 이름. `continued`면 로그인 요청에 실려 간 쿠키 이름) |
| `session_seen_anonymous` | `set_cookie`인 쿠키 이름 가운데, 같은 회차에서 로그인 전 요청에도 대상이 준 이름. NodeGoat `connect.sid`처럼 익명에게도 주는 쿠키는 이것만으로 성공 근거가 안 된다 |
| `session_sent_as` | 뒤 요청이 이 세션을 실어 보낸 방식. `cookie`이거나 헤더 이름과 접두(예: `Authorization`, `Bearer `). 아직 없으면 빈 값 |
| `followup` | 이 세션을 실은 뒤 요청의 결과 신호(§4). `authenticated_contrast`·`no_login_form`·`login_form`·`none` |
| `contrast_source` | 대조를 이룬 세션 없는 응답이 어디서 왔는지. `observed`(이 회차에 이미 오간 요청)·`probe`(프로그램 대조 요청, §4)·빈 값 |
| `contrast_probes` | 이 시도를 위해 보낸 프로그램 대조 요청 수(§4) |
| `session_ended` | 성공한 뒤 대조 URL을 이 세션으로 다시 열었을 때 '막힘'이었는지(세션 끊김, §2-2·§4 같은 기준) |
| `outcome` | `succeeded`·`unconfirmed`·`failed`·`not_sent`·`result_unknown`(§4) |
| `consecutive_failures` | 이 시도까지 같은 아이디의 연속 실패 수(§5) |

- 세션 값은 회차 메모리에서만 들고 뒤 요청과 대조한다. 회차가 끝나면 버린다. 이 대조로 `session_sent_as`·`followup`·`session_ended`를 채운다.
- `json_field`·`header` 후보는 토큰 모양 값만 본다: 설정 하한(기본 16바이트) 이상이고 영문·숫자와 `-_.=+/~:`만 든 값이다. 공백이 든 안내 문장·`@`가 든 메일 주소·`/`로 시작하는 경로는 세션이 아니다(실패 응답 `{"message":"Password is not correct…"}`가 세션으로 잡히지 않게). 뒤 요청이 실제로 실어 보낸 후보가 있으면 `session_source`·`session_names`를 그것으로 좁힌다.
- `session_sent_as`는 `cookie`이거나 `헤더이름:접두`(예: `Authorization:Bearer `)다.
- `followup`·`outcome`·`session_ended`는 뒤 요청이 올 때 갱신한다. 한 시도의 행은 덧붙이기로 고치고, 마지막 행이 그 시도의 지금 값이다.

## 4. 성공·실패 판정

어느 한 신호만으로 성공 처리하지 않는다. 입증할 신호가 없으면 성공이 아니라 `unconfirmed`다(개발 계획 '쿠키 로그인의 성공 판정', #958 동찬 리뷰).

**로그인 응답의 실패 신호** — 하나라도 있으면 `failed`다. §2-2의 '분명한 실패'와 같은 목록이다.
- 상태가 400 이상이다.
- 세션이 없다(`session_source: none`, 새 세션도 이어진 세션도 없음). 예: 200 응답인데 로그인 폼·리다이렉트·쿠키·토큰이 하나도 없음 → `failed`, §2-2 예외 상태 `로그인 안 됨`, §5 연속 실패 +1.
- 로그인 화면을 다시 준다(`login_form_returned`). 다음 둘 중 하나다.
  - 응답이 HTML이고 `type="password"`인 입력 칸이 있다.
  - 리다이렉트 경로가 로그인 시도 경로와 같다.

**용어** — 아래 판정은 같은 origin의 GET 요청을 **질의 값까지 같은 URL**로 본다(#963 동찬 리뷰 P2: `GET /orders?id=1` 403과 `GET /orders?id=2` 200은 자원 차이라 대조가 아니다). 비교에 쓰는 질의 값은 회차 메모리에서만 들고 기록에는 남기지 않는다(기록은 `path`·`query_keys`만).
- **로그인 화면 경로**: 로그인 시도 경로, 그리고 같은 회차에서 **세션 없이** 받은 HTML 응답에 `type="password"` 입력 칸이 있었던 경로. 세션을 실은 화면(비밀번호 바꾸기·프로필)은 여기 들지 않는다.
- **막힘**: 401·403이거나, 3xx이고 `Location` 경로가 로그인 화면 경로다. NodeGoat처럼 세션이 없으면 로그인 화면으로 302를 보내는 앱도 막힘이다(`GET /` → 302 `/login`).
- **열림**: 상태가 400 미만이고, 로그인 화면 경로로 리다이렉트되지 않았다. 다른 경로로의 3xx도 열림이다(NodeGoat 세션 있는 `GET /` → 302 `/dashboard`).
- **세션 없는 응답**: 실제로 인증을 싣지 않은 요청의 응답이다. `Cookie`·`Authorization` 헤더가 없고, 이 회차에 세션 자리로 알려진 헤더(§3 `session_names`·`session_sent_as`의 헤더 이름)도 하나도 싣지 않아야 한다. 다른 계정 세션으로 보낸 요청의 403처럼 인증을 실은 응답은 대조 근거가 아니다(#963 동찬 리뷰). 정적 크롤은 늘 인증 없이 탐색 에이전트보다 먼저 돌므로 대개 여기서 나온다.

**뒤 요청 신호** (`followup`) — 아직 `unconfirmed`인 시도의 세션을 실은 뒤 요청에서 본다.
- `authenticated_contrast`: 질의 값까지 같은 GET URL에 이 회차의 세션 없는 응답 가운데 **막힘**이 있고, 이 세션을 실은 응답은 **열림**이다. 두 응답의 순서는 따지지 않는다(세션 없는 응답이 로그인 뒤에 와도 된다). **성공 근거는 이것뿐이다.**
- `no_login_form`: 이 세션을 실은 응답이 열림인데, 아직 대조할 세션 없는 막힘 응답이 없다. 약한 신호라 성공으로 올리지 않는다.
- `login_form`: 이 세션을 실은 GET이 로그인 화면 경로로 리다이렉트된다. 실패 신호이고 §5 연속 실패에 센다. 로그인 시도 경로를 다시 열었을 때 비밀번호 칸이 보이는 것은 신호로 보지 않는다(로그인한 뒤에도 로그인 화면을 그대로 보여 주는 앱이 있다).

**모델이 먼저 로그인해 대조할 응답이 없을 때 — 프로그램 대조 요청**
- `no_login_form`인 요청이 생겼는데 질의 값까지 같은 URL의 세션 없는 응답이 이 회차에 없으면, 프로그램이 그 URL로 세션 없는 GET을 한 번 보낸다.
  - 모델이 보낸 그 요청의 **정확한 URL**(경로·질의 값 그대로)을 다시 쓰고, `Cookie`·`Authorization`과 이 회차에 세션 자리로 알려진 헤더를 모두 뺀다.
  - 탐색 단계는 탐색 경계를, 진단 단계는 E②를 지나는 프로그램 요청이다. 승인 범위·제외 경로·위험 경로 단어 검사와 요청 예산을 그대로 따른다.
  - 모델이 이미 이 세션으로 GET한 URL만 고른다. 새 URL을 만들어 보내지 않는다.
- 결과가 막힘이면 `authenticated_contrast`가 되고 `contrast_source: probe`를 남긴다. 열림이면 그 URL은 공개 화면이라 대조가 안 된다. 다음 `no_login_form` 요청이 생기면 다시 시도한다.
- 대조 요청은 시도마다 서로 다른 URL 3개까지 보낸다(설정값, 기본 3). 다 쓰도록 막힘을 못 찾으면 `unconfirmed`로 남는다.
- 대조 요청은 로그인 시도가 아니다. §5 연속 실패에 세지 않는다.
- 대조 요청은 단계와 상관없이 작업대 `target_requests`의 `login` 칸과 `total`에 센다(사용자 결정 2026-11-26). 요청 상세 목록에서는 프로그램 요청 종류 `login_contrast`, 화면 글 "프로그램 대조 요청"으로 다른 요청과 구분한다. 총계 화면(마우스를 올리면 내역)도 이 기준을 따른다(경준님).
- NodeGoat 예:
  - 정적 크롤이 세션 없이 `GET /` → 302 `/login`(막힘)을 남긴다. 로그인 뒤 모델이 세션으로 `GET /` → 302 `/dashboard`(열림)를 받으면 대조가 선다(`observed`).
  - 모델이 `/dashboard`만 열었으면 프로그램이 세션 없이 `GET /dashboard`를 보낸다. 302 `/login`(막힘)을 받으면 대조가 선다(`probe`).
  - 비밀번호가 틀리면 로그인 응답이 200에 비밀번호 칸이 있는 화면이라 바로 `failed`다.

**결과** (`outcome`)
- `succeeded`: 로그인 응답에 실패 신호가 없고, 세션이 있고(`session_source`가 `none`이 아님 — 새 세션이든 이어진 세션 `continued`든), `followup`이 `authenticated_contrast`다. 이어진 세션은 로그인 전 세션 없는 응답과 같은 쿠키일 수 있으므로, 대조의 '세션 없는 응답'은 그 쿠키를 싣지 않은 응답만 센다.
- `failed`: 로그인 응답에 실패 신호가 있거나 `followup`이 `login_form`이다.
- `unconfirmed`: 위 둘 다 아니다. 세션을 받았지만 대조할 경로가 아직 없는 경우 등이다.
- `not_sent`·`result_unknown`: 전송 결과를 그대로 남긴다. 결과 불명 로그인은 자동으로 다시 보내지 않는다.
- 한 번 `succeeded`가 된 시도는 바뀌지 않는다. 대조 URL을 그 세션으로 다시 열어 '막힘'이면 `session_ended: true`만 남긴다(세션 끊김, 실패 아님, §2-2와 같은 기준). 다른 URL의 막힘은 기록하지 않는다. 모델은 다시 로그인하면 된다.

**화면 계정 상태(`account_auth`)로 싣는 법**

등록 계정 라벨마다 그 계정의 시도 기록으로 정한다. 아래 표를 **위에서부터 차례로 보고 처음 맞는 행** 하나만 쓴다(우선순위 = 행 순서).

- **보낸 시도**: 결과(`outcome`)가 `succeeded`·`unconfirmed`·`failed`·`result_unknown`인 시도다. `not_sent`는 대상에 나가지 않았으므로 보낸 시도가 아니다.
- **마지막 보낸 시도**: 보낸 시도 가운데 시도를 시작한 순서(`attempt_ref`를 매긴 순서)로 가장 늦은 것이다. 뒤 요청으로 결과가 나중에 바뀌어도 순서는 시작 순서로 본다. 그 뒤에 온 `not_sent`는 건너뛴다.

| 순서 | 조건 | `account_auth` 값 |
|---|---|---|
| 1 | 그 계정의 시도 기록이 0건 | `not_attempted`(새 값) |
| 2 | 보낸 시도 가운데 하나라도 `succeeded` | `authenticated`(뒤 `failed`가 덮지 않음, E③ 재사용과 같은 규칙) |
| 3 | 기록은 있지만 보낸 시도가 없음(모두 `not_sent`) | `not_sent` |
| 4 | 마지막 보낸 시도가 `failed` | `login_failed`(연속 실패 상한에 닿은 계정도 여기) |
| 5 | 마지막 보낸 시도가 `unconfirmed` | `unconfirmed`(새 값) |
| 6 | 마지막 보낸 시도가 `result_unknown` | `result_unknown` |

예: `result_unknown` → `not_sent` 순서면 마지막 보낸 시도가 `result_unknown`이라 6행 `result_unknown`이다. `not_sent` 1건뿐이면 3행 `not_sent`다. `failed` → `succeeded` → `failed`면 2행 `authenticated`다. 4~6행은 보낸 시도가 하나 이상일 때만 닿으므로 빈칸이 없다.

- `session_not_found`는 모델 로그인에서 쓰지 않는다. E③ 재사용 로그인(`actor: program`)이 세션 자리를 못 찾았을 때만 남긴다.
- 값이 바뀔 때마다 `account_auth_updated_at`도 그 계정 것만 갱신한다(#936 규칙).
- 새 값(`not_attempted`·`unconfirmed`)을 서버가 싣는 PR은 **웹 파서(닫힌 값 목록)를 같은 PR에서 같이 고친다.** 화면 파서는 모르는 값을 받으면 회차 상태 응답 전체를 거부한다(#929 → #938과 같은 문제).
- 화면 경고 문구는 경준님 몫이다. `unconfirmed` 경고 제안(경준님): "로그인 성공을 확인하지 못했습니다. 이 계정은 확정 단계에서 쓰지 않을 수 있습니다. 점검은 멈추지 않습니다."

## 5. 연속 실패 상한

- 아이디별로 연속 실패를 센다. 탐색·진단·확정 단계를 합쳐 회차당이다.
  - `failed`가 되면 1을 더한다. 로그인 응답의 실패 신호로 정해졌든, 뒤 요청 `login_form`으로 나중에 정해졌든 같다(결과와 차단 기준을 맞춘다, #963 동찬 리뷰 P2). `succeeded`가 되면 0으로 되돌린다.
  - `unconfirmed`·`not_sent`·`result_unknown`은 세지도 되돌리지도 않는다.
  - 이미 `succeeded`인 시도의 대조 URL이 그 세션으로 다시 '막힘'이 되는 것은 `session_ended`이고 실패가 아니다(§2-2·§4). 다른 URL의 막힘은 세지도 기록하지도 않는다.
- 연속 실패가 3에 닿은 아이디로 새 로그인 시도를 하면, 탐색 경계와 E②가 보내기 전에 거부한다. 고정 사유는 `login_attempts_exhausted`다.
  - 그 요청만 실패하고 회차는 계속한다.
  - 거부한 시도도 한 행으로 남긴다(`transport: not_sent`, `refusal: login_attempts_exhausted`). 연속 실패 수에는 세지 않는다.
  - 뒤 요청으로 나중에 `failed`가 정해지면, 그 사이에 이미 보낸 다른 시도는 되돌리지 않는다. 상한은 그다음 시도부터 막는다.
- 아이디가 없는 시도(아이디 칸 없음)는 빈 아이디 하나로 묶어 센다.
- 상한 3은 설정값으로 둔다(코드에 박지 않음). 기본 3은 사용자 결정 2026-11-26이다.

## 6. 저장과 읽는 쪽

- 회차 상태 디렉터리의 보호 파일 `login-attempts.jsonl`(0600, 회차 단위, 덧붙이기)에 둔다. 보관·삭제는 실행 기록과 같다. 서명 저널(E② v3)에는 넣지 않는다. 저널은 지금처럼 요청 단위 감사를 맡고, 이 기록은 `transport_ref`로 저널과 잇는다.
- **E③ 로그인 재사용**(이동찬)은 `account_label`이 있고 `outcome: succeeded`인 마지막 시도에서 다음을 가져와 같은 방식으로 로그인한다.
  - `method`·`path`·`format`
  - `identifier_field`·`password_field`·`other_fields`·`fields_from_response`
  - `session_source`·`session_names`·`session_sent_as`
  - 값은 등록 자격으로 채운다. `fields_from_response` 칸은 로그인 화면을 먼저 받아 같은 이름의 값을 쓴다.
  - 성공한 시도가 없으면 그 계정은 확정 단계에 쓰지 않는다(지금의 `test_accounts_unavailable`와 같은 처리).
- 화면·보고서는 내부 담당자만 본다. 라벨이 있으면 라벨로 보이고, 등록 밖 아이디는 `identifier`로 보인다.
- 남기지 않는 것: 비밀번호 값, 세션 값, 응답 본문, OpenRouter 키·관리자 비밀번호·승인 ID 같은 우리 통제 비밀, E③ 표식.

### 6-1. 배운 로그인 방법 (회차 밖, #963 경준 리뷰 P2-B)

11/26 분담대로 계정 화면에 계정별 "로그인 방법: 배움 / 검증됨"을 보이려면 회차를 넘어 남는 값이 있어야 한다. 그래서 배운 로그인 방법을 대상 계정 저널(보호 저널, 감사 기록)에 계정별로 남긴다.
- **남기는 것**: §6 E③ 재사용이 쓰는 칸과 같다. `method`·`path`·`format`·`identifier_field`·`password_field`·`other_fields`·`fields_from_response`·`session_source`·`session_names`·`session_sent_as`. 값(아이디·비밀번호·세션)은 넣지 않는다. 출처 `run_ref`·`attempt_ref`·시각도 남긴다.
- **상태**: 계정별 하나.
  - `none`: 아직 없음.
  - `learned`: 이 계정 라벨의 모델 로그인 시도가 `succeeded`. 더 뒤의 성공이 오면 그 방법으로 바꾼다.
  - `verified`: 저장된 그 방법으로 E③ 재사용 로그인(`actor: program`)도 `succeeded`. 방법이 바뀌면 다시 `learned`가 된다.
- **비우는 때**: 대상 재승인(판이 바뀜)·계정 자격 변경·계정 삭제 때 `none`으로 돌린다. 범위나 자격이 바뀌면 그 방법이 맞는지 다시 확인해야 하기 때문이다.
- **E③ 재사용 순서**: 이 회차에 `succeeded` 시도가 있으면 그것을 먼저 쓰고, 없으면 저장된 방법을 쓴다. 둘 다 없으면 그 계정은 확정 단계에 쓰지 않는다.
- **계정 목록 응답**: 계정별 `login_method: {state: "none"|"learned"|"verified", run_ref, at}` 칸을 싣는다. 방법의 칸 이름까지 화면에 보일지는 화면 PR에서 정한다. 이 칸을 싣는 서버 PR은 웹 파서(닫힌 칸 목록)를 같은 PR에서 고친다(§4 규칙).
- 저장·갱신은 로그인 시도 기록을 구현하는 모델 로그인 PR(최민준)이, `verified` 표시는 E③ 재사용 PR(이동찬)이 한다.

## 7. 열린 것과 순서

- 다단계 로그인(MFA·OTP·캡차)은 범위 밖이다(사용자 결정: 향후).
- Basic 인증 로그인은 v1 범위 밖이다(§2-1). 지원하려면 Basic 전용 성공 규칙(세션 대신 자격 헤더 자체로 대조)과 E③ 재사용 규칙이 따로 필요하다.
- 비밀번호 이름 규칙·아이디 이름 규칙에 맞지 않는 로그인 칸(예: 앱 고유 이름)은 등록 값 일치로만 잡는다. 기본 계정 시험처럼 등록 값이 없고 이름도 안 맞으면 로그인 시도로 보지 않는다. 탐색 경계는 그 POST를 지금처럼 쓰기로 다룬다.
- 탐색 단계 로그인은 모델이 브라우저(MCP)에서 직접 한다(절대규칙 1). 브라우저가 폼을 채워 보낸 요청도 경계가 같은 모양으로 보므로 같은 규칙을 쓴다. 브라우저가 받은 세션 쿠키를 뒤 요청과 대조하는 것도 같다.
- 로그인 설정 9칸을 서버가 그만 받는 시점은 따로 정한다. 모델 로그인 PR(최민준)과 E③ 재사용 PR(이동찬)이 둘 다 들어간 뒤 한 PR에서 그만 받는다. 모델 로그인 PR 뒤에도 E③ 재사용 PR 전까지는 확정 단계가 지금 로그인 설정으로 다시 로그인한다.
  - 화면 정리(새 점검 '로그인' 칸, `TargetLoginForm`, 진행 화면 `login_method_missing` 경고)는 그 PR 순서에 맞춘다(경준님).
