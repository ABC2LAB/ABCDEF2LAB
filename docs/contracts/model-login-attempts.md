# 모델 로그인 시도 기록 계약 (v1)

상태: 계약 초안(최민준 작성, 이동찬 리뷰). 2026-11-26 사용자 결정을 따른다.
- 탐색·진단 모두 모델이 직접 로그인한다.
- 모델이 비밀번호와 세션 토큰을 보는 것을 허용한다.
- 모델의 성공한 로그인을 기록해 E③(증거 판정) 확정 단계 로그인에 다시 쓴다. 그래서 로그인 설정 9칸은 없앤다.

이 문서는 프로그램이 **어떤 요청을 로그인 시도로 보는지**와 **시도마다 무엇을 남기는지**를 정한다. E③ 로그인 재사용(이동찬)은 이 기록만 읽어 로그인 방법을 배운다.

## 1. 범위

- 탐색 단계는 탐색 경계를, 진단 단계는 E②(실제 전송 통제)를 지난다. 두 단계의 모델 요청이 모두 대상이다. 확정 단계의 프로그램 로그인(E③ 재사용)도 같은 칸으로 남긴다(`actor: program`).
- 판정·기록은 프로그램이 한다. 모델이 "로그인했다"고 쓴 글은 근거가 아니다(절대규칙 4).
- 대상 앱의 로그인 경로·필드 이름·쿠키 이름을 코드에 넣지 않는다. 아래 규칙은 요청·응답의 모양만 본다.
- 아이디 제한은 없다. 등록한 시험 계정이 아닌 아이디(기본 계정 시험 등)도 로그인 시도로 보고 같은 칸·같은 실패 상한을 적용한다.

## 2. 로그인 시도로 보는 요청

보내기 전에 요청만 보고 정한다. 탐색 경계는 이 판정으로 "로그인 POST만 예외"를 집행한다. 그래서 응답을 보기 전에 결정돼야 한다.

요청이 아래 (가) 또는 (나)이면 로그인 시도다.

- **(가) 본문 로그인**: 메서드가 `POST`이고, 본문이 아래 형식 중 하나이며, 본문 칸 가운데 **비밀번호 칸**이 정확히 하나 있다.
  - 본문 형식은 `application/x-www-form-urlencoded`, `application/json`(객체), `multipart/form-data`(파일 부분 없음)다.
  - **비밀번호 칸**은 다음 둘 중 하나다.
    - 칸 이름이 비밀번호 이름 규칙에 맞는다. 대소문자를 무시하고 칸 이름 전체나 끝 조각이 `password`·`passwd`·`passphrase`·`pass`·`pwd` 가운데 하나다(예: `password`, `user[password]`, `loginPassword`, `user.pwd`).
    - 끝 조각은 칸 이름을 `.`·`[`·`]`·`_`·`-`와 소문자→대문자 경계로 나눈 마지막 조각이다.
    - 칸 값이 이 회차에 등록된 시험 계정 비밀번호와 정확히 같다.
  - **아이디 칸**은 비밀번호 칸 말고 문자열 값을 가진 칸 가운데 아래 순서로 처음 맞는 하나다. 없으면 아이디 칸 없음으로 남긴다.
    1. 값이 등록된 시험 계정 아이디와 정확히 같은 칸
    2. 칸 이름 전체나 끝 조각이 `username`·`user`·`login`·`email`·`mail`·`id`·`account` 가운데 하나인 칸(예: NodeGoat `userName`은 전체가 `username`)
  - 본문 상한은 이 판정을 위해 따로 두지 않는다. 경계·E②의 요청 본문 상한을 그대로 쓴다.
- **(나) Basic 인증**: `Authorization: Basic …` 헤더를 단 요청이다(메서드 무관). 아이디는 헤더 안의 아이디다.

이것은 로그인 시도로 보지 않는다.
- 세션 쿠키나 토큰만 단 요청
- 비밀번호 칸이 둘 이상인 본문(비밀번호 바꾸기·가입일 수 있음). 탐색 경계는 이 요청을 예외로 받지 않는다. 진단 단계는 E②의 기존 쓰기 승인 범위를 따른다.

## 3. 시도마다 남기는 칸

기록 이름은 `jindo.login-attempt/v1`이고, 한 시도가 한 행이다. **비밀번호 값, 세션 값(쿠키 값·토큰), 우리 통제 비밀은 넣지 않는다.** 대상 응답 본문도 넣지 않는다.

| 칸 | 뜻 |
|---|---|
| `attempt_ref` | 이 기록의 시도 참조(회차 안에서 유일) |
| `run_ref`·`stage` | 회차, 단계(`exploration`·`diagnosis`·`confirmation`) |
| `actor` | `model`(모델 요청) 또는 `program`(E③ 재사용 로그인) |
| `transport_ref` | 경계 기록 순번(탐색) 또는 E② `call_ref`·`attempt_id`(진단·확정). 경계·E② 기록과 잇는 열쇠다 |
| `at` | 보낸 시각(UTC) |
| `account_label` | 아이디가 등록된 시험 계정과 같으면 그 계정 라벨, 아니면 빈 값 |
| `identifier` | 아이디 원문(256바이트까지). 아이디 칸이 없으면 빈 값 |
| `password_registered` | 비밀번호 값이 그 계정의 등록 비밀번호와 같은지(참·거짓). 값 자체는 남기지 않는다 |
| `method`·`path` | 메서드, 이 origin 기준 경로(질의 값 없음) |
| `query_keys` | 질의 키 이름 |
| `format` | `form`·`json`·`multipart`·`basic` |
| `identifier_field`·`password_field` | 아이디·비밀번호 칸 이름. JSON은 점 경로(`user.email`)로 남긴다. `basic`은 빈 값 |
| `other_fields` | 나머지 본문 칸 이름(32개·64바이트까지, 값 없음) |
| `fields_from_response` | 나머지 칸 가운데, 값이 같은 회차에서 앞서 받은 대상 응답에 그대로 있던 칸 이름. CSRF 토큰처럼 로그인 화면에서 먼저 받아야 하는 칸을 배우는 데 쓴다 |
| `status` | 응답 상태. 응답이 없으면 0 |
| `transport` | `sent`(응답 받음)·`not_sent`(보내기 전 거부)·`result_unknown`(보냈는지·응답을 모름) |
| `redirect_path` | 같은 origin으로 리다이렉트하면 그 경로, 아니면 빈 값 |
| `login_form_returned` | 응답이 로그인 화면을 다시 준 신호(§4) |
| `session_source` | 이 응답이 새로 준 세션 자리. `set_cookie`(쿠키 이름 목록), `json_field`(점 경로), `header`(헤더 이름), `none` |
| `session_names` | 위 자리의 이름들(쿠키 이름·점 경로·헤더 이름) |
| `session_seen_anonymous` | `set_cookie`인 쿠키 이름 가운데, 같은 회차에서 로그인 전 요청에도 대상이 준 이름. NodeGoat `connect.sid`처럼 익명에게도 주는 쿠키는 이것만으로 성공 근거가 안 된다 |
| `session_sent_as` | 뒤 요청이 이 세션을 실어 보낸 방식. `cookie`이거나 헤더 이름과 접두(예: `Authorization`, `Bearer `). 아직 없으면 빈 값 |
| `followup` | 이 세션을 실은 뒤 요청의 결과 신호(§4). `authenticated_contrast`·`no_login_form`·`login_form`·`none` |
| `outcome` | `succeeded`·`unconfirmed`·`failed`·`not_sent`·`result_unknown`(§4) |
| `consecutive_failures` | 이 시도까지 같은 아이디의 연속 실패 수(§5) |

- 세션 값은 회차 메모리에서만 들고 뒤 요청과 대조한다. 회차가 끝나면 버린다. 이 대조로 `session_sent_as`·`followup`을 채운다.
- `followup`·`outcome`은 뒤 요청이 올 때 갱신한다. 한 시도의 행은 덧붙이기로 고치고, 마지막 행이 그 시도의 지금 값이다.

## 4. 성공·실패 판정

어느 한 신호만으로 성공 처리하지 않는다. 입증할 신호가 없으면 성공이 아니라 `unconfirmed`다(개발 계획 '쿠키 로그인의 성공 판정', #958 동찬 리뷰).

**로그인 응답의 실패 신호** — 하나라도 있으면 `failed`다.
- 상태가 400 이상이다.
- 로그인 화면을 다시 준다(`login_form_returned`). 다음 둘 중 하나다.
  - 응답이 HTML이고 `type="password"`인 입력 칸이 있다.
  - 리다이렉트 경로가 로그인 시도 경로와 같다.

**뒤 요청 신호** (`followup`) — 이 세션을 실은 뒤 요청에서 본다.
- `authenticated_contrast`: 같은 회차에서 세션 없이 보냈을 때 401·403이었거나 로그인 경로로 리다이렉트된 GET 경로가, 이 세션을 싣자 2xx다. **성공 근거는 이것뿐이다.**
- `no_login_form`: 상태가 400 미만이고, 로그인 경로로 리다이렉트되지 않았고, HTML이면 비밀번호 입력 칸이 없다. 약한 신호라 성공으로 올리지 않는다.
- `login_form`: 로그인 경로로 리다이렉트되거나 HTML에 비밀번호 입력 칸이 있다. 실패 신호다.

**결과** (`outcome`)
- `succeeded`: 로그인 응답에 실패 신호가 없고, 새 세션이 있고(`session_source`가 `none`이 아님), `followup`이 `authenticated_contrast`다.
- `failed`: 로그인 응답에 실패 신호가 있거나 `followup`이 `login_form`이다.
- `unconfirmed`: 위 둘 다 아니다. 세션을 받았지만 대조할 경로가 아직 없는 경우 등이다.
- `not_sent`·`result_unknown`: 전송 결과를 그대로 남긴다. 결과 불명 로그인은 자동으로 다시 보내지 않는다.

화면 계정 상태는 `succeeded`만 인증됨으로 보인다. `unconfirmed`는 "확인 안 됨"으로 보이고 계정 경고를 띄운다.

## 5. 연속 실패 상한

- 아이디별로 연속 실패를 센다. 탐색·진단·확정 단계를 합쳐 회차당이다. `failed`면 1을 더하고 `succeeded`면 0으로 되돌린다. `unconfirmed`·`not_sent`·`result_unknown`은 세지도 되돌리지도 않는다.
- 연속 실패가 3에 닿은 아이디로 새 로그인 시도를 하면, 탐색 경계와 E②가 보내기 전에 거부한다. 고정 사유는 `login_attempts_exhausted`다.
  - 그 요청만 실패하고 회차는 계속한다.
  - 거부한 시도도 한 행으로 남긴다(`transport: not_sent`). 연속 실패 수에는 세지 않는다.
- 아이디가 없는 시도(아이디 칸 없음)는 빈 아이디 하나로 묶어 센다.
- 상한 3은 설정값으로 둔다(코드에 박지 않음). 기본 3은 사용자 결정 2026-11-26이다.
- 뒤 요청 신호로 나중에 `failed`가 된 시도도 그때 센다. 그 사이에 이미 보낸 시도는 되돌리지 않는다.

## 6. 저장과 읽는 쪽

- 회차 상태 디렉터리의 보호 파일 `login-attempts.jsonl`(0600, 회차 단위, 덧붙이기)에 둔다. 보관·삭제는 실행 기록과 같다. 서명 저널(E② v3)에는 넣지 않는다. 저널은 지금처럼 요청 단위 감사를 맡고, 이 기록은 `transport_ref`로 저널과 잇는다.
- **E③ 로그인 재사용**(이동찬)은 `account_label`이 있고 `outcome: succeeded`인 마지막 시도에서 다음을 가져와 같은 방식으로 로그인한다.
  - `method`·`path`·`format`
  - `identifier_field`·`password_field`·`other_fields`·`fields_from_response`
  - `session_source`·`session_names`·`session_sent_as`
  - 값은 등록 자격으로 채운다. `fields_from_response` 칸은 로그인 화면을 먼저 받아 같은 이름의 값을 쓴다.
  - 성공한 시도가 없으면 그 계정은 확정 단계에 쓰지 않는다(지금의 `test_accounts_unavailable`와 같은 처리).
- 화면·보고서는 이 기록의 라벨·경로·칸 이름·결과만 보인다(내부 담당자만 봄). `identifier`는 내부 화면에만 보인다.
- 남기지 않는 것: 비밀번호 값, 세션 값, 응답 본문, OpenRouter 키·관리자 비밀번호·승인 ID 같은 우리 통제 비밀, E③ 표식.

## 7. 열린 것

- 다단계 로그인(MFA·OTP·캡차)은 범위 밖이다(사용자 결정: 향후).
- 비밀번호 이름 규칙·아이디 이름 규칙에 맞지 않는 로그인 칸(예: 앱 고유 이름)은 등록 비밀번호 값 일치로만 잡는다. 기본 계정 시험처럼 등록 값이 없고 이름도 안 맞으면 로그인 시도로 보지 않는다. 탐색 경계는 그 POST를 지금처럼 쓰기로 다룬다.
- 브라우저(MCP)로 폼을 채워 로그인하는 경우도 경계는 같은 요청을 보므로 같은 규칙을 쓴다. 브라우저가 쓴 세션 쿠키를 뒤 요청과 대조하는 것도 같다.
