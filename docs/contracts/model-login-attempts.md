# 모델 로그인 시도 기록 계약 (v1)

상태: 계약 초안(최민준 작성, 이동찬 리뷰). 2026-11-26 사용자 결정을 따른다.
- 탐색·진단 모두 모델이 직접 로그인한다.
- 모델이 비밀번호와 세션 토큰을 보는 것을 허용한다.
- 모델의 성공한 로그인을 기록해 E③(증거 판정) 확정 단계 로그인에 다시 쓴다. 그래서 로그인 설정 9칸은 없앤다.

이 문서는 프로그램이 **어떤 요청을 로그인 시도로 보는지**와 **시도마다 무엇을 남기는지**를 정한다. E③ 로그인 재사용(이동찬)은 이 기록만 읽어 로그인 방법을 배운다.

## 0. 기존 결정과의 관계·효력 조건

이 계약은 아래 기존 결정과 반대 방향이다. 2026-11-26 사용자 결정으로 그것들을 대체한다.

- [계정 로그인 결정안](../account-login-decision.md)
  - 결정 3: 로그인은 프로그램의 인증 준비가 하고, 로그인 설정 칸을 둔다.
  - 결정 4: 세션은 지침 줄로 준다.
  - '하지 않는 것' 가운데 "모델이 비밀번호를 입력하는 로그인, 모델이 로그인 설정을 만드는 것".
  - S09 "프로그램이 모델 입력에 비밀번호를 넣는 일은 없다".
- CLAUDE.md 절대규칙 2의 옛 문장 "비밀번호는 어떤 계정이든 모델에 넣지 않는다". 이 문장은 2026-11-26에 이미 개정됐다. 지금 규칙 2는 등록 계정의 아이디·비밀번호를 모델 입력에 넣을 수 있고, 제품 기록은 가리지 않는다(DLP 폐기).
- E②의 "모델 요청 속 등록 비밀번호 거부"([비밀번호 응답 보호](password-response-protection.md), 사용자 결정 2026-11-23).

효력 조건은 다음과 같다.
- 이 계약은 지금 dev에서 효력이 없다. 기록 칸·판정 규칙의 합의만 먼저 한다.
- 모델 로그인 구현 PR은 그 PR이 바꾸는 동작을 설명하는 계약을 같은 PR에서 고친다: 계정 로그인 결정안(결정 3·4·'하지 않는 것'), [비밀번호 응답 보호](password-response-protection.md), [탐색 경계](exploration-boundary.md) §8과 수용시험 S09. 개발 계획·동의 문장·그 밖의 문서는 문서 PR에서 고친다(사용자 순서 2026-11-26: 모델 로그인 11/30, 문서 12/5). 절대규칙 2는 이미 개정됐다.
- E② 실행 허용을 바꾸는 부분(모델 요청 속 비밀번호 거부 삭제, 탐색 경계 로그인 예외)은 계정 로그인 결정안의 규칙대로 이동찬 또는 윤재상 승인 없이 머지하지 않는다.
- **계정 분류 폐지의 담당·순서**(#963 경준 리뷰 P2-A):
  - 서버가 회차 계정을 고를 때 `시험 계정` 표시를 보지 않는 것은 모델 로그인 PR(최민준)이 한다(`runAccounts`).
  - 표시·해제 API(`mark-test`·`unmark`)와 계정 분류 화면은 이경준 PR에서 걷는다 — 화면 #972, 서버(경로 · 제어 작업 · `ProductAccount` 분류 칸 · 표시 진술) 그 뒤 서버 PR. 예전 저널의 표시 · 해제 줄은 다시 읽기만 한다.
  - 회차별 계정 동의(`external_test_accounts`)는 설치 동의 PR(#965)이 대신한다.
  - 대상에 로그인 방식(로그인 설정 9칸)이 없으면 계정을 결속하지 않는 조건은 9칸 폐지 PR(§7)까지 그대로다.
  - 그래서 그 전까지 이 계약의 "등록 계정"은 **자격이 저장되고 대상에 로그인 방식이 있는, 그 회차에 결속된 계정**이다. 결속되지 않은 계정은 `account_label`도 §2-2 쓰기 예외도 받지 않는다.

외부 모델 회차에서는 프로그램이 탐색 목표에 넣은 등록 계정 비밀번호도 제공자로 간다. 11/23 갱신은 대상 응답에 비친 비밀번호까지만 다뤘다. 그래서 **모델 로그인 구현 PR은 설치 단위 외부 전송 동의(#965, 이경준)가 먼저 들어간 뒤에만 머지한다**(#963 동찬 리뷰 P1).
- #965의 설치 동의 문장은 등록 계정의 아이디·비밀번호와 대상이 발급한 세션을 가리지 않고 외부 모델 제공자에게 보낸다는 것을 담는다. 동의가 없는 설치의 외부 모델 점검은 시작하지 않는다(`external_transfer_consent_required`).
- 그래서 모델 로그인 PR은 동의 문장을 따로 고치지 않는다. 옛 회차별 동의(11/23 문장, "로그인 비밀번호는 프로그램이 입력하며 모델에 넣지 않습니다")만 있는 설치는 #965 규칙대로 새 동의 전까지 외부 모델 점검이 시작되지 않는다.
- 로컬 모델 회차는 외부 전송이 없어 이 조건과 상관없다.

## 1. 범위

- 탐색 단계는 탐색 경계를, 진단 단계는 E②(실제 전송 통제)를 지난다. 두 단계의 모델 요청이 모두 대상이다. 확정 단계의 프로그램 로그인(E③ 재사용)도 같은 칸으로 남긴다(`actor: program`).
- 판정·기록은 프로그램이 한다. 모델이 "로그인했다"고 쓴 글은 근거가 아니다(절대규칙 4).
- 대상 앱의 로그인 경로·필드 이름·쿠키 이름을 코드에 넣지 않는다. 아래 규칙은 요청·응답의 모양만 본다.
- 판정은 계정 등록 여부와 상관없이 제품 회차마다 한다(E② 정책 최상위 `login_attempts`, 탐색 경계는 `open`의 `login`). 계정을 등록하지 않은 회차도 등록 밖 아이디 로그인의 §5 상한을 받는다(사용자 결정 2026-11-26). 계정 없는 회차의 진단 단계에서 모델이 세션(쿠키·`Authorization`)을 싣지 못하는 것은 ⑤ 전과 같다(E② 경계 결정, 측정 뒤 다시 본다).
- 아이디 제한은 없다. 등록 계정이 아닌 아이디(기본 계정 시험 등)도 로그인 시도로 보고 같은 칸·같은 실패 상한을 적용한다. 다만 §2-2 탐색 예외는 등록 계정 쌍에만 있고, 등록 밖 아이디 로그인은 쓰기 승인 범위로만 나간다.
- **등록 계정**은 대상에 등록된 계정(라벨·아이디·비밀번호) 목록이다. 프로그램은 계정을 따로 분류하지 않는다(절대규칙 2, 시험 계정만 등록하라는 공지는 사용자 책임). 아래에서 "등록 계정과 같다"는 그 목록의 아이디·비밀번호와 값이 같다는 뜻이다.

## 2. 로그인 시도로 보는 요청

두 가지를 따로 정한다(#963 동찬 리뷰 P1).
- **로그인 시도 기록**(§2-1): 무엇을 기록하고 연속 실패를 셀지. 넓게 잡는다.
- **쓰기 예외 허용**(§2-2): 쓰기 승인이 없는 회차에서 로그인 POST만 보내 주는 조건. 좁게 잡는다. 요청 모양만으로는 로그인과 비밀번호 바꾸기·가입을 안전하게 가를 수 없기 때문이다.

둘 다 보내기 전에 요청만 보고 정한다.

### 2-1. 로그인 시도 기록

요청이 아래이면 로그인 시도로 기록한다.

- **본문 로그인**: 메서드가 `POST`이고, 본문이 아래 형식 중 하나이며, 아래 규칙으로 **비밀번호 칸**이 정확히 하나 정해진다.
  - 본문 형식은 `application/x-www-form-urlencoded`, `application/json`(객체), `multipart/form-data`(파일 부분 없음)다.
  - 칸 순서는 요청 바이트에 나온 순서다(폼은 본문 순서, JSON은 키가 나온 순서).
  - **끝 조각**은 칸 이름을 `.`·`[`·`]`·`_`·`-`와 소문자→대문자 경계로 나눈 마지막 조각이다. 이름 비교는 대소문자를 무시한다.
  - **비밀번호 후보**는 다음 둘의 합집합이다.
    - 값이 등록 계정 비밀번호와 정확히 같은 칸
    - 값이 든 문자열 칸 가운데, 칸 이름 전체나 나눈 조각 가운데 하나가 `password`·`passwd`·`passphrase`·`pass`·`pwd`인 칸. 값이 `on`·`off`·`true`·`false`·`yes`·`no`·`1`·`0`·빈 값인 켜고 끄는 칸(`rememberPassword=on`·`showPassword:false`)은 이름이 맞아도 후보가 아니다(#963 재상 봇 P3, 등록 비밀번호와 값이 같은 칸은 그대로 후보)(예: `password`, `user[password]`, `loginPassword`, `user.pwd`, `oldPassword`, `newPassword`, `passwordConfirm`). 끝 조각만 보면 가입의 `passwordConfirm`(끝 조각 `confirm`)을 놓쳐 후보가 하나로 남는다(구현에서 찾음).
  - 비밀번호 후보가 **정확히 하나**일 때만 그 칸이 비밀번호 칸이다. 둘 이상이면 로그인 시도가 아니다. 예: 비밀번호 바꾸기 `oldPassword`·`newPassword`, 가입 `password`·`passwordConfirm`.
  - **아이디 칸**은 비밀번호 칸과 `fields_from_response`(§3, CSRF 토큰 같은 칸)를 뺀 문자열 칸 가운데 아래 순서로 처음 맞는 하나다. 없으면 아이디 칸 없음으로 남긴다.
    1. 값이 등록 계정 아이디와 정확히 같은 칸
    2. 칸 이름 전체가 `username`·`user`·`login`·`email`·`mail`·`account`·`id` 가운데 하나인 칸(예: NodeGoat `userName`)
    3. 끝 조각이 `username`·`user`·`login`·`email`·`mail`·`account` 가운데 하나인 칸. `id`는 끝 조각으로는 보지 않는다(`csrf_id` 같은 칸을 잡지 않게).
  - 본문 상한은 이 판정을 위해 따로 두지 않는다. 경계·E②의 요청 본문 상한을 그대로 쓴다.

이것은 로그인 시도로 보지 않는다.
- 세션 쿠키나 토큰만 단 요청
- 비밀번호 후보가 없거나 둘 이상인 본문
- **Basic 인증**(`Authorization: Basic …`): v1은 다루지 않는다. Basic 자격은 로그인 뒤 일반 요청에도 매번 붙고, 응답이 새 세션을 주지 않아 §4 성공 규칙과 맞지 않는다(#963 동찬 리뷰 P1). Basic을 단 요청은 기존 메서드·쓰기 범위 검사를 그대로 받는다. §7 열린 것.

### 2-2. 탐색의 쓰기 예외 (팀 합의 2026-11-26: 세션 기준)

쓰기 승인 없는 탐색(`read_only`)에서 로그인 POST만 보내 주는 규칙이다. **진단 단계(E②)와 확정 단계(E③)의 로그인은 예외 없이 지금처럼 쓰기 승인 범위를 따른다.** 로그인 화면이나 주소 이름으로 로그인인지 판별하지 않는다. 대신 계정별 로그인 상태로 예외를 켜고 끈다.

**계정별 상태(예외용)** — 등록 계정 라벨마다 하나. 탐색 경계가 회차 메모리에 든다.
- `로그인 안 됨`: 처음 상태. 예외가 켜져 있다.
- `확인 중`: 예외 POST를 보냈고 판정 전이다.
- `로그인됨`: 예외가 꺼져 있다.

**예외로 보내는 요청** — 아래를 모두 채워야 한다.
- 그 계정 상태가 `로그인 안 됨`이다.
- §2-1의 본문 로그인이다(비밀번호 후보 정확히 하나).
- 아이디 칸과 비밀번호 칸의 값이 같은 등록 계정 하나의 아이디·비밀번호 쌍과 정확히 같다.
- 파일 부분이 없고, 승인 origin·경로 범위 안이며, 제외 경로·위험 경로 단어 검사를 지난다.
- 그 아이디가 §5 연속 실패 상한에 닿지 않았다.
- 요청이 그 계정의 확인된 세션 값(`succeeded` 시도의 세션을 §3 `session_sent_as` 방식 그대로)을 싣지 않았다. 실었으면 로그인됨으로 보고 원래 규칙(쓰기 승인 범위)을 따른다. 브라우저 문맥을 바꿔 상태가 `로그인 안 됨`이 돼도 직접 요청(curl)은 그 세션을 들고 있을 수 있고 서버 세션은 살아 있을 수 있기 때문이다(사용자 결정 2026-11-26). 이 판단은 그 요청에만 쓰고 계정 상태는 바꾸지 않는다.

**상태가 바뀌는 때**
- 예외 POST를 보내면 `확인 중`이 된다. 판정 전까지 그 계정의 다른 예외 POST는 보내지 않는다(한 번에 하나). 그 요청만 고정 사유 `login_verification_pending`으로 실패하고 탐색은 계속한다.
- 실패가 분명하면 `로그인 안 됨`으로 돌리고 §5 연속 실패에 센다. 분명한 실패는 다음 셋이다.
  - 400 이상(401·403 포함)
  - 로그인 화면으로 돌아감(§4 `login_form_returned`)
  - 세션이 없음(`session_source: none`): 응답이 새 세션을 주지 않았고, 로그인 요청에 실려 간 세션 쿠키(이어진 세션)도 없다. 로그인 전부터 받은 세션 쿠키를 로그인 뒤에도 그대로 쓰는 앱(세션 고정)은 `continued`라 여기에 들지 않고, 성공 여부는 대조(§4)로 가린다(#963 재상 봇 리뷰).
- §4 성공 기준(`authenticated_contrast`)이 서면 `로그인됨`이 된다.
- 실패가 분명하지 않은데 대조도 세우지 못하면(`unconfirmed`) 예외용 상태는 안전하게 `로그인됨`으로 쳐서 예외를 끈다. 화면 계정 상태(§4 표)는 그대로 `unconfirmed`다. 꺼지는 것은 쓰기 예외뿐이다. 브라우저 세션(쿠키)은 그대로 두고 모델은 그 세션으로 탐색을 계속한다.
- 보냈는지·응답을 모르는 예외 POST(`result_unknown`)도 예외를 끈다(`로그인됨`). 결과 불명 쓰기는 자동으로 다시 보내지 않는다.
- 다른 경계 규칙(범위·제외 경로·예산 등)으로 예외 POST를 보내지 못하면 상태는 보내기 전으로 되돌린다.
- **세션 만료**: 성공 판정에 쓴 대조 URL(질의 값까지 같은 URL)을 지금 세션으로 다시 열었을 때 '막힘'(401·403이거나 로그인 화면 경로로 리다이렉트, §4 용어)이면 `로그인 안 됨`으로 돌려 다시 로그인을 허용하고 `session_ended`를 남긴다. 다른 URL이 막히거나 로그인 화면으로 가는 것만으로는 만료로 보지 않고 기록도 하지 않는다(§4와 같은 기준).

**`로그인됨`일 때** 예외는 꺼진다. 그 뒤 POST는 원래 규칙(회차의 쓰기 승인 범위)을 따른다. 승인이 없으면 그 요청만 보내지 않고 사유를 기록한다. 승인 알림은 띄우지 않고 탐색은 계속한다.

**계정별 분리**: 예외 상태는 계정마다 따로다. 브라우저 문맥(쿠키 저장소)도 계정마다 따로 둔다. 한 계정의 로그인 세션이 다른 계정 상태를 바꾸지 않는다.
- 방식은 **한 번에 한 계정 문맥**이다(사용자 결정 2026-11-26 (나)). 탐색 모델은 `switch_browser_account`로 지금 문맥을 닫고 쿠키 없는 새 문맥을 연 뒤 다른 계정으로 로그인한다. 쿠키가 섞이지 않아야 요청이 어느 계정 세션을 실었는지 분명하고, 세션 기준 쓰기 예외가 그것을 전제로 한다. A·B 비교는 진단 단계(E②)와 E③가 한다.
- 같은 브라우저 문맥에 다른 등록 계정이 로그인 중이거나(판정 대기) 로그인해 있으면(성공·`unconfirmed`), 그 문맥의 다른 계정 로그인은 보내기 전에 막는다(`browser_account_in_use`, 행 `refusal`). 실패한 계정은 문맥을 잡지 않는다. 직접 입구(Bash·curl) 요청은 이 '한 문맥 한 계정' 규칙만 받지 않는다. 계정 상태·쓰기 예외·§5 연속 실패 상한은 입구와 상관없이 똑같이 받는다(우회 방지).
- 문맥을 새로 열면 닫힌 문맥에서 로그인한 계정은 쿠키가 사라졌으므로 `로그인 안 됨`으로 돌아가 다시 로그인할 수 있다. 지금 구현은 저장해 둔 세션을 새 문맥에 다시 싣지 않는다.
- 다시 싣는 구현을 넣으면: 다시 실은 계정은 `로그인됨`으로 두고 예외를 끈다. 만료가 확인되면(위 세션 만료 기준) 그때 `로그인 안 됨`으로 돌린다. 다시 실은 세션을 `로그인 안 됨`으로 시작하면 로그인된 상태에서 예외가 켜진 채가 된다(사용자 결정 2026-11-26).

**남는 위험(받아들임)** — 아래 둘은 이 규칙으로 구별하지 못한다. 시험 계정만 등록하라는 공지 범위(절대규칙 2, 사용자 책임)에서 받아들이고, 보고서 '한계' 항목 후보로 표시한다.
- 로그인 안 된 상태에서 아이디·비밀번호 한 번으로 계정을 바꾸는 요청(공개 탈퇴·계정 삭제 화면 등). 위험 경로 단어 검사에 걸리지 않는 경로면 예외로 나갈 수 있다.
- 로그인 제출에 다른 효과가 같이 붙는 경우(로그인하면서 설정을 바꾸는 폼 등).

**로그인 기록(§3)** 은 예외로 보낸 탐색 로그인뿐 아니라, 쓰기 승인 범위로 보낸 진단 단계 로그인 성공도 남긴다(E③ 재사용 §6과 배운 방법 §6-1이 이를 읽는다).

## 3. 시도마다 남기는 칸

기록 이름은 `jindo.login-attempt/v1`이고, 한 시도가 한 행이다. **비밀번호 값, 세션 값(쿠키 값·토큰), 우리 통제 비밀은 넣지 않는다.** 대상 응답 본문도 넣지 않는다. 이것들은 가림 대상이라서가 아니라 로그인 방법을 배우는 데 필요 없어서 넣지 않는다(DLP 폐기 뒤에도 기록을 작게 둔다).

| 칸 | 뜻 |
|---|---|
| `attempt_ref` | 이 기록의 시도 참조(회차 안에서 유일) |
| `run_ref`·`stage` | 회차, 단계(`exploration`·`diagnosis`·`confirmation`) |
| `actor` | `model`(모델 요청) 또는 `program`(E③ 재사용 로그인) |
| `transport_ref` | 경계 기록 순번(탐색) 또는 E② `call_ref`·`attempt_id`(진단·확정). 경계·E② 기록과 잇는 열쇠다 |
| `at` | 보낸 시각(UTC) |
| `account_label` | 아이디가 등록 계정과 같으면 그 계정 라벨, 아니면 빈 값 |
| `identifier` | 아이디 원문(256바이트까지). 아이디 칸이 없으면 빈 값. 제품 기록은 내부 담당자만 보므로 가리지 않는다(절대규칙 2, DLP 폐기) |
| `password_registered` | 비밀번호 값이 그 계정의 등록 비밀번호와 같은지(참·거짓). 값 자체는 남기지 않는다 |
| `method`·`path` | 메서드, 이 origin 기준 경로(질의 값 없음) |
| `query_keys` | 질의 키 이름 |
| `format` | `form`·`json`·`multipart` |
| `write_exception` | 쓰기 승인 없이 §2-2 탐색 예외로 보냈는지(참·거짓) |
| `identifier_field`·`password_field` | 아이디·비밀번호 칸 이름. JSON은 점 경로(`user.email`)로 남긴다 |
| `other_fields` | 나머지 본문 칸 이름(32개·64바이트까지, 값 없음) |
| `fields_from_response` | 비밀번호 칸 말고 값이 같은 회차에서 앞서 받은 대상 응답에 그대로 있던 칸 이름. CSRF 토큰처럼 로그인 화면에서 먼저 받아야 하는 칸을 배우는 데 쓴다 |
| `status` | 응답 상태. 응답이 없으면 0 |
| `transport` | `sent`(응답 받음)·`not_sent`(보내기 전 거부)·`result_unknown`(보냈는지·응답을 모름) |
| `refusal` | `not_sent`일 때 고정 사유(예: `login_attempts_exhausted`). 그 밖에는 빈 값 |
| `redirect_path` | 같은 origin으로 리다이렉트하면 그 경로, 아니면 빈 값 |
| `login_form_returned` | 로그인 응답이 로그인 화면을 다시 준 신호(§4) |
| `session_source` | 이 시도의 세션 자리. `set_cookie`(응답이 새로 준 쿠키 이름 목록), `json_field`(점 경로), `header`(헤더 이름), `continued`(응답은 새 세션을 주지 않았지만 로그인 요청에 실려 간 세션 쿠키가 있음 — 세션 고정 앱), `none`(둘 다 없음) |
| `session_names` | 위 자리의 이름들(쿠키 이름·점 경로·헤더 이름. `continued`면 로그인 요청에 실려 간 쿠키 이름) |
| `session_seen_anonymous` | `set_cookie`인 쿠키 이름 가운데, 같은 회차에서 로그인 전 요청에도 대상이 준 이름. NodeGoat `connect.sid`처럼 익명에게도 주는 쿠키는 이것만으로 성공 근거가 안 된다 |
| `session_sent_as` | 뒤 요청이 이 세션을 실어 보낸 방식. `cookie`이거나 헤더 이름과 접두(예: `Authorization`, `Bearer `). 아직 없으면 빈 값 |
| `followup` | 이 세션을 실은 뒤 요청의 결과 신호(§4). `authenticated_contrast`·`no_login_form`·`login_form`·`none` |
| `contrast_source` | 대조를 이룬 세션 없는 응답이 어디서 왔는지. `observed`(이 회차에 이미 오간 요청)·`probe`(프로그램 대조 요청, §4)·빈 값 |
| `contrast_probes` | 이 시도를 위해 보낸 프로그램 대조 요청 수(§4) |
| `session_ended` | 성공한 뒤 대조 URL을 이 세션으로 다시 열었을 때 '막힘'이었는지(세션 끊김, §2-2·§4 같은 기준) |
| `outcome` | `succeeded`·`unconfirmed`·`failed`·`not_sent`·`result_unknown`(§4) |
| `consecutive_failures` | 이 시도까지 같은 아이디의 연속 실패 수(§5) |

- 세션 값은 회차 메모리에서만 들고 뒤 요청과 대조한다. 회차가 끝나면 버린다. 이 대조로 `session_sent_as`·`followup`·`session_ended`를 채운다.
- `json_field`·`header` 후보는 토큰 모양 값만 본다: 설정 하한(기본 16바이트) 이상이고 영문·숫자와 `-_.=+/~:`만 든 값이다. 공백이 든 안내 문장·`@`가 든 메일 주소·`/`로 시작하는 경로는 세션이 아니다(실패 응답 `{"message":"Password is not correct…"}`가 세션으로 잡히지 않게). 뒤 요청이 실제로 실어 보낸 후보가 있으면 `session_source`·`session_names`를 그것으로 좁힌다.
- `session_sent_as`는 `cookie`이거나 `헤더이름:접두`(예: `Authorization:Bearer `)다.
- `followup`·`outcome`·`session_ended`는 뒤 요청이 올 때 갱신한다. 한 시도의 행은 덧붙이기로 고치고, 마지막 행이 그 시도의 지금 값이다.

## 4. 성공·실패 판정

어느 한 신호만으로 성공 처리하지 않는다. 입증할 신호가 없으면 성공이 아니라 `unconfirmed`다(개발 계획 '쿠키 로그인의 성공 판정', #958 동찬 리뷰).

**로그인 응답의 실패 신호** — 하나라도 있으면 `failed`다. §2-2의 '분명한 실패'와 같은 목록이다.
- 상태가 400 이상이다.
- 세션이 없다(`session_source: none`, 새 세션도 이어진 세션도 없음). 예: 200 응답인데 로그인 폼·리다이렉트·쿠키·토큰이 하나도 없음 → `failed`, §2-2 예외 상태 `로그인 안 됨`, §5 연속 실패 +1.
- 로그인 화면을 다시 준다(`login_form_returned`). 다음 둘 중 하나다.
  - 응답이 HTML이고 `type="password"`인 입력 칸이 있다.
  - 리다이렉트 경로가 로그인 시도 경로와 같다.

**용어** — 아래 판정은 같은 origin의 GET 요청을 **질의 값까지 같은 URL**로 본다(#963 동찬 리뷰 P2: `GET /orders?id=1` 403과 `GET /orders?id=2` 200은 자원 차이라 대조가 아니다). 비교에 쓰는 질의 값은 회차 메모리에서만 들고 기록에는 남기지 않는다(기록은 `path`·`query_keys`만).
- **로그인 화면 경로**: 로그인 시도 경로, 그리고 같은 회차에서 **세션 없이** 받은 HTML 응답에 `type="password"` 입력 칸이 있었던 경로. 세션을 실은 화면(비밀번호 바꾸기·프로필)은 여기 들지 않는다.
- **막힘**: 401·403이거나, 3xx이고 `Location` 경로가 로그인 화면 경로다. NodeGoat처럼 세션이 없으면 로그인 화면으로 302를 보내는 앱도 막힘이다(`GET /` → 302 `/login`).
- **열림**: 상태가 400 미만이고, 로그인 화면 경로로 리다이렉트되지 않았다. 다른 경로로의 3xx도 열림이다(NodeGoat 세션 있는 `GET /` → 302 `/dashboard`).
- **세션 없는 응답**: 실제로 인증을 싣지 않은 요청의 응답이다. `Cookie`·`Authorization` 헤더가 없고, 이 회차에 세션 자리로 알려진 헤더(§3 `session_names`·`session_sent_as`의 헤더 이름)도 하나도 싣지 않아야 한다. 다른 계정 세션으로 보낸 요청의 403처럼 인증을 실은 응답은 대조 근거가 아니다(#963 동찬 리뷰). 정적 크롤은 늘 인증 없이 탐색 에이전트보다 먼저 돌므로 대개 여기서 나온다.

**뒤 요청 신호** (`followup`) — 아직 `unconfirmed`인 시도의 세션을 실은 뒤 요청에서 본다.
- `authenticated_contrast`: 질의 값까지 같은 GET URL에 이 회차의 세션 없는 응답 가운데 **막힘**이 있고, 이 세션을 실은 응답은 **열림**이다. 두 응답의 순서는 따지지 않는다(세션 없는 응답이 로그인 뒤에 와도 된다). **성공 근거는 이것뿐이다.**
- `no_login_form`: 이 세션을 실은 응답이 열림인데, 아직 대조할 세션 없는 막힘 응답이 없다. 약한 신호라 성공으로 올리지 않는다.
- `login_form`: 이 세션을 실은 GET이 로그인 화면 경로로 리다이렉트된다. 실패 신호이고 §5 연속 실패에 센다. 로그인 시도 경로를 다시 열었을 때 비밀번호 칸이 보이는 것은 신호로 보지 않는다(로그인한 뒤에도 로그인 화면을 그대로 보여 주는 앱이 있다).

**모델이 먼저 로그인해 대조할 응답이 없을 때 — 프로그램 대조 요청(진단 단계만)**
- 대조 요청은 **진단 단계만** 보낸다(E② 프로그램 호출 `login_contrast`). **탐색 단계는 관찰 대조만** 한다: 정적 크롤이 세션 없이 먼저 돌아 막힘 응답이 대개 있다. 탐색에서 대조를 세우지 못한 로그인은 `unconfirmed`로 남고 쓰기 예외만 꺼진다(사용자 결정 2026-11-26 (나), 측정 뒤 다시 볼 수 있음). 브라우저 세션은 그대로 두고 탐색을 계속한다.
- `no_login_form`인 요청이 생겼는데 질의 값까지 같은 URL의 세션 없는 응답이 이 회차에 없으면, 프로그램이 그 URL로 세션 없는 GET을 한 번 보낸다.
  - 모델이 보낸 그 요청의 **정확한 URL**(경로·질의 값 그대로)을 다시 쓰고, `Cookie`·`Authorization`과 이 회차에 세션 자리로 알려진 헤더를 모두 뺀다.
  - E②를 지나는 프로그램 요청이다(GET만, 본문·인증 헤더 없이). 승인 규칙 범위·제외 경로와 요청 예산을 그대로 따르고, 진단 흐름 경계·요청 승인은 거치지 않는다(모델이 이미 그 경계를 지나 GET한 URL이다).
  - 모델이 이미 이 세션으로 GET한 URL만 고른다. 새 URL을 만들어 보내지 않는다.
- 결과가 막힘이면 `authenticated_contrast`가 되고 `contrast_source: probe`를 남긴다. 열림이면 그 URL은 공개 화면이라 대조가 안 된다. 다음 `no_login_form` 요청이 생기면 다시 시도한다.
- 대조 요청은 시도마다 서로 다른 URL 3개까지 보낸다(설정값, 기본 3). 다 쓰도록 막힘을 못 찾으면 `unconfirmed`로 남는다.
- 대조 요청은 로그인 시도가 아니다. §5 연속 실패에 세지 않는다.
- 대조 요청은 작업대 `target_requests`의 `login` 칸과 `total`에 센다(사용자 결정 2026-11-26). 요청 상세 목록에서는 프로그램 요청 종류 `login_contrast`, 화면 글 "프로그램 대조 요청"으로 다른 요청과 구분한다. 총계 화면(마우스를 올리면 내역)도 이 기준을 따른다(경준님).
- NodeGoat 예:
  - 정적 크롤이 세션 없이 `GET /` → 302 `/login`(막힘)을 남긴다. 로그인 뒤 모델이 세션으로 `GET /` → 302 `/dashboard`(열림)를 받으면 대조가 선다(`observed`).
  - 모델이 `/dashboard`만 열었으면 프로그램이 세션 없이 `GET /dashboard`를 보낸다. 302 `/login`(막힘)을 받으면 대조가 선다(`probe`).
  - 비밀번호가 틀리면 로그인 응답이 200에 비밀번호 칸이 있는 화면이라 바로 `failed`다.

**결과** (`outcome`)
- `succeeded`: 로그인 응답에 실패 신호가 없고, 세션이 있고(`session_source`가 `none`이 아님 — 새 세션이든 이어진 세션 `continued`든), `followup`이 `authenticated_contrast`다. 이어진 세션은 로그인 전 세션 없는 응답과 같은 쿠키일 수 있으므로, 대조의 '세션 없는 응답'은 그 쿠키를 싣지 않은 응답만 센다.
- `failed`: 로그인 응답에 실패 신호가 있거나 `followup`이 `login_form`이다.
- `unconfirmed`: 위 둘 다 아니다. 세션을 받았지만 대조할 경로가 아직 없는 경우 등이다.
- `not_sent`·`result_unknown`: 전송 결과를 그대로 남긴다. 결과 불명 로그인은 자동으로 다시 보내지 않는다.
- 한 번 `succeeded`가 된 시도는 바뀌지 않는다. 대조 URL을 그 세션으로 다시 열어 '막힘'이면 `session_ended: true`만 남긴다(세션 끊김, 실패 아님, §2-2와 같은 기준). 다른 URL의 막힘은 기록하지 않는다. 모델은 다시 로그인하면 된다.

**화면 계정 상태(`account_auth`)로 싣는 법**

등록 계정 라벨마다 그 계정의 시도 기록으로 정한다. 아래 표를 **위에서부터 차례로 보고 처음 맞는 행** 하나만 쓴다(우선순위 = 행 순서).

- **보낸 시도**: 결과(`outcome`)가 `succeeded`·`unconfirmed`·`failed`·`result_unknown`인 시도다. `not_sent`는 대상에 나가지 않았으므로 보낸 시도가 아니다.
- **마지막 보낸 시도**: 보낸 시도 가운데 시도를 시작한 순서(`attempt_ref`를 매긴 순서)로 가장 늦은 것이다. 뒤 요청으로 결과가 나중에 바뀌어도 순서는 시작 순서로 본다. 그 뒤에 온 `not_sent`는 건너뛴다.

| 순서 | 조건 | `account_auth` 값 |
|---|---|---|
| 1 | 그 계정의 시도 기록이 0건 | `not_attempted`(새 값) |
| 2 | 보낸 시도 가운데 하나라도 `succeeded` | `authenticated`(뒤 `failed`가 덮지 않음, E③ 재사용과 같은 규칙) |
| 3 | 기록은 있지만 보낸 시도가 없음(모두 `not_sent`) | `not_sent` |
| 4 | 마지막 보낸 시도가 `failed` | `login_failed`(연속 실패 상한에 닿은 계정도 여기) |
| 5 | 마지막 보낸 시도가 `unconfirmed` | `unconfirmed`(새 값) |
| 6 | 마지막 보낸 시도가 `result_unknown` | `result_unknown` |

예: `result_unknown` → `not_sent` 순서면 마지막 보낸 시도가 `result_unknown`이라 6행 `result_unknown`이다. `not_sent` 1건뿐이면 3행 `not_sent`다. `failed` → `succeeded` → `failed`면 2행 `authenticated`다. 4~6행은 보낸 시도가 하나 이상일 때만 닿으므로 빈칸이 없다.

- `session_not_found`는 모델 로그인에서 쓰지 않는다. E③ 재사용 로그인(`actor: program`)이 세션 자리를 못 찾았을 때만 남긴다.
- 값이 바뀔 때마다 `account_auth_updated_at`도 그 계정 것만 갱신한다(#936 규칙).
- 새 값(`not_attempted`·`unconfirmed`)을 서버가 싣는 PR은 **웹 파서(닫힌 값 목록)를 같은 PR에서 같이 고친다.** 화면 파서는 모르는 값을 받으면 회차 상태 응답 전체를 거부한다(#929 → #938과 같은 문제).
- 화면 경고 문구는 경준님 몫이다. `unconfirmed` 경고 제안(경준님): "로그인 성공을 확인하지 못했습니다. 이 계정은 확정 단계에서 쓰지 않을 수 있습니다. 점검은 멈추지 않습니다."

## 5. 연속 실패 상한

- 아이디별로 연속 실패를 센다. 탐색·진단·확정 단계를 합쳐 회차당이다.
  - `failed`가 되면 1을 더한다. 로그인 응답의 실패 신호로 정해졌든, 뒤 요청 `login_form`으로 나중에 정해졌든 같다(결과와 차단 기준을 맞춘다, #963 동찬 리뷰 P2). `succeeded`가 되면 0으로 되돌린다.
  - `unconfirmed`·`not_sent`·`result_unknown`은 세지도 되돌리지도 않는다.
  - 이미 `succeeded`인 시도의 대조 URL이 그 세션으로 다시 '막힘'이 되는 것은 `session_ended`이고 실패가 아니다(§2-2·§4). 다른 URL의 막힘은 세지도 기록하지도 않는다.
- 연속 실패가 3에 닿은 아이디로 새 로그인 시도를 하면, 탐색 경계와 E②가 보내기 전에 거부한다. 고정 사유는 `login_attempts_exhausted`다.
  - E② 영수증 사유는 운영자 제외 경로(#627)처럼 `policy_denied`로 두고 E② 사유 어휘는 늘리지 않는다. 고정 사유는 이 기록의 `refusal`과 진단 로그(`login_attempt_refused`)에 있다.
  - 그 요청만 실패하고 회차는 계속한다.
  - 거부한 시도도 한 행으로 남긴다(`transport: not_sent`, `refusal: login_attempts_exhausted`). 연속 실패 수에는 세지 않는다.
  - 뒤 요청으로 나중에 `failed`가 정해지면, 그 사이에 이미 보낸 다른 시도는 되돌리지 않는다. 상한은 그다음 시도부터 막는다.
- 아이디가 없는 시도(아이디 칸 없음)는 빈 아이디 하나로 묶어 센다.
- 단계를 넘어 이어 센다: 진단 단계는 시작 때 탐색 행을 기록 순서대로 다시 읽어, 시도의 결과가 바뀐 행마다 실패 수를 바꾼다(판정기는 결과가 바뀔 때마다 그 행을 바로 남기므로 기록 순서가 실제 순서다). 앞 시도의 성공이 뒤 시도의 실패보다 늦게 확정돼도 같은 수가 된다(#969 동찬 리뷰 P2).
- 탐색 기록을 넘겨받지 못하면(경계 조회·기록 쓰기 실패, 상한으로 빠진 행, 깨진 줄) 회차 공통 상한을 지킬 수 없다. 그때는 진단 단계가 로그인 시도만 보내기 전에 막는다(고정 사유 `login_history_unavailable`, E② 영수증은 `policy_denied`). 일반 요청과 감사 기록은 그대로다.
- 인계 표지(`login-attempts.unavailable`, 회차 상태 디렉터리, 0600)는 인계가 확인되기 전 상태다. 제품 탐색 경계를 쓰는 회차는 탐색이 경계를 열기 전에 표지를 쓰고, 탐색 행을 모두 기록에 옮긴 것이 확인될 때만 지운다(경계를 열기 전에 끝난 탐색은 탐색 로그인이 없으므로 읽지 않고 지운다). 그래서 탐색 뒤 기록과 표지 저장이 모두 실패해도 표지가 남아 진단 단계가 로그인을 막는다(#969 동찬 리뷰). 시작 때 표지를 쓰지 못하면 탐색을 열지 않는다(대상 송신 없이 계획 준비 실패 `planning_exploration_failed`).
- 상한 3은 설정값으로 둔다(코드에 박지 않음). 기본 3은 사용자 결정 2026-11-26이다.

## 6. 저장과 읽는 쪽

- **탐색 로그인 요약**: 탐색 단계가 끝나면 탐색 단계 행만으로 계정별 결과를 §4 `account_auth` 규칙(6행)으로 정해 회차 상태 디렉터리 `login-summary.json`(0600)에 쓴다. 모양은 `{"format":"abc2lab.login-summary/v1","exploration":{"<라벨>":"authenticated|unconfirmed|login_failed|not_sent|result_unknown|not_attempted"}}`다. 탐색이 대조를 못 세운 비율(`unconfirmed`)을 회차마다 보려는 것이다(사용자 결정 2026-11-26, 측정 뒤 탐색 대조 요청 (가)를 다시 볼 근거). 화면 API에는 싣지 않는다.

- 회차 상태 디렉터리의 보호 파일 `login-attempts.jsonl`(0600, 회차 단위, 덧붙이기)에 둔다. 보관·삭제는 실행 기록과 같다. 서명 저널(E② v3)에는 넣지 않는다. 저널은 지금처럼 요청 단위 감사를 맡고, 이 기록은 `transport_ref`로 저널과 잇는다.
- **E③ 로그인 재사용**(이동찬)은 `account_label`이 있고 `outcome: succeeded`인 마지막 시도에서 다음을 가져와 같은 방식으로 로그인한다.
  - `method`·`path`·`format`
  - `identifier_field`·`password_field`·`other_fields`·`fields_from_response`
  - `session_source`·`session_names`·`session_sent_as`
  - 값은 등록 자격으로 채운다. `fields_from_response` 칸은 로그인 화면을 먼저 받아 같은 이름의 값을 쓴다.
  - 성공한 시도가 없으면 그 계정은 확정 단계에 쓰지 않는다(지금의 `test_accounts_unavailable`와 같은 처리).
- 화면·보고서는 내부 담당자만 본다. 라벨이 있으면 라벨로 보이고, 등록 밖 아이디는 `identifier`로 보인다.
- 남기지 않는 것: 비밀번호 값, 세션 값, 응답 본문, OpenRouter 키·관리자 비밀번호·승인 ID 같은 우리 통제 비밀, E③ 표식.

### 6-1. 배운 로그인 방법 (회차 밖, #963 경준 리뷰 P2-B)

11/26 분담대로 계정 화면에 계정별 "로그인 방법: 배움 / 검증됨"을 보이려면 회차를 넘어 남는 값이 있어야 한다. 그래서 배운 로그인 방법을 대상 계정 저널(보호 저널, 감사 기록)에 계정별로 남긴다.
- **저장·갱신 담당**: `learned`는 모델 로그인 PR(최민준, ⑤-B)이, `verified`는 E③ 재사용 PR(이동찬)이 쓴다.
- **E③ 재사용 순서**: 이 회차에 `succeeded` 시도가 있으면 그것을 먼저 쓰고, 없으면 저장된 방법을 쓴다. 둘 다 없으면 그 계정은 확정 단계에 쓰지 않는다.
- 값(아이디·비밀번호·세션 값·응답 본문)은 저널에도 API에도 넣지 않는다. 방법의 칸 이름·경로·세션 자리만 남긴다.

#### 6-1-1. 상태와 바뀌는 때

계정별 상태는 셋이다.

| 상태(`state`) | 뜻 | 화면 글 제안 |
|---|---|---|
| `none` | 쓸 수 있는 배운 방법이 없음 | 아직 없음 |
| `learned` | 이 계정의 로그인 시도(탐색·진단, `actor: model`)가 §4 `succeeded`였고 그 방법을 저장함 | 배움 |
| `verified` | 저장된 그 방법(같은 `method_sha256`)으로 E③ 재사용 로그인(`actor: program`)도 `succeeded` | 검증됨 |

- 더 뒤의 `succeeded`가 다른 방법이면 그 방법으로 바꾸고 `learned`가 된다(검증 표시는 이전 방법의 것이라 버린다). 같은 방법이면 `learned` 근거만 최신으로 바꾸고 `verified`는 유지한다.
- 따로 지우는 사건은 없다. 서버가 상태를 계산할 때 저장된 방법이 **지금 대상 판(`target_revision`)과 지금 자격 해시(`credential_sha256`)** 둘 다에 묶여 있을 때만 쓴다. 어느 하나가 바뀌면 `none`이고 `cleared_reason`을 준다. 계정을 지우면 계정 행이 없어진다.

#### 6-1-2. 대상 계정 저널 사건

대상 계정 저널(`productAccountEvent`)에 사건 두 가지를 더한다. 기존 칸(`target_id`·`label`·`action`·`actor`·`at`·`target_revision`·`credential_sha256`)은 그대로 쓰고, `actor`는 그 회차를 시작한 대상 승인자다.

| `action` | 쓰는 쪽 | 더하는 칸 |
|---|---|---|
| `login_method_learned` | 모델 로그인(⑤-B) | `login_method`(아래 방법 객체), `method_sha256`, `run_ref`, `stage`(`exploration`·`diagnosis`), `attempt_ref`, `evidence`(`observed_contrast`·`probe_contrast`) |
| `login_method_verified` | E③ 재사용(이동찬) | `method_sha256`(검증한 방법), `run_ref`, `stage`(`confirmation`), `attempt_ref`, `evidence`(`e3_relogin`) |

- `at`은 그 시도가 `succeeded`로 판정된 시각(UTC)이다.
- `method_sha256`은 방법 객체를 키 순서 고정 JSON으로 만든 SHA-256이다. `verified`는 지금 `learned` 방법의 해시와 같을 때만 상태에 반영한다.
- `credential_sha256`·`target_revision`은 그 회차에 결속된 자격 해시와 대상 판이다(위 '따로 지우는 사건은 없다'의 근거).

**방법 객체(`login_method`)** — §6 E③ 재사용이 쓰는 칸과 같다. `http_method`는 §3 기록 행의 `method`에서, 나머지는 §3의 같은 이름 칸에서 가져온다(#969 동찬 리뷰 P3).

| 칸 | 예 |
|---|---|
| `http_method` (§3 `method`) | `POST` |
| `path` | `/login` |
| `format` | `form`·`json`·`multipart` |
| `identifier_field`·`password_field` | `email`, `password` (JSON은 점 경로) |
| `other_fields` | `["_csrf","remember"]` |
| `fields_from_response` | `["_csrf"]` |
| `session_source` | `set_cookie`·`json_field`·`header`·`continued` |
| `session_names` | `["connect.sid"]`, `["auth_token"]` |
| `session_sent_as` | `cookie`, `Authorization:Bearer ` |

#### 6-1-3. 계정 목록 API (`ProductAccount.login_method`)

계정 목록·계정 변경 응답의 계정마다 `login_method` 객체를 **늘** 싣는다(배운 것이 없으면 `{"state":"none"}`).

```json
{
  "state": "verified",
  "learned": {"at": "2026-11-26T12:00:00Z", "run_ref": "…", "stage": "diagnosis", "attempt_ref": "diagnosis-3", "evidence": "observed_contrast"},
  "verified": {"at": "2026-11-26T12:30:00Z", "run_ref": "…", "attempt_ref": "confirmation-1", "evidence": "e3_relogin"},
  "method": {"http_method": "POST", "path": "/login", "format": "form", "identifier_field": "email", "password_field": "password",
             "other_fields": ["_csrf"], "fields_from_response": ["_csrf"], "session_source": "set_cookie", "session_names": ["connect.sid"], "session_sent_as": "cookie"}
}
```

| 칸 | 있는 때 | 값 |
|---|---|---|
| `state` | 늘 | `none`·`learned`·`verified` |
| `cleared_reason` | `state: none`이고 예전 방법이 무효가 됐을 때만 | `target_reapproved`(대상 판이 바뀜)·`credential_changed`(자격을 다시 등록함) |
| `learned` | `learned`·`verified` | `at`(UTC), `run_ref`, `stage`, `attempt_ref`, `evidence`(`observed_contrast`: 회차에 이미 오간 세션 없는 막힘과 대조, `probe_contrast`: 프로그램 대조 요청으로 대조) |
| `verified` | `verified`만 | `at`(UTC), `run_ref`, `attempt_ref`, `evidence`(`e3_relogin`) |
| `method` | `learned`·`verified` | 위 방법 객체. 화면에 어디까지 보일지는 화면 PR이 정한다 |

- 기존 `login_method_missing`(bool)은 로그인 설정 9칸이 없다는 뜻이고 이 칸과 다르다. 9칸 폐지 PR(§7)에서 없어진다.
- 이 칸을 싣는 서버 PR은 웹 파서(닫힌 칸·값 목록)를 같은 PR에서 고친다(§4 규칙). 모르는 `state`·`evidence`·`cleared_reason` 값은 파서가 거부한다.
- 서버가 이 칸을 싣기 전 응답에는 칸이 없다. 화면은 칸이 없으면 '아직 없음'으로 보인다.

### 6-2. 확정 단계 로그인 재사용 (E③ 재사용 PR, 이동찬)

§6·§6-1을 구현할 때 정한 세부다. 코드: `learnedlogin/`(순수 판정), `server/e2_http_learned_login.go`(E② 송신), `cmd/first-controlled-diagnosis/product_learned_login.go`(계정 저널·확정 단계 연결).

**배우는 시도(§6 "마지막 시도"의 뜻)**
- 같은 `attempt_ref`의 마지막 행이 그 시도의 지금 값이고, 시도 순서는 `attempt_ref`가 처음 나온 순서다(파일 마지막 행 순서가 아님).
- 적격: 이 회차 `run_ref`, `actor: model`, `stage`가 `exploration`·`diagnosis`, 이 회차에 결속된 계정 `account_label`, `password_registered: true`, `transport: sent`, `outcome: succeeded`, `followup: authenticated_contrast`, `transport_ref` 있음, 상태 100~399, `login_form_returned: false`, `session_source`가 `none`이 아님.
- 계정마다 적격 시도 가운데 가장 늦게 시작한 것 하나만 본다. 그 방법을 재현할 수 없으면(아래 지원 범위 밖) 더 앞의 성공으로 돌아가지 않고 사유를 남긴다.
- 한 시도의 고정 칸(회차·단계·주체·시각·라벨·아이디·메서드·경로·형식·칸 이름·`transport_ref`)이 행마다 다르면, 그 시도의 어느 행에든 나온 이 회차 결속 라벨은 이 회차에서 배우지 않는다(`learned_login_record_invalid`).
- 중복 JSON 키(대소문자 변형 포함)나 잘못된 JSON이 있는 행은 기록 전체를 무효로 본다. 같은 시도의 이전 행을 최신 값으로 쓰지 않는다.
- 출처 결속(`transport_ref`): 고른 시도는 실제 송신 근거와 맞아야 쓴다(`learnedlogin.VerifyTransport`).
  - 마지막 성공 행에서 참조가 빠졌거나 형식이 잘못됐으면 `learned_login_transport_unverified`로 막는다. 앞선 성공이나 로그인 설정으로 넘어가지 않는다.
  - 진단 단계 행: `transport_ref`는 `call_ref/attempt_id`다. 그 회차 E② 실행이 감사 기록기에 남긴 결과 사건(`Execution.Events`, `stage: result`)에서 같은 호출·시도를 찾아, 같은 회차(`run_ref`, 행과 사건 둘 다), 모델 호출(프로그램 목적·E③ 요청이 아님), 같은 메서드, 허용(`allowed`), 요청을 실제로 씀·응답을 끝까지 받음, 같은 상태 코드, 감사 완료가 모두 맞아야 한다. 하나라도 다르거나 사건이 없거나 감사 조회를 열 수 없으면 `learned_login_transport_unverified`이고, 그 계정은 로그인 설정으로도 넘어가지 않는다(§6-3). E② 결과 사건에는 경로·계정이 없으므로 경로·아이디 결속은 같은 회차 기록 행의 고정 칸 대조(위)로만 본다.
  - 탐색 단계 행: `transport_ref`는 탐색 경계 기록 순번(양의 십진수, 앞자리 0 없음)이어야 한다. 제품에는 탐색 경계 기록을 확정 단계에서 대조할 감사 근거가 없으므로 출처는 `exploration_unaudited`로 남기고 "실제 송신 확인"을 주장하지 않는다. 대조하려면 탐색 경계 기록을 확정 단계가 읽는 별도 계약이 필요하다(§7).
- 기록 파일은 회차 상태 디렉터리의 보호 파일(0600·실행 uid·링크 아님·읽는 동안 안 바뀜)만 읽는다. 파일이 없으면 배운 것이 없고, 보호 파일이 아니거나 읽지 못하는 줄(JSON 오류·뒤에 붙은 값·같은 키 중복·대소문자 별칭·잘못된 UTF-8·상한 초과)이 하나라도 있으면 기록 전체를 쓰지 않는다(`learned_login_record_invalid`). 손상된 갱신 행을 건너뛰면 그 시도의 이전 행이 최신 값으로 골라질 수 있기 때문이다. 이 파일은 서명 저널이 아니므로 기록의 `succeeded`만으로 실행 권한을 주지 않는다: 재현 요청은 아래 E② 허용을 따로 지나고, `verified`는 프로그램이 직접 대조를 세웠을 때만이다.

**확정 단계 재사용 순서와 로그인 설정(9칸)**
- 이 회차 적격 성공 → 계정 저널의 유효한 저장 방법(지금 실행에 결속한 대상 판·자격 판과 같을 때) → 둘 다 없으면 로그인 설정 다시 로그인(전환 기간 호환, §7).
- 이 회차 인증 결과(`account_auth`)가 `authenticated`가 아니어도 쓸 배운 방법(이 회차 성공·저장된 방법)이 있는 계정은 확정 단계 계정 역할(A·B)로 쓴다(§6·§6-1 "둘 다 없으면 쓰지 않는다"). 실제 인증은 확정 직전 다시 로그인과 바로 뒤 신원 확인이 정하고, 실패하면 신원 미확인 UNDECIDABLE이다.
- 저장 방법은 `learned` 저장(모델 로그인 PR ⑤-B)이 대상 레지스트리에 읽기 경계(`learnedLoginMethod(대상, 라벨, 대상 판, 자격 해시)`, `cmd/first-controlled-diagnosis/product_learned_login.go`의 `productLearnedMethodReader`)를 구현할 때부터 쓴다. 그 전에는 이 회차 성공만 쓴다.
- 배운 방법이 있는데 재현에 실패하면 로그인 설정으로 대신하지 않는다(실패 사유를 숨기지 않음). 그 계정은 확정 단계 신원 확인에서 `product_identity_unverified`가 된다.

**E② 허용(§2-2 "확정 단계 로그인은 쓰기 승인 범위를 따른다")**
- 확정 단계 다시 로그인 호출(`BeginE3ReloginCall`, 확정 몫)만 쓰는 송신 목적 둘: `learned_login`(로그인 POST), `login_prep`(로그인 화면 GET, 세션 없는 대조 GET). Worker `refresh_session`·모델 요청·처음 인증 준비는 쓰지 못한다.
- 전용 규칙이 아니라 그 실행의 Worker 승인 규칙이 메서드·경로를 덮어야 한다. 쓰기 승인이 없는 실행(Worker 규칙이 GET뿐)은 로그인 POST를 보내지 않는다. 질의가 있는 요청, 운영자 제외 경로, 모델 단계 진단 쓰기 정책의 위험 동작 단어(삭제·로그아웃·탈퇴 등) 경로는 보내지 않는다. 위험 단어는 원래 경로와 한 번 푼 경로(E②가 범위를 볼 때와 같은 해석) 둘 다에서 보고, 풀 수 없는 경로는 보내지 않는다. 건별 승인을 받는 실행(수동·사용자 승인)에서는 쓰기 승인 범위의 건별 승인도 따른다: 로그인 POST는 E③ 생성 요청처럼 늘 승인을 받고, 로그인 화면·대조 GET은 모델 GET과 같이 미리 승인한 읽기만 승인 없이 나간다. 승인이 거절·만료되면 보내지 않는다(`learned_login_not_sent`). 처음 인증 준비(로그인 설정 9칸)는 지금처럼 승인 대기가 없다.
- 응답은 도구·모델로 가지 않고 프로그램 판정만 본다. 잘림·부분·압축 응답은 보류한다. 돌려줄 세션·쿠키에 보호 비밀번호가 들어 있으면 받지 않는다. 비밀번호는 보내기 전에 보호 값으로 등록하고, 새 세션 값은 출력 가림에 등록한다(인증 준비와 같음).
- 같은 계정 다시 로그인 줄 세우기, 계정별 연속 실패 3회(`refresh_limit`)·간격 10초(`refresh_cooldown`)를 지금 다시 로그인과 같이 쓴다. §5 연속 실패는 회차 기록에서 아이디별로 다시 세어 3에 닿았으면 보내지 않는다(`login_attempts_exhausted`). 결과 불명 로그인은 다시 보내지 않는다.
- 확정 몫(요청): 다시 로그인 5 = 계정 둘 × (로그인 화면 GET 1 + 로그인 POST 1) + 세션 없는 대조 GET 1. 고정 몫은 신원 2를 더해 7이다([E③ 제품 계약](e3-product-confirmation-interface.md) §7.1).
- 집계: 로그인 화면 GET·로그인 POST·세션 없는 대조 GET은 모두 확정 몫의 다시 로그인 호출(E② 프로그램 `refresh_session`)로 나가 감사 완료 결과 사건이 되고, 회차 `target_requests`의 `login` 몫으로 센다. 모델 단계 예산은 쓰지 않는다. 대조 GET은 모델 단계의 `login_contrast` 프로그램이 아니다(모델 단계가 닫힌 뒤라 그 호출을 쓸 수 없음). 서버 시험이 감사 사건 수 = 학습 로그인 요청 수 + 대조 1 = 대상이 받은 수, 모델 예산 불변을 본다.

**요청 재구성**
- 형식: `form`(URL 인코딩), `json`(객체, 점 경로는 중첩 객체), `multipart`(파일 부분 없음). 칸 순서는 아이디·비밀번호·나머지 칸(기록 순서)이다.
- 아이디·비밀번호 값은 그 실행에 결속한 자격 파일에서만 읽는다. 아이디 칸이 없는 방법은 비밀번호만 보낸다.
- 나머지 칸 값은 지어내지 않는다. `fields_from_response` 칸은 로그인 화면 응답의 HTML 입력 칸 값(같은 이름 값이 여럿이면 모두 같아야 함) 또는 JSON 응답의 같은 점 경로 문자열이다. 그 밖의 나머지 칸은 HTML 로그인 화면의 숨은 칸·제출 단추에 적힌 값만 쓴다(사람이 입력하는 칸·체크 칸 값은 모름). 값이 없거나 모호하면 보내지 않는다.
- 다시 만들 수 없는 것: 질의가 있던 로그인(`query_keys` 있음, 값 미기록), 나머지 칸이 32개(판정기가 잘랐을 수 있음), JSON 칸 경로가 겹침(`a`와 `a.b`), 비밀번호 칸 없음, 메서드가 POST가 아님. 모두 보내지 않는다.

**로그인 화면(CSRF·로그인 전 쿠키) 재수집**
- 로그인 화면은 로그인 경로의 GET이다(§6 "로그인 화면을 먼저 받아"). 나머지 칸이 있거나 `session_source: continued`이면 받는다. 응답이 2xx HTML이면 비밀번호 칸이 있어야(로그인 화면) 칸 값을 꺼낸다. 2xx JSON이면 `fields_from_response`만 꺼낸다.
- §3 기록에는 값이 나온 응답의 경로가 없다. 그래서 로그인 경로와 다른 경로가 발급하는 CSRF(예: `GET /api/csrf`), 헤더로 보내는 CSRF, 메타 태그만 있는 CSRF는 재현하지 않는다(`learned_login_prep_unavailable`·`learned_login_prep_field_missing`). 지원하려면 §3에 값 출처 경로 칸이 필요하다(§7).
- 로그인 화면의 Set-Cookie는 그 계정·그 다시 로그인 한 번만의 쿠키 문맥에 담아 로그인 요청에 싣는다. 브라우저가 싣지 않을 쿠키(경로가 로그인 경로를 덮지 않음, Domain이 대상 호스트를 덮지 않음, https가 아닌 origin의 Secure)와 만료·삭제 쿠키는 빼고, 한 응답이 같은 이름을 다른 값으로 둘 이상 주면 그 이름은 쓰지 않는다. 같은 키가 둘인 JSON 응답(로그인 화면·로그인 응답)은 값을 꺼내지 않는다. 다른 계정·예전 시도의 쿠키·CSRF 값은 쓰지 않는다.

**로그인 응답 판정과 세션**
- 실패 신호(§4): 400 이상, HTML의 비밀번호 칸, 로그인 화면 경로로의 같은 origin 리다이렉트 → `failed`(`learned_login_rejected`).
- 세션 쿠키(`set_cookie`·`continued`)는 유효 경로가 `/`여야 한다(`Path` 속성, 없으면 그 응답 요청 경로의 기본 경로, RFC 6265 5.1.4). 확정 단계의 다른 경로 요청(신원·생성·조회)에 싣기 때문이다. 아니면 `learned_login_format_unsupported`다.
- 세션: `set_cookie`는 배운 쿠키 이름을 이 응답이 모두 새로 줘야 한다. `continued`는 로그인 요청에 실린 그 쿠키가 응답 뒤에도 남아 있어야 한다. `json_field`·`header`는 배운 자리 하나의 토큰 모양 값(§3)이어야 한다. 뒤 요청에 싣는 방식은 배운 `session_sent_as`다. 찾지 못하면 `failed`(`learned_login_session_not_found`, `account_auth`의 `session_not_found`).
- 응답을 끝까지 판정할 수 없으면(보류) 실패 신호가 아니므로 `unconfirmed`이고 연속 실패에 세지 않는다.

**성공(`succeeded`)과 `verified`**
- 세션을 받은 것만으로는 `unconfirmed`다. 아래가 모두일 때만 `succeeded`이고 그 방법을 `verified`로 남긴다.
  - 세션 없는 대조 GET(동결 선언의 신원 경로, 인증 헤더 없음, 회차에 한 번)이 막힘(§4)이다.
  - 그 계정의 확정 단계 신원 요청(E③, 이 세션으로 나감)이 열림이고 정상 응답에 신원 값이 있다.
  - 두 계정(A·B) 모두 정상 신원 관찰(2xx·신원 값 있음)이 있고 그 값이 서로 다르다. 상대 계정 관찰이 없으면 다르다는 근거가 아니다.
  - 확정 단계가 끝까지 돌았고(`completed`), 그 신원 관찰이 신원 확인을 통과시킨 판정(`identity_check: yes`)의 근거 호출에 들어 있다. 신원 관찰은 E② 봉인 대조·관찰 검증을 지난 것만 근거가 되므로, 봉인 조회가 확정 시한에 걸려 버려진 관찰·진위 실패·중단·꺼진 회차로는 성공을 세우지 않는다.
  - 신원 응답은 2xx다(신원 관찰에는 리다이렉트 목적지가 없어 3xx를 열림으로 보지 않는다).
  - 다시 로그인 뒤 확정 단계가 끝날 때까지 그 계정 결속 참조(세션)가 바뀌지 않았다.
- HTTP 200, 쿠키·토큰을 받음, 모델의 성공 기록, 지난 회차 성공, 저장소에 세션이 있음은 성공 근거가 아니다. 재사용 성공은 E③ 취약점 판정과 상관없다(신원·객체·증거 판정은 그대로).
- 프로그램 로그인은 같은 기록 파일에 `actor: program`, `stage: confirmation`, `attempt_ref: confirmation-N` 행으로 남긴다. 로그인 응답 판정 뒤 한 행, 대조로 성공이 정해지면 같은 시도 행을 덧붙인다(`followup: authenticated_contrast`, `contrast_source: probe`). 이 행은 다음 회차 학습 대상이 아니다(`actor: model`만 배움).

**`verified` 기록(계정 저널 `login_method_verified`)과 방법 해시**
- 방법 객체·`method_sha256`은 §6-1-2를 따른다(§6-1-1~§6-1-3은 모델 로그인 PR #969 `cdf1ae9f`의 계약 갱신이고, 그 PR이 들어오면 이 문서에 합쳐진다): 칸 이름 `http_method`·`path`·`format`·`identifier_field`·`password_field`·`other_fields`·`fields_from_response`·`session_source`·`session_names`·`session_sent_as`를 이 순서로 둔 JSON(빈 목록은 `[]`)의 SHA-256이다. `learned` 저장과 `verified`가 같은 값을 쓰도록 `learnedlogin.Method.Digest()` 하나로 계산한다(칸 이름·순서는 `TestMethodObjectMatchesContract`가 고정).
- 위 성공 조건을 모두 채운 계정마다 `login_method_verified` 줄 하나를 쓴다. 칸: `target_id`·`label`·`action`·`actor`(대상 승인자)·`at`(성공을 판정한 시각, UTC. 기록 행의 `at`=보낸 시각과 다름)·`target_revision`·`credential_sha256`(그 회차에 결속한 대상 판·자격 해시)·`method_sha256`(재현한 방법)·`run_ref`·`stage: confirmation`·`attempt_ref`(`confirmation-N`)·`evidence: e3_relogin`. 값은 없다.
- 쓰기 전에 레지스트리 잠금 안에서 그 회차가 결속한 대상 판·자격 해시가 지금도 같은지 본다. 다르면(재현 도중 재승인·자격 변경) 쓰지 않는다. `verified` 줄은 방법 해시마다 따로 둔다(다른 방법의 결과가 지금 방법의 검증을 덮지 않음). 같은 방법·판·자격의 `verified`가 이미 있거나 같은 방법의 더 뒤 결과가 있으면 쓰지 않는다.
- 상태 반영은 계산 때 한다(§6-1-2 "지금 `learned` 방법의 해시와 같을 때만"): 지금 `learned` 방법 해시의 `verified` 줄이 지금 대상 판·지금 자격 해시와 같고, 그 방법이 지금 것이 된 시각(다른 방법에서 바뀐 시각. 같은 방법을 다시 배우면 그대로) 뒤에 검증됐을 때만 `verified`다(`loginMethodVerifiedFor(…, methodSince)`). 그래서 "A 검증 → B 배움 → A 다시 배움"에서 옛 A 검증은 다시 보이지 않는다(§6-1-1). 따로 지우는 사건은 없다.
- 다시 열 때(재시작) `login_method_verified` 줄을 검증한다: 칸 모양(`stage`·`evidence`·`attempt_ref`·해시·회차 참조), 그때 계정이 있고 그때 자격 해시와 같음, 같은 방법의 앞선 줄보다 대상 판·시각이 뒤임. 다른 동작 줄에 이 칸들이 붙으면 저널 손상으로 본다.
- 계정 목록 API `login_method`(§6-1-3)는 `learned`를 싣는 모델 로그인 PR이 웹 파서와 같이 낸다. 이 PR은 API 칸을 바꾸지 않는다.

**실패 사유(고정 코드, 값 없음)** — 회차 기록 `refusal`(보내지 않았을 때)과 진단 로그 `reason_code`에 남긴다.

### 6-3. 확정 단계에서 이력 오류와 차단을 처리하는 기준

- 보호 파일을 읽지 못하거나 손상됐거나 인계 실패 표지(`login-attempts.unavailable`)가 있으면 기존 설정과 배운 방법을 모두 거부한다. 인증 개편 전 회차는 보호된 실행 정책으로 결속되며 이력 파일이 없을 수 있다.
- 기록의 회차 참조·단계·주체를 읽을 수 없거나 전송 상태와 결과가 서로 맞지 않으면 손상으로 본다.
- 배운 방법이 없다는 고정 사유에서만 기존 설정으로 넘어갈 수 있다. 기록 불일치, 대상·자격 판 변경, 입력 재구성 불가는 사유를 유지한다. 미전송이나 기존의 인증 세션만으로 새 로그인 검증을 기록하지 않는다.
- 결과 불명인 요청은 자동으로 다시 보내지 않는다. 기존 설정 경로는 보호된 아이디별 실패 수를 전달받지 않으므로, 회차에 상한 차단이나 결과 불명 이력이 있으면 보수적으로 거부한다.
- 제품 탐색 경계에서 이력 인계를 추적하는 회차는 경계를 열기 전에 `login-attempts.unavailable`을 남긴다(§5, 선행 #969). 표지를 쓰지 못하면 탐색 경계를 열지 않는다. 탐색 기록을 모두 넘겼거나 탐색 경계를 열지 않은 것을 확인했을 때만 표지를 지운다.
- 진단 판정기와 확정 단계는 같은 표지를 읽는다. 탐색이 끝난 뒤 이력과 표지를 모두 다시 쓰지 못해도 초기 표지가 남으므로 진단 단계는 로그인 시도를, 확정 단계는 다시 로그인을 막는다.
- 개편 전 회차나 외부 Host 탐색처럼 인계 추적 대상이 아닌 회차에는 표지가 없을 수 있다. 외부 Host의 탐색 이력은 이 경로에서 인계하지 않는다.

## 7. 열린 것과 순서

- 다단계 로그인(MFA·OTP·캡차)은 범위 밖이다(사용자 결정: 향후).
- Basic 인증 로그인은 v1 범위 밖이다(§2-1). 지원하려면 Basic 전용 성공 규칙(세션 대신 자격 헤더 자체로 대조)과 E③ 재사용 규칙이 따로 필요하다.
- 비밀번호 이름 규칙·아이디 이름 규칙에 맞지 않는 로그인 칸(예: 앱 고유 이름)은 등록 값 일치로만 잡는다. 기본 계정 시험처럼 등록 값이 없고 이름도 안 맞으면 로그인 시도로 보지 않는다. 탐색 경계는 그 POST를 지금처럼 쓰기로 다룬다.
- 탐색 단계 로그인은 모델이 브라우저(MCP)에서 직접 한다(절대규칙 1). 브라우저가 폼을 채워 보낸 요청도 경계가 같은 모양으로 보므로 같은 규칙을 쓴다. 브라우저가 받은 세션 쿠키를 뒤 요청과 대조하는 것도 같다.
- 로그인 설정 9칸을 서버가 그만 받는 시점은 따로 정한다. 모델 로그인 PR(최민준)과 E③ 재사용 PR(이동찬)이 둘 다 들어간 뒤 한 PR에서 그만 받는다. E③ 재사용 PR 뒤에는 확정 단계가 배운 방법을 먼저 쓰고, 배운 방법이 없는 계정만 지금 로그인 설정으로 다시 로그인한다(§6-2).
- 제품 탐색 단계의 모델 로그인 성공은 출처를 `exploration_unaudited`로만 남긴다(§6-2). 탐색 경계 기록 순번을 확정 단계가 대조하려면 경계 기록을 회차 상태로 넘기는 계약이 따로 필요하다.
- §3에 `fields_from_response` 값이 나온 응답 경로 칸이 없어, 로그인 경로와 다른 경로가 발급하는 CSRF는 재현하지 않는다. 지원하려면 판정기가 그 경로(질의 값 없음)를 남기는 칸을 계약에 더해야 한다(§6-2).
- 9칸 폐지 PR은 결속 조건("대상에 로그인 방식이 있어야 계정 결속", §0)과 확정 단계 다시 로그인 연결 조건(지금은 처음 인증 준비로 인증된 계정이 있을 때만 다시 로그인 경로가 열림)을 같이 바꾼다.
  - 화면 정리(새 점검 '로그인' 칸, `TargetLoginForm`, 진행 화면 `login_method_missing` 경고)는 그 PR 순서에 맞춘다(경준님).
