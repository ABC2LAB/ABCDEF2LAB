# 후보별 별도 E② 실행: 구현 계약과 검증 조건

이 문서의 `active/v1` 고정 GET 계획은 이전 회차의 계약이다. 새 비 IDOR 회차의 요구사항은 [선택 LLM 검증 계약](selected-candidate-llm-verification.md)을 따른다.

**상태: 백엔드 구현, 합성 E② 종단 수용시험 대기.** [후보별 API](selected-candidate-verification.md)는 계획과 별도 결정을 기록한다. 승인 요청 자체는 송신 권한이 아니며 보호 실행기가 현재 결속을 재검사하고 새 권한을 발급한다. #925의 같은 회차 `passive/v2` 검증은 그대로 유지한다.

## 분리 이유와 실행 단위

최초 진단 task의 E② lease, session, 예산 및 `diagnosisprep` Job은 진단 종료 후 소모된다. 현재 제품의 `Create`/`Start`는 전체 진단을 시작하므로 후보 하나의 GET 검증에 재사용할 수 없다. 기존 finding retest는 일반 finding을 전제로 하며 제품 E② 집행·권한 결속을 갖추지 않았다. 따라서 **선택한 후보 하나를 원본 task에 연결하는 제한적 내부 후속 task**를 사용한다. 이 task는 별도 run ref, 신규 E② 권한, 독립 예산 및 완료 기록을 가지며 Planner/Worker의 전체 탐색을 시작하지 않는다. 원본 후보를 finding으로 승격하지 않는다.

## 계획, 승인 및 집행 경계

1. 관리 API는 원본 task/candidate/digest와 최신 원본 판본, 현재 승인된 대상·메서드·제외 경로를 검사한다. 원본 근거의 `exact_function=true` 및 비민감 기능 표시만으로 실제 URL을 역산하지 않는다. 승인된 실제 정확한 경로와 원래 대상 동일성을 신뢰한 보호 정책 자료에서 재구성할 수 없으면 `insufficient/target_binding_unavailable`로 멈춘다.
2. 읽기 전용 계획은 후보 ID, 원본 digest/run, 검증 목적, 현재 대상/승인 scope digest, 구체적인 메서드·안전한 경로 표시, 예상 GET 수(최대 2), 시간·응답 상한, 부작용 가능성, 독립 예산, 규칙 버전과 기준을 고정한다. GET도 대상의 상태를 변경할 수 있으므로 기존 대상 승인에 읽기 요청의 실행 허가가 필요하다. 계획 SHA-256과 예상 revision을 저장한다. 계획 조회는 송신하지 않는다.
3. 사용자의 별도 승인/거부는 계획 digest·revision·후속 task·후보 digest에 결속한다. 승인 전에 실행/송신 0건이어야 한다. 계획이나 대상 승인이 바뀌면 재승인이 필요하다. 만료·철회·중단은 새 호출 admission 전에도 확인한다. 현재 모델 자동 모드는 이 별도 승인을 대신하지 않는다.
4. 보호된 준비/실행 호스트가 신규 lease와 E② session을 후속 task에만 발급한다. 관리 API의 DB INSERT나 보고서 GET은 lease를 만들 수 없다. 설치 잠금, DNS/TLS 경계, 현재 메서드·경로·제외 규칙, E② 요청 승인·감사·drain·봉인과 독립 예산을 그대로 적용한다. 결과 불명 요청은 자동 재전송하지 않는다.
5. `#927`의 끊긴 실행 정리는 **해당 후속 task**의 결속 저널과 마감 기록만 처리해야 한다. 원본 진단의 종료 기록을 다시 열거나 일시정지로 바꾸지 않는다. 후속 task의 강제 종료와 다음 검증 시작 경합은 잠금 순서와 보호 Job 상태까지 포함한 통합 시험이 필요하다.

## 판정과 이력

초기 대상은 HTML `nosniff` 누락과 Server 버전 배너로 한정한다. 새 회차에서 승인된 정확한 기능의 독립 GET 2건이 모두 최종·감사 완료, 응답 완료, 비절단이며 같은 상태일 때만 해당 **현재 설정 사실**을 확정하거나 부정한다. 다른 응답, 정책 변경, 호출 실패, 계정 미확인 또는 충돌은 `insufficient` 또는 실행 `failed`다. 과거 후보의 최초 응답과 새 회차 시도 번호를 직접 비교하지 않는다. 원본과 현재 대상·기능·정책의 비교 가능성은 별도 결속 판본으로 검증한다.

요청 이력에는 계획/승인/후속 task/run/감사 참조, 규칙 버전, 사용 예산, 비민감 관찰 digest와 처리 사건을 append한다. 최초 자동 판정과 원본 종료 기록은 보존한다. 보고서는 **최초 자동 판정**, **마지막 유효한 현재 대상 판정**, **최근 실행 시도 상태**, **stale 여부**를 별도로 보여야 한다. 실패한 최신 시도가 과거 확정 사실을 삭제해서도 안 되고, 과거 확정만으로 현재 대상을 확정해서도 안 된다. E③의 IDOR 판정은 이 비 IDOR 규칙으로 대체하지 않는다.

## 현재 제한과 수용 조건

보호 실행기는 원본 대상에 활성 E③ 선언이 있으면 후보 실행을 거부한다. 기존 E③ 대상 연결·TLS 고정 경로를 생략하지 않고 단일 GET 정책만 발급됐는지 확인하기 위한 제한이다. 별도의 후보 전용 E③ 발급 계약과 독립 수용시험 없이는 이 제한을 풀지 않는다.

저장 API, 계획·결정, 독립 관찰의 프로그램 판정, 완료 이력과 HTML·DOCX 갱신은 PostgreSQL 합성 시험으로 검증한다. 실제 E② 호스트에서 새 task/권한을 발급해 합성 대상 GET 두 건을 송신하고 감사·봉인·복구까지 확인하는 제품 종단시험은 별도 완료 조건이다. 이 시험이 통과하지 않으면 전체 백엔드 완료나 팀의 `합성 통과`로 표시하지 않는다. 유료 모델 및 실제 대상 호출은 이 시험에 포함하지 않는다.
