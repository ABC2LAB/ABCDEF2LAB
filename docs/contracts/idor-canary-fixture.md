# IDOR canary fixture 준비 절차 (제안)

작성: 2026-10-30 · 최민준 · **제안 초안 — 확인 필요: 이경준(KG 등록), 윤재상(계정 provisioning), 이동찬(상태변경 setup 승인 경계)**
연결: [IDOR 검증기 seam §2.2](./idor-verifier-seam.md) · [KG→판정·집행 §3.1](./kg-policy.md) · [E② 전송기](./e2-http-transmitter.md) · [평가 프로토콜 §2](../evaluation/evaluation-protocol.md)

## 0. 왜 필요한가
읽기 전용 진입점 `idor.VerifyRead`와 HTTP 실행기는 상태변경 요청을 보내지 않는다. 그래서 소유자 A의 자원에 비민감 표식(canary)을 **검사 전에 별도 단계로** 준비해 둬야 owner 읽기로 setup-success를 보이고, 오라클 (c) 데이터 확인과 비교기의 비자명 매칭이 쓸 근거가 생긴다. 표식이 없으면 결과는 판단불가다(fail-closed).

이 문서는 그 준비 단계의 **책임과 순서**만 정한다. 실행 코드·대상 앱 엔드포인트·계정 값은 담지 않는다.

## 1. 무엇을 심나
- **역할별 계정 × 자원 × 비민감 고유 표식.** 소유자 A의 자원마다 A 고유 값을 하나 이상 둔다.
- **실데이터가 아니다.** 개인정보·자격증명·실응답 원문을 표식으로 쓰지 않는다(절대규칙 2·8, DLP). reset 세대·계정·자원마다 새로 생성한 무작위 문자열을 쓴다.
- **소유자를 식별할 수 있어야 한다.** 표식 값 → 소유 계정 라벨 대응은 KG 등록(§2)에 둔다. 값 자체에 계정 원문·토큰을 넣지 않는다.
- **비자명 필드에 둔다.** 식별자(id·owner_id 류)와 구분되는 데이터 필드에 심어야 `Trivial=false`로 등록할 수 있다. 확신이 없으면 `Trivial=true`(제외)가 기본이다(kg-policy §3.1).
- **어디에 심을지는 앱의 자원 모델(KG·설정)로 정한다.** 평가 정답(챌린지 목록)을 보고 고르지 않는다(절대규칙 7). 임의 웹앱에 같은 절차가 적용돼야 한다.

## 2. 심기와 KG 등록은 한 세트
- 심은 표식은 같은 준비 단계에서 KG에 `Canary{Field, Value, Trivial}`로 등록한다(kg-policy §3.1, 등록·분류는 KG 소유). 등록 없는 심기, 심기 없는 등록은 둘 다 준비 실패로 처리한다.
- **세대 토큰(발급·전달 계약 제안)**: 평가 하네스(윤재상의 fixture)가 **실제 reset 성공·헬스 확인 뒤 해당 세대에 한 번 발급하는 불투명 식별자**다. 서버/하네스가 관리하는 `(run_id, reset_generation)` 및 대상 인스턴스의 reset 완료 근거에 불변 결속한다. `run_id`와 reset 세대는 별도 축이며 토큰만으로 둘을 대체·추론하지 않는다. reset 없는 동일 묶음 재시도는 같은 토큰을 재사용하지만, 새 reset이면 같은 run 문맥에서도 새 세대·새 토큰이 필요하다. KG는 토큰과 그 결속을 저장만 하고 발급·재결속 권한은 없다.
- **세대 연결의 서버 책임(구현 예정)**: 등록에는 위 회차/세대·묶음 참조·소유 계정 라벨·전체 자원 ref(`type:id`, seam §1)를 함께 묶는다. 향후 서버 어댑터가 KG 등록·실행기 설정의 `Scope.RunRef`/`ResetRef`·캡처 증거 ref·판정 envelope의 `run_id`·레코드의 `reset_generation`을 같은 불변 실행 묶음으로 보존·대조한다([seam §6.1](./idor-verifier-seam.md#61-현재-호출과-새-실행-책임), [판정 레코드 §2](./verdict-record.md)). 누락·다른 세대·출처 불명은 현재 실행에 재사용하지 않으며 Evaluate 전 판단불가로 처리한다. 현재 `idor.Capture`/`Result`·`PolicyResolver`에는 토큰/세대 필드가 없다. 토큰을 캡처 본문·canary 값에 삽입하지 않으며 별도 메타데이터의 물리 형식/API는 Open #5다.
- **값 유일성과 멱등 등록**: KG는 한 세대 안에서 canary 값의 **전역 유일성**을 강제한다. 등록 키는 `(run_id, reset_generation, 세대 토큰, bundle_ref, owner_ref, resource_ref, Field)`이며 `Value`·`Trivial`·생성 규칙 버전 등 불변 내용도 고정한다. **같은 키와 모든 불변 내용이 동일한 재시도**는 기존 등록 참조를 반환하는 멱등 성공(no-op)이며 새 등록이나 재생성이 아니다. 같은 값을 **다른 등록 키**에 쓰거나, 같은 키의 불변 내용을 바꾸려 하면 준비 실패다. 유일성 확인과 등록은 동시 요청에도 원자적으로 처리해야 하며 나중 등록이 덮어쓰는 last-writer-wins는 금지한다. 값 → 소유자 역참조는 이 유일성에 근거한다(구현/API는 Open #1·#5).
- 소유 계정과 자원의 연결은 신뢰할 수 있는 준비 결과·정본 등록에서 확인한다. owner 응답의 HTTP 200이나 표식 노출만으로 소유권을 추정하지 않는다. 등록 소유자와 실제 준비 결과가 다르거나 확인되지 않으면 준비 실패다.
- 회차·reset 세대·계정·자원·필드·생성 규칙 버전과 한 번 생성한 표식을 **불변 준비 묶음**으로 고정한다(저장 형식/API는 §7의 열린 항목). fixture 심기·KG 등록은 이 묶음을 소비하고, 향후 서버 어댑터가 그 KG 정본 snapshot에서 실행기의 등록 사본을 구성한다. 어느 쪽도 독립적으로 값을 재생성하지 않는다. 표식 원문은 비공개 준비/KG/실행기 내부에만 두고, 공유 근거에는 묶음 참조·세대·완료 여부를 남긴다.
- **값 생성자 = fixture, 정본 등록 = KG, 실행기 = 불변 사본의 소비자**: fixture가 한 번 생성한 값을 KG에 등록하고 KG는 그 소유·자원·세대 결속과 `Trivial` 분류의 정본을 보유한다(kg-policy §3.1). 실행기가 KG에서 값을 생성하거나 실시간 자동 동기화하는 기능이 있다는 뜻은 아니다. 현재 `transmit.NewHTTP`는 서버가 준 설정을 복사하고 `tx.VerifyRead`는 등록된 `(Field, Value, Trivial)` 집합과 KG 응답의 정확한 일치를 검사한 뒤 정책·표식을 한 번 고정한다. 불일치·중복·미등록은 송신 전 판단불가이며, 이 값 비교만으로 KG 출처나 세대 결속까지 증명하지 않는다([E② 전송기](./e2-http-transmitter.md)). 정본 snapshot에서 설정 사본을 만들고 위 메타데이터를 검증하는 서버 연결은 Open #3·#5다. 새 세대/등록에는 이전 실행기를 중지하고 새 불변 사본을 구성하며 실행 중 사본을 몰래 갱신하지 않는다.

## 3. 리셋 후 멱등 재적용
평가는 스캔마다 인스턴스를 재생성한다(평가 프로토콜 §2). 앱 상태가 사라지므로 fixture는 **매 회차 다시** 적용한다.

1. 인스턴스 리셋 → 헬스 확인 → 해당 run/reset 세대의 출처 결속과 세대 토큰 발급
2. 계정 provisioning
3. canary 심기 + KG 등록(§2)
4. 확인: E②에 비변경 행동으로 등록된 각 소유자의 조회로 표식이 실제로 있는지 확인하고 §2의 소유 바인딩과 대조한다. 표식 부재·소유 불명/불일치·예상 밖 상태변경이 하나라도 있으면 준비 실패
5. setup·확인 요청의 신규 송신 중지와 진행 요청 종료 확인 → pre 스냅샷 저장 → 엔진 검사(이후는 평가 프로토콜 §2)

- **멱등**: reset 없이 같은 세대·같은 준비 묶음을 다시 적용하면 같은 상태가 된다. §2의 동일 등록 재시도는 기존 참조를 반환하며 토큰·표식을 새로 뽑지 않는다. 다른 키의 값 충돌이나 불변 내용 변경은 멱등 재시도가 아니다. 부분 실패하면 고치며 이어가지 말고, 진행 요청 종료·회차 폐기를 확인한 뒤 리셋부터 새 묶음으로 다시 한다.
- **세대 고정**: 새 reset에는 새 `reset_generation`·세대 토큰·표식을 발급하며 이전 세대 값을 재사용하지 않는다. 평가 회차 도중 reset이 생기면 같은 회차로 계속 채점하지 않고 폐기한 뒤 새 `run_id`로 다시 시작한다(평가 프로토콜 §2). run과 reset 세대를 같은 식별자로 취급하지 않는다.
- **사전 해결**: 준비 작업이 어떤 항목을 해결해 버리면 pre 스냅샷에 드러나고, 그 항목은 판단불가로 남는다(평가 프로토콜 §4). fixture 설계에 챌린지 목록을 쓰지 않는다.
- **비교 조건 동일**: baseline과 개선 후는 같은 fixture 준비 조건에서 잰다(평가 프로토콜 §5).

## 4. 승인 분리 — 쓰기 단계와 조회 경로
- canary 심기는 **상태변경**이다. 얇은 조회 경로(`VerifyRead`·HTTP 실행기) 밖의 **별도 승인 setup 단계**에서, 리셋 가능한 상태변경 시험환경에서만 한다(절대규칙 6).
- 조회 경로는 읽기만 한다. HTTP 실행기는 상태변경 요청을 거부한다.
- setup 단계에도 같은 원칙을 건다: 대상 origin만(절대규칙 1), 자격 원문을 로그·기록에 남기지 않음(절대규칙 2), 실행 허가는 승인 경계가 정함(절대규칙 3). 누가·언제·어느 회차에 승인했는지 기록한다.
- setup 전송도 최종 대상·계정·행동·승인·예산·중지를 실제 송신 전에 확인하고, 지원하는 redirect/retry는 매번 재검사한다. 지원하지 않는 후속 전송은 차단한다. 준비용 쓰기를 허용하기 위해 조회 전송기의 제한을 풀지 않는다. 승인 기록만으로 실제 송신 통제가 구현됐다고 판단하지 않는다.
- 검증기·판정 쪽은 setup 실행 허가를 쥐지 않는다(판정·허용 권한 분리).

## 5. cleanup
- 회차 끝의 컨테이너 제거(평가 프로토콜 §2)로 앱 안의 fixture는 사라진다.
- 컨테이너 밖의 KG/실행기 등록·승인·세션은 해당 회차가 끝나면 만료·폐기하여 다음 회차에 사용하지 않는다. 폐기·격리를 확인할 수 없으면 다음 회차를 시작하지 않는다.
- 비민감 승인·준비·확인 증적은 회차/reset 참조와 함께 평가·감사 보존 기준에 따라 유지한다. 실행 권한/자격 폐기와 증적 보존을 구분하고, 증적에 표식 원문·자격·세션 값을 복사하지 않는다.
- 표식 값·자격·세션은 결과물·비밀이므로 커밋하지 않는다.
- 리셋할 수 없는 대상에는 이 절차를 쓰지 않는다.

## 6. 설정 — 하드코딩 금지
- 계정 라벨·역할, 자원 ref와 URL, 표식 필드명, 표식 생성 규칙은 설정(`.env`·KG)에서 온다. 코드·문서에 특정 앱의 엔드포인트·계정을 박지 않는다.
- 자격 원문은 `.env`·비밀 저장소에만 두고 커밋하지 않는다.

## 7. 확인 필요 (Open)
1. **KG 등록 계약(이경준)** — 경준은 등록 **계약**(`Canary{Field, Value, Trivial}` + 세대 토큰 + 소유 계정 라벨 + resource_ref)을 소유·설계한다. KG write 저장·엔드포인트 **구현**은 `db/`·`server/` 쪽이며 이동찬·최민준이 협의·리뷰한다. 여기서 "API"는 계약을 뜻하고 구현 소유가 아니다. 확인할 것: 등록 시점, run/reset/토큰 결속 저장(발급 아님), 세대 내 원자적 값 유일성·동일 등록 재시도 no-op·다른 키 충돌/불변 내용 변경 시 준비 실패, 표식 → 소유 계정 역참조 방식.
2. **계정 provisioning·세대 토큰(윤재상)** — 역할별 계정 수·생성 방식·세션 확보, fixture 적용 스크립트의 소유, 실제 reset 성공 뒤 회차/세대에 결속한 토큰 발급·동일 세대 재시도 재사용·새 reset 재발급(§2, 제안/확인 필요).
3. **setup 승인 경계·실행기 snapshot 연결(이동찬)** — 상태변경 시험환경·승인 기록 방식. fixture가 생성하고 KG가 정본 등록한 snapshot을 서버가 실행기 설정 사본으로 제공하는 연결과 회차/세대 검증을 정렬한다. 현재 정확한 표식 비교·고정과 미구현 서버 연결을 구분하고, 자동 KG 미러/값 생성 완료로 주장하지 않는다(§2).
4. **표식 생성 규칙** — 길이·문자 집합·충돌 방지·필드별 형식 제약.
5. **불변 준비 묶음** — 참조·생성 규칙 버전·회차/reset 결속의 물리 저장 형식, KG/실행기 등록 API와 부분 실패 검출·폐기 방식. 세대 토큰과 run/reset·인스턴스의 불변 대응, 동일 등록 재시도/충돌 원자성, 실행별 캡처·판정 메타데이터 연결도 포함한다. 위 절차를 구현할 때 정할 항목이며 현재 구현 완료가 아니다.
6. **resource_ref `type` 명명 — 공유 의존** — `type` 명명은 [seam §5](./idor-verifier-seam.md)에서 아직 미정이다. 이 결정을 쓰는 소비자가 셋이다: 접근통제 지도, 평가 상관(#19), 이 canary 바인딩(§2). `type`이 확정되면 셋을 함께 다시 본다. canary fixture는 그 세 번째 소비자다(경준 #26 지적).
