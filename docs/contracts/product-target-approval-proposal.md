# 회차별 대상 승인 권한 모델

상태: **#353에서 분리한 후속 구현(#360). 권한 모델은 아래 세 역할 구조로 2026-11-11 팀 합의로 채택했다**(2026-11-10 제안, #360 리뷰에서 최민준 승인). CLAUDE.md 절대 규칙 1이 이 구조를 따른다.
기존 설치 시 대상 origin 고정과 별개로, 로그인한 운영자가 대상 소유와 읽기 전용 진단 권한을 확인해 회차별 범위를 등록하는 정책이다. 이 문서나 시험 성공을 특정 공개 사이트를 진단해도 된다는 승인으로 간주하지 않는다. 실제 대상은 회차마다 아래 절차와 고객사 승인을 거친다.

## 역할

프로그램을 배포받아 설치해서 쓰는 구조다. 설치 뒤에는 개발팀이 관여하지 않으므로 상한과 승인은 설치 조직 안에서 끝난다.

| 역할 | 누구 | 정하는 것 |
|---|---|---|
| 개발팀 | 코드에 고정 | 설치 조직이 넘을 수 없는 선: 메타데이터·loopback 차단, 요청 상한 최대 100, 승인 최대 24시간, E② 집행 |
| 설치 조직 | 프로그램을 배포받아 설치하는 조직 | `target_policy`의 허용 포트·사설 대역·요청 상한. 개발팀 서명 정책은 두지 않는다 |
| 운영자 | 설치 조직의 로그인 사용자 | DNS 소유 증명과 본인 진술로 새 대상을 등록·승인한다. 진단 권한의 책임은 그 조직에 있다 |

## 변경 범위와 담당자 결정

| 항목 | 기존 #353 | 후속(#360) |
|---|---|---|
| 대상 권위 | 설치자가 고정한 origin/IP/path | 설치 상한 안에서 운영자가 DNS 소유 증명·범위를 등록하고 승인 |
| 설치 형식 | v1 고정 대상 | v2 대상 정책과 모델 정책 분리, 기존 v1 자동 이관 없음 |
| 최종 집행 | 기존 E②·보호 준비 서비스 | 동일 경로에 회차별 origin/IP/port/path/method/TLS SPKI·만료 결속 |
| 합의 | Workbench/UI 삭제·설치 승인 | 새 대상 승인 권한 모델, 허용 네트워크/포트, TLS 사전 접촉·감사(11/11 팀 합의) |

단일 관리자 로그인 이름은 ABC2LAB이고 내부 승인 주체 ARTEX는 유지한다. 로그인 계정이 하나라 등록과 승인을 같은 사용자가 한다. DNS 소유만으로 모든 검사를 허용하지 않는다. 운영자에게 실제 진단 권한이 있어야 하며 GET/HEAD 경로의 비변경 근거·요청 상한을 함께 등록한다. 비변경 근거는 운영자 진술이며, 서버는 길이·범위·승인 결속만 검사한다. 내부 Attestation.Verified는 이 승인 결속을 뜻하고 GET/HEAD가 상태를 변경하지 않는다는 자동 분석 결과가 아니다. 추가 권한 역할·제공자·쓰기 검사·IP literal 소유 증명은 별도 범위다.

최민준은 권한·보안·설치 경계를, 윤재상은 대상 승인 Workbench를, 이경준은 공용 계약·화면 접점을 검토한다. 사용자 제품 요구를 이들의 동의로 대신하지 않는다. #353의 UI 삭제 동의와도 별개로 검토한다.

## 허용과 거부

- 등록은 pending과 무작위 TXT challenge만 만든다. 로그인·URL·체크박스만으로 실행 권위를 만들지 않는다.
- DNS 소유 확인은 30분 내에 수행한다. 승인 요청의 valid_hours는 1~24시간이며 UI 기본값은 4시간이다. UI 요청 상한 기본값은 4이고 설치 상한을 넘지 않는다.
- 모든 해석 주소를 검사한다. 메타데이터·보호 서비스·loopback/link-local은 거부하고 사설 주소는 설치자가 별도로 승인한 좁은 CIDR만 허용한다. 보호 서비스 검사기가 누락되면 승인·시작을 거부한다.
- IP literal은 `dns_ownership_required`로 등록 단계에서 거부한다. TXT 실패라는 다른 가드에 의존하지 않는다.
- 시작 직전 TXT·DNS 주소 집합·선택 IP의 TLS SPKI·만료·철회를 재검증한다. 실제 대상 전송은 승인된 ConnectIP로 고정하며 기존 체인 검증 뒤에 SPKI를 추가 검사한다. 리다이렉트·다른 대상의 승인 재사용은 허용하지 않는다.

주소 집합은 최초 승인과 정확히 같아야 한다. CDN의 정상 회전도 자동 확대하지 않으므로 새 승인이 필요하다. 시작 키와 위임 예산을 동기 예약한 뒤 재검증하며, DNS/TLS 불일치로 실패해도 해당 회차/예약은 복구하거나 환불하지 않는다.

C34 결정([#566](https://github.com/ABC2LAB/ABCDEF2LAB/pull/566))에 따라 MaxTargets는 기본 32, 코드 상한 1024다.
소유 확인 기한이 남은 pending과 승인 기한이 남은 approved만 자리를 차지한다. 철회·기한 만료 기록은
감사·과거 보고서를 위해 그대로 남기며 자리를 차지하지 않는다. 같은 origin의 새 등록도 새 ID·TXT 증명·
범위 승인이 필요하고 이전 계정 분류나 실행 권한을 승계하지 않는다. 활성 자리가 가득 차면 새 등록을 거부한다.
삭제·초기화 API나 저널 삭제로 용량·기존 실행 예산을 재설정하지 않는다.

## 만료와 실행 중 처리

승인 ExpiresAt은 승인 시각+valid_hours와 검증한 인증서 NotAfter 중 빠른 값이다. 파생 회차의 정책 기한은 모델/설치 기한과 대상 승인 기한을 넘지 않는다. 만료 직전은 허용하되 **만료 시각과 그 이후**는 거부한다. TLS 확인 중 인증서가 만료되면 승인을 기록하지 않는다.

- lookup은 만료 승인으로 새 회차 자료를 만들지 않는다.
- current와 시작 recheck도 만료를 거부한다. 만료 뒤에는 DNS·TLS 재접촉 전에 실패한다.
- 실행 중 정상 철회·만료는 기존 준비/실행 검사와 250ms 감시로 신규 admission을 닫고 E② 전송을 중단한다. 이미 예약된 모델 호출만 원래 deadline과 마감 제한(설치 ShutdownTimeoutSeconds의 절반과 30초 중 작은 값, 기본 10초) 안에서 응답·검증된 usage를 저장한다. 예약은 환불하지 않는다. 대기 호출은 추가 예약 없이 종료한다. 사용자 중단·전체 deadline·설치/감사 실패는 즉시 취소하며, 실제 모델 오류·usage 불명·마감 제한 초과는 계속 unknown으로 잠근다. 감사 감시는 정상 대상 종료 뒤에도 마감까지 유지한다. 이미 전송한 바이트의 복구를 보장하지 않는다.
- 과거 보고서용 승인 참조는 보존한다. 만료·철회가 과거 결과를 새 권위로 바꾸거나 다른 대상의 범위를 수정하지 않는다. 새 실행에는 새 승인 절차가 필요하다.

## 시작 전 실제 접촉과 감사

초안·범위 조회가 무접촉이라는 설명과 **대상 승인·시작 사전 검사**를 구분한다.

| 단계 | DNS/TXT | 대상 TLS 접촉 | 대상 HTTP·모델 completion |
|---|---|---|---|
| 대상 등록·초안·범위 조회 | 없음 | 없음 | 없음 |
| 소유 확인 후 승인 | 조회 | 정상 경로 1회. 실패한 후보 IP가 있으면 주소별 1회, 최대 8회 시도 | 없음 |
| 명시적 시작 직전 재검증 | 재조회 | 승인된 선택 IP로 1회 | 이 검사 자체는 없음 |
| 승인된 진단 실행 | ConnectIP 고정 | 기존 E② TLS 경로 | 승인된 경로·예산 안에서만 수행 |

사전 TLS 검사는 HTTP 바깥에서 대상에 직접 연결하므로 E② HTTP 전송 카운터에 합산하지 않는다. UI도 이 접촉을 승인·시작 전에 안내한다. 시작 전 대상 HTTP 0은 **대상과 통신이 전혀 없다는 뜻이 아니다.**

별도 보호 저널 `state/targets/tls-contacts`에 `abc2lab.product-tls-contact/v1`을 기록한다. target_id·revision·승인/시작 단계·contact ID·host/IP/port·시간과 attempt/completed·verified/unverified 결과를 결속한다. 인증서 원문·키·TLS 오류 원문을 기록하지 않는다. 시도를 동기 저장한 뒤 연결하고 결과 저장 실패도 승인·시작을 차단한다. 완료 기록 없는 시도는 접촉 여부/결과가 불명이다. verified는 TLS 검사 결과이며 대상 승인 완료·진단 시작을 뜻하지 않는다.

## 검증과 별도 수용

만료 시간/인증서 만료의 직전·동일·직후, IP literal 고유 오류, 검사기 누락 시 TLS 0을 정상 조건과 대조한다. 만료 가드·IP 가드·nil 거부를 제거한 시험 전용 overlay에서 각각 회귀 실패를 확인한다. TLS 감사 재기동 복원·원문 비노출·감사 실패 시 접촉 0도 검사한다. PostgreSQL 16의 실제 provider 래퍼에서 철회·만료 후 정상 응답/usage 마감·대기 요청 0회, 사용자 중단·감사 실패·마감 초과·모델 오류의 unknown 보존을 대조한다. 서비스 저널에서는 known 취소 후 다음 실행/재기동을 허용하고 이전 예약을 보존하며, 실제 unknown은 계속 전체 시작을 막는지 검사한다.

대상 승인 패널은 HTTPS·userinfo 거부, 404/501 미지원, 결과 불명 뒤 재조회, 철회, 교차 origin 응답 거부, URL 변경/중복 클릭을 단위 시험으로 확인한다. 결과 불명 상태에서 등록·승인·철회를 재전송하지 않는다.

[이전 두 URL 수용 기록](../product-targets-v2-acceptance.md)은 b676e38/1b12c51의 합성 Docker 결과다. 이번 보강은 코드·회귀 검증이며 그 기록을 새 Docker 수용으로 대신하지 않는다. 실제 유료 Qwen·공개 대상 회차는 NOT_RUN이다. E③ 일반 HTTP 후보를 확정 판정으로 승격하지 않는다.


## 사용량 불명으로 설치가 잠긴 경우

정상 철회·만료 뒤 진행 중 응답이 유예(최대30초)를 넘기면 `grace_timeout`, 진행 중 모델 호출을 사용자 중지로 끊으면 `user_stop` 경로에서 usage가 불명일 수 있다. 해당 회차는 `unknown`으로 보존하고 이후 Start는 `busy`로 거절한다. 로컬 모델 경로는 P3 결정안 C05(`docs/run-outcome-model-decision.md`)에 따라 이렇게 끊긴 호출을 예약한 양으로 정산하므로 usage가 불명이 되지 않고 이 잠금에 들지 않는다(`unknown_usage_calls`로 상한 정산을 표시). OpenRouter 경로는 transport가 비정상 종료마다 정책을 막으므로 C06 전까지 이 잠금이 그대로다. 재시작은 잠금을 해제하지 않는다. 회차·예약·원장·unknown 표식을 삭제하거나 예산을 환불해 재전송하지 않는다.

운영자는 진단 ID와 시각·reason code·소비/예약 사용량을 보호 저장소에 보존하고 제공자 대시보드의 실제 호출/사용량과 대조한 뒤 관리자에게 전달한다. 키·요청 원문·DSN은 티켓에 복사하지 않는다. 자동 복구나 사후 usage 보정 API는 아직 없으므로, 관리자가 외부 사용량과 감사 증거를 확정하기 전에는 그 설치에서 새 회차를 실행하지 않는다. 새 설치도 기존 잠금·조직 총예산을 우회하는 수단으로 쓰지 않는다. 실제 대상·유료 모델을 처음 실행하기 전 팀 확인 항목에 `grace_timeout`·`user_stop`의 잠금과 운영 절차를 포함한다.

이번 보강은 Execute가 호출하는 감시 루프의 정상 대상 종료(그 뒤에도 hard 취소 없이 drain 유지), 모델 drain 중 hard 취소, 취소된 문맥의 상태 조회 실패를 각각 회귀로 검증한다. 진단 로그(감사 정본과 분리된 운영 기록)의 기록 실패로는 감시 루프가 실행을 취소하지 않는다(P3 결정안 C10, `docs/run-outcome-model-decision.md`). 전체 Execute에서 실제 외부 모델까지 연결하는 철회 종단 수용을 완료했다고 주장하지 않는다.
