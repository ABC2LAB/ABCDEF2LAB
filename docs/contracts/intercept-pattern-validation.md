# 통제 규칙 정규식 검증

PR #67의 UI 변경과 별개인 엔진 후속이다. 일반 HTTP 생성·수정은 기존에도 정규식을 검사했으나,
DB 직접 호출이나 기존 잘못된 행은 로딩에서 조용히 제외돼 화면의 사용 상태와 적용 상태가 달라질 수 있었다.

DB 생성·수정은 꺼진 규칙도 포함해 잘못된 정규식을 저장 전에 거부한다. 활성화는 행 잠금을 잡은 상태에서
현재 저장된 패턴을 검증하고 커밋한다. 정규식 원문과 컴파일 진단을 오류에 포함하지 않는다.
문자열 규칙의 패턴은 정규식으로 해석하지 않는다. 정규식 검증 HTTP 오류는 고정된 400 응답이며 번역을 제공한다.

활성 규칙의 저장된 정규식을 컴파일할 수 없으면(검사 전에 저장됐거나 DB를 직접 고친 행) 규칙 동작에 따라
나눈다(P3 결정안 C12, `docs/run-outcome-model-decision.md`). 깨진 **허용** 규칙은 그 규칙만 빼고 설정을 올린다
(허용이 가장 느슨한 결과라 빼면 더 엄격해질 뿐이다). 깨진 **막기·확인** 규칙은 `invalid`로 표시해 남기고 설정을
올리되, 그런 규칙이 하나라도 있으면 Guard가 연결된 모든 도구 호출을 우선순위가 가장 높은 깨진 규칙의 ID·이름과
고정 사유 `rule_invalid`로 차단한다(#86의 fail-closed와 같은 범위). 적재할 때 깨진 규칙 수와 규칙 ID를 경고 로그로
한 번 남긴다. DB·활성 도구 설정 읽기 실패와 잘못된 설정 JSON은 지금처럼 설정 확인 실패로 처리해 캐시를 발행하지 않는다. 설정 조회 API도 빈 목록 대신 오류를 반환한다.
명시적인 빈 도구 배열은 기존처럼 유효한 제외 설정이다. 설정을 읽을 수 없으면 제외 도구 목록도 확정할 수 없으므로,
Guard가 연결된 모든 도구 호출은 정상 설정에서 제외한 도구까지 포함해 고정 사유로 차단하고,
LLM fallback이나 다른 허용 규칙으로 넘기지 않는다. 정규식의 매칭 범위를 추측하거나 가상의 규칙 적중을
기록하지 않는다. 설정 확인 실패(`configuration_unavailable`) 판정의 RuleID는 0이고, 깨진 막기·확인 규칙 판정
(`rule_invalid`)은 그 규칙의 ID·이름을 담는다. 어느 쪽도 정규식 원문을 담지 않는다. 진단 로그에는 실패 종류와 필요한 규칙 ID만 남긴다.

실패 감사의 저장 위치는 경로에 따라 다르다. `CheckToolEnabled` 오류는 Guard의 메모리 감사에 남고,
그 뒤 재로딩 경합으로 `Match`가 실패하면 source `unknown`의 denied 행으로 남는다.
설정 확인 실패는 캐시하지 않으므로 복구 전에는 호출마다 DB 재조회와 진단 로그가 발생한다. 깨진 정규식은 설정 확인
실패가 아니어서 캐시되고 경고 로그도 적재 때 한 번만 남는다.

잘못된 기존 행은 삭제·비활성화하거나 유효한 패턴으로 수정할 수 있다. API로 고치거나 끄면 기존처럼 캐시를 무효화해
바로 풀리고, 직접 DB를 수정한 운영자는 캐시 무효화 또는 재시작이 필요하다(깨진 규칙이 캐시된 상태로 남기 때문). 이미 성공적으로 캐시한 뒤 발생한 외부 DB 변경을
실시간 탐지하는 기능은 아니다. 정상 설정에서는 기존 우선순위 내림차순·ID 오름차순의 첫 일치 동작과
명시적으로 제외한 도구·비활성 규칙의 처리를 유지한다.

실제 PostgreSQL 회귀는 전용 DB에 ARTEX_PG_DSN을 지정한다. Guard·로딩 통합 시험에는
ARTEX_INTERCEPT_TEST_DSN도 같은 전용 DB로 지정한다. 새 로딩·Guard 통합 시험은 schema 적용 전부터
기존 db/server 시험과 같은 연결 고정 advisory lock을 잡아 패키지 간 설정 변경을 직렬화한다.
이 시험은 실제 도구를 실행하지 않는다.
