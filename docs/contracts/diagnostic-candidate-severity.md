# 진단 후보 예상 심각도 계약

후보의 예상 심각도는 검토 우선순위 제안이다. E③ 확정 판정·송신 권한·CVSS 점수가 아니며, 새 모델 요청을 만들지 않는다.

## 입력과 저장

기존 `submit_diagnostic_candidate`에 선택 필드 `suggested_severity`, `severity_rationale`를 추가한다. 허용 등급은 `critical | high | medium | low | info`다. 표시 근거는 한국어가 포함된 한 줄로, DLP 후 공백을 정리해 최소 8자·최대 UTF-8 1,024바이트를 수용한다. 도구의 영문 설명에도 바이트 상한과 한국어 약 300자 이내 권장을 명시한다. JSON Schema의 `maxLength`는 글자 수이므로 저장 바이트 상한을 대신하지 않는다. 도구에 들어온 긴 문자열 근거는 실행 보호 값·DLP를 먼저 가린 뒤 UTF-8 글자 경계에서 자르고 ` … [근거 일부 생략]`을 포함해 1,024바이트 이내로 저장한다. 줄바꿈·제어 문자 또는 한글 근거 부족을 생략 문구로 유효화하지 않는다. 이 형식 조건은 설명한 영향의 사실 여부를 자동 검증했다는 뜻은 아니다. 모델 지시는 유형명만으로 추정하거나 CVSS를 만들지 않도록 한다.

근거 문장의 길이 조정은 도구 제출 단계에만 적용한다. DB·보고서 reader는 상한을 넘는 저장 필드를 계속 미평가로 취급한다. 설명 잘림은 실제 HTTP 관찰의 잘림과 다르므로 `output_truncated`·증거·증거 digest는 바꾸지 않는다. 원본 JSON의 SourceDigest는 기존대로 실제 저장 문장을 포함한다.

다음 조건을 모두 만족해야 평가를 보존한다.

- 기존 task/intent/run/call·증거 버전·digest 검증 통과
- 실제 E② 호출의 `completed` 관찰, 호출·Bash·프로세스·프록시 마감 및 감사 완결
- 실제 전송·응답 수가 있고 불명 수가 0
- 순번·시도 참조·시각이 있는 허용 HTTP 응답 관찰, 응답 완료·감사 완결
- 출력 및 관찰이 잘리지 않았고, 관련 호출도 같은 조건을 만족함

서버는 `severity_source=worker_estimate`를 고정한다. 모델은 출처·판정·증거 원문을 지정할 수 없다. 근거 설명은 가리지 않는다(2026-11-26 DLP 폐기, CLAUDE.md 절대규칙 2). 우리 제어 비밀 · E③ 표식은 후보 저장 때 실행의 저장 기록 가림(`RedactRecord`)이 맡는다. 문자열 enum 오류·누락·잘못된 선택 필드 타입·근거 부족은 **평가만 생략**하고 유효한 후보는 계속 저장한다. 기존 핵심 입력·증거 위반까지 수용하는 것은 아니다.

이 도구는 SDK의 `RawInput` 경로에서 입력을 직접 검사한다. 제공자에 알리는 정상 문자열 스키마와 권한 검사는 유지하며, 실행 전에는 새 평가 두 필드만 제외한 핵심 스키마로 필수 네 필드와 기존 선택 필드의 타입을 확인한다. 이후 엄격 JSON 디코더가 미등록 필드·뒤따르는 JSON을 거부하고 후보 결속 검사를 수행한다. 새 평가 필드의 `null`·잘못된 타입은 평가 생략으로 처리하지만, 필수 필드 누락·null·잘못된 타입이나 기존 `remediation`·`related_call_refs`의 null을 수용하는 변경은 아니다.

`DiagnosticCandidate`의 선택 JSON 필드로 저장한다. `diagnostic_candidate_v1`과 기존 fact 저장소를 유지하므로 SQL 마이그레이션은 없다. 이전 기록은 새 필드가 없어도 읽으며 미평가다. 새 reader는 평가 메타데이터를 정규화하지만 기존 증거 검증은 완화하지 않는다. 이전 reader는 선택 필드를 무시할 수 있고 기존 원본은 보존된다.

동일 call·유형·이름·증거의 재제출은 기존 ID를 반환한다. 등급만 바꾸거나 이전 기록에 등급을 추가해 덮어쓰지 않는다. 평가로 finding·E③ verdict를 생성하지 않으며 `verification=manual_review_required`, 후보의 `outcome=review`를 유지한다.

## 지문과 조치 자료

`EvidenceDigest`는 기존 관찰만의 지문이므로 평가 필드가 바뀌어도 변하지 않는다. 기존 조치 `SourceDigest`는 저장 JSON 전체를 해시하므로 평가 메타데이터가 바뀌면 달라지고 이전 조치 자료는 stale이다. 이 계약을 우회하려고 새 필드를 원본 지문에서 제외하거나 기존 저장본을 자동 수정하지 않는다.

## 보고서·공개 범위

내부 remediation API의 `severity`에 유효한 예상 등급을 전달하고, 선택 필드 `severity_source`, `severity_rationale`를 함께 제공한다. 기존 필드만 있는 응답도 수용한다. 작업대 UI에서 후보는 등급 딱지 **높음**과 별도 **검토 필요** 딱지로 표시한다 — 확정이 아님은 '검토 필요'가 말하고 등급 딱지에 '예상'을 붙이지 않는다(2026-11-24 결정). 확정 finding은 **높음**, 미실행·불명·등급 없는 항목은 **위험도 미평가**로 표시한다. 내려받는 HTML·DOCX는 지금 후보 등급에 '예상 '을 붙인다(`report/diagnostic.go` `SeverityText`). 화면과 맞출지는 보고서 담당(이동찬)과 정해 이 줄을 고친다. `info`는 **정보성**이다. 모르는 값을 낮음·정보성으로 대체하지 않는다.

`SourceLoadFailed`, 훼손, 불명, 미실행, 잘림 및 평가 근거 부족은 미평가다. 확정 심각도 분포는 E③ 증거로 확정된 finding만 센다. 후보 분포는 확정 분포와 섞지 않고 '검토 필요' 문구를 붙여 따로 표시하며(예: 점검 진행 '검토 필요 높음 3 · 중간 1'), 목록 필터는 실제 서버 평가를 사용한다.

공유 API에는 새 평가 출처·근거를 내보내지 않고 심각도는 기존 미평가 정책을 유지한다. 공유 HTML·DOCX에서도 후보 평가와 근거를 제거한다. 기존 공유용의 확정 finding 등급 공개 정책은 바꾸지 않는다. 새 필드로 자유문장·원문 비밀·추정 등급의 공개 범위를 확대하지 않는다.

## E③ 저장 경계

`e3record.Source.Severity`는 기존 검증 경로에서 검사되며 `db/e3_findings.go`의 확정 finding 삽입 시 findings와 finding 노드에 저장된다. 보고서는 기존 finding의 저장 등급을 그대로 사용한다. finding에 연결되지 않은 issuance/manifest/verdict의 조회에는 재사용할 독립 심각도 필드가 없다. 따라서 IDOR라는 유형명으로 새 등급을 만들지 않으며 미평가를 유지한다. `allowed` verdict는 비취약 판정이고 위험도 분포에 포함하지 않는다.

이번 변경은 E③의 불변 저장 스키마·오라클·manifest·증거 결속·확정 조건을 변경하지 않는다.
