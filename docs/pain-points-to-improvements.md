# ABC2LAB — 불편·문제 → 개선안 대장 (프로젝트 방법론 스파인)

> **초기 조사·개선 가설과 당시 관찰을 보존하는 대장입니다.** 아래 코드 위치·검증상태·다음 할 일은 최신 `dev` 구현 목록이 아닙니다. 현재 방향과 우선순위는 [개발 계획](development-plan.md), 통합 구현·미검증 항목은 [첫 진단 기동](first-diagnosis-launch.md)을 확인합니다. 과거 관찰을 현재 제품 전체의 한계나 검증 완료로 확대하지 않습니다.

> **방법론**: ARTEX·다른 AI 진단 도구를 쓰면서 불편하거나 잘 안 되던 걸 전부 적고, 각각을 해결하는 방향으로 개선한다. **모든 개선안엔 "왜(어떤 불편)"가 붙는다.**
> **엔트리 형식**: 문제·가설 → 출처(+버전) → 우리 재현조건·증거 → 개선안 → 성공기준 → 검증상태.
> **출처**: `[코드]` ABCDEF2LAB 실제 코드 · `[백서]` 티오리 ARTEX 백서(2026.10, 원문 보유) · `[연구]` 외부 연구/벤치 · `[경쟁]` 상용 도구 · `[사용]` 우리가 직접 돌려 관찰.
> **검증상태**: `가설`(아직 확인 안 함) · `재현`(우리 버전에서 확인됨) · `미재현`(확인했는데 문제 없었음) · `개선후검증`.
> **핵심 원칙 (이동찬 리뷰 반영)**: **[백서]가 ARTEX에 대해 주장한 것 ≠ 우리 코드가 실제로 하는 것.** 백서·연구의 비판은 "재현해볼 알려진 실패 모드(가설)"로 두고, 코드로 실제 동작을 확인한 뒤 성공기준으로 측정한다. ARTEX는 코드상 생각보다 많은 걸 이미 갖고 있음(아래 다수 `[코드]` 교정).
> ⚠️ `[사용]` 관찰은 아직 비어 있음 — ARTEX를 직접 돌려 채워야 가설→사실이 된다. (코드 대조=이동찬이 절반, 실행 관찰=남은 절반)

## 통제·안전

### P1. 범위 밖·파괴적 행동
- **문제·가설**: 통제 환경에서 LLM 안전장치를 켰는데도 실험 데이터가 삭제됨.
- **출처**: `[백서]` ARTEX 실험(안전장치 ON에도 삭제). 우리 버전 재현 여부 미확인.
- **우리 재현·증거**: 아직 — 격리 랩에서 재현 시도 필요.
- **개선안**: 범위 강제 + 상태변경·파괴 행동 사람 승인 + dry-run + 재현 전 DB 리셋.
- **성공기준**: 승인 없는 상태변경 0건, 범위 밖 전송 0건.
- **상태**: 가설. ※DB 리셋·상태변경 증명은 **격리 시험환경 한정** — 운영 서비스 안전장치로 일반화 금지.

### P2. 차단 규칙 우회
- **문제·가설**: 문자열 차단 규칙이 셸 변수/스크립트로 우회될 수 있다.
- **출처**: `[백서]` ARTEX 정규식 차단 우회 주장. `[코드]` guard/intercept 규칙 존재(AssetInterceptRule: exact/fuzzy/cidr).
- **우리 재현·증거**: 아직 — 실제 우회되는지 재현 필요.
- **개선안**: 프록시 길목에서 **실제 요청 기준** 통제(문자열 아닌) + 규칙 시뮬레이터.
- **성공기준**: 알려진 우회 패턴이 길목에서 차단됨.
- **상태**: 가설.

### P3. 대량 요청 부하
- **문제·가설**: 에이전트가 짧은 시간에 대량 요청을 보내 대상에 부하.
- **출처**: `[백서]` **CyberStrikeAI** 사례(20분 ~3.2만 요청) — **ARTEX 수치 아님.** ARTEX의 rate-limit 부재 여부는 코드로 확인 필요.
- **우리 재현·증거**: 아직 — ARTEX 실행 시 요청량 측정 필요.
- **개선안**: rate limit + 순차 모드 + 대상 장애 감지 자동중지 + kill-switch.
- **성공기준**: 설정 상한 내 요청량 유지, 장애 징후 시 자동 중단.
- **상태**: 가설.

## 감사·기록

### P4. 감사 기록 충분성
- **문제·가설**: 원시 트래픽·LLM 기록이 기본 OFF라, 감사에 필요한 기본 수집·보존·누락 탐지가 충분한가? ('에이전트가 로그 삭제 가능'은 실제 권한으로 **별도 재현 필요**.)
- **출처**: `[코드]` 작업·승인·실행·증거 기록은 **존재**함(server/manager.go:234 기본 설정). 원시 트래픽/LLM 기록만 기본 off.
- **우리 재현·증거**: 코드로 "기록 존재" 확인. "삭제 가능"은 미재현.
- **개선안**: 변조불가 감사 seal(에이전트 손 밖) + 기본 수집 범위 재검토 + 누락 탐지.
- **성공기준**: 전송된 요청이 감사에서 100% 재구성됨 + 로그 변조 시 탐지.
- **상태**: 가설(삭제 가능성), 재현(기록 존재).

### P5. 커버리지 세분·표기
- **문제·가설**: 커버리지 그래프는 **이미 있음**. 다만 **계정×기능×검사항목별 완료 여부**를 알기 어렵다.
- **출처**: `[코드]` 커버리지 그래프 존재, 자산 연결 fact를 검사 여부로 계산(db/task_assets_context.go:48).
- **우리 재현·증거**: 코드로 커버리지 그래프 확인.
- **개선안**: 접근통제 지도(신원×자원×검사항목). **회색 = '미검사'로 표기**('미탐'은 정답(GT)과 비교해야 알 수 있으므로 미검사와 구분).
- **성공기준**: 운영자가 "역할×엔드포인트별 뭘 안 봤나"를 한눈에 파악.
- **상태**: 재현(그래프 존재), 개선 대상(세분·표기).

### P7. 숨겨진 식별자 미탐
- **문제·가설**: ID가 숨겨져(base64/UUID) 있으면 변형을 포기해 놓칠 수 있다. **단 ID 역공학은 중심 해결책이 아님** — Base64는 표현 변환이고 무작위 UUID는 역산 대상이 아니다. 복잡한 식별자도 인가 검증을 대신하지 못한다(OWASP).
- **출처**: `[연구/OWASP]`.
- **우리 재현·증거**: 아직.
- **개선안**: **중심 = 테스트 계정들이 소유한 유효 식별자 확보 + 소유권 관계 연결**. ID 역공학(순번 등 약한 스킴)은 **보조**.
- **성공기준**: 숨겨진 ID 대상에서도 소유권 기반 교차 테스트가 수행됨.
- **상태**: 가설.

### P19. 새 작업 설명·목표가 필수처럼 안 보임
- **문제·가설**: 새 작업 생성 시 설명·목표가 필수 입력처럼 보이지 않는다.
