# 제품 회차 IDOR 확정 경로 결정안 — 프로그램이 표식 심기 (E③ 1번)

상태: **결정**(2026-11-16, 사용자 결정. 최민준 작성, 리뷰 이동찬·이경준). 구현은 측정(보존율·공식 비교) 뒤에 한다. 이 문서는 무엇을 왜 정했는지와 바뀌는 계약, 시험 계획을 적는다. 담당별 구현 PR이 이 문서와 다르면 이 문서를 먼저 고친다.

## 1. 왜

- 제품 회차의 IDOR 후보(`submit_diagnostic_candidate`, `agent/e2_diagnostic_candidate.go`)는 `manual_review_required`로만 남는다. 관찰만으로는 확정할 수 없다. "B가 읽었다"는 관찰이고, "B가 읽으면 안 됐다"는 정책이다.
- 지금 E③(구조화 증거 판정)이 CONFIRMED를 낼 수 있는 길은 평가용 등록 GET 경로뿐이다. 운영자가 회차 전에 계정·자원·표식을 수동 레지스트리에 등록하고, 등록 GET 전송기(`transmit`)로 조회한다. 제품 입구는 이 모드를 거부한다(`cmd/first-controlled-diagnosis/gateway.go:92-96`).
- 그래서 제품 회차에서 쓸 확정 경로를 정한다. 사용자 결정(2026-11-14)은 1번 "프로그램이 표식 심기"다.

## 2. CONFIRMED의 뜻 (제품 확정 경로)

"운영자가 소유자 전용이라고 선언한 자원·필드를, 다른 시험 계정이 실제로 읽었다." 선언한 정책에 비춘 확정이다.

E③ 판정 규칙은 바꾸지 않는다: 정책·신원·데이터 세 확인이 모두 서야 하고, 반사·템플릿은 제외하며, 증거가 부족하면 UNDECIDABLE이다([e3-oracle.md](contracts/e3-oracle.md)). 바뀌는 것은 정책과 표식, 소유가 어디서 오는지다.

## 3. 쓰는 조건

아래를 모두 만족할 때만 확정 단계를 돈다. 하나라도 빠지면 후보까지만 남기고(수동 검토), 확정 단계를 돌지 않은 이유를 회차 기록에 남긴다.

1. 대상이 쓰기를 승인했고(`write_consent`) 리셋할 수 있다고 등록됐다(`reversible_writes`, `cmd/first-controlled-diagnosis/product_targets.go:48-52`).
2. 시험 계정 표시 A·B가 둘 다 그 회차에서 인증됐다(`account_auth`가 `authenticated`, [C14 결정안](account-login-decision.md)).
3. 그 대상에 유효한 운영자 선언(§4)이 있다.
4. 회차 예산 안에 확정 단계 몫이 남아 있다(§7).

## 4. 운영자 선언 (결정 4: 대상 등록 보호 저널)

### 4.1 선언하는 것 (자원 종류마다)

| 칸 | 뜻 |
|---|---|
| `type` | 자원 종류. `resource_ref`의 접두가 된다(`type:id`) |
| `sharing` | `shared` 또는 `owner_only` |
| `owner_only_fields` | 소유자만 읽어야 하는 필드 목록(응답 JSON 경로). 표식은 이 중 하나에만 심는다 |
| `create` | 생성 경로(승인 범위 안의 정규 경로)·메서드(POST 또는 PUT)·본문 틀(form 또는 JSON, 표식 자리는 소유자 전용 필드 하나)·응답 속 객체 ID 위치(JSON 경로) |
| `read` | 조회 경로 틀(`{id}` 한 조각만, 예: `/api/things/{id}`)·응답 모양(데이터 위치, 상태 위치는 선택) |
| `identity` | 신원 확인 경로(내 정보 조회 등, GET)와 응답 속 사용자 식별자 위치(조건 (b), §5.1) |

`owner_only`가 아니거나 소유자 전용 필드가 없거나 표식을 심을 수 없는 종류는 UNDECIDABLE이다.

### 4.2 저장과 감사

- 대상 등록 디렉터리 안의 보호 저널에 둔다. C14 계정 분류(`accounts/`)와 같은 방식이다.
- 선언은 그 대상의 승인자만 한다. 누가·언제·어느 대상 판에 선언했는지 감사 기록에 남긴다.
- 대상을 다시 승인하면 선언이 무효가 된다(`target_reapproved`). 선언의 유효창은 대상 승인 기간과 실행 기간이 겹치는 구간이다.
- 실행 시작 때 선언을 동결하고 digest를 남긴다. KG resolver는 이 동결본만 읽고, `policy_version`은 동결본 digest다.
- 레지스트리 내용과 판정을 다른 사람이 쥐는 분리([kg-fixture-registry.md](contracts/kg-fixture-registry.md) §8 #2)는 유지한다. 선언은 운영자가 하고, 최민준은 형식 리뷰만 한다.

### 4.3 고른 것과 버린 것

- 고름: 대상 등록 보호 저널. 제품 회차에는 레지스트리를 쓸 하네스가 없고, C14와 같은 무효화를 쓸 수 있다.
- 버림: KG 레지스트리 파일 형식 v2. 하네스가 회차 전에 0600 파일로 쓰는 전제라 제품 흐름에 맞지 않는다.

## 5. 흐름

확정 단계는 **모델 활동이 모두 끝난 뒤에만** 돈다(#596 이동찬 리뷰). 표식은 확정 단계가 시작될 때 처음 만들어진다. 그 시점에는 대상 응답을 받는 모델 호출(탐색·Planner·Worker와 그 마무리 턴)이 더 없어서, 대상이 표식을 어떤 인코딩으로 돌려주든 표식이 모델 입력에 들어갈 수 없다(CLAUDE.md 절대규칙 2 "E③ 판정 표식은 계속 모델 밖").

0. 실행 시작: 선언 동결, 세대·인스턴스 참조를 서버가 실행마다 발급. E②가 확정 단계 몫(시간·요청)을 떼어 두고, 모델 단계는 남은 범위에서만 돈다(§7 예산). 이전 회차 표식 점검(§6.1).
- 모델 단계: 탐색·진단을 지금처럼 돈다. 이 단계에는 표식이 아직 없다.
- 모델 단계 마감: 모든 모델 호출이 끝나고 그 회차의 모델 승인 예약을 닫는다. 그 뒤로는 모델 호출을 시작하지 않는다.
1. 확정 단계 시작: 표식 생성(§6), 신원 확인(§5.1). 신원 확인이 실패하면 그 대상은 UNDECIDABLE이고 2 이하를 돌지 않는다.
2. 생성: 프로그램이 선언의 본문 틀에 표식을 넣어 A 세션으로 보낸다(E② 프로그램 생성 규칙). E②가 응답에서 객체 ID를 꺼내고, 영수증에 요청 계정(A)과 ID digest를 남긴다. 결과가 불명이면 다시 보내지 않고 그 종류를 UNDECIDABLE로 둔다.
3. A 대조: 조회 경로 틀에 ID를 넣어 A 세션으로 GET한다. E②가 응답의 표식 유무를 검사해 구조화 관찰만 남긴다(§7).
4. B 교차: 같은 URL을 B 세션으로 GET한다. 관찰은 3과 같다.
5. E③: 관찰과 선언 동결본, 신원 확인 결과만 받아 판정한다(§8).
6. 후보와 판정 연결(§9).
7. 봉인: 판정을 저장하면 그 회차 표식의 수명이 끝난다(§6.1). 만든 객체는 지우지 않는다(DELETE는 막혀 있음). 대상 리셋으로 정리하고, 만든 객체 목록(종류·ID digest)을 회차 기록과 보호 저장소에 남긴다.
- 확정 단계 뒤에 대상 응답을 모델에 넣는 호출은 없다. 보고서 생성(`server/diagnostic_report.go`, `server/diagnostic_report_overview.go`, `server/first_diagnosis_report.go`)과 수정 프롬프트 조립(`remediation/context.go`, `remediation/prompt.go`, `server/diagnostic_remediation.go`)에는 모델·제공자 호출이 없다(2026-11-16 코드 확인). 수정 프롬프트는 저장된 비민감 관찰 칸으로 글을 만드는 결정적 조립이고, 프로그램 확정 요청의 응답 본문은 저장하지 않으므로(§7) 표식이 들어갈 자리가 없다. 이 조건은 구현 PR의 시험으로 고정한다(§13).

### 5.1 신원 확인 (조건 (b))

- 프로그램이 선언된 신원 확인 경로를 A·B 세션으로 각각 GET한다.
- E②가 응답에서 선언된 위치의 사용자 식별자를 꺼내, 둘이 서로 다른지를 기록한다. 식별자 원문은 남기지 않고, 실행별 키로 만든 digest와 "다름" 여부만 남긴다.
- 확인하지 못하면(경로 실패, 식별자 없음, 둘이 같음) 그 대상은 UNDECIDABLE이다.
- 오라클의 신원 status(`AccountRef.Status`)는 C14 `account_auth=authenticated`와 이 확인이 둘 다 설 때만 확인됨이다.

## 6. 표식 (결정 3과 조건 (1))

- 형식: 소문자 영숫자만 쓰고, 가림 최소 길이 이상으로, 회차마다 무작위로 만든다.
- **정규화기.** 소문자 영숫자도 JSON `\u0061`, URL `%61`, HTML `&#97;`처럼 쓸 수 있어서 대소문자 무시만으로는 다 잡지 못한다(#596 이동찬 리뷰). 그래서 지원 인코딩을 아래로 고정하고, 이것들을 푼 사본에서 대소문자를 무시하고 대조한다. 표식 검사(§7)와 가림이 같은 정규화기를 쓴다.
  - JSON 문자열 이스케이프(`\uXXXX` 등)
  - URL 퍼센트 인코딩(`%XX`)
  - HTML 숫자 엔티티(`&#NN;`·`&#xNN;`)와 이름 엔티티
  - 한 번만 푼다. 푼 결과에 다시 이스케이프가 있어도 더 풀지 않는다.
- **가림 자리.** 정규화기는 푼 글자마다 원문 위치를 기억한다. 원문에서 맞은 자리든 푼 사본에서만 맞은 자리든, 그 원문 구간을 가린다.
- **지원 밖.** base64, 압축 본문, 여러 겹 인코딩 등 지원 밖의 응답은 "표식 없음"이 아니라 "검사 미지원"으로 남긴다. 그 A·B 쌍은 UNDECIDABLE이다.
  - 압축 본문(`Content-Encoding`이 identity가 아님), 글이 아닌 content-type, 부분 응답은 미지원으로 바로 분류한다.
  - A 대조에서 지원 인코딩으로 표식이 보이지 않으면 그 종류는 검사 미지원이다. 그래서 B 쪽 "표식 없음"은 A와 같은 방식으로 표식이 보였을 때만 차단 근거가 된다. 미리 알아챌 수 없는 인코딩(base64 등)도 이 규칙으로 UNDECIDABLE이 된다.
- **겹 방어.** 표식은 모델 단계가 끝난 뒤에만 생기므로(§5) 정규화기와 가림은 표식이 모델 입력에 들어가는 것을 막는 주 수단이 아니다. E② 표식 검사(§7)의 일치 판단과, 아래 §6.1의 다음 회차 보호에 쓴다. 지원 밖 인코딩은 판정 쪽에서 "검사 미지원"으로 UNDECIDABLE이 된다. 모델 입력 쪽은 순서(§5)가 막는다.
- 모델 쪽: 표식이 생길 때 모델 단계는 끝나 있다. 탐색 중에는 표식이 없으므로 가림·보류 때문에 탐색이 줄지 않는다.
- 표식 값은 저널·로그·근거 파일·보고서·화면 API·모델 입력 어디에도 남기지 않는다(CLAUDE.md 규칙 2 "E③ 판정 표식은 모델 밖"). 사용자 승인 모드의 승인 미리보기(요청 승인 기록의 `input_preview`, `db/request_approvals.go:38`)와 그 저장 기록에서도 표식 값을 가린다(§7 회차 모드).
- B 요청은 프로그램이 만드므로 표식이 들어갈 일이 없다. 그래서 반사로 표식이 돌아오는 경우는 생기지 않는다. 오라클의 반사 제외 규칙은 그대로 둔다.
- 고른 것과 버린 것: 확정 단계를 모델 단계 뒤로 옮겼다(#596 이동찬 리뷰). 처음 안(회차 중 표식 생성 + 가림)은 지원 밖 인코딩에서 표식이 모델 입력에 남을 수 있어 절대규칙 2의 예외가 됐다. 정규화기를 넓히고 검사 못 하는 응답을 보류하는 안은 인코딩 종류가 끝이 없어 완전하지 않고 탐색을 줄인다.

### 6.1 표식 수명과 다음 회차

- 수명: 표식은 그 회차 확정 단계 시작 때 만들고, 그 회차 판정을 봉인하면 끝난다.
- 절대규칙 2 범위: CLAUDE.md 규칙 2는 "E③ 판정 표식은 계속 모델 밖에 둔다"이고 시간 제한이 없다. 그래서 봉인 뒤 대상에 남은 값도 규칙 2 범위 안으로 본다. 봉인 뒤를 범위 밖으로 두면 규칙의 예외가 되므로 그렇게 읽지 않는다.
- 남는 이유: 만든 객체는 대상에 남는다(DELETE는 막혀 있고 지우지 않는다). 리셋하지 않으면 다음 회차의 모델 단계가 지난 표식을 볼 수 있다.
- 보호:
  - (a) 회차 사이 리셋은 운영자 의무다. 확정 단계에서 쓰기(프로그램 생성)를 한 대상은 다음 회차(읽기 전용 회차 포함)를 시작할 때 "지난 회차 뒤 대상을 리셋했다"를 확인받는다. 확인이 없으면 회차를 시작하지 않는다. 확인은 운영자 진술이고, 누가·언제 진술했는지 대상 등록 보호 저널에 남긴다.
  - (b) 다음 회차 시작 때, 모델 단계 전에 프로그램이 지난 회차에 만든 객체(보호 저장소의 종류·ID)를 선언된 조회 경로로 읽어 지난 표식이 정규화기로 보이는지 확인한다. 보이면 모델 단계를 시작하지 않는다(`previous_markers_present`). 그 대상의 지난 표식 값은 리셋 확인 전까지 다음 회차의 가림 값으로 계속 올린다.
- 남는 위험: 운영자가 리셋하지 않고도 리셋했다고 거짓으로 확인했고, 대상이 지난 표식을 지원 밖 인코딩으로 돌려줘 (b)가 놓치면, 다음 회차 모델이 그 값을 볼 수 있다. 이것은 규칙의 예외가 아니라 운영자 의무 위반이다(거짓 진술). 진술 기록(누가·언제)으로 책임을 남긴다.

## 7. E② 쪽 (결정 1: 제품 E² 확장, 조건 (3)(6))

- **프로그램 목적 규칙.** 로그인용 프로그램 송신(`auth_prep`)처럼 목적이 붙은 규칙을 둘 더한다. 하나는 표식 생성(선언된 경로 정확 일치, 메서드 하나), 다른 하나는 표식·신원 조회(경로 틀 `{id}` 한 조각 또는 신원 경로 정확 일치, GET)다. 모델 요청의 규칙 찾기에서는 빠진다. 지금 규칙 검증은 `auth_prep`의 POST 하나만 받으므로 바꾼다(`e2proxy/execution.go:190`).
- **신뢰 프로세스 안 검사.** 이 경로의 프로그램 요청에 한해 E² 안에서 응답을 검사하고, 저널에는 구조화 관찰만 남긴다: 표식 유무·일치 방식(정확 일치/대소문자 무시)·상태 코드·content-type·본문 digest. 생성 요청은 객체 ID digest를, 신원 요청은 식별자 digest와 다름 여부를 더한다. 원문 본문과 표식 값은 저널·로그·모델 어디에도 남기지 않는다. E③은 이 관찰만 받는다.
- **요청별 계정.** 프로그램 요청은 서버가 C14 세션(`E2HTTPSessions`)에서 고른 계정을 붙이고, 영수증에 계정 라벨을 남긴다. 지금 영수증(`e2proxy/types.go:156-179`)에는 계정·URL·본문이 없다.
- **표식 정규화기.** 지금 실행 가림은 정확 일치다(`bytes.ReplaceAll`, `e2proxy/execution.go:1430`). E② 안에 §6의 정규화기를 두고, 표식 값의 가림과 표식 검사가 이것을 같이 쓴다. 관찰의 일치 방식은 원문·대소문자 무시·디코딩(어느 인코딩) 중 무엇으로 맞았는지 남긴다. 지원 밖이면 "검사 미지원"이다. 다른 가림 값의 동작(정확 일치)은 바꾸지 않는다.
- **형식 판.** 영수증·저널 형식을 v3로 올린다. 기존 `Scope`·`CallRef`·`AttemptID`·`PolicyRevision`은 그대로 두고 아래를 더한다.
  - 요청 결속: 프로그램 목적, 실제로 쓴 C14 계정 라벨과 결속 참조, 선언 동결본 digest. 모델이 전달한 라벨은 근거로 쓰지 않는다.
  - 관찰 위치와 상태: 검사한 선언 필드와 일치 방식. 검사 완료·부분 응답·미지원·실패를 구분하고, 검사하지 못한 것을 "표식 없음"으로 기록하지 않는다. 본문 digest도 전체와 부분을 구분한다.
  - 객체·신원 비교: 객체 ID와 신원 식별자는 실행별 키를 쓰는 digest로 남기고, "서로 다름" 판정에는 비교한 A·B 영수증 참조를 함께 남긴다.
  - 무결성과 호환: 새 칸도 저널 무결성 검증 범위에 넣는다. 평가 내보내기·검증기는 v1·v2도 계속 읽되, 없는 계정·관찰 정보를 추정해서 제품 확정 근거로 쓰지 않는다.
- **예산.** 확정 단계 몫(시간·요청)은 회차 시작 때 E②가 떼어 둔다. 모델 단계는 그 몫을 뺀 범위에서만 돈다. "남으면 쓴다"가 아니다. 새 기본값에서는 모델 단계가 시간·예산을 다 쓰는 일이 흔해서, 남는 몫을 쓰면 확정 단계가 매번 UNDECIDABLE이 된다. 이 몫이 확정 단계 전용 상한이다. 상한에 닿으면 그 단계만 끝내고 남은 종류를 UNDECIDABLE로 둔다. 회차 전체 예산이 바닥나면 지금처럼 새 송신을 멈춘다. 칸 이름과 기본값은 구현 PR에서 설치 상한 결정안(install-limits-decision)에 맞춰 정한다. 확정 단계는 모델을 부르지 않으므로 모델 예산은 떼어 두지 않는다.
- **쓰기.** 모델의 쓰기 허용(C21)과 따로 둔다. 프로그램 생성은 §3 조건에서만 열린다. DELETE는 계속 막는다. 결과 불명 쓰기는 다시 보내지 않는다.
- **회차 모드.** 운영자가 동의한 문구를 그대로 지킨다(#596 윤재상 리뷰).
  - AI 자동 모드 회차: 쓰기 동의대로 프로그램 생성 요청을 건별 확인 없이 보낸다.
  - 사용자 승인 모드 회차: 프로그램 생성 요청도 기존 요청별 확인 경계를 거친다. 확인 화면에는 "확정 단계 프로그램 생성"과 선언된 자원 종류를 보인다. 승인 미리보기(InputPreview)와 저장 기록에서 표식 값은 가린다. 승인 대기에는 기존 요청 승인 시간 초과를 요청마다 따로 적용하고, 거부하거나 시간이 지나면 그 종류만 UNDECIDABLE이다. 확정 단계는 모델 단계 뒤라, 시작 화면에서 "모델 단계가 끝난 뒤 확정 단계에 승인 요청이 뜬다"를 알린다.
  - 지금 등록 코드는 되돌릴 수 있는 쓰기를 승인하면 `write_consent`를 늘 자동 판으로 채운다(`cmd/first-controlled-diagnosis/product_targets.go:317-320`). 그래서 모드 구분은 동의 판이 아니라 회차 모드로 한다.
  - 동의·고지 문구 두 곳에 확정 단계 생성을 적는다(§10 표).
- 고른 것과 버린 것: 등록 GET 전송기(`transmit`)를 넓히는 안을 버렸다. 한 회차에 전송 통제가 둘이 되어 예산·감사·대상 승인을 두 곳에서 맞춰야 한다. 게다가 생성 POST·실행 중 자원 등록·제품 입구는 그 안에서도 새로 만들어야 한다. 이 결정에서는 제품 입구의 등록 GET 거부(`gateway.go:92-96`)를 바꾸지 않는다. 확정 단계는 일반 HTTP 회차 안에서 돈다.

## 11. 평가와의 관계 (결정 5)

- 두 경로를 함께 둔다. 평가 회차의 수동 레지스트리·등록 GET 경로는 그대로다.
- 구현이 측정 뒤라서 P0 보존율과 공식 비교에는 들어가지 않는다.

## 12. 기본값

- 생성 결과가 불명이면 다시 보내지 않고 그 종류를 UNDECIDABLE로 둔다.
- 만든 객체는 지우지 않고 리셋으로만 정리한다.
- 객체 ID는 생성 응답에서만 찾는다. 목록 응답에서는 찾지 않는다.
- B 쪽 대칭 객체는 만들지 않는다.
- 표식은 §6 형식으로 회차마다 무작위로 만든다.
- 세대·인스턴스 참조는 서버가 실행마다 발급한다.
- 선언 유효창은 대상 승인 기간과 실행 기간이 겹치는 구간이다.

## 13. 시험 계획

- 단위
  - 표식이 소문자 영숫자·가림 최소 길이 이상이고 회차마다 다르다.
  - 정규화기 수용시험: 대상이 표식을 대문자로 바꾸거나 지원 인코딩(JSON `\uXXXX`, URL `%XX`, HTML `&#NN;`·`&#xNN;`·이름 엔티티)으로 돌려준 응답, 그리고 이들을 섞은 응답에서 도구 출력·기록·모델 입력에 원문이 0이다. 같은 응답의 E② 관찰은 "표식 있음"과 일치 방식을 남긴다.
  - 지원 밖(base64, 압축 본문, 여러 겹 인코딩, 글이 아닌 content-type, 부분 응답)은 관찰이 "검사 미지원"이고 "표식 없음"으로 기록되지 않으며, 그 쌍은 UNDECIDABLE이다.
  - A 대조에서 지원 방식으로 표식이 보이지 않으면, B 결과와 상관없이 그 종류는 UNDECIDABLE이다.
  - 사용자 승인 모드: 프로그램 생성 요청이 요청별 확인을 거치고 미리보기·저장 기록에 표식 값이 없다. 거부·시간 초과면 그 종류가 UNDECIDABLE이다. AI 자동 모드에서는 확인 없이 보낸다.
  - 프로그램 목적 규칙이 모델 요청 매칭에서 빠지고, 다른 경로·메서드는 거부된다.
  - 생성 결과가 불명이면 재전송하지 않는다.
  - 저널 관찰에 본문·표식 값·식별자 원문이 없다.
  - 검증기·평가 내보내기가 v1·v2·v3를 모두 읽는다.
- 통합(소유 fixture 대상)
  - 소유자 전용 필드가 B에게 새는 앱: CONFIRMED.
  - B에게 403을 주는 앱: CONFIRMED가 아님(차단 확인).
  - 신원 확인 식별자가 A·B 같음: 그 대상 UNDECIDABLE.
  - 선언이 없음, 쓰기 미승인, 리셋 불가: 확정 단계가 돌지 않고 후보만 남는다.
  - 템플릿 응답(모든 객체가 같은 본문): UNDECIDABLE.
  - 확정 단계 상한에 닿음: 남은 종류 UNDECIDABLE, 회차는 계속.
  - 후보 경로 패턴이 조회 틀 하나와 맞음, 0개, 둘 이상: 각각 연결됨, 따로, 따로.
- 순서와 다음 회차(§5·§6.1)
  - 표식 생성 요청이 모든 모델 호출이 끝난 뒤에만 나간다(모델 호출 시각과 E② 생성 시도 시각 대조). 확정 단계 중 모델 호출 0.
  - 확정 단계 몫: 모델 단계가 시간·요청을 다 써도 확정 단계 몫은 남아 확정 단계가 돈다.
  - 대상이 표식을 base64·이중 퍼센트 인코딩으로 돌려주는 fixture에서도 모델 입력·도구 출력·활동 기록에 표식(원문과 그 인코딩 형태 모두) 0. 판정은 검사 미지원으로 UNDECIDABLE.
  - 확정 단계에서 쓰기를 한 대상의 다음 회차(읽기 전용 포함): 리셋 확인이 없으면 시작하지 않는다. 확인하면 진술이 저널에 남는다.
  - 리셋하지 않은 다음 회차: 지난 표식이 지원 인코딩으로 보이면 모델 단계를 시작하지 않는다(`previous_markers_present`). 리셋한 다음 회차는 정상 시작.
  - 사용자 승인 모드: 확정 단계 승인 대기 시간 초과는 그 종류만 UNDECIDABLE, 다른 종류는 계속.
  - 확정 단계 뒤 보고서·수정 프롬프트 생성에서 모델·제공자 호출 0.
- 수용(구현 뒤): 연습 대상(VAmPI)과 소유 fixture의 시험 계정 A·B 실제 회차(개선 반복은 공식 측정 대상인 Juice Shop에서 돌리지 않는다). 표식 원문이 모델 입력·기록·화면 API·보고서에서 0인지는 건수 스크립트로 확인한다.
- 가드마다 변이 검사.

## 14. 발표 전 대체

발표 전에 §13 수용시험을 통과하지 못하면, 제품 회차는 후보까지만 보여주고 확정은 평가용 등록 GET 경로로 시연한다.

### 14.1 대체 경로 실제 대상 확인 (2026-11-17)

- 연습 대상 VAmPI(BOLA: `GET /books/v1/{book_title}`)에 실제 시험 계정 A·B의 로그인 세션으로 한 번 돌렸다. 판정 `confirmed`, 접근통제 지도 교차 셀 `confirmed`, 저장 finding 1, 대상 GET 2건이었다. 유료 모델 호출은 없다(모델 자리만 각본).
- 지나간 경로: 실제 PG16, production 기동(`StartFirstDiagnosisControlled`), 실제 Supervisor, 원본 Engine, 등록 GET 전송기, E③ 저장, 결과 API. 시험은 opt-in `TestE3RegisteredGETRealTargetConfirmed`(`server/e3_real_target_acceptance_linux_test.go`)이고, 대상·세션·표식·응답 판정 규칙은 0600 보호 입력에서 읽는다. 발표 전 재확인에 같은 시험을 다시 쓴다.
- 응답 판정 설정의 뜻: VAmPI 책 응답에는 상태 칸이 없어서, 응답 판정 규칙(`JSONViewRule`)의 상태 칸 자리(`StatusPath`)에 `owner` 칸을, 정상 값에 A 계정 이름을 넣었다. 즉 "등록 소유자의 책으로 돌아온 응답을 정상으로 본다". 확정에는 여전히 소유자·교차 응답 모두에서 표식 정확 일치가 필요하다.
- 한계: 이 설정에서 고쳐진 대상이 교차 계정에 주는 404(`{"status":"fail"}`)는 정상 차단이 아니라 "분류 안 됨"이 되어 UNDECIDABLE로 남는다. 반대 대조(가짜 대상)에서 확정 0건을 확인했다.
- 대상 설정 변경: 이 회차용 VAmPI는 토큰 수명(`tokentimetolive`)을 기본 60초에서 1800초로 늘려 띄웠다. 등록 GET 경로에는 세션 재로그인이 없다.

### 14.2 등록 GET 경로 보완 (측정 뒤 구현, 이동찬)

14.1에서 나온 두 가지를 E③ 1번 구현 항목에 더한다.

1. **상태 칸 없는 JSON 응답의 판정 선택지**: 응답 판정 규칙에 HTTP 상태 코드로 정상·차단을 가르는 선택지를 둔다. 그러면 고쳐진 대상의 차단 응답도 차단으로 분류할 수 있다. 단, 200 본문으로 오류를 돌려주는 API가 있으므로 확정 조건은 낮추지 않는다. 소유자·교차 응답 모두에서 표식 정확 일치가 지금처럼 필수다.
2. **세션 재로그인**: 등록 GET 경로는 보호된 세션 헤더 파일만 쓰고 재로그인이 없어, 토큰 수명이 짧은 대상에서는 준비와 실행 사이에 세션이 끊긴다. 제품 E²의 재로그인 처리(#614)와 같은 처리를 둔다. 프로그램이 소유한 인증 준비로 하고, 계정별 횟수 상한을 두며, 실패도 횟수에 센다.

## 15. 후속

- 탐색 경계 기록에서 관찰된 생성 요청으로 선언 초안을 만들고, 운영자는 확인만 하게 한다. 운영자 부담을 줄이기 위해서다(조건 (7)).
- 모델이 생성 요청을 쓰고 표식 자리만 E②가 채우는 방식(자리표시자 방식). 이번에 버린 이유: 지금 시험 계정 모드는 어느 계정 세션으로 보냈는지 기록하지 않아 소유가 모델 요청에 기대게 되고, E②가 본문을 바꾸면 요청 경계·감사·재전송 의미가 달라진다.
