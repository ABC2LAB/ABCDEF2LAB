# LLM 도입·성능 개선·증거 기반 보고서 계획

2026-11-06 · **이동찬의 11/06 개발 방침 / 구현·실측 및 팀 계약 변경과 구분**

모델 도입과 개선 순서는 이 문서를 기준으로 한다. 팀의 작업 순서·역할은
[개발 계획](development-plan.md), 실행 통제·판정·출력은 각 계약,
공식 ARTEX 비교 조건은 [평가 프로토콜](evaluation/evaluation-protocol.md)이 정본이다.
이 계획은 기존 팀 채택 사항이나 과거 실험 결과를 소급 변경하지 않는다.

## 1. 상태와 적용 경계

코드 확인 기준은 `dev`의 `adca969238fb2ab2dfb50ae78e31feb628213746`이다.
아래 구현 사실은 코드 경로를 확인한 범위이며 실제 모델·대상 실행의 검증 결과가 아니다.

| 구분 | 확인한 내용과 한계 |
|---|---|

| 기존 팀 채택 사항 | E②·E③ 우선, 첫 IDOR 회차의 M01~M04와 착수 조건 유지. 공식 비교는 기존 프로토콜의 GPU 로컬 조건을 따름 |

| 미검증·후속 과제 | Qwen3.5의 DAST 적합성·장비 실측, RAG 검색·출처 결속, 단계별 실제 스크린샷 수집·저장·삽입, 내부 재현 보고서의 별도 출력 정책 |

RAG와 스크린샷 관련 제품 경로는 `agent/`·`server/`·`db/`·`report/`의 코드 조사에서
확인하지 못했다. 문서 요구를 이미 연결된 기능으로 표현하지 않는다.
첫 통합 진단의 기존 착수 조건에 RAG·파인튜닝·학습 서버를 추가하지 않는다.

## 2. 초기 로컬 기준 모델과 장비

초기 **로컬 개발 기준 모델(검증 전)**은 [`Qwen/Qwen3.5-35B-A3B`](https://huggingface.co/Qwen/Qwen3.5-35B-A3B)다.
우리 DAST에서 최적 성능이 입증됐거나 최종 고객 배포 모델로 확정됐다는 뜻은 아니다.
이번 개발안에서 중국계 모델을 후보에서 제외하지 않는다. 고객별 모델 출처·보안·라이선스
정책은 배포 전에 별도로 확인한다. 모델 카드의 일반 벤치마크를 우리 진단 성능으로 옮기지 않는다.

한국어 특화와 이미지 이해 능력은 선정의 필수 조건으로 두지 않는다. 핵심 기준은 다음이다.

- 실제 도구 호출의 정확성과 관찰에 따른 계획·재계획 능력
- 제한된 대상 요청 예산 안의 진단·재현 성능
- 실제 증거에 근거한 보고서 작성
- 로컬 추론의 지연·메모리·운영 부담

모델 artifact·revision·tokenizer·양자화·서빙 버전과 실제 서버의 모델 식별자를 기록한다.
저장소 이름과 서빙 서버의 태그를 같은 문자열이라고 추정하지 않는다.
MoE의 활성 파라미터 수는 전체 가중치 메모리가 아니다. 장비 요구량은 실제 가중치·양자화·
문맥·출력 한도·동시성·캐시와 런타임을 고정해 측정한다.
보안·DAST 특화 성능, 다른 모델 대비 우위나 고객 장비 요구량은 아직 미확인이다.

지금은 추론 환경을 우선 준비한다. 고객사 최소·권장 사양은 최종 배포 모델과 설정으로
실측한 뒤 확정한다. 학습용 80GB급 GPU와 학습 파이프라인을 현재 개발 일정·첫 진단의
선행 조건이나 고객 설치 조건으로 넣지 않는다. 이 문서 수정은 모델 다운로드·학습·배포를 수행하지 않는다.

## 3. 개선 순서와 실패 분류

1. 기본 모델을 연결해 통합 실행과 기준 성능을 측정한다. 연결 스모크와 실제 진단 성공을 구분한다.
2. 프롬프트·도구 명세·모델 입력·실행 피드백·문맥 관리를 개선한다.
3. 참고 지식 부족이 확인된 부분에 작은 자료 집합으로 RAG를 추가한다.
4. 남은 실패를 분석하고 모델 교체·서빙·실행 구조 개선도 비교한다.
5. 그래도 해결되지 않는 반복적인 문제에 한해 파인튜닝을 최후 수단으로 검토한다.

파인튜닝은 현재 필수 개발 항목이 아니다. 학습 데이터·권한·비용·별도 평가 계획을 갖춘
후속 검토로 두며, 프롬프트나 RAG로 모든 성능 문제가 해결된다고 약속하지 않는다.

| 실패 종류 | 먼저 확인할 근거 |
|---|---|
| 도구 연결 오류 | 실제 도구명·입력 schema·binding·반환값과 실행 여부 |
| 실행 환경 문제 | 모델 접속·서빙 한도·대상 상태·승인·E②·감사 경로 |
| 검색 실패 | 허용된 자료의 존재·검색 결과·출처·버전·적용 조건 |
| 모델 판단 오류 | 올바른 입력·관찰을 받았는데도 잘못 고른 행동·설명 |

E②의 정책 거부는 대상 HTTP 거부 응답과 다르다. 전송 결과 불명과 증거 부족도 각각 남기며,
도구 오류를 모델 지식 부족으로 묶어 학습 과제로 넘기지 않는다.

## 4. 역할·프롬프트·실행 입력

Planner·Worker·Reporter는 역할과 도구 권한을 분리한다. 초기에는 **같은 모델 서버를 공유**하는
구성을 우선 검증하며 역할별 별도 모델은 필수가 아니다. 현재 [provider 선택 경로](../server/task_llm.go)는
agent binding과 task profile을 지원하므로, 공유 검증에서는 각 역할의 실제 선택값까지 확인한다.
도구 목록·binding은 프로그램이 정하고 모델이 자신의 실행 권한을 확대할 수 없게 한다.

| 역할 | 개선할 입력·결과 |
|---|---|
| Planner | 계정·역할·자원·소유관계, 이미 수행한 검사·확보한 증거, 다음 행동에 필요한 관찰과 반복 방지·종료 조건 |
| Worker | 정확한 도구명·입력 schema·호출 예시, 승인된 참조, 정책 차단·HTTP 거부·전송 불명·증거 부족을 구분한 결과 |
| Reporter | 실제 행동·관찰·증거 ID와 버전, 재현 전제·제한, 사실과 추정 원인의 구분, 근거 있는 수정 권고 |

프롬프트의 길이 자체를 개선으로 보지 않는다. 문맥 한도·요약 시점·출력 상한은 실제 모델 서버
설정과 역할별 실행 문맥으로 검증하며, 요약 뒤에도 판정·승인과 증거 참조의 차이를 유지한다.

### 소스 기본값과 실제 적용값

[카탈로그](../agent/promptcatalog.go)의 기본 본문은 [서버 seed](../server/assembly.go)를 거쳐
DB에 들어가고, [DB의 현재 프롬프트·버전](../db/config.go)과 실행의
[`PromptOverride`](../agent/prompt.go)가 실제 본문에 영향을 준다.
별도의 기본값 이관 경로도 있으므로 소스 문자열이나 프롬프트 이름만으로 적용값을 단정하지 않는다.

개선 실험에서는 실제 선택한 DB 프롬프트 버전과 렌더링에 사용한 템플릿·변수 구성·도구 명세의
식별자/해시를 보호된 기록에 남기는 경로를 확인한다. 실제 증거·비밀값이 포함된 프롬프트 원문은
공유 저장소에 올리지 않는다. 이번 작업은 프롬프트 코드·DB·실제 적용값을 변경하지 않는다.

## 5. RAG의 자료와 신뢰 경계

초기 RAG는 작은 검증용 자료 집합으로 시작한다. 출처·버전·적용 조건·접근권한을 보존한다.

| 용도 | 우선 자료 |
|---|---|
| 진단 참고 | 현재 지원 취약점의 검사 조건·절차, 정상 대조·증거 확보 방법, 흔한 오판, 도구 사용법·지원 범위 |
| 보고서 참고 | OWASP 등 검토 가능한 보안 지침, 기술·버전별 공식 프레임워크 보안 문서, 검토된 사내 작성 기준·비민감 사례, 수정 후 검증 지침 |

키워드 검색과 의미 검색의 조합은 검토할 수 있다. 특정 벡터 DB·프레임워크 도입을 확정하지 않는다.
자료·인덱스·검색 설정의 버전과 사용한 출처를 기록하고, 검색된 지침이 해당 기술·버전에 맞는지 확인한다.

다음은 일반 참고자료 RAG와 구분한다.

| 정보 | 조회 기준 |
|---|---|
| 현재 승인·계정 권한·만료·요청 예산 | 서버의 현재 권위 상태를 정확히 조회하고 송신 전 E②에서 재검사 |
| 정본 KG 정책·실제 판정 근거 | 해당 task·실행·reset 세대·정책 버전에 결속된 신뢰 경로 |
| 요청·응답·실행 기록 | 실제 증거 ID·버전과 실행 귀속 |
| 스크린샷 | 실제 캡처와 실행 단계·증거 참조의 연결 |

검색 문서와 대상 응답의 지시문은 실행 권한이 아니다. 프롬프트 인젝션·출처·최신성·문서 접근권한을
검사할 경계를 설계한다. 우리가 제공하는 자격값은 외부 서비스에 보내지 않고, 기밀 자료를 외부 검색·임베딩 서비스로 자동 전송하지 않는다.
대상 응답 원문(대상이 발급한 토큰 포함)을 외부 LLM에 전달하는 실제 진단은 제공자·전달 범위를
[사전 고지·승인](external-llm-notice-ko.md)받아 명시적으로 선택한다. 선택한 모델 입력에 대상 응답을 일괄 마스킹하지 않는다.
폐쇄망·민감 환경의 로컬 방침을 유지하고, 공개 연습 대상의 평가 예외를 조직 자료나 RAG로 확대하지 않는다.

## 6. 실무형 재현 보고서와 실제 스크린샷

목표는 발견된 취약점을 설명하고 **실제 수행 기록에 근거한 단계별 재현 방법과 대응 방안**을
제공하는 것이다. 다음 항목은 내부 재현 보고서의 요구이며 현재 공유 export의 완료 기능이 아니다.

- 취약점 개요·영향 범위·판정 상태, 재현 환경·사전 조건
- 단계별 수행 행동, 기대 결과와 실제 관찰 결과
- 요청·응답·실행 로그의 증거 참조와 해당 단계의 실제 스크린샷
- 확인된 사실과 추정 원인의 구분
- 즉시 완화책·근본 수정 방안·수정 후 검증 방법
- 별도 재현 검증의 실시 여부와 제한 사항. 하지 않은 재검증은 미실시로 표시

스크린샷 요구는 재현 가능한 증거를 단계별 실제 화면으로 보여주는 기능이다.
AI의 이미지 해석이나 이미지 입력 모델·OCR·비전 파인튜닝을 필수로 추가하지 않는다.

| 구성 | 책임과 후속 연결 |
|---|---|
| 실행 프로그램 | 승인된 작업을 수행하고 요청·응답·로그와 필요한 실제 스크린샷 수집 |
| 증거 저장부 | 실행·단계·계정 참조·증거 ID·캡처 시각·스크린샷 참조 연결 |
| 보고서 모델 | 기록된 행동과 결과를 설명하고 재현 절차·수정 권고 작성 |
| 출력 프로그램 | 참조·버전·접근권한을 검증하고 실제 스크린샷을 번호·캡션과 함께 삽입 |

AI가 증거 이미지를 생성하거나 없는 화면·미실행 단계를 만들면 안 된다.
요청·응답을 이미지로 렌더링한 것은 실제 웹페이지 캡처와 구분해 표시한다.
누락·끊긴 증거 참조는 누락으로 드러내고 생성 이미지로 채우지 않는다.
캡처를 위한 새 로그인·요청·상태 변경은 새로운 실행으로 취급해 기존 승인·E② 통제를 적용한다.

공유용 export는 [기존 DLP 계약](contracts/report-export-dlp.md)의 원문·PoC 마스킹을 유지한다.
내부 재현 보고서와 공유 사본은 출력 목적별 권한·비밀 처리·캡처 보관·마스킹·참조 유효성 정책을
별도로 합의해야 한다. 화면에 포함된 쿠키·토큰·개인정보도 보호 대상이다.
그 합의와 구현 전에는 공유 export에 원문이나 스크린샷을 자동 첨부하지 않는다.


### 유형 독립적 결과 수집과 종합 출력

보고서의 완료 기준은 IDOR 한 건 저장이 아니라 **여러 유형의 관찰 → 근거에 연결한 후보 → 판정·한계 구분 → 개별 상세 → 종합 출력**이다.
모든 유형을 보고서에서 표현한다는 뜻은 모든 자동 검증기나 실제 모델 탐지 성능이 완성됐다는 뜻이 아니다.
등록 IDOR의 계정 A/B·KG·표식 조건은 해당 검증 경로에만 유지하며 다른 유형의 후보 저장 조건으로 확장하지 않는다.

첫 종단 구현은 일반 E② Bash 실제 관찰에 연결한 `submit_diagnostic_candidate`와 기존 fact 저장소를 재사용한다.
모델은 유형·이름·요약·수정 제안만 제출하고, 서버 소유 task/run/intent/call·관찰 시각·실제 출력과 SHA-256을 결속한다.
후보의 `manual_review_required`는 확정 취약점이 아니며, `completed`는 실행 결과일 뿐이다.

`GET /api/report/diagnostic?task=<id>`는 명시한 작업의 모든 저장 회차에 속한 후보·finding·미확정 E③ 판정을
같은 읽기 전용 repeatable-read 스냅샷에서 읽는다. `audience=internal`은 기존 단일 ARTEX 관리자 인증 하의 상세 사본이고,
기본값은 공유용 전체 자유문장 마스킹이다. `download=1`은 외부 리소스·스크립트 없는 자체 포함 HTML을 내려준다.
다른 작업이나 상속 결과는 합치지 않는다. 회차 필터는 아직 지원하지 않으며 지정하면 거부한다.
합계 10,000건·출력 16 MiB 초과나 근거 무결성 오류는 부분 성공 대신 생성 오류다.

집계는 프로그램이 계산한다. 확인된 E③ 최초 판정 링크·digest·현재 증거 버전이 함께 맞는 finding만 확정 집계한다.
기존 status만 confirmed인 행이나 버전이 어긋난 보고서는 검토 필요로 남긴다. 승인 거절/미지원, 오류/결과 불명,
추가 검토 후보와 E③ allowed 결과는 확정 취약점 총계에 넣지 않는다. 심각도와 유형별 확정 집계도 별도로 제공한다.
수정/triage 상태를 검증 성공으로 바꾸지 않으며, 같은 이름의 별도 근거를 임의 중복 제거하지 않는다.

현재 상세는 저장된 실제 명령·도구 결과, 관찰 시각·귀속·버전과 모델의 수정 제안을 구분해 제공한다.
완전한 요청/응답 보존, 계정 준비 방법, 단계별 기대값, 별도 재현·패치 후 재검증, 실제 캡처가 없는 경우
그 내용을 발명하거나 완료로 표시하지 않는다. 임의 본문에 숨은 비밀을 완전히 탐지하는 기능도 주장하지 않는다.
실행의 기존 비밀 치환에 더해 알려진 자격정보 형식·URL·연락처를 제거하고 HTML 자동 이스케이프와 CSP를 적용한다.
원문 blob·첨부·외부 URL은 열지 않으며 공유용 사본은 자유문장을 통째로 마스킹한다.
실제 스크린샷 수집·삽입과 유형별 검증/권한 있는 검토 확정 절차는 남은 구현이다.
합성 구성 시험과 실제 코드 경로 통합 시험은 실제 모델 탐지 성능과 구분해 보고한다.


### 저장된 기술별 조치와 AI 수정 프롬프트

공통 결과의 저장 증거 → 보안 조건·완화·근본 수정·설정/코드 예시 → 복사용 AI 수정 프롬프트를
같은 결과 아래에 연결한다. `remediation` 순수 생성기는 닫힌 유형·기술·출처·확인 수준과 근거 수/버전만 받는다.
실제 대상의 응답 문장, URL, 임의 모델 설명, 파일명이나 검색 문서 지시를 프롬프트 명령에 삽입하지 않는다.
따라서 상세 보고서는 보호된 관찰 내용을 따로 표시하고, 복사용 프롬프트는 필요한 재현 전제와 영향 위치를
권한 있는 비민감 자료에서 추가 확인하도록 명시한다. 이 버전은 완전한 재현 녹취나 실제 고객 패치 생성기가 아니다.

기술 입력은 인증된 담당자가 명시적으로 제공한다. API는 출처를 `user_provided`로 고정한다.
현재 자동 핑거프린트 신뢰 출처의 채택은 구현하지 않았으며 모델 문장을 관측 사실로 승격하지 않는다.
Java/Python 언어 정보만으로 Spring/Django를 선택하지 않는다. SQL 인젝션의 Java JDBC/Python DB-API 안내는
해당 접근 방식이 실제 저장소에서 확인된 경우에만 적용할 조건부 예시이며 실제 파일명·함수명·수정 버전을 발명하지 않는다.
미확인 기술·버전은 unknown으로 보존하고, 조회하지 않은 공식 문서/RAG 출처를 생성하지 않는다.

생성 API는 `POST /api/report/diagnostic/remediation?task=<id>&audience=internal`이다.
본문은 `entry_id`, 현재 `expected_source_digest`, `technologies`이며 본문에서 판정·근거·버전을 받지 않는다.
서버는 원본 귀속·현재 근거를 잠그고 source digest CAS를 확인한 뒤 기존 fact 저장소에 새 불변 조치 artifact를 저장한다.
finding의 E③ 판정·보고서·처리 상태를 바꾸지 않는다. 같은 입력은 기존 artifact를 반환한다.
기술 변경은 새 조치/input digest로 연결하고, 원본 증거·설명·조치 제안·보고서의 변경은 기존 artifact를 stale로 만든다.
legacy 증거 revision 0은 미발급이라고 명시하는 미확정 안내만 허용하며 확정 근거로 승격하지 않는다.

`GET /api/report/diagnostic/remediation?task=<id>&audience=internal`에서 실제 상세와 최신 저장 조치를 조회한다.
기본 shared는 기존 마스킹 정책대로 자유문장·원본 digest·복사 프롬프트를 반환하지 않는다.
복사 직전에는 `GET /api/report/diagnostic/remediation/prompt`에 task/audience/entry/record/digest를 보내,
같은 읽기 스냅샷의 현재 원본과 최신 artifact를 확인한다. 원본이 바뀌었거나 다른 버전이면 409로 복사를 거부한다.
웹 화면·복사 응답·종합 HTML/export는 같은 저장 bundle을 사용하고, stale일 때 조치/프롬프트 본문을 제외한다.
공유 사본에는 bundle을 넣지 않는다. 생성·조회·복사는 대상 접근·고객 코드 수정·push·PR·배포를 실행하지 않는다.
외부 개발 AI의 권한은 그 세션에서 고객이 별도로 허용해야 한다.

합성 검증은 Java/Python의 조건부 차이, 미확인 프레임워크, 기술 불일치 대응, 설정/코드 조치,
확정/미확정, 비밀값·악성 지시 비전파, 저장·조회·복사·export 일치, 기술 변경과 근거 변경의 stale/CAS를 구분한다.
실제 고객 저장소에 적용한 수정이나 모델 탐지 성능으로 이 시험을 해석하지 않는다.

## 7. 실행 통제와 판정

사용자가 승인 중심·조건부 자동·자동 실행 수준을 선택하는 제품 방향을 유지한다.
이 선택 기능이 이미 완성됐다는 뜻은 아니다. 모델은 검사와 다음 행동을 제안하고 프로그램이 집행한다.

- 승인·대상·범위·예산·중지 집행은 E② 책임이다. 프롬프트와 RAG는 통제·격리·감사를 대신하지 않는다.
- 현재 지원 유형의 구조화 근거 판정은 [E③ 계약](contracts/e3-oracle.md)을 따른다.
  모든 취약점 유형에 같은 강제 판정이 구현됐다고 확대하지 않는다.
- 미실행·정책상 검증 불가·결과 불명을 취약점 없음이나 성공으로 바꾸지 않는다.
- Reporter의 설명이나 검색 문서가 증거·판정·실행 승인을 새로 발급하지 않는다.

## 8. 모델 개선 실험과 공식 평가의 구분

| 비교 축 | 목적 |
|---|---|
| 기본 모델 | 이 모델 개선 실험의 기준 성능 |
| 프롬프트·도구 입력 개선 | 같은 모델에서 입력·실행 피드백·문맥 관리 변경의 효과 |
| 프롬프트 개선 + RAG | 위 조건에 참고자료 검색을 더한 효과 |

동일한 대상·초기화·허용 범위·예산·모델 가중치·양자화·문맥·출력 한도·샘플링·서빙 환경으로 설계한다.
동시성·도구 버전·warmup/cache 조건도 고정한다. 바꾸는 입력·검색 조건과 프롬프트 버전,
RAG 자료·인덱스·검색 설정 버전을 기록한다. 현재 도구가 이 기록을 자동 수집하는지는 별도 확인한다.
프롬프트 [언어 전환](engine-language-migration.md) 전후 회차는 별도 조건으로 기록하고 같은 기준선으로 묶지 않는다.

측정 항목은 실제 발견·재현 결과, 오탐·증거 부족 처리, 도구 호출 오류, 불필요한 반복·대상 요청 수,
전체 진단 시간·추론 메모리, 보고서의 근거 없는 문장·누락 전제·증거 참조 불일치다.
[개발용 연습 대상](evaluation/practice-targets.md)과 최종 평가 사례를 분리하고, 최종 대상의 풀이·정답·성공 로그는 RAG나 호출 예시에 넣지 않는다.

여기서 **기본 모델은 ARTEX baseline이 아니다.** [평가 프로토콜 §6](evaluation/evaluation-protocol.md#6-모델환경-핀)의
API 개발 측정과 GPU 로컬 공식 비교도 2026-11-06 결정으로 Qwen3.5를 쓰지만, 이 문서의 개선 실험과 평가 회차는 별개다.
개선 실험이 평가 프로파일·샘플링·GT·회차 규칙·과거 기록을 덮어쓰거나 서로 다른 모델의 수치를 한 비교표에 합치지 않는다.
API 개발 측정과 GPU 로컬 공식 비교도 기존대로 구분한다.

공식 평가에 새 모델이나 프롬프트·RAG 조건을 넣으려면 평가 담당 최민준과 별도 합의하고,
정본 프로토콜·프로파일·기록 계약을 먼저 정한다. 이번 문서만으로 공식 조건을 바꾸지 않는다.

## 9. 남은 구현·실측·합의

- 실제 로컬 서빙·도구 호출·통합 실행을 확인하고 이 모델의 지연·메모리·DAST 기준 성능을 측정한다.
- 역할별 적용 프롬프트·도구 schema와 실행 피드백의 기록·평가 경로를 확인한다.
- 지식 부족이 입증된 부분부터 RAG 자료·접근권한·검색·출처 결속을 설계·검증한다.
- 실제 스크린샷 수집·증거 연결·출력 삽입과 내부/공유 보고서 정책은 관련 담당자의 계약 리뷰를 받는다.
- 고객별 모델 출처·보안·라이선스 조건, 최종 배포 장비와 공식 평가 변경은 각각 별도 확인·합의한다.

모델 변경이나 문서 작성만으로 진단 성능·재현성·보안성·배포 준비가 검증됐다고 기록하지 않는다.
