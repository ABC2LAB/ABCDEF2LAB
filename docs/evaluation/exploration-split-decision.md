# 탐색 분리 배치(`exploration-split/v1`) 러너 결정안

상태: 결정안. §2~§6(A·B·C·D, 엔진 끝 신호, 429 기록, 목표 동등성)은 2026-11-16 사용자 결정이고, 이 문서는 그 정본과 구현 순서다. §7 회차 처리 규칙은 사용자가 정한 조건으로 쓴 평가 프로토콜 §5.1 개정 제안이며, 리뷰(이동찬)로 확정해 측정 전에 고정한다. 담당 최민준.

출발점: [개발 계획](../development-plan.md) "공식 측정 프로토콜 고정 전 필수"의 탐색 분리 배치 항목(#612), [탐색 경계 계약 §4.1](../contracts/exploration-boundary.md) 경계 원자료(#615), [보존 서명 회차](preservation-signed-runs.md), [러너](runner.md).

## 1. 정하는 것과 정하지 않는 것

- 정하는 것: 보존율 측정에서 개선 후(O)를 제품 배치(엔진·E②·탐색 경계·브라우저·MCP)로, 원본(B)을 원본 그대로 돌리면서 둘을 같은 계측기·대상·예산·모델 핀에 묶는 러너 배치와 그 근거 형식.
- 정하지 않는 것: 지표·통과선·반복 수(평가 프로토콜 §5.1, 보존 문서). 측정 전 추정값도 적지 않는다.
- 바뀌지 않는 것: 제품 동작. 평가 전용 설정(경계 평가 upstream, 근거 디렉터리)은 제품 설치·`explore-init`에 나오지 않음을 시험으로 고정한다.

## 2. 결정 A(c) — 제품 compose 그대로 + 평가 overlay

`deploy/product/compose.yaml`은 손대지 않는다. 평가 overlay는 망 IPAM·서비스 고정 주소만 바꾸고(평가 대역으로), 다음을 더한다: 계측기(본 입구·탐색 입구), 대상, 평가 fixture DNS, 경계 근거 디렉터리 마운트(경계에만), 경계 평가 upstream 설정.

| 망(제품 이름) | 제품에서 붙는 서비스 | overlay가 더 붙이는 것 |
|---|---|---|
| `control`(internal) | postgres, preparation(api·workbench는 같은 netns) | fixture DNS |
| `target`(internal) | preparation(E② 진단 송신), explore-boundary | 계측기 본 입구(대상 이름 별칭) |
| `frontend` | preparation(workbench 리슨·모델 호출), explore-boundary | 없음 |
| `explore_control`(internal) | preparation, explore-mcp | 없음 |
| `explore_browser_ingress`(internal) | explore-boundary, explore-browser | 없음 |
| `explore_direct`(internal) | preparation, explore-boundary | 없음 |
| `explore_cdp`(internal) | explore-browser, explore-mcp | 없음 |
| 평가 전용 대상 뒤쪽 망(internal) | — | 계측기 두 입구의 뒤쪽, 대상 |
| 평가 전용 탐색 입구 망(internal) | — | explore-boundary, 계측기 탐색 입구 |

- 대상은 http로 등록한다(C22). B도 `http://eval-meter:<포트>`로 대상에 닿고, 계측기가 TLS를 끝내지 않게 하려는 것이다. 제품 경계의 TLS·SPKI 고정은 그대로다.
- 경계는 평가 upstream 모드에서 승인 대상 전달을 계측기 탐색 입구로만 보낸다. 경계는 제품 배치상 `target` 망에도 있어 본 입구에 망 수준으로 닿을 수 있다. 이 경로의 오용은 경계 원자료↔탐색 입구 대조(P03)로 잡는다.
- 렌더 시험(`docker compose config` 결과): ① 모든 주소가 평가 대역 안 ② 제품 서비스의 보안 칸(user·cap·read_only·security_opt·seccomp·tmpfs·망 소속·internal)이 제품 렌더와 같음 ③ overlay가 엔진(preparation·api·workbench)·브라우저·MCP에 볼륨을 더하지 않음 ④ 근거 디렉터리는 경계 컨테이너에만.
- 대역 겹침 검사: up 전에 호스트의 기존 Docker 망 subnet과 overlay 대역이 하나라도 겹치면 시작하지 않는다. 같은 머신에 다른 스택이 제품 기본 대역(172.31.247~255.0/24)을 쓰고 있을 수 있다(2026-11-16 실제로 그랬다).

### 2.1 망 점검(여러 출발점)

현행 러너는 엔진 netns에서만 점검한다. 이 배치는 출발점마다 `docker run --network container:<출발 컨테이너>`로 점검 컨테이너를 붙이고, 출발점당 대상은 64개 이하로 둔다. 기대값이 어긋나면 회차를 시작하지 않는다(pre) 또는 무효로 한다(post).

| 출발점 | 닿아야 함 | 닿으면 안 됨 |
|---|---|---|
| preparation(엔진·E²) | 계측기 본 입구, MCP 제어 입구(`explore-mcp`의 MCP 포트, 기본 8931), 경계 직접 입구(`explore-direct:3129`, 서버 정적 fetch·직접 Bash 탐색 경로) | 계측기 탐색 입구, 대상(직접), 경계 브라우저 입구(3128)·브라우저 CDP(9222) 등 위 둘 밖의 탐색 망 주소·포트 |
| explore-boundary | 계측기 탐색 입구 | 대상(직접) |
| explore-browser | 경계 브라우저 입구 | 계측기 두 입구, 대상, 외부 |
| explore-mcp | 브라우저 CDP | 계측기 두 입구, 대상, 외부 |
| B 엔진(원본 직접 배치) | 현행 러너 기대값 그대로 | 현행 그대로 |

탐색 망의 금지 범위는 망이 아니라 주소·포트(입구) 기준으로 적는다. 제품 compose에서 preparation은 `explore_control`·`explore_direct`에 붙어 MCP와 경계 직접 입구를 쓰므로(`deploy/product/compose.yaml`, 제품 탐색 host의 `DirectFetch`), 망 단위로 막으면 정상 제품이 점검에 걸린다. 포트 값은 overlay 렌더 결과에서 읽어 기대값을 만든다(위 기본값을 코드에 박지 않음). preparation의 외부 도달(모델 호출 경로, D(b))은 제품 설계라 실패로 보지 않고 기록한다. E² 샌드박스 안 직접 Bash에서의 점검은 열린 항목이다(§9).

## 3. 결정 B(a) — 러너가 만드는 닫힌 설치 입력과 공통 지문

- 러너가 회차마다 제품 설치 입력을 만든다. `runtime_limits`·워크플로·탐색 상한 칸은 넣지 않는다(제품 기본값 그대로, `cmd/first-controlled-diagnosis/product_install_linux.go`의 기본 상한).
- 서명에 넣는 것: 제품 이미지 ID·소스 SHA, `config/policy.json`·launch·예산 파일 SHA, 제어 정책 상한 스냅숏, E² 실행 조건(`e2-runtime-conditions`).
- 쪽별로 달라도 되는 칸은 `driver_sha256`(원본 직접 구동 / 제품 API 구동 코드) 하나로 좁힌다. 모델 핀·대상 이미지·회차 시간·러너 예산·목표 문장 SHA(§6)는 공통 지문에 남는다.
- 공통 예산은 계측기 기준 전체 전달 수(본 입구 + 탐색 입구)로 양쪽을 같게 둔다. O 안쪽 E② 대상 요청 상한(제품 기본 400)이 먼저 걸리면 통제 비용으로 결과에 드러나게 한다.
- 어느 상한이 먼저 걸렸는지(`first_limit`)를 회차 결과에 남긴다. 값과 출처:

| `first_limit` | 출처 |
|---|---|
| `engine_completed` | 엔진 끝 신호(§3.1)가 다른 상한보다 먼저 옴 |
| `runner_request_budget` | 계측기 종료 사유 `request_budget` |
| `runner_time_budget` | 계측기 종료 사유 `time_budget` |
| `product_limit:<사유>` | O 제품 실행이 `budget_limited`로 닫힘(사유는 제품 마감 사유 코드 그대로) |

- 보존 sidecar는 v3로 올린다(v2 = 경계 원자료, #617). v3는 위 서명 항목, `driver_sha256`, `first_limit`, 엔진 끝 신호, 도구 면 측정 지문(§4), 모델 프로파일 스냅숏 지문(§5)을 더한다. 배치에 해당 없는 칸은 더미 값이 아니라 `null`이다.

### 3.1 엔진 끝 신호(B·O 공통)

러너는 엔진이 스스로 끝냈는지 멈췄는지 추정하지 않는다. 회차 창 동안 폴링해 첫 종료 상태와 시각을 남기고, `down` 전에 마지막 상태를 한 번 더 읽어 서명 근거에 넣는다(엔진 DB는 `down`과 함께 사라진다).

- B: 원본 작업 조회 API(`GET /api/tasks/{id}`)의 `status`(`created|running|paused|done|failed`)·`completed_at`과 Planner 판정에 해당하는 `goals_total`·`goals_met`, 그리고 `in_flight`·`llm_failover_state`. 값은 원본 그대로 옮기고 해석하지 않는다.
- O: 제품 실행 상태(`completed`·`failed`·`cancelled`·`unknown`, 결과·마감 사유 칸). 목표 수·달성 수와 같은 뜻의 칸이 제품 실행 기록에 없으면 PR 4에서 기록에 더한다(전송·판정 동작은 그대로).
- 근거: 2026-11-16 파일럿에서 B가 회차 중간부터 모델 호출 0이었는데, 러너 기록으로는 원본이 끝낸 것인지 멈춘 것인지 가를 수 없었다(§8).

### 3.2 429 건수

회차마다 B·O의 모델 호출 429 건수를 결과에 남긴다(B는 게이트웨이 행, O는 제품 호출별 기록 §5). 파일럿에서 429 비율이 계속 높으면 측정 전에 제공자 처리량 확인을 [개발 계획](../development-plan.md)의 공식 측정 전 필수 항목으로 올린다. 2026-11-16 파일럿: 1차 B 22행 중 13·O 63행 중 7, 재실행 B·O 모두 0.

## 4. 결정 C(a) — 도구 면: 버전 핀 패치와 측정

- B 빌드 = 원본 커밋 + 버전 핀 패치 하나(`@playwright/mcp@0.0.84`, `@playwright/cli@0.1.23`, `playwright@1.65.0`). 패치 SHA를 선언 차이로 서명한다.
- 프로토콜 §2 도구 동등성을 "모델이 쓸 수 있는 도구 면"으로 다시 정의한다. 도구 면에는 MCP 도구 목록·버전과, Bash에서 쓸 수 있는 CLI 목록·버전을 넣는다(B는 샌드박스 없음, O는 E² 샌드박스 안).
- MCP 버전·도구 목록은 선언이 아니라 러너가 회차 전에 측정해 지문으로 남긴다. 지금 보존 옵션의 선언 칸(`mcp_tools_sha256`·`browser_image_id`·탐색 정책 지문)은 e2-legacy 회차에서 의미 없는 값을 억지로 채워야 했다(§8).

## 5. 결정 D(b) — O의 모델 경로

- O는 제품 자체 OpenRouter 경로로 모델을 부른다(`llmpolicy`의 `openrouter.ai:443` 고정에 평가 분기를 두지 않음).
- 근거 대등성: 제품 OpenRouter 제공자가 호출마다 generation ID를 기록한다(전송은 그대로, 기록만). 러너가 게이트웨이의 generation 검증 코드로 사후 검증하고, 제품 모델 프로파일(샘플링) 스냅숏에 서명해 B 게이트웨이가 넣은 값과 대조한다.
- 같은 기록에 호출 끝 모양(정상 종료·위쪽 끊김·호출자 취소)과 429·5xx 횟수를 남긴다. §7 규칙이 B 게이트웨이 기록과 같은 기준으로 O를 보려면 필요하다.

## 6. 목표 동등성

- 2026-11-16 파일럿(e2-legacy)에서는 B·O 작업 생성 본문이 바이트까지 같았다(러너 `task_request`, `official_task_request_sha256`). 목표 분해 지시(`agent/goals.go`)는 원본 중국어를 영어로 옮긴 것뿐이다. 그래서 이번 B 멈춤의 원인은 목표 차이가 아니다.
- D(b)로 O를 제품 API로 몰면 O의 목표 문장은 러너 본문이 아니라 제품 코드(`urlDiagnosisGoal`, `cmd/first-controlled-diagnosis/url_preparation_runtime.go`)가 만든다. 이 문장은 취약점 찾기·인가 먼저·"지도 그리기는 수단"을 지시해서, 지금 B 본문("다른 사용자의 자원이나 권한 밖 기능에 접근되는지 확인한다")과 지시 수준이 다르다. 그대로 두면 보존율이 엔진 능력이 아니라 목표 문장 차이를 잰다.
- **결정(사용자 11/16):** B 작업 본문의 목표를 제품 목표 문장과 같은 글로 맞춘다(같은 대상 origin·승인 메서드로 채움). O에만 있는 E② 경계·워크플로 문장은 선언 차이로 둔다. 목표 문장 SHA는 `driver_sha256`이 아니라 공통 지문에 넣는다.
- **제품 목표 문장 변경 반영(사용자 11/16):** 제품 목표 문장에 승인 경로 목록과 "시험했다고 볼 범위" 문장이 더해진다(회차·PR 담당 세션 PR 예정). B 본문은 그 변경 뒤 문장을 따른다.
  - 맞추는 부분(B·O 같은 글): 목적 + 승인 경로 목록 + 시험했다고 볼 범위 + 보고 문장. 공통 지문에는 이 부분의 SHA를 넣는다.
  - O에만 있는 부분: E② 경계(승인 메서드·쓰기 승인 방식)·워크플로 문장. 따로 SHA를 남겨 선언 차이로 둔다.
  - 제품 쪽(#625): 공통 부분은 `urlDiagnosisCommonGoal(origin, approvedPaths, accountLabels)`(`cmd/first-controlled-diagnosis/url_preparation_runtime.go`)가 만든다. 순서는 승인 경로 문장 → 목적(인가 먼저 + 시험했다고 볼 범위) → 시험 계정 라벨 문장 → 보고 문장이다. 예시 출력은 `cmd/first-controlled-diagnosis/testdata/goal-common-example.txt`에 바이트 그대로 고정돼 있다. O 실행 기록(`first_diagnosis_run_v1`)의 `goal` 칸(`goal-digest/v1`)에 `common_sha256`(공통 부분 바이트, 앞 공백 포함)과 `product_sha256`(제품 전용 앞부분 + 끝 문장)이 남는다. 러너는 O의 공통 SHA를 이 칸에서 읽는다.
  - 승인 경로 목록은 러너가 만드는 설치·대상 승인 입력(§3)의 값이고, O 승인과 B 본문에 같은 목록을 쓴다. B에서는 글로만 들어가고 집행되지 않는다(집행 차이는 통제 효과로 잰다).
  - B 본문의 목표는 같은 공통 부분 바이트다. 러너(Python)는 Go 함수를 직접 부를 수 없으므로 렌더를 따로 두되, 두 겹으로 어긋남을 막는다.
    - 같은 testdata 파일(`goal-common-example.txt`)과 바이트를 대조하는 러너 시험. 제품 쪽은 Go 시험 `TestURLDiagnosisCommonGoalIsSharedAndPinned`(`cmd/first-controlled-diagnosis/url_goal_test.go`, #625)가 예시 입력(origin `https://owned.example:8443`, 경로 `/api/v1`·`/openapi.json`·`=/`, 라벨 `tester-a`·`tester-b`)의 Go 렌더 + 끝 줄바꿈 하나 = 파일 바이트를 고정한다. 러너 시험은 같은 입력의 Python 렌더 + 끝 줄바꿈 하나를 같은 파일과 비교한다. 그래서 Go 렌더가 바뀌면 파일 갱신이 강제되고, Python 렌더가 어긋나면 회차 SHA 대조까지 가지 않고 CI에서 잡힌다.
    - 회차마다 B 본문 공통 부분의 SHA와 O `goal.common_sha256`을 공통 지문에 넣는다. 다르면 짝으로 묶지 않는다.
  - origin 문자열: 제품 `urlGoalOrigin`은 대상 URL의 `scheme://host[:port]`를 적힌 그대로 쓴다(소문자화·기본 포트 정리 없음). 그래서 B·O가 같은 대상 origin 문자열을 써야 공통 SHA가 같다. overlay에서 두 쪽 모두 같은 대상 이름(계측기 본 입구 별칭)을 쓰고, 러너 사전검사의 `target_origin` 조건(지금 `NOT_EVAL_METER`)은 PR 4에서 그 별칭에 맞춘다.
  - 시험 계정 라벨 문장은 "호스트가 시험 계정으로 로그인해 Worker에 세션을 준다"고 말한다. 원본은 그런 준비가 없으므로, B 본문에는 B에도 같은 세션을 주는 조건(프로토콜 §2 caller 자격 통과 모드)에서만 라벨을 넣는다. 그 밖에 O에만 계정이 결속된 회차는 공통 SHA가 달라 짝으로 묶이지 않는다(의도한 거부). 공식 프로파일은 익명 준비라 두 쪽 모두 라벨이 없다.
  - 승인 경로 목록 입력(정확 일치는 `=` 접두, 렌더 때 `(exact)`)은 러너가 만드는 설치·대상 승인 입력의 값을 두 쪽에 그대로 쓴다.
  - 경로 렌더 주의: 원본 `parseTarget`(`server/server.go`)은 작업 설명+목표 글에서 첫 URL을 먼저 잡으므로, 설명에 대상 URL이 있으면 경로 이름이 대상으로 심기지는 않는다. 러너 `task_request`는 더 엄격하다. URL 밖의 도메인 꼴 글(`_TARGET_DOMAIN`)이 하나라도 있으면 `task_target_mismatch`로 거부하는데, 점이 든 경로 이름(`/openapi.json`, `/static/main.js`)이 여기에 잡힌다. 또 목표 분해기의 범위 등록(`add_task_scope`, 모델 판단)이 그런 이름을 호스트로 잘못 읽을 수 있다(B·O 공통). 렌더 방식으로 피한다: 승인 경로는 같은 origin의 절대 URL로, 점검 주소 뒤에 쓴다(회차·PR 담당 세션이 제품 쪽 렌더를 맡음).
  - **러너 가드 변경(사용자 11/16, PR 4에서 구현·시험 고정):** 지금 `task_request`는 URL이 회차 origin과 정확히 같을 때만 받아 경로 붙은 같은 origin URL도 거부한다. 그래서 URL 비교만 "같은 scheme·host·port면 경로 허용"으로 바꾼다. 가드의 목적(엔진이 볼 대상이 회차 origin 하나뿐)은 그대로다. 시험으로 고정할 것:
    1. 본문 첫 URL은 점검 주소와 정확히 같아야 한다. 원본 `parseTarget`이 첫 URL의 scheme·host·port를 대상으로 쓴다.
    2. origin 정규화: 호스트 대소문자와 기본 포트 명시 여부가 달라도 같은 origin으로 본다. 거부: userinfo(`http://eval-meter:8080@evil`), 호스트 꼬리(`http://eval-meter:8080.evil.com`), 포트만 다른 URL.
    3. 다른 origin URL과 URL 밖 도메인·IP 꼴 글은 지금처럼 거부한다.
  - 순서: 제품 문장 변경 PR이 머지된 뒤 B 본문과 official-run 고정값을 맞춘다.
- 버린 선택지: 서로 다른 목표를 선언 차이로만 남기기(비교 해석이 어려움), 제품에 평가용 목표 덮어쓰기 입력 열기(제품 노출면이 늘어남).
- 공식 작업 요청 SHA가 바뀌므로 [official-run.md](official-run.md)의 고정값을 같은 구현 PR에서 갱신한다. O의 실제 목표 문장 SHA를 러너가 얻는 경로(제품 실행 기록에 남기기를 추천)는 PR 4에서 정한다.

## 7. 회차 처리 규칙(평가 프로토콜 §5.1 개정 제안): 제공자 장애 멈춤

조건은 사용자가 정했고(11/16), 리뷰(이동찬)로 확정해 측정 전에 프로토콜 §5.1에 옮긴다. B·O에 같게 적용한다.

- **무효 조건(기계적, 셋 다):**
  1. 제공자 장애 기록: 모델 호출이 위쪽 스트림 끊김(게이트웨이 `upstream_cut_*`, 또는 제품 호출 기록의 같은 끝 모양)으로 끝났거나, 엔진의 429 다시 보내기가 소진됐다(그 요청의 마지막 시도가 429이고 엔진이 다시 보내지 않음).
  2. 그 기록이 끝난 뒤 T초 동안 그 쪽 모델 호출 0·대상 요청 0(계측기 두 입구 합).
  3. 그동안 엔진 끝 신호(§3.1)가 없다.
- **처리:** 그 회차를 무효(`provider_fault_stall`)로 하고 §5.1 무효 회차 규칙대로 다시 돈다.
- **항상 남김:** 쪽별 `provider_fault_stall` 무효 회차 수를 결과에 늘 싣는다(0이어도).
- **무효 비율 상한:** 쪽별 무효 비율이 상한을 넘으면 그 조건만 미완으로 두지 않고 측정 전체를 실패로 한다. 무효 회차를 골라 남기는 것을 막으려는 것이다.
- **T와 상한 값:** 파일럿 기록으로 정해 측정 전에 고정한다. 아직 정하지 않는다. 지금 근거는 2026-11-16 2쌍이다: 모델 호출·대상 요청 모두 없던 정상 구간의 최장 공백은 1차 B 2.0초·O 0.9초, 재실행 B 3.0초·O 0.9초. 1차 B가 멈춘 구간은 약 359초다(마지막 활동 끝 → 계측기 봉인). 파일럿 기록을 더 모아 정하고, 대상 요청 없이 긴 명령을 도는 정상 공백이 T 후보보다 길게 나온 적이 있는지도 같이 본다.
- **바꾸지 않는 것:** 원본 Planner 심장박동 기본값(600초, 하한과 같음)은 원본 설정이라 그대로 둔다. 시간 예산을 늘리는 것으로 이 규칙을 대신하지도 않는다. 원본은 Planner 오류 뒤 다음 깨움을 심장박동까지 기다려(`server/engine.go`의 Planner 루프) 어느 예산에서도 그만큼을 잃는다. 개선 후 엔진의 Planner 루프도 같다. 다만 제품 모델 경로의 일시 오류 재시도가 끊김을 먼저 흡수할 수는 있다.
- 장애에 약한 쪽이 지워지지는 않는다. 쪽별 무효 회차 수와 429 건수(§3.2)가 결과에 남는다. 이 규칙은 보존율이 엔진 능력 대신 제공자 장애를 재지 않게 하려는 것이다.

## 8. 2026-11-16 e2-legacy 파일럿에서 나온 것

VAmPI, 600초·요청 100, B·O 각 1회씩 두 번(1차, #623을 합친 재실행). 측정이 아니라 러너 경로 확인이다. 수치는 건수만 적는다.

1. **시작 상태 지문 버그** — 보존 sidecar의 `initial_state_sha256`이 회차 신원(run_id·컨테이너 ID)이 든 관측 봉투 hash여서, 관측 원문이 같은 B·O도 서명 재계산에서 `preservation_conditions_mismatch`로 멈췄다. 대상 상태 지문으로 고침(#623). 그 전 서명 sidecar는 다시 돌린다.
2. **B 멈춤** — B 모델 호출 행 22개 중 429가 13개였다(SDK가 다시 보내 성공 생성 9개, O는 63개 중 7개). 한 대화로 이어진 Planner 첫 라운드의 마지막 호출이 위쪽 끊김(`upstream_cut_before_done`)으로 끝났고, 그 뒤 seal까지 모델 호출 0·대상 요청 0이었다. 의도를 아직 만들기 전이라 Worker 종료 알림이 없었고, 다음 심장박동은 회차가 끝난 뒤였다. 엔진 task 상태는 러너가 모으지 않고 엔진 DB도 회차 끝에 지워져, 게이트웨이 행과 원본 코드로만 갈랐다 → §3.1, §3.2, §7.
3. **선언 옵션** — e2-legacy에 해당 없는 MCP 도구·브라우저 이미지·탐색 정책 지문을 억지로 채웠다 → §4, v3의 `null`.
4. **도구 트리** — B·O를 같은 세션에서 연달아 빌드해 도구 트리가 같았다. MCP 0.0.84·cli 0.1.23·playwright 1.65.0이 B에도 들어간 것은 빌드 캐시 덕이지 핀이 아니다 → §4 버전 핀 패치.
5. **비대화형 실행** — 러너가 관리자 비밀번호를 getpass로만 받아 터미널을 떼고 표준 입력으로 넣어야 했다 → `--admin-password-file`(#623).
6. **모델 호출 비용** — OpenRouter 키 사용량 증가는 1차 B·O 합쳐 $0.05 안쪽, 재실행 $0.07 안쪽이었다(키는 팀 공용이라 다른 사용이 섞였을 수 있음).
7. **재실행(#623 합침)** — 서명 재계산(`preservation.py` R-P)이 종료 코드 0으로 서명 회차 2개를 검증했다(요약 v8, 경계 `NOT_RUN`, 판정 `NOT_RUN`은 e2-legacy라 원래 값). B는 멈추지 않았다: 위쪽 끊김 0·429 0, 계측기 봉인(140.1초) 직전까지 대상 요청이 이어졌고(마지막 끝 139.2초) 봉인 전 최장 공백 3.0초였다. 봉인 뒤에도 B 엔진은 모델 호출 66번·대상 요청 12번을 더 시도했고 게이트웨이·계측기가 전부 거부했다. 엔진이 살아 있던 근거지만 끝 신호를 대신하지는 않는다(스스로 끝냈을지·목표 달성 판정은 이 기록으로 알 수 없다).
8. **먼저 걸린 상한** — 1차 O와 재실행 B·O는 러너 요청 예산 100에 1~2분 만에 닿아 끝났다(재실행 B 140초·O 81초). 1차 B만 시간 예산(600초)으로 끝났는데, 그것도 엔진이 멈춘 뒤였다. 지금 예산에서는 회차가 엔진 진행이 아니라 러너 요청 예산으로 끝난다 → §10.
