# 선택 후보 검증: 소유 합성 제품 수용시험

이 시험은 `selected_candidate_product_acceptance.py`가 실제 제품 관리 API를 호출한다. 제품 설치, PostgreSQL 16, 보호 준비 서비스, E② Host, 격리 Runner, 로컬 합성 모델, 소유 HTTPS 대상 및 DNS 증명을 사용한다. OpenRouter와 외부 대상에 송신하지 않는다. 합성 모델의 판정은 실제 LLM 품질 측정이 아니다.

## 격리와 재실행

- 전용 worktree와 Compose 프로젝트를 사용한다. 다른 세션의 컨테이너, DB, 네트워크 및 볼륨은 중지하거나 삭제하지 않는다.
- 기본 Compose의 `172.31.252.0/24`와 `172.31.253.0/24`가 다른 프로젝트에서 사용 중이면 `scripts/eval/prepare_selected_owned_compose.py <시나리오>`로 같은 디렉터리에 `10.93.*` 전용 Compose 사본을 만든다. 지원 시나리오는 스크립트의 `MODES`를 따른다. 이 사본은 커밋하지 않는다. 해당 대역도 점유됐다면 충돌하지 않는 새 전용 대역을 설계·검증한 후 실행한다.
- `scripts/eval/create_selected_owned_install.py <새 0700 디렉터리> 10.93`으로 비공개 설치 입력을 만든다. S03·S04는 마지막 인자 `allow-login-post`를 추가한다. 이 시험에서만 합성 대상의 로그인 POST를 승인한다. S03·S04 회차는 워크플로 자동 모드(`ai_auto_v1`)로 돌고 시작 주소는 합성 대상의 공개 로그인 화면(`/login`)이다(상품 경로는 세션 없이 401이라 크롤 시작이 될 수 없다). 진단 Worker의 합성 모델이 지침의 등록 계정 줄로 대상 로그인 API에 직접 로그인한다(모델 로그인 계약 §2-2: 진단 단계 로그인은 쓰기 승인 범위를 따른다). 프로그램은 세션을 채우지 않는다. 생성된 자격값과 DNS 제어 토큰은 출력·커밋하지 않는다.
- 제품과 fixture 이미지는 같은 **전체 커밋 SHA**를 `VCS_REF`로 빌드한다. 수용 스크립트는 두 이미지의 revision label이 `--head`와 일치하지 않으면 시작하지 않는다. 기존 S01~S09 시나리오는 각자 새 설치·DB 볼륨을 쓴다. `99536a7e`부터 fixture의 목표 증명은 현재 Planner `graph_overview`의 열린 목표와 저장 후보 fact를 산출한 의도·yield 결속을 사용하며, 빈 DB의 고정 노드 번호에 의존하지 않는다. 같은 설치의 연속 진단 제품 재시험은 아래에 별도 기록한다.
- 생성된 Compose 사본 네 개를 순서대로 `docker compose -p pr950-selected93 -f <base> -f <acceptance> -f <selected> -f <scenario>`에 준다. `PRODUCT_SOURCE_SHA`, `PRODUCT_TAG`, `PRODUCT_INSTALL_FILE`, `PRODUCT_POSTGRES_PASSWORD_FILE`, loopback 제품·fixture 포트를 지정해 `up -d --no-build --wait`한다. `fixture-init`의 `/target-tls/control-token`을 전용 0600 파일로 복사한 뒤 `python3 -I scripts/eval/selected_candidate_product_acceptance.py <install.json> <dns-token> --head <SHA> --scenario <ID>`를 실행한다. 끝나면 **자신의 프로젝트만** `down -v`한다.

수용 스크립트는 원본 후보 1건, 정상 종료와 감사 완료, 승인 전 대상 송신 0건, 승인 후 송신 수, 범위 밖 송신 0건, 최신 보고서 후보 상태, 내부용·공유용 HTML/DOCX 200 및 합성 자격값 비노출을 검사한다. S03은 모델 로그인 1건(회차 `account_auth`가 `authenticated`)·후속 로그인 1건과 인증 읽기를 별도로 세고, 모델의 세션 없는 대조 읽기 1건은 인증 읽기에서 뺀다. S04는 계정 변경 뒤 후속 송신과 결정적 판정이 없는지 확인한다. S05는 정확한 Query·헤더 정상 대조 요청을 센다. S06은 모델의 POST 제안과 Body 입력의 계획 API 거부를 확인한다. S07은 바뀐 계획 digest의 승인 거절과 사용자의 거부, S07B는 소유 설치의 `max_runs=1`에서 후보 예약 실패, S07P는 계획 만료, S07R은 첫 후속 GET을 지연시킨 사이 대상 승인을 철회하고 남은 송신을 차단하는지 확인한다. S08은 모델의 존재하지 않는 출처 인용이 최종 판정으로 저장되지 않는지 확인한다. S09C·S09R·S09M은 각각 실행 중 취소, 대상 응답 중 준비 서비스 강제 종료·재시작, 최종 모델 응답 중 준비 서비스 강제 종료·재시작을 검사한다. 지연·종료 제어는 소유 fixture에만 적용한다.

S09M은 재시작 후 **새** 선택 요청의 정상 완료를 확인한다. S09R은 전송 중 결과가 불명인 Host 저널의 복구를 거부하는 현재 E② 계약을 확인하고, 새 요청도 송신·확정 없이 차단되는지 검사한다. 이 상태에서 후속 진단이 정상 시작할 수 있다고 주장하지 않는다. 안전한 운영자 복구 절차는 별도 계약이 필요하다. 끊긴 기존 요청 자체는 재전송하지 않는다.

### 같은 설치 연속 회차 재시험 (2026-11-26)

HEAD `99536a7e`의 제품·fixture 이미지를 같은 SHA로 빌드하고, 독립 Compose 프로젝트 `pr950-repeat1126`의 동일 DB·Host 볼륨에서 S02를 두 번 연속 실행했다. 두 번째는 `--reuse-target`으로 기존 승인 대상을 사용했다. **두 회차 모두 PASS**: 일반 진단 `audit_complete=true`, 후보 1건, 승인 전 추가 송신 0건, 승인 후 GET 1건, 범위 밖 송신 0건, 내부·공유 HTML/DOCX 4종 출력, `model_supported`. 로컬 합성 모델만 사용했고 유료 모델 호출 0건이다. 첫 시도 HEAD `7efdf85f`는 탐색 의도가 범위 밖 시도 때문에 `blocked`인 상황에서도 후보 사실을 저장했으나 fixture가 `done` 의도만 선택해 진단 완료를 놓쳤다. `99536a7e`는 실제 저장 후보 fact의 의도·yield 결속을 요구하며 `blocked`를 허용한다. 실패한 첫 시도는 별도 소유 볼륨에서 종료·정리한 뒤 빈 시험 볼륨으로 재시험했다. 이 결과는 복구를 거친 R03과 별개의 연속 회차 시험이다.
