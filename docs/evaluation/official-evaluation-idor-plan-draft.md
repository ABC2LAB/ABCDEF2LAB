# ABC2LAB 공식 평가와 IDOR 통합 검증 계획 초안

작성 기준일은 2026년 11월 4일이며, 발표 목표일은 12월 18일이다. 원문 검토 기준은 dev `a6db21c28d791dd0b878173669f261a760065350`, 저장소 게시 준비 기준은 dev `f21d73fe89315ae69bd70051fb2d043d363ea1d0`이다. 본문의 고정 소스 링크는 원문 검토 기준을 가리키며, 아래 PR 상태는 게시 준비 시 다시 확인했다.

공식 비교는 동일한 초기 입력과 실행 조건에서 원본 ARTEX와 ABC2LAB의 차이를 측정한다. IDOR 기능 시연은 준비한 시험 계정과 자원으로 증거 기반 판정 경로를 확인한다. **E② 네트워크 경계 집행은 통제가 강화된 펜테스팅 도구의 필수 범위**이며, 지원 송신은 권한 검사·감사를 통과하고 그 밖의 경로는 차단돼야 한다. 실제 배치 검증은 host 권한, 키, 감사, 실행 수명이 실제 환경에서 유지되는지 확인한다. 각 결과는 목적과 완료 기준을 구분해 보고한다.

**상태는 팀 검토용 보강 초안이다.** 2026년 11월 4일 이동찬의 요청으로 E② 네트워크 경계 집행을 12월 18일 필수 범위에 반영했다. 이어 전체 실험 비용은 견적 비교 후 상한 결정, 발표용 최종 비교는 GPU에서 원본·개선본 반복 측정, E②는 HTTP·HTTPS 요청 검사까지 필수 목표로 채택했다. 원문에 기록된 민준의 IDOR 제시 방식 결정과 저장소의 현행 평가 규칙은 유지한다. 실제 금액·사양·배치·담당 일정은 확인 후 결정표에 기록한다. 이 선택은 팀 전체의 설계 승인이나 실제 구현·권한 발급 완료를 뜻하지 않는다.

평가 규칙의 정본은 [평가 프로토콜](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/evaluation/evaluation-protocol.md), 개발 우선순위와 역할의 정본은 [개발 계획](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/development-plan.md)이다. 초안과 현행 계약이 다르면 계약 변경을 검토한 뒤 적용한다.

| 구분 | 입력과 실행 | 주요 산출물 | 주장 범위 |

공식 비교는 여러 변경을 합친 엔진 전체 비교다. 별도 분리 실험 없이 결과를 E②나 E③ 하나의 효과로 귀속하지 않는다.

현재 공식 프로파일은 계정과 자원을 제공하지 않는 `anonymous` 준비 조건이다. 이는 엔진이 실행 중 스스로 회원가입·로그인을 시도하지 못하게 한다는 뜻은 아니다. 원본이 스스로 IDOR 챌린지를 해결하면 현행 규칙에 따라 해결 수에 포함한다. 수동 A/B fixture를 사용하는 기능 시연 결과는 이 익명 비교표에 합산하지 않는다.

Juice Shop은 이미 개발·스모크에 사용한 **고정 평가 대상**이다. 처음 보는 holdout으로 표현하지 않는다. 임의 앱에 대한 일반화는 추후 독립적인 여러 앱에서 확인한다. [공식 프로파일](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/evaluation/profiles/official-35b.json)

## 결정 상태와 구현 기준

### 유지하는 기준

원문에는 11월 4일 민준의 담당 결정으로, IDOR을 원본 대비 탐지 증가율 대신 구조화된 검증 기능의 추가로 제시한다고 기록돼 있다. 시연에서는 소유·기대 권한, 검증된 계정, 실제 접근 증거, 보수적인 판정, 통제와 감사를 보여준다. “원본은 IDOR을 못 푼다” 또는 “오탐이 더 많다”는 주장은 이 결정에 포함하지 않는다.

공식 비교의 반복·예산·귀속·분류 규칙은 현행 평가 프로토콜을 따른다. 기능 범위와 담당 일정은 별도 확인 대상이다.

## 공식 비교의 입력과 환경 고정

### 고정할 입력

baseline과 개선본에 같은 작업 문구와 대상 범위, 준비 조건을 준다. 작업 요청 본문 해시와 프로파일 지문을 회차 기록에 결속한다. 한쪽에만 계정·소유 정보·정답 단서를 추가하면 별도 실험 조건으로 분리한다.

GT는 평가·채점에만 사용한다. 챌린지 목록과 해결 여부를 planner, 후보 생성기, KG의 소유·기대 권한 또는 fixture 자원 선택의 근거로 공급하지 않는다. 정답을 보고 수정한 뒤 같은 버전을 최초 공식 결과처럼 제시하지 않는다.

원본과 개선본의 정확한 commit SHA, 이미지 digest, 모델 설정, 분류 매핑과 수집기 버전을 고정한다. baseline에 평가 관측용 변경이 필요하면 변경 내용과 행동에 미치는 영향을 명시한다.

### 대상과 머신

현행 대상은 Juice Shop v15.0.0이며 이미지 digest는 공식 프로파일을 따른다. 회차마다 대상과 엔진 상태를 새로 준비한다. 준비 작업이 만든 사전 해결 상태는 pre snapshot에 남긴다.

같은 백엔드 안의 원본·개선본은 같은 평가 머신과 동등한 자원 제한에서 실행한다. CPU·코어·메모리·디스크, 커널·Docker·런타임 버전, 네트워크 정책, 시간 기준, 동시 작업 여부를 기록한다. 같은 물리 머신이라는 조건만으로 동등성을 판단하지 않는다.

전용 Linux 인스턴스를 우선 검토하되 실제 제공자·사양·비용·사용 시간은 결정표에서 정한다. WSL2를 채택하면 native dockerd와 점검 도구의 요구를 확인한다. 특정 개발 머신의 메모리 사용 관찰을 보편적인 최소 사양으로 사용하지 않는다.

API 기준 모델 ID는 `qwen/qwen3.6-35b-a3b`, 제공자는 `deepinfra/fp8`, provider fallback은 비활성이다. 샘플링 기준은 다음과 같다.

| top_p | 0.95 |
| top_k | 20 |
| min_p | 0.0 |

설정 파일의 선언과 실제 적용을 대조한다. 제공자 metadata는 세션마다 재조회하고, 선택 endpoint와 파라미터 지원이 고정 근거와 다르면 시작하지 않는다. seed를 지정해도 실행 결과의 결정성을 보장한다고 표현하지 않는다.

검토 기준 dev에는 공식 샘플링 주입이 아직 반영되지 않았다. #174의 변경을 채택하고 실제 적용 기록을 확인하기 전의 회차는 해당 공식 샘플링 조건을 갖춘 것으로 사용하지 않는다. [모델·환경 기준](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/evaluation/evaluation-protocol.md#6-모델환경-핀)

## 반복 예산과 회차 유효성

### 시범 회차

baseline과 개선본을 시간 1,200초·대상 전달 요청 400건으로 각 1회 실행한다. 시범 회차는 공식 점수에 포함하지 않는다. 종료 사유, 전달 건수와 초과분, 소요 시간과 비용을 보고 예산을 한 번만 조정할 수 있다. 양쪽에 동일한 변경을 적용하고 근거를 기록한다. 해결한 GT 항목을 보고 유리한 예산을 고르지 않는다.

시범 후 공식 반복 수, 예산, 작업 문구와 프로파일을 고정하고 태그를 남긴다. 다른 조건 변경이 필요하면 기존 공식 묶음과 구분되는 새 실험 버전으로 계획한다.

### 공식 반복

조건당 유효 회차는 N ≥ 3이다. N=5 적용 여부는 시범 비용을 보고 공식 시작 전에 정한다. 실행 순서는 짝마다 선행 조건을 바꾸며, N=3이면 `B O O B B O`를 사용한다. 각 실행의 reset은 별도로 수행한다.

각 반복의 원자료와 평균·표본 표준편차를 함께 보고한다. 완료한 반복 수와 시도 수, 범위도 제시한다. 적은 반복으로 통계적 동등성이나 일반적인 우월성을 확정하지 않는다.

### 실패와 무효 처리

기술적 무효 회차는 삭제하지 않고 사유 코드와 함께 보존한다. 조건별 시도 상한은 2N이다. 상한을 넘으면 해당 조건을 미완으로 보고하고 원인을 수정한 뒤 다음 실험 버전을 계획한다. 양쪽 무효율과 사유별 수를 각각 보고한다.

엔진의 정상적인 실패·무발견·시간 또는 요청 예산 도달을 결과가 불리하다는 이유로 무효 처리하지 않는다. 수집·격리·설정 위반 등 기술적 무효와 제품의 실행 결과를 사전에 구분한다. timeout은 발생 단계와 기존 러너 분류에 따라 남긴다.

재실행 규칙과 순서는 현행 프로토콜·세션 도구를 따른다. 실패한 쓰기의 결과가 불명인 상황에 별도 RunRef를 만들어 자동 재송신하는 방식은 추가하지 않는다. [사전 고정 규칙](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/evaluation/evaluation-protocol.md#51-공식-회차-사전-고정-규칙)

## 지표와 결과 해석

### 첫 공식 비교

주 지표는 회차당 **엔진에 귀속된 해결 수**다. 코어 인가 GT 9개와 BAC category 전체 10개 결과를 모두 제시한다. 사전 해결 항목을 한쪽 분모에서만 제거하지 않는다.

해결 귀속은 run-record v1.1의 `isolated_window` 규칙을 따른다. pre 이후 새 해결이라는 사실 외에, 구간 전체의 격리·관측·준비 작업 중지·요청 종료 근거가 있어야 엔진 성과로 귀속한다. 유효한 서명이 실제 관측의 진실성을 대신하지는 않는다.

보조 지표는 실제 대상 전달 HTTP 요청 수, 별도의 차단 시도 수, 종료 사유, 예산 초과분, 구간 소요 시간과 조건별 무효율이다. LLM 호출과 전송 전 차단은 대상 전달 요청 수에 합산하지 않는다.

양쪽이 요청 상한에 도달했다면 같은 요청 수를 효율 개선의 근거로 쓰지 않는다. 시간 지표는 시작·종료 기준과 준비·drain 포함 여부를 명시한다. 확정이 없었던 회차에 시간 상한을 대입해 “확정까지 시간”의 성공 표본으로 만들지 않는다.

### 판정 품질

판정 레코드가 미수집이면 확정·오탐·미탐을 임의 계산하지 않는다. 해당 판정 칸은 현행 계약에 따라 판단불가로 두고, 해결 귀속과 실행 지표는 별도로 보고한다. findings 수는 원자료로 남기되 품질 지표로 사용하지 않는다.

현행 챌린지별 확정·오탐·미탐·판단불가 집계는 그 판정표의 의미로 보고한다. 일반적인 오탐률이나 precision으로 확장하려면 별도 판정 단위, 중복 제거, 음성 사례와 분모를 먼저 정의한다. 미검사, 증거 부족, 정상 차단과 범위 밖 finding을 동일한 음성으로 합치지 않는다.

### 발표 표

공식 결과에는 다음을 함께 싣는다.

- 조건별 시도 수, 유효 수, 무효 사유와 미완 여부.

- 코어 GT 9개와 BAC 전체 10개의 반복별 해결 귀속 결과.

- 평균·표본 표준편차, 요청 수와 종료 사유, 비용과 초과분.

- 판정 자료의 수집 범위와 재채점 가능 여부.

- 모델·백엔드·머신·소스 버전과 주장 범위.

- 원본 대비 개선이 없거나 나빠진 결과, 제한된 표본으로 남는 불확실성.

## 회차 자료 보존과 재채점

회차를 재실행하지 않고 판정 지표를 재채점하려면 필요한 원자료가 종료 전에 보존돼야 한다. 정리 전에 다음 자료의 존재·문맥·무결성을 대조한다.

| 자료 | 보존 목적 |
| --- | --- |
| 서명된 run record와 설정·소스 지문 | 회차, 모델, 실행·reset 문맥과 고정 조건 확인 |
| pre/post snapshot과 격리 근거 | 새 해결 집합과 엔진 귀속 확인 |
| meter·LLM gateway 요약 | 실제 요청 수, 종료·drain, 모델 제공 조건 확인 |
| E② 정책 지문·집행 요약·송신 및 우회 시험 근거 | 허용·차단·집행 실패와 회수·장애 시 동작 대조 |
| findings와 분류 매핑 해시 | 보고된 finding과 해석 규칙 재현 |
| 수집 가능한 판정 export와 실제 traffic 증거 참조 | 구조화 판정의 근거 대조 |
| coverage와 수집 상태·누락 사유 | 미검사와 판단불가·미탐 구분 |

현재 러너의 `findings.json` 수집만으로 위 판정 export와 evidence·coverage가 모두 보존된다고 가정하지 않는다. 개선본의 판정 페이지 export와 baseline 어댑터 출력의 보존 경로를 확인하고, 없는 자료는 미수집으로 기록한다. 엔진 DB를 내린 뒤 사라진 원자료를 나중에 복원할 수 있다고 약속하지 않는다.

어댑터와 매핑 규칙은 재채점 결과를 보기 전에 고정한다. 기존 서명 형식이 새 자료를 포함하지 못하면 임의 필드를 추가하거나 기존 서명을 바꿔 쓰지 않는다. 현행 저장·검증 계약 안에서 근거를 보존하고 필요한 계약 변경은 별도로 검토한다.

자료는 레포 밖의 보호된 저장소에 보관한다. 비밀번호·쿠키·토큰·실키·원문 journal·DB dump는 커밋하거나 발표 자료로 공유하지 않는다. 검증 가능한 참조와 digest, 비민감 요약을 사용한다.

현행 HMAC 서명키는 검증과 발행에 모두 쓰인다. 따라서 검증을 위해 키를 복사하는 행위도 기록 발행 권한의 이전이다. 키는 엔진·LLM과 분리된 신뢰 러너 경계에서 관리하고 채점도 신뢰 환경에서 수행한다. 보존 기간과 접근 담당자는 실행 전에 정한다. [현재 findings 수집](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/scripts/eval/runner_engine.py#L191), [서명 신뢰 경계](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/evaluation/run-record.md)

## IDOR 최소 통합 경로

### 시연의 범위

첫 시연은 LLM 없이 수동으로 준비한 두 계정 A/B와 하나 이상의 등록 자원으로 수행한다. 목표는 수평 읽기 IDOR 한 사례가 조회·판정·감사·저장·화면 조회까지 일관되게 연결되는지 확인하는 것이다.

URL, 필드, identity 확인 방식, 토큰·응답 형식은 설정과 fixture로 받는다. Juice Shop 전용 값을 production 코드에 하드코딩하지 않는다. 시험 자원은 정상 사용 과정에서 확인한 A 소유의 비민감 자료와 표식을 사용하며, 평가 GT에서 역으로 고르지 않는다.

B의 교차 시험 요청 자체는 시험 범위 안에서 승인돼야 하고, 애플리케이션의 기대 정책은 B에게 해당 자원 조회를 금지해야 한다. 이 **시험 송신 승인**과 **대상 앱의 기대 접근 권한**을 구분한다.

### 실제 입력

A/B의 현재 검증된 신원, 계정별로 분리된 유효 세션, 자원의 소유 근거, 기대 차단 정책, 공유·위임 해소 상태, 표식과 응답 규칙을 확보한다. 인증된 producer와 보호 참조·유효기간을 기록하고, 참조 문자열 일치만으로 출처를 인증하지 않는다.

세션·권한·KG·fixture와 task, intent, run, reset generation, instance, model 문맥을 대조한다. 평가용 실행과 비평가 통합 진단의 문맥을 임의로 바꾸지 않는다.

### 실행 순서

1. 운영자가 승인된 fixture 준비를 마치고 A의 소유·표식과 A/B 신원을 확인한다.

2. 실제 task와 동결된 E② 설정, KG와 Source·저장 공급부를 결속한다.

3. 전송 gate를 통과한 A의 정상 조회와 B의 교차 조회를 수행한다.

4. 같은 자원·응답 의미·표식·반사 및 오류 화면 제외 조건을 비교한다.

5. 관찰 시점의 유효한 기대 권한과 신원, 자료 증거로 판정한다.

6. 필수 감사 마감과 checkpoint·증거 결속을 확인하고 최종 저장한다.

7. 저장된 결과와 실행 증거를 대조해 화면에 표시한다.

표식을 만드는 상태 변경은 읽기 검증 경로에서 수행하지 않는다. 승인된 준비 단계로 분리한다. 실제 producer가 없거나 증거가 불충분하면 진행을 거부하거나 정해진 판단불가 사유를 남긴다. [첫 IDOR 통합 계약](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/contracts/first-idor-integration.md), [실제 입력 계약](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/contracts/first-idor-real-input-adapter.md)

## IDOR 수용시험과 지도 표시

| 시험 사례 | 수용 기준 |
| --- | --- |
| 기대 차단인 B에게 A의 정상 자료가 반환됨 | 검증된 A/B, 유효 정책, 같은 자원과 비민감 표식, 실제 전송 증거를 모두 확인한 경우만 확정 |
| 대상이 B의 접근을 정상 차단함 | 취약점으로 확정하지 않고 대상 응답의 의미를 확인 |
| B에게 명시적으로 공유된 자료 | 정상 허용과 취약점을 구분 |
| 세션 만료·계정 불일치 | 정상 완료나 접근 불가로 포장하지 않고 신원·만료 사유를 표시 |
| 공유·위임·소유·기대 정책 불명 | 판단불가 사유를 보존 |
| HTTP 200 오류·로그인 화면·ID 반사·공통 템플릿 | 상태 코드나 문자열 유사성만으로 확정하지 않음 |
| E②에서 전송 전 차단 | 대상이 거부한 요청과 구분하며 실제 검사 커버리지로 세지 않음 |
| Source·감사·저장 실패 | 실패 단계와 결과를 보존하고 UI 성공으로 표시하지 않음 |
| commit 성공 후 ACK 유실 등 결과 불명 | 취소를 rollback으로 기록하지 않고 자동 재송신하지 않음 |
| 실행·reset·revision 문맥 불일치 | 다른 회차 증거를 합치지 않고 거부 |

지도에는 기대 권한과 관측 결과를 함께 표시한다. 최소 상태는 정상 허용, 정상 차단, 취약 확정, 판단불가, 미검사다. 전송 전 차단·실행 오류·저장 결과 불명은 이유를 추가로 표시한다. 코어 판정 enum과 화면 상태의 대응은 기존 API 계약에 맞춘다.

계정×자원별로 마지막 관찰 시각, 실행·reset 문맥, 정책 출처와 상태, 근거 참조를 연결한다. 이전 reset의 관찰이나 추론 정책을 현재 확정 사실처럼 표시하지 않는다. 실제 데이터 API의 필드·페이지 처리·상태 매핑을 확인하기 전에는 UI 연결을 단순한 데이터 소스 교체로 산정하지 않는다.

익명으로 A의 자료를 조회하는 검증은 별도 후속 후보로 둔다. 익명 요청의 신원·정책 의미와 현재 검증기의 수용 계약을 먼저 확인한다. 현재 A/B 경로와 같은 수준으로 지원된다고 표현하지 않는다.

원본과의 구조적 차이는 정확한 baseline SHA의 코드로 설명한다. 실제 오탐·미탐이 더 많다는 주장은 별도의 실측 근거를 요구한다. “원본 LLM은 보통 한 계정으로 ID만 바꾼다”는 일반화는 제거한다. [E②의 실제 검증 경로](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/transmit/verifier.go), [E③의 현재 판정 코드](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/oracle/oracle.go)

## Host 권한과 실행 수명

실제 통합 진단은 보호 root와 복원 연속성, 현재 읽기 권한, 키 mapping, 정확한 checkpoint scope·epoch·sealed head, 실제 자식 실행 종료 근거를 공급해야 한다. 항상 성공하는 callback, keyfile 존재, MAC 일치 또는 동일 참조 문자열로 권위를 만들어 채우지 않는다.

RootAnchor는 장기 handle과 검증된 배치에 결속한다. 새 경로를 열었다는 사실만으로 복원 연속성을 인정하지 않는다. 작업 정지는 inflight 수 외에 planner·예약 worker·chat·자식 실행의 추적 범위와 종료 handle로 확인한다.

새 journal admission의 active 키 검사와 과거 journal 검증용 키 소비를 구분한다. checkpoint는 현재 권위로 읽은 정확한 문맥을 사용한다. 감사 게시자의 CloseWitness를 실제 transmitter와 모든 자식의 drain 전체를 대신하는 증명으로 해석하지 않는다.

읽기 권한은 fresh Source, Prepare, 최종 DB save가 끝나는 동안 유지돼야 한다. 실제 provider가 권한 수명과 회수 의미를 보장하고, 권위 상실·취소가 진행 중 연산에 전달돼야 한다. 같은 context 전달이나 CheckRoot 재검사만으로 지속적인 권한 보장을 주장하지 않는다.

성공·각 단계 실패·취소에서 자원 해제 순서를 확인한다. SQL·collector·runtime·Publisher 잠금을 잡은 채 외부 권한 조회나 프로세스 종료·drain을 기다리지 않는다. 이미 commit한 결과와 불명 쓰기를 취소로 되돌렸다고 기록하지 않는다.

이동찬의 공급·연결 작업과 팀원의 입력·KG 산출물을 최종 bootstrap에서 결합한다. 실제 계정·UID·DB role·GRANT·키·epoch와 운영 서비스 활성화는 선택한 배치의 승인 절차에 따른다. 실제 환경의 권위 상실·회수·종료 시험을 통과한 범위만 배치 검증 완료로 표시한다. [실제 공급 주체 대장](https://github.com/ABC2LAB/ABCDEF2LAB/blob/a6db21c28d791dd0b878173669f261a760065350/docs/contracts/first-idor-host-inputs.md)

## API와 GPU 측정 계획

### 개발과 최종 측정

API는 개발·탐색과 실행 절차 점검에 사용한다. **12월 18일 발표용 최종 정량 비교는 우리가 관리하는 GPU 환경에서 원본·개선본을 같은 조건으로 반복 측정하는 것을 필수로 한다.** GPU에서 실행만 시연하고 API 수치를 로컬 최종 성능으로 대체하지 않는다. API 결과는 해당 백엔드의 보조 결과로 구분해 보고한다.

채택한 흐름은 API에서 개발·시범을 진행하고, 엔진 버전을 고정한 뒤 GPU에서 원본·개선본을 모두 최종 측정하는 것이다. 초기 GPU 점검은 모델 적재, 도구 호출, sampling·context·동시성 적용과 자원 한계 확인에 사용한다. GPU 공식 비교는 현행 반복·순서·예산·무효 규칙을 그대로 적용한다.

여기서 로컬 모델 실측은 우리가 관리하는 GPU 클라우드 인스턴스 안에 모델 서버를 두고 외부 모델 API를 사용하지 않는 실행을 포함한다. 이 결과를 모든 온프레미스 하드웨어의 성능으로 일반화하지 않는다. 완전 로컬 모드의 외부 연결 차단은 별도 수용시험으로 확인한다. GPU 회차는 local backend·실제 모델 endpoint·checkpoint와 tokenizer revision·sampling·context·자원 제한을 별도 프로파일로 고정한다. 현재 API용 프로파일을 그대로 GPU 프로파일이라고 부르지 않으며, 공통 작업·GT·예산·귀속 규칙은 유지한다. 필요한 도구·프로파일 변경은 평가 계약의 담당 검토 후 적용한다.

원본/API, 개선본/API, 원본/GPU, 개선본/GPU의 네 조건을 비교하면 백엔드마다 원본 대비 차이를 계산한다. 원본/API와 개선본/GPU를 직접 비교해 엔진 개선 효과로 제시하지 않는다.

### 비교 조건과 유사성

동일 모델 ID와 FP8 표기만으로 동등성을 가정하지 않는다. checkpoint와 tokenizer revision, chat template, thinking·tool parser, context·출력 제한, 런타임 버전, 실제 샘플링, 동시성, cache·warmup 정책을 기록한다. API에서 확인할 수 없는 항목은 비교 한계로 남긴다.

API↔GPU 동등성을 보기 위한 네 조건 각 3회 정도의 비교는 실행 가능성과 변동을 보는 시범으로 취급한다. 같은 백엔드 안의 원본·개선본 공식 비교는 현행 N ≥ 3 규칙을 따르되, 그것만으로 통계적 동등성을 주장하지 않는다. API↔GPU 동등성을 주장하려면 허용 가능한 차이, 지표, 반복·분석 계획을 결과 전에 정의한다. 평균이 비슷하거나 개선 방향이 같다는 이유만으로 동등성을 확정하지 않는다. 동등성 판단이 없더라도 백엔드별 결과를 독립적으로 보고할 수 있다.

현행 local gateway는 요청 본문을 그대로 전달하는 경로다. GPU 회차에서도 sampling의 실제 적용을 검증해야 하며, API 전용 주입만으로 완료로 보지 않는다. 필요한 도구 수정의 작업량은 착수 조사 후 정한다.

### GPU 사양과 비용

VRAM을 고정된 보편적 최솟값으로 단정하지 않는다. 실제 checkpoint·정밀도, 최대 context, KV cache, 동시성에서 작은 시험부터 시작해 메모리와 timeout을 확인한다. 선택한 제한은 양쪽에 동일하게 적용하고 OOM·실패도 보존한다.

**전체 실험 비용은 견적을 비교한 뒤 상한을 결정한다.** CPU 평가 서버, GPU 서버, 모델 API, 저장공간·트래픽을 합산하고 모델 적재·시범·공식 반복·최대 재시도·정리·보관 시간을 포함한다. 보유 크레딧은 유효기간·적용 범위와 실제 과금 조건을 확인해 별도로 기록한다. 현재 확정된 금액은 없으며, 제공자·GPU 종류·개수·사양·지역·사용 시간과 총상한을 기록한 뒤 유료 자원을 예약한다.

견적은 후보별 시간당 가격, 필요한 사용 시간, CPU·API·저장·트래픽 비용, 크레딧 적용 후 금액, 중지 후 남는 비용을 같은 표로 비교한다. 작은 시범의 예상 비용과 전체 상한을 구분하고, 비용 확인·중지 담당자와 종료 시점을 정한다. 공식 반복 수와 재시도 상한으로 필요한 실행 시간을 계산해 견적에 반영하며, 실제 금액·사양은 견적 확인 전 임의로 채우지 않는다.

## E② 네트워크 경계 집행

**E② 네트워크 경계 집행은 제품의 필수 기능이며, 12월 18일 최소 완성 범위에 포함한다.** 엔진과 추적되는 자식 프로세스의 대상 송신은 E②를 통과해야 하고, 미승인·미지원 경로는 기본 차단한다. 채택 여부는 결정됐으며 구현 방식·지원 경로·배치·일정은 담당 검토로 확정한다.

권장 구성은 엔진의 대상 송신을 독립된 E② 집행점으로 모으고 모델 연결은 별도 승인된 gateway로 제한하는 방식이다. **첫 완성 범위는 HTTP·HTTPS 모두에서 실제 요청의 대상·메서드·경로·권한을 검사하는 것이다.** 개발 중 HTTP부터 검증할 수 있으나 최종 완료 조건에서 HTTPS를 제외하지 않는다. 그 밖의 미지원 프로토콜과 검사 불가능한 연결은 기본 차단하며, 검사 없는 CONNECT·TLS 터널로 통과시키지 않는다. 구체 배치는 기존 코어·공유 계약과 대조해 정한다.

유일한 송신 경로만으로 요청의 주체와 권한이 인증되지는 않는다. 신뢰 공급자가 제공한 task·run·reset·계정·자원과 현재 승인, lease·예산·감사를 실제 송신에 결속한다. 모델이 넣은 계정 header나 임의 참조 문자열은 신뢰 입력이 아니다. 승인 누락·만료·회수와 집행점 장애에는 신규 admission을 거부하며, 진행 중인 요청은 정해진 취소·drain·결과 분류를 따른다.

셸·MCP·사용자 정의 도구·추적 자식 프로세스가 proxy 환경변수를 지우거나 직접 소켓을 열어도 집행점을 우회할 수 없어야 한다. 직접 IP·DNS·IPv6·호스트 및 다른 network 경로, redirect·retry, CONNECT·TLS 터널 등은 배치별 송신 경로 목록에 포함해 허용·집행 또는 차단을 검증한다. 미지원 WebSocket·raw TCP·DB 접속과 인증서 고정 도구도 명시적으로 거부한다. 검증한 엔진 실행 경계와 지원 경로를 결과에 기재한다.

엔진이 집행점 설정·승인 저장소·감사 키를 변경하거나 host network·Docker socket·특권 경로로 나갈 수 있으면 네트워크 경계가 성립하지 않는다. 실제 배치에서 이 권한 분리를 확인한다. 엔진 경계 밖의 호스트 프로세스, 로컬 파일·프로세스와 외부 부작용은 별도 위협 모델로 다루며, 기존 부정 연결 점검만으로 현재 권한·회수·전체 수명 검증을 대신하지 않는다.

### 필수 수용시험

| 시험 | 확인할 결과 |
| --- | --- |
| 승인된 HTTP·HTTPS 정상 요청 | 각 프로토콜에서 실제 요청 검사를 거쳐 대상에 도착하고 응답·감사 근거가 연결됨. 전체 송신 차단을 성공으로 오인하지 않음 |
| HTTPS의 정상 권한과 범위 위반 | 암호화된 터널 허용만으로 통과하지 않고 실제 메서드·경로·계정·자원 정책을 검사해 허용·차단 |
| HTTPS 신뢰·인증서·검사 실패 | 승인된 검사 CA 신뢰와 대상 인증서·호스트 검증을 확인. 검증 생략이나 검사 없는 터널로 우회하지 않음 |

| 승인 만료·회수·권한 조회 실패 | 신규 송신을 거부하고 진행 요청의 취소·drain 및 결과를 보존 |
| 예산 소진·동시 요청 | 기존 예산 의미를 유지하고 허용량을 우회해 추가 전달하지 못함 |

| 실행 중 network·권한·설정 변경 | 감시 근거와 구간 연속성을 확인하고 위반 시 성공 판정을 중단 |
| 전송 후 감사·저장·ACK 오류 | 이미 보낸 사실과 결과 불명을 보존하며 자동 재전송·허위 rollback 없음 |

허용·차단·실패 결과는 실제 송신 관측과 대조하고, 정책·실행·회수 문맥 및 비민감 사유를 감사에 연결한다. 필수 감사가 준비되지 않은 신규 송신은 거부한다. 전송 후 기록 실패를 “전송되지 않음”으로 바꾸지 않는다. 새 이벤트 종류·export·서명 형식이 필요하면 기존 감사 계약의 담당 검토를 거쳐 추가한다.

정책 함수나 합성 callback 시험에 더해 소유한 격리 Linux 배치에서 실제 OS·컨테이너 송신과 허용·차단을 확인한다. 내부 권한·키·root·외부 복원 근거는 신뢰 공급자가 제공해야 한다. 미실행·skip은 수용시험 통과로 세지 않는다.

### 공식 평가와 연결

평가 계측기는 원본·개선본에 동일한 외부 격리·관측 기준을 제공한다. 제품 E②는 개선본의 비교 대상 기능으로 둔다. baseline에 제품 E②를 추가해 원본을 바꾸거나, 제품 집행점을 평가 계측기로 간주해 독립 관측을 없애지 않는다.

공통 대상 범위·작업·예산과 개선본의 E② 정책·승인 입력을 공식 실행 전에 동결한다. 현행 공식 scope와 충돌하는 변경은 별도 계약 검토와 실험 버전 고정 후 적용한다. 허용된 대상 전달, 제품 차단, 집행 실패를 구분해 보고하고 통제 정책 차이와 실행 비용을 결과 해석에 포함한다.

통제가 강화된 제품의 최종 공식 평가·완료 시연에는 위 집행 수용시험 통과를 필수 조건으로 둔다. 도구 개발용·비채점 시범은 기존 격리 조건 아래 별도로 수행할 수 있지만, E②가 미완이면 제품 통제 완료나 최종 기능 평가로 제시하지 않는다.

12월 18일 필수 완료 조건은 **HTTP·HTTPS를 검사하는 E② 네트워크 경계 집행과 등록 자원의 읽기 통합 경로**다. 일정이 부족하면 자동 로그인·쓰기 IDOR·수직 지도·HTTP·HTTPS 외 추가 프로토콜을 먼저 줄이고, 집행 미완을 선택 기능 제외로 처리하지 않는다. 담당 구현 순서와 실제 배치 수용시험 일정은 확인한다. ## 로그인 쓰기와 알고리즘 확장

### 프로그램이 수행하는 로그인

수동 세션 이후의 선택 단계다. 모델은 계정 label과 로그인 의도만 제안하고, 프로그램이 승인된 로그인 endpoint의 지정 필드에서만 비밀을 치환한다. 세션 수집과 신원 확인을 마친 뒤 불투명 handle로 대여한다.

앱별 identity 요청·응답 규칙과 anti-reflection 근거가 필요하다. 신원 확인이 없으면 세션을 검증됨으로 취급하지 않는다. 계정별 cookie jar, 만료·회수, 시도 예산·잠금, 응답 비밀 가림도 검증한다.

CSRF·다단계 로그인·OAuth/SSO·2FA·CAPTCHA·SPA별 처리는 지원 템플릿과 범위를 따로 정한다. 미지원이면 수동 세션으로 진행하거나 명시적으로 거부한다. 모든 앱에서 추가 코드 없이 작동하거나 모든 비밀을 완벽히 가린다고 주장하지 않는다.

### 쓰기 IDOR와 보상 동작

현재 최소 경로는 GET 조회 전용이다. destructive-last는 실행 허가가 아니며, 회차마다 환경을 새로 만드는 것은 제품의 공격 후 rollback과 다르다.

쓰기 지원은 별도 승인된 시험 환경에서 endpoint·method·resource·횟수를 제한하는 후속으로 검토한다. 시험 계정 소유 자원, 전후 snapshot, 정리 보고서, 소유자 권한의 보상 API와 결과 재확인을 요구한다.

필드 내용을 되돌려도 수정 시각·이력·ID·알림·메일·재고·외부 호출까지 원복된다고 주장하지 않는다. 부분 복구·수동 정리 필요·복구 실패를 구분하고, 결제·계정 삭제 등 되돌리기 어려운 동작은 기본 차단 범위로 둔다.

### 접근통제 지도와 알고리즘

첫 지도는 계정 2개와 등록 자원의 작은 수평 범위다. 수직 인가, 여러 역할·tenant, 본문·헤더·GraphQL·batch·2차 IDOR는 별도 계약과 수용시험 후 확장한다.

논문 알고리즘은 후보 생성, ID 흐름 추적, 소유·기대 정책 추론, 응답 비교에 연결할 수 있다. 추론은 출처가 확인된 사실과 구분하고, 유사도만으로 확정을 만들지 않는다. 모든 후보는 E② 실행 허용과 E③ 증거 규칙을 통과해야 한다. 알고리즘의 일반적인 성능 주장은 여러 독립 앱에서 별도 비교한다.

공식 비교와 IDOR 시연은 각자의 입력 준비 조건을 구분하되, 통제 강화 제품의 최종 공식 평가와 완료 시연에는 E② 네트워크 경계 집행 수용을 공통 필수 조건으로 둔다. 자동 로그인·쓰기·수직 지도는 후속으로 분리할 수 있다. 익명 비교나 개별 IDOR 성공만으로 네트워크 통제·실제 권한 공급·배치 보안 검증의 완료를 대신하지 않는다.

평가 시작·종료와 실패 판단 담당자를 정한다. 실행 중 인프라·권한·설정 위반이 발생하면 현재 회차 자료와 사유를 보존하고 해당 규칙에 따라 중단한다. 결과를 본 뒤 유리한 회차만 선택하거나 제한을 바꾸지 않는다.

## 발표와 결과 문서의 기준

공식 비교에서는 평가한 모델·백엔드·대상·예산 안에서의 결과를 제시한다. 발표용 최종 비교는 GPU에서 원본·개선본을 반복 측정한 결과를 사용한다. 첫 비교에서 판정이 미수집이면 해결 귀속 지표로 범위를 한정한다. API 수치는 해당 조건의 보조 결과로 구분하고 GPU·로컬 수치로 대체하지 않는다.

IDOR 시연에서는 “등록한 A/B와 자원에 대해 기대 권한·신원·실제 접근 증거를 대조하고 감사·저장까지 연결했다”는 식으로 검증 단위를 명시한다. 엔드포인트 전체, 모든 IDOR, 수직 인가나 모든 도구 송신을 지원한다는 표현으로 넓히지 않는다.

배치 검증에서는 실제로 시험한 엔진 실행 경계, 권한 공급·수명과 경로별 허용·차단 근거를 명시한다. 최종 제품은 E②를 우회한 대상 송신이 없어야 하며, 미지원 경로는 차단 상태로 확인한다. 이를 충족하지 못하면 통제 강화 제품의 완료로 발표하지 않는다. 합성 callback·임시 root 시험은 실제 운영 공급자 검증과 구분한다. 미실행·skip·실패·판단불가·미검사·저장 불명을 성공이나 “취약점 없음”으로 바꾸지 않는다.

원본의 출처와 라이선스 표시는 유지한다. 결과가 개선을 보이지 않더라도 반복 원자료와 한계를 함께 보고한다.
