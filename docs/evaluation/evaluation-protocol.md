# 평가 프로토콜 — ABC2LAB vs baseline(원본 ARTEX)

> baseline(원본 ARTEX, 윤재상 구동)과 개선 후(우리 포크)를 **같은 조건**으로 비교하기 위한
> 측정 조건의 **단일 원본**. 조건은 이 파일에서 정하고, 관련 계약·README는 이 정본을 참조한다.
> 챌린지 목록은 **평가 정답(GT)으로만** 쓴다 — 스캐너·탐색·판정·시나리오 입력에 넣지 않는다
> (CLAUDE.md 절대규칙 7).

## 1. 목적
- baseline vs 개선 후 공정 비교. 측정 조건의 단일 원본.
- 조건(버전·모델 태그·판정 기준·매트릭스)은 여기서 수정하며, 다른 문서에 별도 판정 규칙을 두지 않는다.
- **구현 상태:** `scripts/eval`은 서명된 러너 기록에 묶인 pre/post 원본·정규화·회차·종료 검증과 v1 직접 관측 이벤트 기반 해결 귀속(합성 시험·과거 형식 회귀 검증용)을 구현했다. 입력 계약은 [러너 기록](run-record.md)을 따른다. 검증은 합성 자료로 수행했으며, 실제 러너/신뢰 관측기·키 격리·baseline 출력 어댑터 연결과 공식 비교 실행은 남아 있다. 이 연결과 실측 검증 전에는 공식 평가 완료로 주장하지 않는다. v1.1(`isolated_window`) 기록 수용은 `scripts/eval/isolation_proof.py`·`run_record.py`가 맡는다: 격리 증명·근거 행(run-record-v1.1 §3·§3.1)·신규 해결 델타 이벤트를 검증하고, records=null이면 GT 판정을 전부 판단불가(판정 미수집)로 둔다. 합성 회귀(IW01~IW17)와 개발 머신 스모크 회차 1건(가짜 LLM, 판정 미수집)의 채점까지 확인했다. v1·v1.1 기록을 섞은 비교와 증명 재사용은 채점 중단이고, v1만 있는 비교표는 공식 비교가 아니라는 경고를 낸다.
- **귀속 입력 계약:** 공식 비교표의 해결 귀속은 baseline·개선 후 모두 [run-record v1.1](run-record-v1.1.md)의 `isolated_window`(서명된 격리 증명 + pre/post 델타)만 쓴다. 아래 §4 판정표·§5 분모/매트릭스는 유지한다. 계약 합의는 채점기 수용·실제 격리 집행·실측 완료를 뜻하지 않는다.

## 2. 평가 대상 고정
- 대상: **OWASP Juice Shop v15.0.0** (첫 과녁).
- Docker 이미지 태그: **`bkimminich/juice-shop:v15.0.0`** (`latest` 금지 — 버전 고정).
- 인스턴스 리셋: **스캔 1회마다 컨테이너 재생성**하여 이전 스캔 상태를 격리한다
  (Juice Shop은 인메모리 상태라 재시작으로 초기화).
- **회차 구성 — 전용 네트워크(러너 v1이 지원하는 유일한 모드).** 엔진(baseline·개선 후 모두)은 컨테이너로 돌리고, 엔진과 대상 사이에는 러너 측 계측기 하나만, 엔진과 LLM 사이에는 LLM 게이트웨이 하나만 둔다. 엔진은 internal 망 하나에만 붙어 바깥으로 직접 나가는 경로가 없다. 망 이름·포트·이미지 digest·모델 태그·LLM 주소·관측 경로는 전부 설정값이며 코드에 두지 않는다. 회차마다 compose project를 새로 만들고 끝나면 내린다. 망은 다음 회차에 재사용하지 않는다.

  | 망 | internal | 구성원(정확히 이것만) |
  |---|---|---|
  | 엔진 망 | true | 엔진, 엔진 DB, 계측기(`eval-meter`), LLM 게이트웨이(`eval-llm-gw`), 엔진 API front(`eval-api`) |
  | 대상 망 | true | Juice Shop, 계측기, 관측 front(`eval-obs`) |
  | LLM 출구 망 | false | LLM 게이트웨이 |
  | 엔진 API 망 | false | 엔진 API front(엔진 API는 `127.0.0.1`에만 publish) |
  | 관측 망 | false | 관측 front(관측 포트는 `127.0.0.1`에만 publish) |

  - Juice Shop은 publish하지 않고 엔진은 대상 망에 연결하지 않는다. 엔진 망과 대상 망을 동시에 잇는 것은 **계측기 하나뿐**이다. 엔진은 엔진 망에만 붙는다.
  - 관측 front를 계측기와 분리하는 이유: internal 망만 붙은 컨테이너는 포트를 publish할 수 없다. 한 컨테이너가 관측 포트까지 맡으면 일반 망에 붙어야 하고, 그러면 엔진이 관측 포트로 대상에 닿는 경로가 생긴다. 두 컨테이너는 같은 바이너리를 역할만 달리 해서 띄운다. 어느 쪽에도 서명 키·Docker 소켓을 주지 않는다.
  - LLM 게이트웨이·엔진 API front를 엔진과 분리하는 이유도 같다. 엔진이 일반 망에 붙으면 NAT로 바깥 어디든 나갈 수 있다. 엔진 API front는 엔진 API(운영·작업 생성·findings 수집)를 고치지 않고 엔진에만 전달한다. 두 컨테이너도 같은 바이너리의 다른 역할이며, 서명 키·Docker 소켓은 주지 않는다. API 키는 LLM 게이트웨이에만 준다.
- **계측기(`eval-meter`)** — 엔진의 대상 요청을 **고치지 않고** 전달하고 센다. Host를 보존하고 전달 헤더를 추가하지 않으며, HTTP 표준의 hop-by-hop 처리만 한다. 러너가 신규 송신을 막으면(seal) 이후 요청은 대상에 보내지 않고 거부 건수로 센다. WebSocket 등 열린 스트림은 강제로 닫고 그 수를 기록한다. 비스트림 진행 요청이 0이 된 시각을 계측기가 직접 기록하고, 러너는 그 기록을 확인한 뒤 post를 수집한다. 봉인 뒤 설정한 유예(러너 drain 시한보다 짧음)가 지나도 끝나지 않은 비스트림 요청(긴 폴링 등)은 계측기가 대상 쪽으로 취소하고 그 수를 drain 기록에 남긴다. 취소된 요청도 봉인 전에 전달된 요청이라 엔진 요청 수에 들어간다. 취소가 있으면 러너는 post 전에 설정한 정착 대기를 둔다. 대상이 끊긴 요청을 그 뒤에도 처리하는지는 통제하지 못하며, 정착 대기 뒤에 생긴 해결은 그 회차 post에 잡히지 않을 수 있다(엔진 쪽으로 과소 집계되는 한계, 다른 actor로 잘못 귀속되지는 않음). 유예·취소 수·정착 대기는 서명 기록에 남는다. 엔진 요청 수(§5 `total_requests`)는 계측기의 전달 건수이며 관측 요청과 섞지 않는다. 로그에는 순번·메서드·상태·시각·바이트 수만 남기고 경로·query·헤더·본문은 남기지 않는다.
- **관측 front(`eval-obs`)** — 등록된 스코어보드 경로 1개에 대한 정확한 GET만 대상에 전달하고 나머지(다른 메서드·경로·query)는 거부한다. 요청마다 통과/거부를 기록한다. 러너는 호스트에서 `127.0.0.1`의 관측 포트로 수집한다(수집기의 loopback 전용 가드 유지). 관측 front 로그의 구간 요청 수가 러너의 수집 호출 수와 다르면 격리 증명을 발행하지 않는다.
- **부정 연결 점검(매 회차, pre 전과 post 후)** — 엔진 컨테이너의 네트워크 namespace 안에서 별도 점검 컨테이너로 확인한다(엔진 이미지 내용에 의존하지 않음). 기대와 다른 경로가 하나라도 있으면 그 회차는 격리 증명을 발행하지 않으며, 새 해결은 귀속 미확인(판단불가)이다. 경로별 기대·실제·시각은 격리 근거에 남긴다.

  | 경로 | 기대 |
  |---|---|
  | 계측기(TCP 연결만, 요청 없음 — 전달 건수에 섞이지 않게) | 성공 |
  | LLM 게이트웨이(TCP 연결만) | 성공 |
  | LLM upstream 직접 — api: API 호스트:443 / local: `EVAL_LLM_HOST_IP`:포트 | 실패 |
  | 대상 망의 Juice Shop IP 직접 | 실패 |
  | 관측 front의 모든 IP | 실패 |
  | 대상·관측 front 이름 해석(서비스·컨테이너 이름·짧은 ID) | 실패 |
  | 엔진 망의 호스트 쪽 게이트웨이 주소(있으면)의 관측 포트 | 실패 |

  - 망마다 internal 여부와 구성원이 위 표와 **정확히** 같아야 한다. publish는 관측 front·엔진 API front 두 개뿐이며 둘 다 `127.0.0.1`이어야 한다. Docker 서버는 28.0.0 이상이어야 한다(그 이전의 같은 L2 구간 접근 예외, [공식 포트 공개 문서](https://docs.docker.com/engine/network/port-publishing/#publishing-ports)). 망 ID·구성원·바인딩이 pre와 post 사이에 바뀌면 증명을 발행하지 않는다.
- **LLM 연결** — LLM 백엔드는 설정값이다(§6: 평가는 외부 API 허용, 로컬 서버도 가능). 엔진은 LLM 게이트웨이에만 닿고, 게이트웨이가 LLM 출구 망으로 나간다(api: https API / local: 고정 IP의 로컬 서버). 두 백엔드가 같은 경로라, 로컬로 바꿀 때는 설정값만 바꾼다. LLM 호출은 계측기를 거치지 않으며 엔진 `total_requests`에 넣지 않는다.
  - 게이트웨이는 등록된 경로의 POST만 받는다. api 백엔드에서는 요청마다 제공자 고정(`provider.order`=전체 slug, `allow_fallbacks:false`)을 넣고(엔진이 `provider`를 보내면 거부) 회차 뒤 generation 조회로 응답 제공자와 fallback 시도를 확인한다(§6). local 백엔드에서는 요청을 고치지 않는다. 리다이렉트를 따르지 않고 환경 프록시를 쓰지 않으며 upstream 호스트 외에는 연결하지 않는다. 기록은 순번·상태·시각·바이트·generation ID뿐이고 본문·헤더는 남기지 않는다.
  - API 키는 비밀 env 파일에서 게이트웨이 컨테이너 환경으로만 넣고, 엔진에는 자리값만 준다. 회차 기록·격리 근거·로그·manifest에는 이름만 남기고 값은 남기지 않는다(절대규칙 2).
  - 같은 머신의 로컬 서버를 쓸 때는 회차와 무관한 고정 IP(`EVAL_LLM_HOST_IP`, 값은 사전검사 선언, 게이트웨이의 compose `extra_hosts`로 주입)로 연결하고 `0.0.0.0` 공개는 쓰지 않는다. compose의 `host-gateway`는 쓰지 않는다. 이 값은 Docker 엔진마다 다른 주소로 풀린다(예: Docker Desktop은 Windows 쪽 주소).
  - 러너는 Docker 데몬의 신원(플랫폼·서버 버전)을 기록하고, 회차 중 바뀌면 증명을 발행하지 않는다.
  - 엔진의 바깥 경로가 게이트웨이뿐이라 평가 회차에서 엔진의 외부 송신은 망으로 막힌다. 다만 이것은 **우리 평가 구성**의 성질이다. 실배포에는 이 게이트웨이가 없으므로, 완전 로컬 모드(엔진 자체의 외부 송신 차단)는 엔진의 LLM·송신 설정으로 따로 지켜야 하며 이 격리 근거로 대신하지 않는다(§6 음성 시험).
- **회차 저장소** — 평가 층에서 엔진 DB와 엔진 데이터(트래픽 저장소·transcripts·E② 상태)는 회차 한정 메모리(tmpfs)이고 크기 상한은 설정값이다. 사용량은 구간 감시가 끝난 직후(seal 뒤) 러너가 엔진 밖 측정 컨테이너(계측기 이미지의 statfs, 엔진 안의 실행파일을 쓰지 않음)로 두 tmpfs의 크기·사용·남은 바이트를 재서 적용 하한과 함께 서명 기록한다. 측정은 대상 mountinfo의 그 마운트 지점 tmpfs에 마운트 ID로 결속하며, 구간 전에 잰 마운트 ID와 같아야 받는다(같은 경로의 다른 마운트는 무효). 구간 중 새 컨테이너·회차 컨테이너 exec는 경계 변경이라 seal 시점에는 재지 않으며, seal과 측정 사이에 사용량이 줄었을 가능성은 배제하지 못한다(한계). 남은 공간이 하한 미만이면 상한에 닿은 것으로 보고 회차를 무효로 한다. 두 크기와 하한은 사전검사 `run_storage`로 선언해 환경 지문(프로파일 v3)에 넣으므로 baseline·개선 후가 같은 조건이어야 비교된다. 측정 전에 끝난 회차는 회차 기록에 `tmpfs_usage: "not_measured"`를 남기고, 그런 회차는 상한 도달 여부를 알 수 없으므로 공식 비교표에 쓰지 않는다(탐색용). 회차 끝에는 엔진 API로 findings만 꺼낸다. transcripts·트래픽 저장소·E② 원본 상태는 기본으로 수집하지 않는다. 계측기·관측 front 로그는 별도 증거 디렉터리에 남는다.
- **엔진 이미지** — baseline은 우리가 수정하기 시작한 원본 `base/artex-import`를 깨끗한 작업 트리에서 빌드한 이미지를 기준으로 한다. upstream 배포 이미지는 그 코드와 같다고 확인된 경우에만 쓴다. 그래야 결과 차이가 우리 변경분에서만 나온다고 말할 수 있다. baseline·개선 후 모두 빌드한 소스 커밋과 이미지 ID를 격리 근거와 manifest에 기록한다.
- **대상 격리** — 회차 구간(pre~post) 동안 대상은 **평가 엔진(계측기 경유)과 등록 관측 front만** 접근할 수 있어야 한다. 네트워크 경계와 같은 호스트의 운영 조건을 함께 확인하며, 서명·기록만으로 실제 격리를 대신하지 않는다.
  - 생성/검사 실패 시 중단하고 기존 망을 성공한 것으로 재사용하지 않는다. 러너는 회차별 project와 Docker가 반환한 망 ID를 결속한다.
  - 루프백 모드(엔진이 호스트 프로세스, 대상 포트를 `127.0.0.1`에 publish)는 프로토콜상 대안이다. 다만 Linux Docker 호스트는 컨테이너 대역으로 라우팅되어, 호스트 프로세스인 엔진이 계측기를 우회해 대상 IP에 닿을 수 있다. 엔진 실행 계정의 컨테이너 대역 접근을 호스트에서 막았다는 근거가 없으면 격리 증명을 발행하지 않으며, 러너 v1은 이 모드를 지원하지 않는다.
  - 내부 네트워크와 publish 생략은 같은 네트워크의 다른 컨테이너나 호스트 프로세스의 접근 권한을 구분하지 않는다([공식 내부 네트워크 문서](https://docs.docker.com/reference/cli/docker/network/create/#network-internal-mode---internal)). 두 모드 모두 **전용 평가 호스트의 운영 조건**을 별도로 확인한다. pre~post 동안 미등록 사용자·비평가 프로세스/컨테이너의 대상 접근과 경계 변경 가능성을 배제한 운영 조건, 확인 시각·적용 구간·근거 참조를 러너의 서명된 회차 기록에 남긴다. 확인 기록이 없거나 구간 전체를 덮지 못하면 격리 귀속은 불가다.
  - 같은 호스트 운영 조건의 실제 점검: 회차 전·후에 다른 컨테이너의 loopback 밖 publish와 호스트 프로세스의 loopback 밖 리슨(`0.0.0.0`·`[::]`·특정 IP 전부)이 없어야 한다. 허용은 local 백엔드일 때 LLM 리슨 하나(고정 IP:포트)뿐이고, api 백엔드일 때는 없다. 개발용 대상 앱 같은 다른 서비스가 떠 있으면 엔진이 엔진 망의 호스트 쪽 게이트웨이 주소로 거기 닿을 수 있다(internal 망에도 호스트 쪽 브리지 주소가 있을 수 있다 — 스모크에서 확인). 위반이 있으면 격리 증명을 발행하지 않는다.
    - 호스트가 스스로 띄운 리슨(예: WSL의 DNS 터널링 주소)은 코드 예외로 두지 않는다. 러너 설정의 허용 목록에 특정 주소·포트와 근거를 함께 적어야 통과하며, 전체 주소(`0.0.0.0`·`::`)는 허용 목록에 넣을 수 없다. 기본은 거부다.
    - 점검 범위는 러너가 도는 Linux 네트워크 namespace의 TCP 리슨(`/proc/net/tcp`·`tcp6`)까지다. WSL 바깥(Windows)·다른 VM의 리슨과 UDP는 이 점검이 보지 않으므로 전용 평가 호스트 운영 조건으로 다룬다.
  - 러너는 회차마다 어느 격리 모드였는지 기록한다(§4 격리 보증 구간 조건 (a)).
- **스코어보드 스냅샷은 회차마다 pre/post 두 시점이 필수다.** `GET /api/Challenges` 응답을 다음 순서로 저장한다.
  - **pre** — 계정 provisioning·비민감 canary/fixture 준비가 모두 끝난 뒤, 엔진의 대상 요청이 시작되기 전. 준비 절차는 [IDOR canary fixture](../contracts/idor-canary-fixture.md)(제안).
  - **post** — 엔진의 신규 송신을 중지하고 진행 요청의 종료(유예 뒤 계측기 취소 포함, §2)를 확인한 뒤, 컨테이너 제거 전. 종료 확인이 안 되면 완료된 회차로 채점하지 않는다.
  - 각 시점에 **원본 응답 + 정규화본**(`{챌린지 key: solved(bool)}`)을 보존한다. 정규화는 원본에서 결정적으로 만들며, 채점은 두 정규화본을 비교한다. post 한 장만으로 해결 주체를 추정하지 않는다.
  - 채점 분모(코어 GT ∪ BAC)의 key가 어느 정규화본에서든 빠지거나 solved가 bool이 아니면 **채점 에러**다. 누락을 미해결로 채우지 않는다.
  - 평가 러너의 회차 기록에 `run_id`·`reset_generation`·정확한 `model_tag`, pre/post의 단계·수집 시각·원본/정규화 경로·내용 해시, 엔진 시작/종료 시각·요청 종료 확인을 묶는다. `pre ≤ 엔진 시작 ≤ 엔진 종료 ≤ post` 순서와 같은 인스턴스/reset 세대를 확인한다.
  - 판정 묶음(envelope)의 필수 `run_id`와 pre/post·traffic·커버리지의 아티팩트 메타데이터가 같은 회차 기록을 가리켜야 한다. pre/post 정규화본은 `{key: bool}`을 유지하고, `run_id`·단계·해시는 바깥 envelope 또는 회차 기록의 메타데이터에 둔다. 경로·내용 해시와 함께 대조하며 모델/reset 문자열만으로 회차 일치를 추정하지 않는다.
  - pre/post와 회차 기록은 필수다. 제공된 판정·traffic·커버리지도 같은 회차/모델/reset 세대에 속하는지 대조한다. traffic·커버리지 미수집은 출처 없음으로 명시하여 해당 증거/커버리지를 인정하지 않는다. 필수 파일·메타데이터 누락, 다른 회차 혼입, 중간 리셋, 해결 상태의 역행(`true→false`), 시각 순서 오류는 **채점 중단**이며 표를 출력하지 않는다. 채점기의 저장 자료 검증은 구현했으며, 러너의 실제 수집·종료 관측·기록 발행 연결은 별도 검증해야 한다.
  - 원본·정규화·회차 기록은 결과물이므로 커밋 금지다. GT를 담는 스냅샷과 귀속 정보는 **평가기 전용**이며 엔진·탐색·판정·시나리오 입력으로 전달하지 않는다.
- 대상 origin은 설정(`.env`)으로 고정, 코드 하드코딩 금지.

## 4. 판정 기준
1. 제목(이름) 매핑만으로 성공 판정하지 않는다.
2. §2의 회차 입력 검증과 아래 **해결 귀속 선행 규칙**을 통과한 뒤, 실제 챌린지 해결 상태 + 요청·응답 증거를 확인한다. **증거 있음 = 아래 3조건 모두 충족**,
   하나라도 확인 못 하면 확정이 아니라 **판단불가**:
   - (a) 판정 레코드의 `traffic_evidence_refs`가 비어 있지 않다.
   - (b) 그 ref가 같은 회차 traffic 기록에 실재한다.
   - (c) 그 증거 요청의 대상이 해당 챌린지 자원이다(GT 상관과 같은 기준).

   **판정 단위**: 레코드는 (a)를 만족하고 (b)·(c)를 **함께** 만족하는 ref가 **하나 이상**이면 증거 충족이다
   (모든 ref일 필요는 없다). 챌린지는 confirmed 레코드 중 증거 충족 레코드가 **하나 이상**이면 확정 경로를 탄다
   (모든 레코드일 필요는 없다). 레코드·ref를 많이 내서 확정을 얻는 길은 (c)가 막는다 — 해당 챌린지 자원을
   가리키지 않는 증거는 세지 않는다. traffic 기록에 없는 ref(끊긴 ref)는 세지 않고 **경고로 표면화**한다.

   증거 조건은 **확정 경로에만** 적용한다. 선행 규칙을 통과한 confirmed 주장인데 종료 시 챌린지가 미해결이면 증거 유무와 무관하게 **오탐**이다
   (증거 부족을 오탐 회피 수단으로 쓰지 않는다).
3. 선정 목록에 매핑 안 된 finding = 즉시 오탐 처리하지 않는다(별도 분류: out-of-list).
4. 미해결 챌린지 = 자동으로 미탐 처리하지 않는다(범위 밖 제외와 구분). GT 챌린지에 엔진 판정이 없고 미해결이면,
   엔진이 그 챌린지 자원을 실제로 검사했다는 **커버리지 기록이 있을 때만 미탐**, 없으면 **판단불가**.
   커버리지 기록은 판정 레코드와 별개 출처(커버리지 지도 등)여야 한다. 같은 엔진 회차에서 해당 검사를 수행한 근거만 인정하고, 준비 작업·단순 후보 등록·차단된 시도를 커버리지로 세지 않는다. 출처가 없으면 = 커버리지 없음.
5. 스캔마다 Juice Shop 인스턴스를 리셋한다(§2와 동일).
6. GT 챌린지에 대한 엔진 판정이 **ALLOWED뿐**이면 **판단불가 + 경고로 표면화**한다. 코어 GT는 전부 실제 취약이라
   ALLOWED는 KG·정책 오류 신호다 — 미탐·취약점없음으로 기록하지 않는다.
7. 러너 기록 v1.1의 판정 레코드(`records`)가 null(**판정 미수집**)인 회차는 그 회차의 GT 판정을 전부 **판단불가**(사유: 판정 미수집)로 두고 확정·오탐·미탐 어디에도 세지 않는다. 커버리지 기록이 있어도 미탐으로 바꾸지 않는다. 해결 귀속(격리 증명·델타)은 따로 검증·보고한다([러너 기록 v1.1](run-record-v1.1.md) §3).

**해결 귀속 선행 규칙**:
- `pre=true`는 엔진 검사 전에 이미 해결된 항목이다. 준비 작업이 만든 solve일 수 있으므로 해당 항목은 **판단불가 + 사전 해결 경고**로 남긴다. 이번 회차의 엔진 확정·미탐으로 세지 않고, GT 분모에서 몰래 빼지도 않는다.
- `pre=false → post=true`는 새 해결 관찰일 뿐, 그 자체로 엔진 귀속의 충분조건이 아니다. 엔진 귀속은 아래 **격리 보증 구간**으로 확인한다. manifest의 자기 선언, 같은 URL·가까운 시각만으로는 충분하지 않다.
- 다른 주체가 만든 solve로 확인된 경우도 엔진 성과에서 제외하며, 귀속 미확인과 함께 아래 표에서 판단불가다.
- 입력 구조 오류·필수 pre 부재 등은 §2에 따라 채점 중단이다. 유효한 입력 안에서 해결 주체나 증거를 확인하지 못한 경우가 **판단불가**이며, 두 경우를 혼동하지 않는다.

**격리 보증 구간** (baseline·개선 후 동일 적용):
- 구간은 **pre 스냅샷**(계정·canary/fixture 준비 후, 엔진의 대상 요청 전 해결 집합)부터 **post 스냅샷**(엔진 신규 송신 중지와 진행 요청 0 확인 후 해결 집합)까지다. 두 정규화본의 델타(`pre=false → post=true`)가 그 구간에 새로 해결된 항목이다.
- 러너가 실제 집행·확인한 뒤 회차 기록에 서명해 남기는 **격리 조건 4개**. (a)~(c)는 pre 스냅샷 관측부터 post 관측 완료까지 연속 적용하고, (d)는 post 수집 전에 확인한다:
  - (a) 대상의 네트워크 경계와 전용 평가 호스트 운영 조건을 함께 확인 — §2의 격리 모드·경계/정책 참조와 **같은 호스트 운영 조건의 확인 시각·적용 구간·근거 참조**를 기록. 네트워크 기록만으로 대체하지 않으며 호스트 확인 기록이 없거나 pre~post 전체를 덮지 못하면 증명 불가.
  - (b) pre 이후 준비 작업(계정 provisioning·fixture·canary 수정) 0건.
  - (c) 러너의 관측기는 등록된 비변경 GET(스코어보드 스냅샷)만 보냄. 해당 대상 버전에서 상태 변경·solve 유발이 없는 경로인지 확인하고 실제 송신 로그와 요청 수를 기록. GET 메서드라는 이유만으로 비변경을 가정하지 않음.
  - (d) 엔진의 스캔 요청이 전부 종료됐음을 확인(진행 요청 0). 봉인 뒤 유예가 지나 계측기가 취소한 요청은 종료로 보되 그 수를 기록한다(§2).
- 네 조건이 모두 서명·충족됐을 때만 델타를 `actor=engine`으로 귀속한다. 러너가 어느 조건을 확인하지 못하거나 불충족이면 증명을 발행하지 않고 미수집/귀속 불가 사유를 남긴다. 유효한 입력에 증명이 없으면 그 회차의 새 해결은 **귀속 미확인 → 판단불가**다(확정·미탐으로 세지 않는다). v1 직접 관측 이벤트는 이 증명을 대신하지 않는다. 반면 `isolated_window` 증명을 제출했다고 주장하면서 필수 기록이 누락·위조됐거나 문맥/해시/구간이 모순되면 **입력 오류로 채점 중단·표 미출력**이며 판단불가로 조용히 낮추지 않는다.
- **새 해결 집합은 스냅샷 델타로 관찰하고, actor 귀속은 서명된 네 격리 조건으로 판단한다.** Juice Shop의 해결 시각(`updatedAt` 등)에 의존하지 않으며, 타임스탬프 근접성으로 귀속하지 않는다.
- 귀속 단위는 회차(엔진 실행 1회)다. 어느 요청이 해결시켰는지는 이 규칙이 판정하지 않으며, 확정 경로의 요청·응답 증거는 위 2번의 3조건으로 따로 확인한다.
- **baseline(원본 ARTEX)에도 같은 구간·같은 조건을 적용한다.** 원본에는 E②가 없어서 E② 전송 기록에 기대는 귀속은 baseline에 적용할 수 없고, 그러면 통제변수가 깨진다. 그래서 귀속 근거를 엔진 내부 기록이 아니라 대상 쪽 격리와 스냅샷 델타에 둔다.
- 러너 기록 입력 형식: **공식 비교표의 해결 귀속은 [러너 기록 v1.1](run-record-v1.1.md)의 `basis=isolated_window`만 쓴다**(baseline·개선 후 동일). [v1](run-record.md)의 직접 관측 이벤트 수용은 합성 시험·과거 형식 회귀 검증용이며, 공식 비교표의 귀속 근거나 격리 증명의 대체 경로가 아니다. v1.1 채점기·러너 구현과 실제 격리 집행 검증 전에는 공식 비교를 하지 않는다. 위 v1.1 오류/미수집 구분은 v1.1 계약의 요구사항이며 현재 코드가 v1.1을 수용한다는 뜻이 아니다.

## 5. 측정 매트릭스 (값은 비움, 틀만)
- 각 조건은 LLM 비결정성 때문에 **N회 반복(권장 3~5회)**, 각 셀은 **평균 ± 표본 표준편차(SD, n−1)**. 1회 숫자로 결론 금지.
- **확정 수는 (a) 코어 GT(인가 9개) 기준과 (b) BAC category 전체(10개) 기준을 둘 다 기록**한다(cherry-pick 방지).
- **총 요청 수 = 실제로 대상에 전송된 HTTP 요청만**(traffic 기록분). E² 차단 시도·LLM 호출은 제외한다. **차단 시도 수는 별도 지표**로 기록한다.

**통제변수 = 단일 모델 태그 하나.** 비교는 **같은 태그**에서 원본 vs 우리로만 성립한다(§6).
계정·fixture 준비 조건과 채점 분모의 pre 해결 상태도 비교 대상 사이에 같아야 한다. 다르면 동일 조건 비교를 중단하고 조건을 재고정한다. 사전 해결 항목을 한쪽 분모에서만 빼서 수치를 맞추지 않는다.
격리 방식도 baseline·개선 후에 **같은 모드·동등한 네트워크 정책과 전용 호스트 운영 조건**으로 고정한다. 한쪽은 전용 네트워크, 다른 쪽은 루프백인 비교는 중단한다. 회차별 네트워크 ID·증명/근거 참조는 각각 새로 발급하므로 그 문자열이 같아야 한다는 뜻은 아니다. 각 회차의 정책 지문·운영 조건 근거로 고정한 조건의 동등성을 확인하고, 확인하지 못하면 같은 비교 표에 넣지 않는다.

## 6. 모델·환경 핀
- **LLM 백엔드** — 실배포·민감 환경은 로컬만 쓴다(절대규칙 8). 35B급은 "보급된 조직이 로컬로 돌릴 수 있는 크기"라는 기준으로 고른 것이며, 평가 자체를 로컬에서 돌려야 하는 것은 아니다. **평가는 공개 연습 대상(Juice Shop)만 다루므로 외부 API(예: OpenRouter)를 허용한다.** 실제 조직 대상이나 민감 자료에는 이 허용을 적용하지 않는다.
- LLM 엔드포인트(사전검사 선언의 `llm.base_url`) = `<TODO: baseline 재실행 때 확정할 엔드포인트>`. 엔진의 `ARTEX_LLM_BASE_URL`은 이 값이 아니라 러너가 LLM 게이트웨이 주소(선언의 경로를 붙임)로 정한다(§2).
- **API 백엔드의 고정 조건** — baseline·개선 후 동일하게 맞추고 회차마다 기록한다.
  - 같은 모델 식별자: 제공자 문자열을 그대로 쓴다(예: OpenRouter 모델 ID).
  - 같은 서빙 제공자: 자동 전환(fallback)을 끈다. 같은 모델 이름이라도 제공자마다 정밀도(양자화)·설정이 다를 수 있다. 엔진 요청 옵션이나 API 계정 설정 중 baseline·개선 후 모두에 같은 방식으로 적용되는 것으로 고정한다.
  - 같은 샘플링 설정: 아래 샘플링 고정값. 제공자가 seed를 지원하지 않으면 그 사실을 기록한다.
  - 회차마다 실제로 응답한 제공자·정밀도를 확인할 수 있으면 기록한다. 고정과 다른 제공자가 섞인 회차는 비교 표에 넣지 않는다. 확인할 수 없으면 "고정 설정만 근거"라고 기록한다.
- 회차 기록에 LLM 백엔드 종류(api|local)를 남긴다. API 고정 조건은 환경 지문에 넣으며, baseline·개선 후 지문이 다르면 사전 점검에서 거부한다.
- **엔진 LLM 정책 모드** — 개선 후 엔진은 평가 회차에서 `ARTEX_LLM_POLICY_MODE=external`로 돈다(엔진의 LLM 송신은 게이트웨이로만, §2). baseline(e53a79f)에는 이 스위치가 없어 회차 기록의 선언값은 null이다. 엔진이 현재 모드를 드러내는 관측 경로는 아직 없고(제안 #133), 생기더라도 **정책 관측은 공식 비교의 적격 조건이 아니며 채점 입력(러너 기록 run-record)에 넣지 않는다.** 관측은 러너의 서명된 근거로만 남긴다. 완전 로컬 모드의 외부 송신 차단은 아래 주장 범위의 별도 음성 시험으로 검증한다.
- **제공자 고정 적용** — 엔진(baseline·개선 후 모두)은 제공자 라우팅 옵션을 요청에 넣지 않으므로, 평가 구성의 LLM 게이트웨이가 넣는다(아래). 게이트웨이 경로를 거치지 않은 회차(러너 이전 실행 포함)는 "제공자 고정 미적용"으로 기록하고, 응답 제공자를 확인하지 못했으면 같은 제공자였다고 주장하지 않는다. API 계정 설정으로 제공자 제한·fallback 끔이 되는지는 확인 필요다. 적용 전 회차의 baseline·개선 후 차이에는 서빙 제공자 차이가 섞였을 수 있으며, 결과 문서에 이를 명시한다.
  - 적용 경로(러너 #126에 구현·머지, 개발 머신 api 스모크 1회 통과 — [러너 문서](runner.md) "스모크 실측"): 평가용 LLM 게이트웨이. 엔진은 게이트웨이에만 닿고(엔진의 외부 경로 0) 게이트웨이가 API로 나간다. 게이트웨이가 요청마다 `provider` 고정(`order`=전체 slug)·`allow_fallbacks:false`를 넣고 API 키를 혼자 가지며, 회차 뒤 generation 조회(`provider_name`·`provider_responses`)로 응답 제공자와 fallback 시도를 확인한다. baseline·개선 후에 같은 경로를 쓰고, 고정과 다른 제공자나 fallback 시도가 있는 회차는 비교 표에서 빼고 사유를 기록한다. 계정의 허용 제공자 설정은 안전망으로만 쓴다(그것만으로는 회차별 증거가 남지 않는다).
  - 판정: 러너가 게이트웨이 검증 마커로 판정한다. 모든 generation이 검증되고(generation ID 없는 응답·미검증 0), 응답 제공자가 러너 설정의 기대 표시 이름이며(고정 slug와 짝, 팀이 정함), 응답한 제공자와 다른 제공자로 간 시도가 없어야(같은 제공자 재시도는 허용) 통과한다. 시도 목록이 비어 fallback 여부를 확인할 수 없으면 통과로 보지 않는다. 엔드포인트 ID는 의미를 실측으로 확인하기 전까지 판정에 쓰지 않고 기록만 한다. 판정 결과와 사유는 회차 근거(`llm-summary.json`)와 서명된 회차 결과에 남는다.
- **현재 한계(평가 검증·기록)** — 러너 PR의 사전검사·환경 지문은 api 백엔드의 외부 API 주소와 제공자·fallback 선언을 받아 환경 지문에 넣는다(dev의 이전 사전검사·지문은 loopback/localhost만 받고 제공자·fallback 필드를 `UNKNOWN_FIELDS`로 거부했다). 선언은 일관성만 보이고, 실제 응답 제공자와 fallback 시도는 러너가 게이트웨이 검증 마커로 판정해 회차 기록에 남긴다(위 판정). 이 판정을 통과한 API 회차만 공식 비교표·baseline 대비 개선 주장에 쓴다. 판정 경로를 거치지 않은 회차와, 실측 스모크로 경로를 확인하기 전 회차는 **탐색용**이다. 공개 연습 대상에 대한 API 사용 허용과 공식 비교 적격성을 구분한다.
- **주장 범위** — 주 주장은 같은 모델·같은 백엔드에서의 baseline 대비 개선(상대 비교)이다. API로 잰 절대 성능·시간 지표를 로컬 배포 값으로 옮기지 않는다. 로컬 배포 성능을 말하려면 의도한 로컬 정밀도와 같은 정밀도로 서빙하는 제공자로 측정하거나, 그 정밀도로 짧은 확인 회차를 돌려 경향이 같은지 보인다. 통제의 정확성(E② 차단·감사)은 LLM 위치와 무관하다. 로컬 엔드포인트의 응답 1회는 연결 스모크로 기록한다. 완전 로컬 모드의 외부 LLM 송신 차단은 별도 음성 시험으로 검증한다. 실제 엔진의 profile/provider 선택·redirect·retry·fallback 경로에서 미등록 외부 LLM 연결을 시도해 **전송 전에 거부되고 실제 dial·외부 수신이 0건**이어야 합격이다([로컬 LLM HTTP 경계](../contracts/local-llm-http.md)). 현재 명시적 로컬 provider 경로의 보장과 기존 서버 선택/fallback의 미연결 범위를 구분해 기록하고, 아직 시험하지 않은 경로까지 차단 완료로 넓히지 않는다.

## 7. 특화점은 측정 후 결정 (미리 못박지 않음)
- **(A) 효율**: 같은 모델에서 확정까지 시간·총 요청 수 감소.
- **(정밀도)**: 오탐 감소 + 판정이 증거로 방어가능(UNDECIDABLE 남용 아님).
- **(B) 경량 생존** (후순위, 현재 측정 대상 아님): 7B급으로도 35B급 품질 유지 → "7B 생존 + 오탐↓". 지금은 35B 단일 태그 측정이 우선, 소형 모델 축은 뒤로.

> 높이는 것이지 탐지 개수를 직접 늘리지 않는다. recall로 자랑하지 않는다.
