## 1. 어느 상한이 먼저 걸리길 의도하나 (`first_limit`) [확정]

- **지금 상태**: 회차마다 `first_limit`(engine_completed / runner_request_budget / runner_time_budget / product_limit:<사유>)를 남기는 것까지 정했다(결정안 §3, [러너](runner.md)). 어느 상한을 의도하는지는 열려 있다(결정안 §10).
- **선택지**
  - (가) 러너 요청 예산이 먼저: 같은 대상 요청 수에서 무엇을 찾았는지 비교한다. 시간 예산은 안전 상한으로 둔다.
  - (나) 시간 예산이 먼저: 같은 시간에서 비교한다. 요청 예산은 크게 둔다.
  - (다) 엔진 완료가 먼저: 두 예산을 모두 크게 두고 엔진이 스스로 끝날 때까지 본다.
- **추천**: (가).
- **근거**
  - 계측기는 실제로 대상에 전달된 요청만 센다. E②가 거부한 요청은 세지 않으므로, 같은 전달 수 안에서의 비교에는 통제 비용(거부·보류)이 결과 차이로 드러난다.
  - 시간 기준은 O의 샌드박스·경계 지연이 그대로 섞인다.
  - (다)는 회차 길이와 비용을 미리 묶을 수 없다.
  - 파일럿(VAmPI, 600초·100건)에서는 1차 O와 재실행 B·O가 요청 예산으로 끝났다(재실행 B 140초, O 81초). 1차 B만 시간 예산으로 끝났는데, 엔진이 멈춘 뒤였다(결정안 §8).
- **결정(2026-11-17)**: (가). 시간 예산이 먼저 걸린 회차도 유효로 두되 `first_limit`별로 따로 집계한다. 제품 E② 상한이 먼저 걸리는 예외(§10)는 회차마다 `first_limit`로 확인한다. 공식 예산에서도 요청 예산이 먼저 걸리는지는 파일럿 기록으로 확인한다.
- **재확인(2026-11-18 사용자 결정)**: (가)를 유지하고 (다)(엔진 완료가 먼저)로 바꾸지 않는다.
  - 근거: 11/18 VAmPI 쌍에서 B는 요청 100 안에서 스스로 끝났고 O는 예산에 닿았다(§15). 그래서 "둘 다 엔진 진행으로 끝나는 예산"을 VAmPI에서 재서 정하면, 그 값은 VAmPI 크기에 묶인다. 공식 대상(Juice Shop)은 훨씬 커서 그 값으로는 모자라다. 그렇다고 Juice Shop에서 미리 재 보는 것은 시험 대상을 건드리는 일이라 하지 않는다(평가 정답·대상 사전 노출 금지와 같은 이유).
  - 그래서 공식 예산은 대상과 무관하게 정한다: 제품 기본 상한(회차 대상 요청 400·실행 1800초)에서 예약 여유를 뺀 값(§10).
  - 러너 예산을 제품 상한보다 낮게 두는 이유는 그대로다: 제품 E② 예약이 도착보다 앞서 예산을 써서 O만 먼저 걸리는 것을 막고(§10의 U − X > C − R 조건), B·O를 같은 기준(계측기가 센 전달 수·같은 시간)에서 끊는다.
  - 엔진이 예산 안에서 스스로 끝났는지는 회차마다 기록한다(`first_limit`의 `engine_completed`와 `engine_terminal_elapsed_seconds`, B는 엔진 끝 신호, O는 제품 끝 상태). 끝났는지는 성능 비교에 섞지 않고 따로 보고한다.

## 2. 멈춤 무효 T값 (`provider_fault_stall`) [180초 확정 — §19]

- **지금 상태**: **T = 180초로 확정했다(2026-11-19 사용자 동의, 근거는 §19 확인 쌍).** 무효 조건 셋은 결정안 §7(제공자 장애 기록 + 그 뒤 T초 동안 활동 사건 없음 + 엔진 끝 신호 없음, B·O 같게, 무효 수는 늘 기록)이고, 활동 사건은 요청 시작·응답 완료다(#756). 공식 회차는 `runner.json`의 `run.fault_stall_seconds: 180`으로 판정한다(official-run.md 0절·4절 7번).
- 아래 선택지·추천·근거·"파일럿 뒤 결정"은 **확정 전 제안 기록(이력)**이다. 값은 위 지금 상태를 따른다.
- **선택지(이력)**
  - (가) 정상 구간 최장 공백보다 크고, 관측된 멈춤 구간보다 작은 값에서 고른다.
  - (나) 원본 Planner 심장박동(600초)에 맞춘다.
- **추천(이력)**: (가). 정상 구간 최장 공백에는 대상 요청 없이 긴 명령을 도는 구간도 넣어 잰다(결정안 §7).
- **근거(이력)**
  - 그때 기록은 2쌍뿐이었다. 정상 최장 공백은 1차 B 2.0초·O 0.9초, 재실행 B 3.0초·O 0.9초였고, 1차 B의 멈춤은 약 359초였다.
  - (나)는 멈춘 회차가 심장박동까지 대상 요청 없이 남는 것을 그대로 받아들이는 값이라, 이 규칙을 둔 이유와 맞지 않는다.
- **파일럿 뒤 결정(이력, 끝남)**: 값은 공식 예산 확인 쌍 기록으로 정했다(§16 조건, §19 결과).

## 3. 무효 비율 상한 [규칙·값 확정 — 쪽별 2회, §16]

- **지금 상태**: **쪽별 `provider_fault_stall` 무효가 그 쪽 시도 중 2회 이상이면 측정 전체 실패로 확정했다(2026-11-19 사용자 동의, §16).** 러너 상한 전에 제공자 장애로 끝난 회차(`provider_fault_end`)도 같은 상한에 같이 센다(§26, 2026-11-21 사용자). E② 저널 게시 ACK 불명은 이 비율에 넣지 않고 §20대로 센다. 세션 집계(`session_runs.py`)가 종료 코드 3으로 멈춘다(#756). 평가 프로토콜 §5.1의 2N 규칙과 따로 둔다(§0). 아래 선택지·근거는 확정 전 제안 기록(이력)이다.
- **선택지**
  - (가) 2N 규칙만 둔다(조건 미완).
  - (나) `provider_fault_stall` 비율 상한만 둔다(측정 전체 실패).
  - (다) 둘 다 둔다. 2N은 모든 무효 사유에, 비율 상한은 `provider_fault_stall`에.
- **추천**: (다). **규칙은 확정(2026-11-17)**, 값은 파일럿 뒤.
- **근거**: 2N은 고장 난 조건을 계속 돌리지 않게 막는다. 비율 상한은 한쪽만 자주 깨질 때 그 회차들을 골라 남기는 효과를 막는다. 막는 대상이 서로 다르다.
- **파일럿 뒤 결정**: 비율 값. 지금은 2쌍뿐이라 근거가 없다.

## 4. 엔진 끝 신호가 오면 회차를 끝낼지 [확정]

- **지금 상태**: 러너는 끝 신호를 기록만 하고 회차를 일찍 끝내지 않는다([러너](runner.md), 결정안 §3.1). 이 동작을 바꿀지는 어느 문서에도 열린 항목으로 적혀 있지 않다.
- **선택지**
  - (가) 지금처럼 기록만 한다.
  - (나) 끝 신호를 받으면 드레인 뒤 회차를 끝낸다.
  - (다) 끝 신호 뒤 정해진 시간 동안 활동이 없을 때만 끝낸다.
- **추천**: (가).
- **근거**
  - (가)에서는 끝 신호의 진위가 결과에 영향을 주지 않는다. 신호가 틀려도 러너 상한까지 그대로 본다.
  - (나)·(다)는 비용을 줄이지만, 신호가 틀린 쪽(B 또는 O)의 회차만 짧아진다.
  - 재실행 파일럿에서 B 엔진은 봉인 뒤에도 모델 66번·대상 12번을 시도했다(결정안 §8). 활동이 끝났다고 보기 어려운 기록이다.

## 10. 예산·시간 [방향·값 확정(2026-11-18), O 모델 예산은 보정 쌍 뒤]

- **지금 상태**
  - 평가 프로토콜 §5.1은 시범 1200초·400건이고, 예산은 한 번만 조정한다.
  - 분리 배치의 공통 예산은 계측기 기준 두 입구 합이다(결정안 §3).
  - O 제품 상한은 기본값이다(회차 대상 요청 400, 실행 1800초).
  - O 모델 예산 값은 기록 방식만 정했고(결정안 §3.3) 공식 값이 없다.
- **추천**(방향은 §1 결정으로 확정)
  - **러너 상한이 먼저 걸리게 둔다**: 공통 요청 예산 R ≤ 제품 대상 요청 상한, 시간 예산 < 제품 실행 1800초.
    - 계측기 전달 수는 O의 E② 쪽 도착과 탐색 쪽 도착을 합한 값이다.
    - 제품 E② 예산은 정책 검사를 통과해 보내려고 예약한 요청을 센다(`e2proxy/execution.go`의 `Ledger.Reserve`, `transmit/budget/budget.go`). 예약은 연결 전에 되돌릴 수 없게 예산을 쓴다. 그래서 대상에 도착하지 않은 예약(연결 실패, 감사 ACK를 기다리는 진행 중 예약, 전송 전 취소 등)도 예산에 들어간다.
    - 따라서 R ≤ 제품 상한만으로 러너 상한이 먼저 걸린다고 보장할 수 없다. 제품 상한을 C, 도착하지 않은 E② 예약 수를 U, 탐색 쪽 도착 수를 X라 하자. E② 예약이 C에 닿는 순간 E② 쪽 도착은 C − U이고, 그때 러너 상한이 아직 안 걸렸다면 (C − U) + X < R이다. 즉 **U − X > C − R일 때 E② 상한이 먼저 걸린다**. R = C면 조건은 U > X이고, 도착이 0이어도 예약만으로 예산이 바닥날 수 있다(동찬님 리뷰 재현: R = C = 2에서 두 예약이 감사 ACK를 기다리는 동안 남은 예산 0). R < C면 두 상한의 차이 C − R만큼 여유가 생긴다(동찬님 리뷰 대조: C = 4·R = 2, U = 1·X = 0이면 러너 예산이 먼저 찬다).
    - 그렇게 걸리면 `product_limit`로 남고 통제 비용이 된다. 공식 예산을 정할 때는 C − R을 미도착 예약이 탐색 도착보다 많아질 수 있는 폭보다 크게 두고, 실제 `first_limit` 관측을 같이 반영한다.
  - **O 모델 예산은 러너 상한보다 늦게 걸릴 값으로 둔다**: 모델 예산이 먼저 걸리면 O만 일찍 멈춰 비교가 기울기 때문이다.

## 17. 끊긴 호출의 미확인 generation [확정(2026-11-19 사용자 결정), 정본은 평가 프로토콜 §6]

- 규칙: 회차를 멈출 때 진행 중이던 호출의 미확인 generation은 따로 세어 보고하고(`unverified_interrupted`) 회차를 무효로 하지 않는다. 정상 완료 호출의 미확인은 지금처럼 무효다. 정지와 상관없이 회차 중간에 실패한 호출은 예외에 들지 않는다.
- "끊긴 호출"은 기록으로 증명된 것만이다: 시작이 정지 신호 전, 응답 완료 기록 없음, 정지·봉인으로 끊김. 이 셋이 기록에 있어야 하고 추정으로 분류하지 않는다(B: 게이트웨이 `cancelled_by_seal`, O: 제품 정지 요청 뒤 `upstream_error`/`client_closed_before_done`). O 제품 호출 기록은 회차 근거로 남긴다.
- 근거: 끊긴 호출의 출력은 엔진이 같이 멈춰 회차 결과에 쓰이지 않는다. 그래서 그 호출의 제공자를 확인하지 못해도 결과에 들어간 출력의 제공자 고정은 흔들리지 않는다. 반면 정상 완료 호출은 출력이 결과에 쓰일 수 있어 미확인이면 무효로 둔다.
- **O 예외 보류(2026-11-19, #735 리뷰)**: 제품 전송기는 끊긴 호출(`upstream_error`/`client_closed_before_done`)에 generation ID를 남기지 않는다(ID는 응답을 끝까지 읽은 `forwarded`에만). 그래서 O에서는 끊긴 호출과 미확인 ID를 잇는 기록 근거가 없고, 근거가 생길 때까지 O의 미확인은 모두 무효 사유다. ## 26. 러너 상한 전에 일찍 끝난 회차 [확정(2026-11-21 사용자), 정본은 평가 프로토콜 §5.1]

- **배경**: 지금까지는 제품이 러너 상한 전에 `cancelled`·`failed`로 끝나도 `first_limit`이 `engine_completed`로 적혀 실제 끝 상태가 기록에 안 남았다. 일찍 끝난 회차를 유효로 둘지·무효로 뺄지 규칙도 없었다. 제공자 장애로 모델을 못 써서 끝난 회차는 제공자 멈춤(§2·§3)과 같은 부류인데 무활동 조건(§2)이 서지 않아 멈춤 무효로 빠지지 않았다.
- **끝 상태 기록**: `first_limit`은 엔진(제품)이 러너 상한보다 먼저 끝났을 때 정상 완료(B `done`·O `completed`)면 `engine_completed`, 그 밖의 끝 상태면 `engine_ended:<끝 상태>`다. 제품 예산 마감(`product_limit:budget_limited`)은 그대로다. 보존 기록(sidecar v3)도 같은 값으로 다시 계산해 대조한다.
- **분류(회차 디렉터리 `early-end.json`)** — 판정은 끝 상태와 그 회차 모델 호출 기록(B 게이트웨이 행, O 제품 호출 기록)을 같이 본다. 제품 초안에는 원인별 고정 코드(감독 실패 사유·모델 예산 사유)가 아직 없다. 그래서 끝 상태 + 호출 근거로 가르고, 제품이 원인 고정 코드를 싣게 되면 그 코드 조건을 더한다(개발 계획 '측정 뒤 다음 단계').
  1. **제공자 장애 끝 `provider_fault_end`(무효, 쪽별 멈춤 상한에 같이 셈)**: 러너 상한 전에 O가 `failed`·`unknown`으로(B는 `failed`로) 끝났고, 끝 직전 마지막 모델 호출(끝 시각까지 완료된 호출 중 마지막)이 제공자 오류(위쪽 끊김 `upstream_cut_*`·429·5xx)이며, 그 오류 뒤에 성공한(2xx로 끝까지 받은) 모델 호출이 없다(끝 뒤에 완료된 것까지 본다). 호출자가 먼저 닫은 행·봉인 때 게이트웨이가 끊은 행은 제공자 오류가 아니다. 호출 기록이 없거나 읽지 못하면 근거가 없는 것이라 빼지 않는다.
  2. **설정 오류 `config_end`(시도로 세지 않고 세션 멈춤)**: ① 모델 호출이 401·402·403·404를 받음(키·크레딧·권한·모델 이름, 끝 상태와 상관없이. 403도 설정 오류로 둔다(사용자 확정 2026-11-21). 403은 OpenRouter 검열(입력이 flagged)일 수도 있는데 호출 기록에 본문이 없어 가르지 못한다. 그래서 근거에 `moderation_possible`을 남기고, 측정 뒤 검토 때 검열로 확인되면 그 회차를 설정 오류로 다시 돌린 것이 회차를 고르는 효과일 수 있음을 결과 문서에 적는다) ② O 제품이 `budget_limited`로 마감했고 승인 장부 합계가 manifest 상한에 닿음(장부로 입증될 때만: 요청 수 ≥ `max_requests`, 또는 남은 비용 < 어떤 호출보다도 작은 예약(입력 4097토큰 = framing 4096 + 1바이트, 출력 1토큰을 manifest 단가로 올림, 제품 전송 계층과 같은 식). 다음 호출은 지난 호출보다 작을 수 있어 '지난 최대 예약보다 작음'은 근거로 쓰지 않는다(#831 리뷰). 입증되지 않으면 제품 예산 마감(유효, `product_limit:budget_limited`)으로 둔다) ③ 제품이 시작 전 설정 사유로 거부(`approval_expired`·`approval_required`·`approval_changed`·`budget_exhausted`·`target_not_approved`·`path_not_approved`·`target_approval_expired`, `busy`·`capacity`·`unavailable` 같은 일시 거부는 넣지 않음). 세션 기록에는 그 줄이 남고, 설정을 고친 뒤 `--resume`하면 같은 칸부터 잇는다.
  3. **그 밖에 일찍 끝남(유효)**: 실제 끝 상태·제품 사유·근거 종류를 기록하고 결과 보고에 드러낸다.
  - **준비 단계에서 끝나 실행 기록이 없는 회차(`product_not_executed`) [사용자 확정(2026-11-21): 무효 시도]**: 제품이 진단 실행 전(준비 단계 계획 실패 등)에 끝나면 제품 실행 기록이 없다(`diagnosis-run`이 `execution: NOT_RUN`, 준비 사용량이 없으면 404). 러너는 실행 기록을 요구하기 전에 위 1·2번을 먼저 가른다(준비 단계 401~404·제공자 오류도 같은 사유로 간다). 그 밖은 목표 SHA·모델 사용량이 없어 완료 기록(B·O 목표 SHA 대조)을 만들 수 없으므로 3번의 유효 회차로 세지 않고 `product_not_executed`로 무효(시도로 셈, 2N)로 둔다. `early-end.json`에 `ended_not_executed`로 남겨 목록에 따로 싣는다. 2026-11-21 합성 회차(계획 요청 503)에서 제품이 12초 만에 `failed/planning_failed`로 끝나 이 경로를 탔다.
- **우선순위**: 설정 오류 → 제공자 장애 멈춤(§2) → 제공자 장애 끝 → 모델 호출 검증 사유. 함께 난 사유는 뒤에 남긴다.
- **보고**: 세션 요약(`official_session.py` 마지막 줄 `early_end_runs`, `session_runs.py` 표)에 규칙이 걸린 회차를 회차 ID·쪽·분류·끝 상태·제품 사유·근거 호출(순번·결정·상태·끝 모양·시각)로 따로 싣는다. 측정 뒤 사용자가 하나씩 검토한다.
- **합성 확인(2026-11-21, 무료, #831 `d8ab5499`)**: 합성 O(제품 로컬 모델 설치)는 OpenRouter 호출 기록(근거 호출)이 없어 제공자 장애 끝(1번)·401~404 설정 오류(2번 ①)를 흉내 낼 수 없다. 이 둘은 실제 제품 호출 기록·게이트웨이 행 모양으로 만든 회차 흐름 시험(`test_runner_early_end.py`)으로만 확인한다. 합성 모델이 진단 Planner 요청에 503을 돌려주게 해서 본 것은 둘이다. ① 처음부터 503: 제품이 12초 만에 준비 단계에서 `failed/planning_failed`로 끝나 실행 기록이 없다 → `product_not_executed`, `early-end.json` `ended_not_executed`·`engine_ended:failed`·근거 없음(`ours-20261120t204806z-d07f47a1`, `ours-20261120t212335z-beee8495`). ② 준비 단계 계획 3번 통과 뒤 503: 실행 단계 계획이 계속 실패해도 제품은 스스로 끝나지 않고 러너 시간 상한까지 간다 → 완료·서명, `runner_time_budget`, 분류 없음(`ours-20261120t210554z-2d7091a2`). 그래서 '실패로 끝나 유효로 남는' 3번 회차는 제공자 오류로는 만들 수 없었다(실행 단계 실패로 끝나는 길은 엔진 작업 실패 `engine_task_failed`뿐이고 합성 모델로 일으키지 못했다).

## 27. 공식 측정의 E② v3 통제 대조 [끔 — 선언된 한계, 사용자 확정(2026-11-21)]

- **결정**: 이번 공식 측정에서는 O 회차의 E② v3 통제 대조(평가 v3 수집 #785: 회차별 감사 키로 E② Host 저널과 봉인된 최종 head를 꺼내 `e2-audit-verify --journal-format e2-http-v3`로 검증)를 켜지 않는다. 공식 `runner.json`에는 `split.e2_v3`를 넣지 않는다.
- **이유(켜려면 먼저 있어야 하는 것이 없다)**:
  - 제품 Host 저널은 `e2-host-state` 볼륨 `journals/<sha256("run-" + 초안 ID)>/events.jsonl`에 있다(E③ 흔적 수집 `runner_e3_traces`가 이미 읽는다). 그런데 v3 수집 설정 `split.e2_v3.subpath`는 `{draft_id}` 자리만 받아 이 해시 경로를 가리키지 못한다.
  - §20은 v3 수집을 열기 전에 ACK 불명 회차를 가를 시각 근거(계측기 기록으로 ACK 불명 시각 뒤 대상 요청 유무)를 먼저 구현하라고 정했다. 아직 없다.
- **이번 측정에 남는 것**: O의 E② 통제는 제품 안에서 그대로 집행된다(정책 지문·상한 스냅숏은 보존 sidecar v3 제품 블록에 서명). 계측기는 두 입구의 대상 요청을 모두 독립적으로 기록하고 하드 상한을 건다. E③ 흔적 수집은 Host 저널·제품 사본의 사건 종류·수를 센다(검증은 아님).
- **결과에 적는 한계**: "O 회차의 E② 저널 무결성(HMAC·체크포인트)과 봉인 head는 이번 측정에서 대조하지 않았다. 통제 효과 주장은 계측기 기록·제품 정책 지문·사건 수 근거로 한정한다." §20의 ACK 불명 규칙은 v3 수집을 끈 이번 측정에는 적용되지 않는다.
- **측정 뒤**: Host 경로 자리(해시된 실행 참조)와 §20 ①의 시각 근거를 구현한 뒤 v3 수집을 연다.
