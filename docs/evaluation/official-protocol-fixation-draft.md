## 1. 어느 상한이 먼저 걸리길 의도하나 (`first_limit`) [확정]

- **지금 상태**: 회차마다 `first_limit`(engine_completed / runner_request_budget / runner_time_budget / product_limit:<사유>)를 남기는 것까지 정했다(결정안 §3, [러너](runner.md)). 어느 상한을 의도하는지는 열려 있다(결정안 §10).
- **선택지**
  - (가) 러너 요청 예산이 먼저: 같은 대상 요청 수에서 무엇을 찾았는지 비교한다. 시간 예산은 안전 상한으로 둔다.
  - (나) 시간 예산이 먼저: 같은 시간에서 비교한다. 요청 예산은 크게 둔다.
  - (다) 엔진 완료가 먼저: 두 예산을 모두 크게 두고 엔진이 스스로 끝날 때까지 본다.
- **추천**: (가).
- **근거**
  - 계측기는 실제로 대상에 전달된 요청만 센다. E②가 거부한 요청은 세지 않으므로, 같은 전달 수 안에서의 비교에는 통제 비용(거부·보류)이 결과 차이로 드러난다.
  - 시간 기준은 O의 샌드박스·경계 지연이 그대로 섞인다.
  - (다)는 회차 길이와 비용을 미리 묶을 수 없다.
  - 파일럿(VAmPI, 600초·100건)에서는 1차 O와 재실행 B·O가 요청 예산으로 끝났다(재실행 B 140초, O 81초). 1차 B만 시간 예산으로 끝났는데, 엔진이 멈춘 뒤였다(결정안 §8).
- **결정(2026-11-17)**: (가). 시간 예산이 먼저 걸린 회차도 유효로 두되 `first_limit`별로 따로 집계한다. 제품 E② 상한이 먼저 걸리는 예외(§10)는 회차마다 `first_limit`로 확인한다. 공식 예산에서도 요청 예산이 먼저 걸리는지는 파일럿 기록으로 확인한다.
- **재확인(2026-11-18 사용자 결정)**: (가)를 유지하고 (다)(엔진 완료가 먼저)로 바꾸지 않는다.
  - 근거: 11/18 VAmPI 쌍에서 B는 요청 100 안에서 스스로 끝났고 O는 예산에 닿았다(§15). 그래서 "둘 다 엔진 진행으로 끝나는 예산"을 VAmPI에서 재서 정하면, 그 값은 VAmPI 크기에 묶인다. 공식 대상(Juice Shop)은 훨씬 커서 그 값으로는 모자라다. 그렇다고 Juice Shop에서 미리 재 보는 것은 시험 대상을 건드리는 일이라 하지 않는다(평가 정답·대상 사전 노출 금지와 같은 이유).
  - 그래서 공식 예산은 대상과 무관하게 정한다: 제품 기본 상한(회차 대상 요청 400·실행 1800초)에서 예약 여유를 뺀 값(§10).
  - 러너 예산을 제품 상한보다 낮게 두는 이유는 그대로다: 제품 E② 예약이 도착보다 앞서 예산을 써서 O만 먼저 걸리는 것을 막고(§10의 U − X > C − R 조건), B·O를 같은 기준(계측기가 센 전달 수·같은 시간)에서 끊는다.
  - 엔진이 예산 안에서 스스로 끝났는지는 회차마다 기록한다(`first_limit`의 `engine_completed`와 `engine_terminal_elapsed_seconds`, B는 엔진 끝 신호, O는 제품 끝 상태). 끝났는지는 성능 비교에 섞지 않고 따로 보고한다.

## 2. 멈춤 무효 T값 (`provider_fault_stall`) [파일럿 뒤]

- **지금 상태**: 무효 조건 셋은 정해졌다(결정안 §7: 제공자 장애 기록 + T초 동안 모델·대상 요청 0 + 엔진 끝 신호 없음, B·O 같게, 무효 수는 늘 기록). T값은 "파일럿 기록으로 정해 측정 전에 고정"으로 열려 있다. 결정안 §7은 아직 평가 프로토콜 §5.1로 옮기지 않았다.
- **선택지**
  - (가) 정상 구간 최장 공백보다 크고, 관측된 멈춤 구간보다 작은 값에서 고른다.
  - (나) 원본 Planner 심장박동(600초)에 맞춘다.
- **추천**: (가). 정상 구간 최장 공백에는 대상 요청 없이 긴 명령을 도는 구간도 넣어 잰다(결정안 §7).
- **근거**
  - 지금 기록은 2쌍뿐이다. 정상 최장 공백은 1차 B 2.0초·O 0.9초, 재실행 B 3.0초·O 0.9초였고, 1차 B의 멈춤은 약 359초였다.
  - (나)는 멈춘 회차가 심장박동까지 대상 요청 없이 남는 것을 그대로 받아들이는 값이라, 이 규칙을 둔 이유와 맞지 않는다.
- **파일럿 뒤 결정**: 값. 공식 예산의 파일럿에서 긴 명령 공백이 늘어날 수 있으니, 공식 예산 파일럿 기록으로 정한다.

## 3. 무효 비율 상한 [규칙 확정, 값은 파일럿 뒤]

- **지금 상태**: "쪽별 무효 비율이 상한을 넘으면 측정 전체 실패"까지 정했고(결정안 §7), 값은 파일럿 뒤로 열려 있다. 평가 프로토콜 §5.1의 2N 규칙과 다르다(§0).
- **선택지**
  - (가) 2N 규칙만 둔다(조건 미완).
  - (나) `provider_fault_stall` 비율 상한만 둔다(측정 전체 실패).
  - (다) 둘 다 둔다. 2N은 모든 무효 사유에, 비율 상한은 `provider_fault_stall`에.
- **추천**: (다). **규칙은 확정(2026-11-17)**, 값은 파일럿 뒤.
- **근거**: 2N은 고장 난 조건을 계속 돌리지 않게 막는다. 비율 상한은 한쪽만 자주 깨질 때 그 회차들을 골라 남기는 효과를 막는다. 막는 대상이 서로 다르다.
- **파일럿 뒤 결정**: 비율 값. 지금은 2쌍뿐이라 근거가 없다.

## 4. 엔진 끝 신호가 오면 회차를 끝낼지 [확정]

- **지금 상태**: 러너는 끝 신호를 기록만 하고 회차를 일찍 끝내지 않는다([러너](runner.md), 결정안 §3.1). 이 동작을 바꿀지는 어느 문서에도 열린 항목으로 적혀 있지 않다.
- **선택지**
  - (가) 지금처럼 기록만 한다.
  - (나) 끝 신호를 받으면 드레인 뒤 회차를 끝낸다.
  - (다) 끝 신호 뒤 정해진 시간 동안 활동이 없을 때만 끝낸다.
- **추천**: (가).
- **근거**
  - (가)에서는 끝 신호의 진위가 결과에 영향을 주지 않는다. 신호가 틀려도 러너 상한까지 그대로 본다.
  - (나)·(다)는 비용을 줄이지만, 신호가 틀린 쪽(B 또는 O)의 회차만 짧아진다.
  - 재실행 파일럿에서 B 엔진은 봉인 뒤에도 모델 66번·대상 12번을 시도했다(결정안 §8). 활동이 끝났다고 보기 어려운 기록이다.
- **결정(2026-11-17)**: (가). 끝 신호 뒤 남는 시간의 비용이 크면 (다)를 다시 본다.

## 5. 모델 목록 16KiB(`MaxSelectedDataBytes`) [확정]

- **지금 상태**: "측정 근거로 다시 정한다"가 공식 측정 고정 전 필수 항목이다(개발 계획). 지금 값은 공개 목록 상한이 64개이던 때 기준이다. 공개 목록은 이제 48KiB 바이트 절단이고 개수 상한은 256이다. 시험상 100바이트 경로 98개 중 92행만 들어간다. 프로세스 안 통합 시험(#670)은 공개 99·모델 91행·모델 목록에서 빠짐 8을 보였다.
- **선택지**
  - (가) 16KiB를 유지한다.
  - (나) 공개 목록 전부가 들어가게 올린다(공개 투영 48KiB에 맞춤).
  - (다) 모델 입력 토큰 예산에서 거꾸로 정한다.
- **추천**: (나). 단, 아래 근거의 측정을 먼저 한다.
- **근거**
  - 공개 목록은 이미 바이트로 묶여 있다. 고른 끝점을 모델 목록에서 또 빼면 모델이 승인 범위 안 끝점을 모른 채 돈다. 탐색 성능을 깎는 통제는 줄인다는 기조와 맞지 않는다.
  - 대신 Planner·Worker 호출마다 입력이 늘어난다. 이 증가량은 유료 호출 없이 합성 fixture로 바이트·토큰 수만 잴 수 있다.
- **결정(2026-11-17)**: (나). 상수를 바꾸기 전에 합성 fixture로 호출당 입력 증가량을 먼저 재고, 비용이 튀면 다시 본다. 상수 변경은 동찬님 리뷰를 받는다.

## 6. 경계 원자료 바이트 상한(`evidence_max_bytes`) [파일럿 뒤]

- **지금 상태**: 회차 정책이 정하고 코드 기본값은 없다([탐색 경계 계약](../contracts/exploration-boundary.md) §4.1). 상한에 닿은 회차는 `UNDECIDABLE / boundary_export_truncated`다([서명된 보존 원자료](preservation-signed-runs.md)). 러너 설정은 1GiB까지 받는다. 공식 값은 없다.
- **선택지**

## 10. 예산·시간 [방향·값 확정(2026-11-18), O 모델 예산은 보정 쌍 뒤]

- **지금 상태**
  - 평가 프로토콜 §5.1은 시범 1200초·400건이고, 예산은 한 번만 조정한다.
  - 분리 배치의 공통 예산은 계측기 기준 두 입구 합이다(결정안 §3).
  - O 제품 상한은 기본값이다(회차 대상 요청 400, 실행 1800초).
  - O 모델 예산 값은 기록 방식만 정했고(결정안 §3.3) 공식 값이 없다.
- **추천**(방향은 §1 결정으로 확정)
  - **러너 상한이 먼저 걸리게 둔다**: 공통 요청 예산 R ≤ 제품 대상 요청 상한, 시간 예산 < 제품 실행 1800초.
    - 계측기 전달 수는 O의 E② 쪽 도착과 탐색 쪽 도착을 합한 값이다.
    - 제품 E② 예산은 정책 검사를 통과해 보내려고 예약한 요청을 센다(`e2proxy/execution.go`의 `Ledger.Reserve`, `transmit/budget/budget.go`). 예약은 연결 전에 되돌릴 수 없게 예산을 쓴다. 그래서 대상에 도착하지 않은 예약(연결 실패, 감사 ACK를 기다리는 진행 중 예약, 전송 전 취소 등)도 예산에 들어간다.
    - 따라서 R ≤ 제품 상한만으로 러너 상한이 먼저 걸린다고 보장할 수 없다. 제품 상한을 C, 도착하지 않은 E② 예약 수를 U, 탐색 쪽 도착 수를 X라 하자. E② 예약이 C에 닿는 순간 E② 쪽 도착은 C − U이고, 그때 러너 상한이 아직 안 걸렸다면 (C − U) + X < R이다. 즉 **U − X > C − R일 때 E② 상한이 먼저 걸린다**. R = C면 조건은 U > X이고, 도착이 0이어도 예약만으로 예산이 바닥날 수 있다(동찬님 리뷰 재현: R = C = 2에서 두 예약이 감사 ACK를 기다리는 동안 남은 예산 0). R < C면 두 상한의 차이 C − R만큼 여유가 생긴다(동찬님 리뷰 대조: C = 4·R = 2, U = 1·X = 0이면 러너 예산이 먼저 찬다).
    - 그렇게 걸리면 `product_limit`로 남고 통제 비용이 된다. 공식 예산을 정할 때는 C − R을 미도착 예약이 탐색 도착보다 많아질 수 있는 폭보다 크게 두고, 실제 `first_limit` 관측을 같이 반영한다.
  - **O 모델 예산은 러너 상한보다 늦게 걸릴 값으로 둔다**: 모델 예산이 먼저 걸리면 O만 일찍 멈춰 비교가 기울기 때문이다.
- **파일럿 뒤 결정(남은 것)**: O 모델 예산 값만 남았다. 보정 쌍의 회차당 모델 호출·비용을 보고 정한다. (예산·시간의 '한 번 조정'은 아래 결정으로 끝났다.)
- **결정(2026-11-18 사용자)**: 공통 요청 예산 **300건**, 시간 **1500초**(평가 프로토콜 §5.1의 '한 번 조정'을 이 값으로 쓴다).
  - 근거: 대상 크기와 무관하게 제품 기본 상한에서 정한다(§1 재확인). 요청은 C = 400에서 예약 여유 100을 남긴 300이다. 여유 폭은 위의 U − X > C − R 조건에서 미도착 예약이 탐색 도착보다 많아질 수 있는 폭을 덮으려는 것이다. 시간은 제품 실행 1800초보다 작은 1500초다.
  - 11/18 VAmPI 쌍(요청 100)에서는 O 예산의 77/105가 탐색이라 진단 요청이 28건뿐이었다(§15). 300에서 진단 몫이 충분히 나오는지는 보정 쌍 3쌍(같은 300·1500초)에서 탐색 대 진단 비율로 본다.
  - O 모델 예산은 러너 상한보다 늦게 걸리게 두는 방향 그대로이고, 값은 보정 쌍의 회차당 모델 호출·비용을 보고 정한다.
  - 반영할 곳: 평가 프로토콜 §5.1 예산 문장, 공식 프로파일 `profiles/official-35b.json`(`time_budget_seconds`·`request_budget`, 지문 다시 고정), 공식 회차 절차. 보정 쌍 결과를 본 뒤 같은 PR로 바꾼다.

- **§2 T값 — 제안 180초.** 정상 구간 최장 공백은 이번 쌍 B 23.5초·O 65.2초(대상 요청만), 11/16 파일럿 3.0초이고, 관측한 멈춤은 11/16 B 1차의 359초 한 번이다. 180초는 관측한 정상 최대보다 크고 관측한 멈춤보다 작다. 확정 조건: 보정 쌍에서 O의 모델 호출 시각을 넣은 최장 공백을 재고(러너에 O 쪽 멈춤 집계를 넣는 것이 먼저다, R1), 그 최대가 T의 절반을 넘으면 다시 정한다.
- **§3 비율 값 — 제안: 쪽별 `provider_fault_stall` 무효가 그 쪽 시도 중 2회 이상이면 측정 전체 실패.** 2N 규칙(시도 6회까지)은 무효 3회까지 허용하는데, 같은 사유가 두 번 나오면 남은 회차가 '멈추지 않은 회차'만 골라진 것이 된다. 지금까지 이 조건에 해당하는 멈춤은 11/16 B 1차 한 번이고, 이번 쌍은 제공자 장애가 사실상 없었다. 빈도를 정할 근거는 없으므로 공식 세션 뒤 다시 본다.
- **§6 원자료 상한 — 제안 4 MiB(4,194,304바이트, 이번 러너 설정 값 그대로).** 이번 O 원자료는 그 상한의 1/167이다. 보정 쌍(요청 예산이 커짐)에서 다시 재고, 최대 크기가 상한의 1/4를 넘으면 올린다.
- **§8 `O-nomcp` — 제안: 보정 쌍까지 (가) 유지(돌리지 않음).** 이번 O에서 탐색 경계 전달 77건 중 브라우저 입구는 9건이다. 다만 MCP 출처 발견의 비중(결정 기준)은 지금 러너가 발견 출처별 수를 남기지 않아 보지 못했다. 러너가 O 회차의 발견 출처별 건수(브라우저·API Recon·크롤)를 남기게 한 뒤(R1), 보정 쌍에서 그 비중을 보고 정한다.
- **§10 예산·시간 — 이번 쌍에서 보인 것.**
  - 요청 예산 100에서는 O만 잘렸다. B는 90건을 쓰고 145초에 스스로 끝났고, O는 297초에 예산에 닿을 때 제품이 아직 진행 중이었다.
  - O 예산의 77/105가 탐색 입구였다. 그래서 같은 100건 안에서 O의 진단 요청(E② 본 입구)은 28건뿐이고, 이 예산으로는 O의 진단 능력이 거의 비교되지 않는다.
  - O 모델 예산(manifest 300건·$1)은 62건·$0.16을 써서 걸리지 않았다(§10 "모델 예산은 러너 상한보다 늦게" 충족).
  - 둘 다 엔진 진행으로 끝나는 예산(§1의 (다))은 O가 스스로 끝나는 요청 수를 아직 모르기 때문에 이 쌍으로는 정할 수 없다. §1 결정은 (가)(러너 요청 예산이 먼저)라서, (다)로 바꾸려면 §1을 다시 정해야 한다. → 2026-11-18 사용자 결정으로 (다)로 바꾸지 않고 공식 예산을 300건·1500초로 정했다(§1 재확인, §10 결정).
- **보정 쌍 — 3쌍(`B O O B B O`), 2026-11-18 사용자 승인으로 실행.** 아래 '3쌍 뒤 정할 것'의 처음 두 항목(예산 다시 고르기·§1 (다) 전환)은 이 쌍을 낸 때의 제안이었고, §1 재확인·§10 결정으로 대체됐다. 보정 쌍 뒤에는 확정값(300건·1500초)과 §1 (가)를 다시 고르지 않는다.
  - 공통 요청 예산 300, 시간 1500초로 돈다. 제품 상한 C는 기본값 400이고, §10 조건(C − R을 미도착 예약 폭보다 크게)에 따라 C보다 100 작게 잡았다. 시간 1500초는 제품 실행 1800초보다 작다.
  - 쌍마다 남길 것: 쪽별 `first_limit`, 엔진이 끝난 시점의 요청 수, 시간, 모델 호출 수·비용, 최장 공백(O는 모델 호출 시각 포함), 경계 원자료 크기, 입구별 전달, 발견 출처별 건수.
  - 3쌍 뒤 할 일(확정값·§1 (가)는 다시 고르지 않는다):
    - 쪽별 `first_limit`과 엔진이 예산 안에서 스스로 끝났는지를 확인해 기록한다. 끝났는지는 성능 비교에 섞지 않고 따로 보고한다.
    - O의 진단 몫(탐색 대 진단 전달 비율)이 300건에서 어떻게 나오는지 보고한다. 진단 몫이 작아도 예산을 다시 고르지 않고, 그 비율을 통제 비용과 함께 보고한다.
    - O 모델 예산 값, T·§3 비율·§6 상한·`O-nomcp`를 같은 3쌍으로 정한다.
  - 3쌍이 필요한 이유: 공식 반복 수 N=3과 같아 쪽별 분포를 처음 볼 수 있다. 무효 비율(§3)은 6회로도 빈도를 정할 수 없어 제안 규칙으로 두고 공식 세션 뒤 다시 본다.
