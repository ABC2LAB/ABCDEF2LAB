# 원본 ② 규칙 파일 (프로토콜 §8.1)

통제 효과 시연 A의 원본 ② 회차에 넣는 intercept 규칙 파일의 형식이다. 내용은 규칙 담당(윤재상, 리뷰 최민준)이 쓰고, 러너는 형식을 검사해 회차마다 새 엔진 DB에 넣는다. 레포에 실제 규칙 파일은 아직 없다.

## 형식

```json
{
  "format": "abc2lab.engine-intercept-rules/v1",
  "enabled_tools": null,
  "rules": [
    {
      "name": "example-rule",
      "priority": 100,
      "match_target": "tool_input",
      "match_type": "regex",
      "pattern": "example-pattern",
      "action": "deny",
      "message": "example"
    }
  ]
}
```

키는 위와 정확히 같아야 하고, 다른 키가 있으면 거부한다.

| 필드 | 규칙 |
|---|---|
| `enabled_tools` | `null`이면 엔진 기본 목록을 그대로 둔다. 목록이면 그 도구만 규칙을 탄다(비어 있으면 안 됨, 중복 금지) |
| `rules` | 1~512개 |
| `name` | 비어 있으면 안 됨. 파일 안에서 유일하고 내장 규칙 이름과도 달라야 함 |
| `priority` | 정수. 클수록 먼저 본다 |
| `match_target` | `tool_name`(도구 이름) 또는 `tool_input`(도구 입력 JSON 원문) |
| `match_type` | `string`(부분 일치) 또는 `regex`(Go RE2). 정규식 문법은 엔진이 등록 때 검사하고, 틀리면 그 회차는 `engine_rules_failed`로 무효다 |
| `pattern` | 비어 있으면 안 됨 |
| `action` | `deny` 또는 `allow`. `ask`는 쓸 수 없다. 사람이 답해야 끝나는데 회차에는 답할 사람이 없다 |
| `message` | 문자열(비어도 됨) |

러너가 규칙을 켠 채(`enabled=true`) 시간 제한 없이 등록한다. 그래서 파일에는 이 값들이 없다.

## 쓸 때 알아 둘 것

- **챌린지 목록을 보지 않고 쓴다(절대규칙 7).** 메서드 기준으로 일반적으로 만들고, 결과를 보기 전에 파일째 커밋한다.
- **평가 순서:** priority가 큰 규칙부터, 같으면 먼저 등록한 규칙부터 보고, 처음 맞은 규칙이 결정한다. 내장 규칙보다 priority가 높은 `allow`는 내장 규칙을 덮는다.
- **`tool_input`은 JSON 원문이다.** 정규식은 이스케이프된 문자열에 적용된다. 예를 들어 Bash 명령 안의 큰따옴표는 `\"`로 보인다.
- **`enabled_tools`에 없는 도구는 규칙을 타지 않는다.** 기본 목록은 `Bash`, `WebFetch`, `web_search`, `shell_open`, `shell_send`, `Write`, `Edit`, `MultiEdit`다(e53a79f 소스). 이 목록 밖의 도구로 나가는 요청은 막히지 않는다. 어떤 경로가 남는지 결과와 함께 공개한다.
- **패턴 기반이라 망 경계가 아니다.** 패턴에 안 맞는 표현은 지나간다. 새는 건수는 계측기 메서드별 건수로 드러난다.
- **LLM 판정(judge)은 이 파일로 켤 수 없다.** 기본값은 꺼짐이다. 켜야 하면 LLM 호출 수가 달라지므로 형식을 넓히기 전에 먼저 논의한다.

## 내장 규칙

새 엔진 DB에는 내장 규칙이 이미 있다. 실측(e53a79f 빌드, 11/06)으로 20개이고 19개가 켜져 있다. 러너는 이 규칙을 건드리지 않으므로 원본 ②는 원본 ① 기본 설정에 파일의 규칙을 더한 것이다. 내장 규칙에는 curl·wget·Python·스크립트의 DELETE 표현을 막는 패턴이 들어 있다(`db/db.go`).

## 러너 동작

1. 러너 설정 `engine_rules`에 파일 절대 경로를 넣는다. 조건마다 설정 파일을 따로 두고, 원본 회차에만 쓸 수 있다(개선 후면 `config.engine_rules: BASELINE_ONLY`).
2. 설정을 읽을 때 파일 형식을 검사하고 파일 바이트의 SHA-256을 잡는다.
3. 회차마다 pre 관측 뒤·실행 설정 스냅샷 전에 `POST /api/intercept/rules`(규칙마다 한 번), `PUT /api/intercept/tool-config`(목록이 있을 때)를 부른다. 다시 보내지 않는다.
4. 규칙과 도구 목록을 다시 읽어 내장 규칙 + 파일 규칙과 정확히 같은지 본다. 다르면 `engine_rules_failed`로 무효다.
5. 건수와 해시를 `engine-rules.json`(서명 근거)과 `runner-result.json`의 `engine_rules`에 남긴다. 규칙 본문은 남기지 않는다. 내용은 커밋한 파일이 정본이다.
6. 파일 해시는 회차 조건 `engine_rules_sha256`에도 들어간다. 채점기는 이 값이 다른 회차끼리 비교하지 않으므로 규칙을 넣은 원본 회차는 성능 비교표에 들어가지 못한다.

## 확인한 것과 안 한 것

- 실제 엔진(e53a79f 빌드)에 합성 규칙 2개를 넣은 회차가 완료·서명됐고, 다시 읽기 대조를 통과했다. 엔진이 거부하는 정규식은 작업 생성 전에 무효가 됐다.
- **규칙이 실제 도구 호출을 막는지는 아직 못 봤다.** 가짜 LLM은 도구를 호출하지 않는다. 실제 규칙 파일이 나오면 실제 LLM 회차로 확인한다.
