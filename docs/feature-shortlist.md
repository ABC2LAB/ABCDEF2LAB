# ABC2LAB — 개선안 & 개발 우선순위 (회의 결정 반영)

> **초기 개선안·회의 결정의 역사적 기록입니다.** 아래 Phase 순서, 사이드카 선택지와 GT 보류 문구는 현재 실행 지침이 아닙니다. 채택된 우선순위·Go 구현·역할은 [개발 계획](development-plan.md), 공식 평가 조건은 [평가 프로토콜](evaluation/evaluation-protocol.md), 현재 통합 범위는 [첫 진단 기동](first-diagnosis-launch.md)을 따릅니다. 후보 기능·기대 효과를 구현 완료나 실제 성능 검증으로 해석하지 않습니다.

> 구조: **base = ARTEX 광범위 탐지(알려진 CVE·주입·RCE 포함) 유지** + 우리 개선.
> **개선안을 3분류로 결정**: ① 이외의 개선 · ② 엔진 개선(핵심 기여) · ③ IDOR 특화.
> **개발 우선순위**: **이외 → 엔진 → IDOR.** (단 아래 주의 참고)
> 표기: ♻️ abc2lab-dast 재사용(설계·로직·테스트, Python→Go 포팅/사이드카) · 🆕 신규 · ⭐ thesis 코어.
> 상세 사유(불편→개선)는 `pain-points-to-improvements.md`, 도구 출처는 `ai-pentest-feature-inventory.md`.

## ⚠️ 우선순위 주의 (그대로 가되 이건 감안)
- **통제의 집행부는 엔진 ②(at-send)** — "이외"에 통제 설정/UI만 두면 집행 없는 설정이 됨. **통제 = 설정(이외) + 집행(엔진 ②) 세트.**
- **엔진이 핵심+최고난도** — "이외 전부 끝내고 엔진"은 위험. **빠른 이외(UI·로컬)만 먼저 → 엔진 일찍 진입 → 나머지 이외.**
- **IDOR는 간판 차별점** — 마지막이라도 **얇은 한 조각(수평 하나)은 발표 안에** 들어가게 역산.
- **GT 평가는 보류(드롭 아님)** — 엔진 개선 후 before/after 증명용으로 최소한은 필요.

## Phase 1 — ① 이외의 개선 (먼저)
- **1-1. UI 간소화(가리기)** 🆕 — enterprise/외부연동 화면 네비에서 숨김(companies·sync=ScopeSentry·연관작업·skills·notify·tools·mcp·llm-records). 백엔드 안 건드림(삭제 아님).
- **1-2. 완전 로컬 모드** 🆕⭐ — 완전 로컬 모드에서 외부 모델 API 0, 폐쇄망 완결. (ARTEX base_url로 로컬 지정 + 외부 송신 차단)
- **1-3. DLP(데이터 유출 방지)** 🆕(마스킹 ♻️) — 대상 민감데이터(PII·카드·자격증명·실응답)를 로그·감사·리포트로 안 흘리게 가림·최소수집. LLM 입력은 가리지 않는다(외부 API는 사전 승인, 승인할 수 없으면 완전 로컬).
- **1-4. 변조불가 감사 seal + run manifest** ♻️(seal 구현 있음) — 기록을 에이전트 손 밖에서 암호화·변조감지 + 통제 설정 전부 실행에 고정 기록. (※ARTEX에 작업·승인·증거 기록은 이미 있음 — 기본 수집 범위·누락 탐지 보강)
- **1-5. 커버리지 세분** 🆕 — ARTEX 커버리지 그래프를 계정×기능×검사항목별로. 회색=미검사 표기.
- **1-6. CVE 최신화** 🆕 — CVE DB 결정적 매칭(버전→후보) + private RAG(비정형 어드바이저리/조치) + 오프라인 피드 import. (CVE 매칭=후보 식별이지 확정 아님)
- **1-7. 모델 교체 + 출처 검증** ♻️(일부) — provider/base_url 교체 + 출처·해시 검증(무결성 확인, 백도어 부재 보장은 아님) + 소형모델용 엄격한 출력 스키마.
- **1-8. 통제 설정/UI** ♻️ — 범위·rate limit·kill-switch·dry-run·사람 승인·시간대. ※집행부는 엔진 ②와 세트.

## Phase 2 — ② 엔진 개선 (핵심 기여 · ARTEX Go 엔진 수술)
> 통합 흐름: **KG 후보 선택 → 허용·필요 증거 확인 → 최소 검사 실행 → 증거 판정 → 확정/추가/보류/종료.**
> 권장 내부 순서: **②③ 먼저(정확성·통제) → ①④(효율).** (그래야 요청 줄었을 때 "생략"인지 구분됨)
- **E②. 실제 전송 직전(at-send) 실행 통제** 🆕⭐ — 자산 규칙이 지금은 자산 등록·의도 생성 단계에만 적용됨(tools.go:1051). → **모든 egress(나가는 요청)가 모이는 MITM 프록시 길목**에서 대상·계정·행동·횟수 검사. **⚠️셸 도구(curl 등)가 우회하므로 반드시 프록시 계층에**(§6.5 버그 재현 방지). + 민감접근 필요 검사는 비민감 증거로 재계획.
- **E③. 구조화 증거 판정** 🆕⭐ — 재검증 저장이 지금은 판정값+설명·증거 문자열 검사(finding_retests.go:192). → **유형별 필수 증거 + 정상 대조를 구조화·강제**, 근거 부족하면 판단불가(UNDECIDABLE). (= 우리 오라클을 엔진에 내장)
- **E①. 탐색 종료·재계획** 🆕 — 기본 planner는 목표 미달성+할 일 없으면 새 의도 생성(planner.go:303). → **'검사 완료·발견 없음'·'증거 부족'·'정책상 검증 불가'를 명시 처리** → 불필요 반복 탐색 감소.
- **E④. 중복 검사·결과 재사용** 🆕 — 중복 판단이 의도 설명 비교에 의존(planner.go:335). → **계정·자원·요청조건·검사목적 기준 dedup + 유효 관찰 재사용**(⚠️상태변경·DB리셋 시 무효화) → 요청·LLM 호출 감소.
> ♻️ 연결: abc2lab-dast의 오라클·policy(at-send)·gateway **설계·로직·테스트가 E②·E③의 스펙**이 됨(Go로 재구현, 코드 drop-in 아님).

## Phase 3 — ③ IDOR 특화 (엔진 ②③·KG 위에 올림)
- **I-1. 소유·권한 KG** 🆕⭐ — 엔드포인트별 path+method+강제 authz 메커니즘 주석. 오라클의 정책·주체 입력원.
- **I-2. IDOR 검증기** ♻️⭐ — 다계정 비교 + setup-success 체크 + 파괴적op 마지막. [BOLABuster]
- **I-3. 접근통제 지도(Authorization Matrix)** 🆕⭐ — 신원×자원 격자. **수평(IDOR)+수직(BFLA/권한상승) 통합** = "인가 취약점 통합 진단". 회색=미검사, 집계·drill-down.
- **I-4. 표식 기반 확인(canary)** 🆕 — **실데이터 안 읽고** 표식된 비민감 자료로 교차 접근 확정 + 민감접근 보류·재계획(없으면 UNDECIDABLE).
- **I-5. ID 스킴 역공학(보조)** 🆕 — 소유한 유효 ID 확보+소유권 연결이 **중심**, ID 변형(약한 스킴)은 보조. verifier+펜스 bounded.

## 보류 (드롭 아님)
- **GT 평가 하네스** — 지금 안 함. 엔진 개선 후 before/after(확정까지 시간·요청수·오탐/미탐/판단불가) 증명용으로 최소한 필요.

## 설계 원칙
- LLM = 단일 스텝, 상태·지식은 결정적 컴포넌트(엔진 E①~④·오라클·KG·CVE DB)가 운반. → 로컬 모델 충분성(35B급)의 근거. 소형(7B급)까지 좁히는 건 후순위.
