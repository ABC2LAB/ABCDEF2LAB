## 1. 목표와 첫 완료 기준

**AI는 검사 후보를 제안하고, Go 엔진은 실행 가능 여부와 취약점 확정 여부를 결정한다.**

해결할 불편은 세 가지다. 어떤 요청을 보낼지 예측하기 어렵고, 발견의 근거가 약하며, 막히거나 이미 본 검사를 반복한다. E②·E③으로 통제와 판정부터 연결하고, 그 결과를 E①·E④의 종료·재사용에 이용한다.

첫 완료 기준은 범용 진단기 완성이 아니다. 운영자가 등록한 두 테스트 계정과 비민감 자료를 이용해 **인가 검사 한 건을 제안 → 전송 통제 → 증거 수집 → 판정 → 기록**까지 연결하는 것이다. KG 전체나 새 UI 완성을 기다리지 않고 같은 의미의 작은 등록 데이터로 시작한다.

| 구분 | 이번 초안의 범위 |
|---|---|
| 기존 확정 사항 | E②·E③ Go 구현, Python 사이드카 미채택, 초기 조회 중심 IDOR, 원본 baseline 선확보 |
| 이번 설계 제안 | 통제 모드의 전용 Go HTTP 실행 도구, 역할별 도구 허용 목록, 발견 저장 전 E③ 강제 |
| 첫 지원 대상 | 승인된 origin·등록 엔드포인트·테스트 소유 자료·등록 계정으로 수행하는 조회 시나리오 |
| 우선 제외 | 임의 셸, MCP, 커스텀 프로세스, 브라우저 자동화, 범용 크롤링, 자동 자산 정찰, 상태 변경 검사 |

도구를 제외하면 원본 ARTEX보다 검사 가능한 범위가 줄어든다. 이를 초기 통제 보장의 대가로 명시하고, 지원 경로를 검증할 때마다 확장한다. 전체 호스트·전체 네트워크의 통제를 달성했다고 표현하지 않는다.

## 3. 전체 흐름과 경계

```text
운영자: 검사 범위·계정·예산·시험 자료 등록
             ↓ 버전이 고정된 실행 정책
LLM/planner: 검사 후보 제안
             ↓ 등록 참조를 담은 실행 계획
E②: 문맥·범위·행동·승인·예산·중지 확인
             ├ 차단/보류 → 사유 기록 → 안전한 대안 또는 종료
             ↓ 허용
전용 Go HTTP 실행기 → 승인된 대상
             ↓ 실행 영수증 + 비밀값을 제거한 구조화 증거
E③: 계정·자료 소유·기대 권한·정상 대조·표식 비교
             ↓ 확정/의심/판단불가 또는 위반 미관찰
기존 그래프·발견 저장·감사·결과 UI
             ↓
E① 종료/재계획 · E④ 중복 방지/관찰 재사용
```

자산 발견이나 KG 열람은 실행 허가가 아니다. LLM이 등록한 scope나 추정한 소유 관계가 운영자 정책을 넓힐 수도 없다. KG에는 관찰·추정·운영자 확인의 출처를 남긴다.

## 4. E② — 실제 전송 통제

### 4.1 첫 실행 경로: 전용 Go HTTP 도구

**제안:** 프록시만 고치는 접근보다, 처음에는 엔진이 직접 요청을 구성하는 전용 Go HTTP 도구를 만든다. 작업·의도 문맥과 계정 참조를 유지한 채 전송 직전 검사할 수 있기 때문이다. 기존 MITM은 기록·표시를 재사용할 후보이며, 유일한 권한 판정기로 삼지 않는다.

- 통제 모드는 서버가 작업 시작 때 고정한다. 모델·프롬프트·도구 호출로 일반 모드로 바꿀 수 없다.
- worker는 허용한 도메인 도구와 전용 HTTP 도구만 받는다. 파일·셸·기본 네트워크 도구와 임의 tool augmentation은 제외한다.
- planner·mainagent에도 같은 원칙을 적용하며, 작업에 연결되는 대화·재검증·보고 역할도 도구 목록을 점검한다. 작업 밖 chat이 같은 자격증명·실행 권한으로 대상에 접근하는 경로도 차단하거나 운영상 격리한다.
- DB 도구 조회 실패나 알 수 없는 MCP·host 도구는 통제 모드에서 허용하지 않는다. 이름만 같은 다른 구현으로 바뀌는 경로도 막는다.
- 도구 표시와 실행 허용을 분리한다. 허용 목록 밖 도구는 직접 호출·지연 로딩·다른 역할 경유로 들어와도 통제 실행 문맥에서 거부한다. 첫 시험 프로세스에서는 일반 모드 작업·별도 스케줄 작업을 함께 돌리지 않는다.
- enrichment는 `nil`로 주입한다. 나머지 백그라운드 네트워크 기능도 목록화하여 비활성화 또는 별도 검증한다.
- 로컬 모델·DB 등 필수 관리 통신은 대상 검사 통신과 구분하여 고정한다. 이 설정만으로 외부 송신 차단이 완료됐다고 주장하지 않는다.

이는 **지원 도구 경로의 통제**다. 임의 코드를 실행할 수 있는 권한이나 다른 호스트 프로세스까지 제한하려면 별도의 OS·컨테이너 네트워크 격리가 필요하다. 그 전에는 셸·MCP를 다시 노출하지 않는다.

### 4.2 전송 직전 검사

1. **실행 문맥:** 작업·의도·실행 주체를 서버 문맥으로 확인한다. 계정 참조가 해당 작업에 등록됐는지도 검사한다.
2. **대상:** scheme·host·port와 실제 경로·쿼리·행동을 검사한다. URL 해석 차이, Host 헤더 불일치, DNS 재바인딩을 고려해 연결 대상도 승인 범위에 묶는다. localhost·사설 IP는 시험 대상일 수 있으므로 무조건 차단하지 않고 등록 범위로 판단한다.
3. **행동:** 등록된 조회 시나리오만 허용한다. GET만으로 무해하다고 판단하지 않으며, 알 수 없는 행동·상태 변경·원문 덤프는 보류한다.
4. **승인:** 승인이 필요한 경우 실제 요청 내용과 정책 버전에 묶는다. 승인 뒤 URL·계정·파라미터가 바뀌면 다시 판단한다.
5. **예산:** 작업별 횟수·속도·동시성·시간 예산을 원자적으로 확인하고 예약한다. 실제 전송 시작 건수와 차단 건수는 따로 센다.
6. **중지:** pause/kill·정책 버전 변경 이후의 신규 전송을 막는다. 승인 대기·예산 대기 중인 요청도 재검사한다.
7. **기록:** 전송 의도 기록이 성공한 후 전송한다. 필수 감사 저장이 실패하면 새 전송을 중단한다. 전송 후 기록 실패는 이미 보낸 사실을 취소하지 못하므로 미완료 영수증과 중단 사유로 남긴다.

최종 요청은 검사한 뒤 다른 코드가 수정하지 못하게 한다. 자격증명은 실행기 내부에서만 주입하고, 그 뒤에도 등록된 계정·origin 바인딩이 유지되는지 확인한다. 인증 원문은 LLM·계약 JSON·공유 로그·근거 파일에 남기지 않는다.

### 4.3 리다이렉트·재시도·취소

첫 버전은 자동 리다이렉트와 애플리케이션 재시도를 끄는 쪽을 권고한다. HTTP/1.1 새 연결 중심의 작은 transport로 시작하고, 라이브러리 내부 재전송도 없는지 대상 수신 건수로 확인한다. 재시도를 지원할 때는 매번 새 전송 판단과 예산 차감이 필요하다.

Go `Client`는 redirect 전 검사 훅을 제공하지만 `Transport` 내부에서는 조건부 자동 retry가 가능하다. 따라서 `Client.Do` 호출 횟수만으로 실제 전송 횟수를 주장하지 않는다. [공식 Client 문서](https://pkg.go.dev/net/http@go1.26.3#Client), [공식 Transport 문서](https://pkg.go.dev/net/http@go1.26.3#Transport).

최초 통합 시험은 로컬 HTTP로 진행한다. HTTPS는 같은 실행기의 TLS 암호화 전 검사와 인증서 검증을 시험한 뒤 지원 표에 추가한다. CONNECT 터널의 존재만으로 HTTPS 내부 요청을 검사했다고 표현하지 않는다.

중지는 신규 전송을 차단한다. 이미 전송된 요청의 서버 처리나 부작용을 되돌린다는 뜻은 아니다. 송신 여부가 불명확한 오류·응답 유실은 `미실행`으로 바꾸지 않는다. Context가 제어하는 범위는 연결·송신·응답 수명이다. [공식 Request 문서](https://pkg.go.dev/net/http@go1.26.3#Request.Context).

## 5. E③ — 구조화 증거로 확정

### 5.1 IDOR 한 유형부터

LLM은 후보와 설명을 만든다. 판정기는 아래 증거의 참조·출처·동일 조건 여부를 프로그램으로 확인한다. 모델이 제출한 `is_owner=true`나 `auth_ok=true` 같은 값은 증거가 아니다.

| 필수 증거 | 확인할 내용 |
|---|---|
| 시험 자료 | 운영자가 허용한 시험 자료이며 A 소유, 비민감 표식이 등록됨 |
| A 정상 대조 | A가 같은 기능 경로에서 자기 표식을 읽을 수 있음 |
| B 정상 대조 | B의 인증이 유효하며 B 자신의 자료를 정상 조회할 수 있음 |
| 기대 권한 | B→A 자료 조회는 애플리케이션 정책상 금지라는 신뢰 가능한 설정·근거가 있음 |
| 교차 조회 | 실제 B의 자격증명으로 A의 등록 자료를 요청했다는 실행 영수증이 있음 |
| 자료 일치 | 응답의 자료 필드에서 A의 표식 확인. 요청 ID 반사·공통 화면·오류 템플릿은 제외 |
| 비교 조건 | 같은 작업·대상 초기화 세대·정책 버전·엔드포인트·자료 상태에 속함 |

**시험 실행 허가와 애플리케이션의 기대 권한은 다른 정책이다.** 운영자는 B→A의 합성 자료 조회 시험을 허가할 수 있고, 동시에 서비스는 그 접근을 거부해야 한다. 이를 섞으면 IDOR 시험 자체를 모두 차단하게 된다.

### 5.2 결과를 세 층으로 분리

- **실행:** 차단·미송신·응답 수신·전송 여부 불명 등. 실제 전송 영수증에서 결정한다.
- **취약점 판정:** 기존 방향인 `CONFIRMED / SUSPECTED / UNDECIDABLE`를 유지한다. 단순 모델 제보는 아직 판정 전 후보다. `SUSPECTED`의 구체적 증거 조건은 최민준 스펙으로 확정한다.
- **검사 결과:** 유효한 대조와 정상적인 접근 거부로 위반이 관찰되지 않은 경우, `이 검사에서 위반 미관찰`을 기록한다. 취약점 발견으로 만들거나 전체 서비스가 안전하다고 일반화하지 않는다.

**저장 제안:** 검사별 구조화 판정 레코드 하나를 별도로 두고 이를 원본으로 삼는다. 의미 필드는 작업·의도·검사 키, 정책 버전·대상 초기화 세대, 계정/자료 참조, 실행 영수증, 검사 결과, 취약점 판정(없을 수 있음), 사유·증거 참조다. 실제 테이블명·마이그레이션은 최민준과 구현 전에 맞춘다.

| 결과 | 구조화 판정 기록 | 기존 발견 저장 |
|---|---|---|
| 확정 | `CONFIRMED` + 필수 증거 참조 | 해당 판정에 연결된 confirmed finding 생성 |
| 의심 | `SUSPECTED` + 충족/부족한 조건 | confirmed 생성 금지. 필요하면 hint로 연결 |
| 판단불가 | `UNDECIDABLE` + 정책 차단/증거 부족/미지원 등 사유 | confirmed 생성 금지. 필요하면 hint로 연결 |
| 위반 미관찰 | 검사 완료 결과 + 유효한 대조·거부 증거, 취약점 판정은 비워 둠 | finding 생성 금지 |

hint/fact나 UI 문구는 이 원본의 보조 표현이다. 별도의 네 번째 취약점 판정을 추가하거나 기존 DB 상태 enum을 전면 교체하지 않는다. 기존 재검증의 `reproduced/fixed/inconclusive`도 별도 유지한다. 재검증의 `fixed`는 앞선 확정과 비교 가능한 조건·정상 대조가 확인됐을 때만 매핑하고, 일반 음성 결과를 자동으로 `fixed`로 바꾸지 않는다.

### 5.3 발견 저장 전 강제

`report_finding` → recorder 또는 fallback → `RecordFindingTx`의 모든 경로를 점검한다. **최하위 확정 저장 함수가 통제 작업인지 DB의 서버 관리 설정에서 확인**하고, 동일 트랜잭션에서 해당 작업·의도·검사·증거 버전에 속하는 `CONFIRMED` 판정 참조를 검증하도록 한다. 이 조건을 상위 도구가 호출 순서로 지켜 줄 것이라고 가정하지 않는다.

판정 레코드는 서버 평가기만 발급한다. 모델이 준 판정 ID만으로 허용하지 않으며, 다른 작업의 ID·이전 증거의 ID는 거부한다. 같은 판정으로 중복 finding을 만들지 않고, 동일한 발행 요청의 재전달은 기존 결과를 반환한다. 통제 작업의 정책 연결이 없거나 조회에 실패해도 일반 모드로 간주하지 않는다. 판단기 누락·오류·미지원 유형은 기존 `confirmed` fallback으로 내려가지 않는다. 일반 노드 삽입·API 등 다른 확정 저장 경로도 같은 불변조건에 포함한다.

판정 전 후보·증거 부족은 기존 hint/fact 등을 활용하되, 확정 finding 수에 섞이지 않게 한다. 재검증도 같은 증거 평가를 호출하고, UI·리포트에는 실행 사실과 판정 근거를 함께 전달한다. DB 최하위 저장 함수와 다른 API 호출자가 우회하지 못하는지도 통합 시험으로 확인한다.

## 6. 민감정보를 읽지 않는 대안 검증

1. 민감 자료·소유 미확인 ID를 읽어야 하는 후보는 **요청 전** 보류한다.
2. 같은 엔드포인트·동일한 권한 검사 경로에서 등록 계정이 가진 시험 자료와 유효 ID를 찾는다.
3. 비민감 표식으로 대체하고 정상 대조·교차 조회를 수행한다. 임의 UUID 복호화나 실제 타인 ID 추측을 전제로 하지 않는다.
4. 같은 취약 조건을 재현하지 못하면 `정책상 검증 불가/UNDECIDABLE`로 남긴다. 다른 경로에서의 성공으로 원래 후보를 확정하지 않는다.

표식 자료 생성은 초기 준비 단계에서 운영자·fixture가 담당한다. 첫 엔진 경로가 허가받지 않은 쓰기 요청까지 수행하도록 늘리지 않는다. 실제 앱의 URL·계정 ID는 설정·fixture에 두고 제품 코드에 하드코딩하지 않는다.

응답을 받은 뒤 마스킹하는 DLP는 저장·공유 노출을 줄이는 보조 수단이다. 모델로 가는 내용은 가리지 않는다. 이미 민감 응답을 받았다면 `민감 자료 미접근`이라고 표현할 수 없다. 알려지지 않은 웹 전체를 읽으면서 민감정보에 전혀 접촉하지 않는 보장도 이번 범위 밖이다.

## 7. E①·E④ — 정확한 결과 위에서 효율 개선

**E①:** 초기 통합 때도 차단·증거 부족·응답 유실 이유를 planner에 구조화해 돌려준다. 같은 정책 차단을 WAF처럼 우회하도록 시키지 않는다. 동등한 안전 대안이 없으면 종료한다. 이후 검사 단위 완료·예산 소진·정책상 검증 불가를 추가해, finding이 없어도 유효한 검사 완료가 가능하게 한다. 기존 목표/타임아웃 종료와 조화시킨다. [현재 계획 루프](https://github.com/ABC2LAB/ABCDEF2LAB/blob/8e9b69047feb07c9905c14751b3b0b4460fa14d0/agent/planner.go#L303), [엔진 종료 처리](https://github.com/ABC2LAB/ABCDEF2LAB/blob/8e9b69047feb07c9905c14751b3b0b4460fa14d0/server/engine.go#L865).

**E④:** URL만으로 중복 판단하지 않는다. 작업·계정·역할·자료·동작·파라미터·검사 목적·정책 버전·대상 초기화 세대를 포함한다. 비교용 A/B 요청과 재현은 중복으로 없애지 않는다. 세션·자료·권한이 바뀌면 관련 관찰을 무효화한다. [현재 중복 처리](https://github.com/ABC2LAB/ABCDEF2LAB/blob/8e9b69047feb07c9905c14751b3b0b4460fa14d0/agent/planner.go#L335).

두 개선의 효과는 같은 평가 조건에서 중복 전송 수, 확정까지 시간, 요청 수, 판단불가 비율로 측정한다. 요청 수 감소만으로 탐지력이 좋아졌다고 판단하지 않는다.

## 8. 새로 합의할 작은 계약과 역할

아래는 **제안하는 의미 필드**다. ARTEX 전체 타입을 대체하는 새 계약 체계를 만들지 않는다.

| 경계 | 최소 합의 | 담당 |
|---|---|---|
| 후보 → E② | endpoint/resource/principal 참조, 조회 행동, 제한된 파라미터, 검사 목적. 작업·의도·정책 버전은 서버가 바인딩 | 이동찬 ↔ 최민준 |
| 통제 UI → E② | 승인 범위·예산·중지·정책 버전. 모델이 수정할 수 없는 원본 | 이동찬 ↔ 이경준 |
| 실행기 → E③ | attempt ID, 실제 계정 참조·요청 식별, 송신/응답 상태, 비밀값 제거 증거 ID, 대상 초기화 세대 | 이동찬 ↔ 최민준 |
| KG/fixture → E③ | 소유·기대 권한·표식 참조와 근거 출처. 추정은 확정 사실과 구분 | 최민준 ↔ 이경준, 이동찬 통합 |
| E③ → 저장/UI | 판정, 사유, 증거 참조, 부족 항목, 검사 완료 상태 | 이동찬·최민준 ↔ 이경준 |

인증 비밀값을 기존 traffic/evidence/LLM 기록이 다시 저장하지 않는지 경계별로 검사한다. 기록에는 동일한 attempt ID를 유지하고 권한 분리·변조 탐지를 붙인다. 해시만 계산했다고 에이전트가 바꿀 수 없는 기록이 되는 것은 아니다.

| 순서 | 작업·주요 수정 후보 | 완료 기준 |
|---|---|---|
| 0 | 원본 소스 구동·평가 조건 고정·baseline | 엔진 변경 전 실행 조건과 1회 결과 보존. 평가기는 정답 목록을 알고 에이전트는 모름 |

## 10. 검증 계획과 남는 위험

아래 시험은 **구현 후 수행할 계획**이며 아직 실행하지 않았다.

| 시험 | 기대 결과 |
|---|---|
| 범위 밖 origin·다른 포트·미등록 계정·변경된 승인 요청 | 대상 수신 0, 차단 사유 기록 |
| 외부로 redirect·예산 초과·정책 조회 실패 | 다음 대상 수신 0, 기존 허용으로 fallback하지 않음 |
| pause/kill과 동시 요청·정책 변경 경쟁 | 중지/변경 경계 이후 신규 전송 시작 0. 이미 시작된 요청은 별도 기록 |
| 동시 실행의 요청 예산 경쟁 | 허용 상한을 초과한 전송 0. 대상 수신 건수와 attempt 집계 대조 |
| 재사용 연결 오류·응답 유실 | 숨은 재전송 여부를 수신 측에서 검증. 미실행/정상으로 오기록하지 않음 |
| Bash·MCP·host/custom tool 재주입, 도구 DB 장애 | 통제 프로필의 허용 목록 유지. 무문맥 실행 거부 |
| 취약/정상/공유 허용 자료·만료된 B 인증·ID 반사·공통 200 응답 | 각 판정 규칙대로 구분. 200 단독 확정 0 |
| E③ 누락·장애·미지원 유형·직접 저장·다른 작업 판정 ID·증거 변경 | 근거 없는 confirmed 생성 0. 구조화 판정 결과와 부족 사유는 보존 |
| 비밀값 sentinel을 인증·응답에 삽입 | 전달 JSON·LLM 입력·공유 로그·근거 파일에 원문 0 |
| 같은 URL의 다른 계정/자료·대상 reset·권한 변경 | 필요한 비교 요청 유지, 오래된 증거 재사용 0 |

정책/오라클 단위 시험 → `httptest` 기반 전송 시험 → DB 포함 저장 경계 시험 → 격리된 소유 로컬 대상의 얇은 통합 순서로 확인한다. Go 코드 변경 시 gofmt·관련 테스트·go vet·소스 빌드를 수행하고, 동시성 변경에는 race 검사를 포함한다.

주요 위험은 허용 목록 때문에 탐색력이 감소하는 것, 정상 대조가 약해 판정이 부풀려지는 것, 기존 기록기에 비밀값이 남는 것, E②·E③ 변경 효과가 평가에서 섞이는 것이다. 각각 지원 범위 공개·대조 시험·경계별 비밀값 시험·기능별 비교 실험으로 확인한다.

baseline과 개선 후에는 소스 SHA, 모델 태그·설정, 대상 이미지·reset, 범위·계정·초기 자료, 시간·요청 예산, worker 수, 하드웨어와 기록 방법을 고정한다. 구형 기록기의 누락을 0건으로 세지 않는다. 필요하면 전후 동일한 대상 측 계측을 추가해 다시 기준 실행한다. 공통 지원 범위의 탐지 성능과 통제 모드의 제한 효과도 구분한다.

finding 제목 매핑만으로 정답을 판단하지 않는다. 선정한 Juice Shop 챌린지의 실제 해결 상태와 요청·응답 증거를 평가기에서 확인한다. 미매핑 finding이나 미해결 챌린지를 곧바로 오탐/미탐으로 세지 않는다. 첫 1회는 구동·계측 확인용이며 성능 주장은 동일 조건 반복 실행 후에 한다.
