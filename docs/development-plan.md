## 현재 제품 목표와 구현 상태 (2026-11-08)

최종 목표는 **고객 내부망에 설치하는 온프레미스 AI DAST**다. 승인된 웹서비스에서 여러 유형의
취약 가능성을 탐색하고 실제 관찰 근거를 수집한다. IDOR는 초기 집중 유형이자 별도 증거 기반 확정
경로이며 제품 전체 범위가 아니다. 인가·비즈니스 로직의 초기 특화 방향은 유지하며, 이 설명 정비로
아래 Phase·역할·일정·축소 순서를 변경하거나 광범위 유형의 구현을 우선하지 않는다.

2026-11-08 확인 시점의 코드 스냅샷은 `origin/dev`의 `d2bfec57f34dae1c17b6026366e747f3a588750b`이며 #317·#323·#325가 반영돼 있다.
새 작업은 최신 `origin/dev`의 정확한 SHA와 적용 계약을 다시 확인한다.
위 #183·#189·#191은 모두 11/05 병합됐으며 현재 기준 커밋에 포함된다. 위 효력 조건과 아래 포크 코드 설명은 결정 이력이다. 현재 실행 통제·판정·평가 기준은
[문서·계약 목차](README.md#구현-경계와-계약)와 [평가 프로토콜](evaluation/evaluation-protocol.md)을 따른다.

### Workbench 단일화 구현 제안 (2026-11-10, 담당자 동의 전)

[#353](https://github.com/ABC2LAB/ABCDEF2LAB/pull/353)은 이동찬의 제품 요청에 따라 Workbench를 `/`의 단일 UI로 연결하고 중복 ABC2LabUI·목업·v1 화면을 제거한 구현 제안이다. **팀의 삭제 동의나 12/18 시연 화면 확정은 아직 아니다.** 이경준의 ABC2LabUI·공용 계약과 윤재상의 Workbench 영역은 해당 담당자가 이관·제외 범위를 명시적으로 검토해야 한다. 최민준의 최종 승인도 별도로 필요하다.

[단일화 검토안](contracts/workbench-consolidation-review.md)에 삭제/이관 실측, 미이관 기능, 서버·Docker와 UI의 검토 범위를 기록했다. 요청별 승인 조작 UI가 없는 모드는 새 시작을 차단하며 지도·KG·세부 커버리지·전체 관리 화면의 동등성을 주장하지 않는다. 기존 Phase·역할·시연 일정은 이 제안만으로 변경하지 않는다.

### 회차별 대상 승인 정책 (2026-11-10 제안, 2026-11-11 팀 합의)

#353의 설치 시 대상 고정과 별도로 Workbench 운영자가 DNS 소유·진단 권한·읽기 범위를 확인해 회차별 대상을 승인하는 후속 구현을 분리했다. 공개 HTTPS 호스트로 대상 권위가 넓어지는 정책 변경이라 [권한 모델·접촉·감사](contracts/product-target-approval-proposal.md)를 따로 검토했고, 11/11 팀 합의로 채택했다. 개발팀은 코드로 넘을 수 없는 한계를 고정하고, 설치 조직이 `target_policy`로 상한을 정하며, 로그인한 운영자가 DNS 소유 증명과 본인 진술로 회차별 대상을 등록·승인한다. CLAUDE.md 절대 규칙 1이 이 구조를 따른다. 이 채택은 특정 공개 사이트를 진단해도 된다는 승인이 아니고, 실제 대상은 회차마다 이 절차와 고객사 승인을 거친다. #353의 UI 삭제 동의와는 별개다.

- **유지하는 통제**: 진단 요청에 대한 E②의 어디로(승인 origin·IP·경로·리다이렉트)·무엇을(승인 메서드·쓰기 범위, 위험 요청 차단)·얼마나(예산·시간·동시성)·감사, TLS 검증, 실행 격리, 권한 결속, 제어 비밀(LLM API 키·E② 권한 토큰·감사 키·러너 서명 키·CA 개인키·관리 API 토큰)과 E③ 판정 표식 보호.
- **새 송신을 멈추는 경우**: 운영자의 중지·실행 취소는 새 송신을 막고, 일시정지는 같은 권한 결속을 유지한 채 재개 전까지 신규 전송·모델 호출 admission을 대기시킨다(권한 철회와 다른 사건). 운영자 조작 밖에서 자동으로 새 송신을 멈추는 경우는 감사 저장 실패, E② 집행 장애, 격리 실패, 권한 철회·만료·결속 실패, 승인된 요청·시간·비용 예산 소진뿐이다. 요청 하나의 범위 밖 거부·연결 실패·미지원·일시 오류는 그 요청만 실패한다. 상태 변경 요청의 결과가 불명이면 그 요청을 자동으로 다시 보내지 않고, 그 요청에 기대는 후속 요청만 상태 확인 전까지 보류한다.
- **계정(결정 11/11, 효력은 계정 분류 기능과 수용시험 S09·탐색 계약 §8 개정이 함께 들어온 뒤)**: 그 전까지는 현행 S09(심어 둔 비밀번호·토큰 표식이 모델 입력·로그·근거 파일에 없다)를 그대로 지킨다.
  - 효력이 생긴 뒤에는 모델 입력과 도구 출력에 `시험 계정` 표시가 붙은 소유·승인된 일회용 시험 계정의 세션만 허용한다. 표시는 모델·도구가 쓴 문자열이 아니라 프로그램이 보호된 계정 등록 정보로 판정하고, 표시가 없거나 판단할 수 없으면 실계정으로 본다. 분류 기능의 첫 등록 대상은 평가 fixture와 연습 대상의 계정이다.
  - 이 결정은 CLAUDE.md 절대규칙 2("우리가 가진 자격은 LLM 입력에도 넣지 않는다")의 예외이고, 범위는 시험 계정에서 대상이 발급한 세션 값(쿠키·토큰)이 도구 출력으로 모델에 가는 것까지다. 비밀번호는 어떤 계정이든 모델에 넣지 않고 로그인은 프로그램의 인증 준비가 맡는다. 고객 실계정·제어 비밀·판정 표식은 예외가 아니다.
  - 외부 API 모드에서는 시험 계정 세션도 제공자로 나가므로, 사전 공지·승인([external-llm-notice-ko](external-llm-notice-ko.md))을 받은 회차에서만 켠다. 평가 회차에서는 원문 통과 모드처럼 명시적으로 켜고 회차 기록에 남긴다.
  - 분류의 저장·승인 주체는 [계약 §9-7](contracts/exploration-boundary.md#9-열린-항목)에서 정한다. CLAUDE.md 절대규칙 2도 같은 효력 시점으로 맞춘다.
- **도구 조건**: WebSearch는 외부 API 모드에서만 켜고 완전 로컬 모드에서는 끈다. 진단 단계에서는 E②를 거치지 않는 브라우저 도구를 쓰지 않는다(원본도 브라우저 MCP를 기본으로 꺼 두며, 11/05 원본 회차의 MCP 호출은 0회). 완전 로컬 모드에서는 탐색의 외부 CDN 요청도 막는다.
- **측정의 위치**: 개발 중 보존율 비교는 어떤 통제를 먼저 풀지 고르는 진단 도구다(시험대 전용, 제품·고객 회차에 넣지 않음). 결과 전 고정은 발표 전 공식 측정 때만 하고, 성과가 나오지 않은 항목은 그대로 남긴다.

초기 로컬 기준 모델(검증 전) `Qwen/Qwen3.5-35B-A3B`를 연결·측정한 뒤 프롬프트·도구 입력·실행 피드백을
개선하고, 확인된 지식 부족에 RAG를 더한다. 남은 실패는 모델·서빙·실행 구조와 비교하며
반복 문제의 파인튜닝은 최후 수단으로 둔다. RAG·학습 GPU·파인튜닝은 첫 통합 진단의 선행 조건이 아니다.

로컬 기본 방침과 별도로, 첫 개발용 실모델 검증을 위한 [OpenRouter 연결](openrouter-first-diagnosis.md)이
`qwen/qwen3.5-35b-a3b` 고정으로 구현돼 있다. 명시적으로 승인된 비민감 개발 환경에서만 선택하며,
연결 구현을 실제 API 호출·진단 성공이나 로컬 배포 성능의 증거로 해석하지 않는다.

이동찬의 개발 방침을 기존 팀 계약의 일괄 채택이나 구현 완료로 해석하지 않는다.

## Phase 2 — 엔진 개선 (핵심 · Go) + 얇은 IDOR 통합
> 내부 순서: E②·E③ 먼저 → 얇은 IDOR 경로로 통합 검증 → E①·E④(효율).

### E② 실제 전송 통제 (Go, 네트워크 경계) — "전수" 주장 금지
- **포크 당시 문제:** ARTEX는 bash에 프록시 env만 주입(worker.go:452), env 무시 도구·MCP·커스텀 프로세스는 우회, MITM 실패 시 무기록 터널링 경로 있음(traffic.go:164). 백서 §6.5와 일치.
- **정의**: 지원하는 실행 경로의 실제 요청을 검사하고 승인 경로 우회 통신을 차단, 지원 안 하는 경로는 명시적 차단/제외. HTTP 요청부터 완성 → 셸·MCP별 통제 범위를 하나씩 검증한 뒤에야 범위 주장.
- **Go 네트워크 경계에서 집행**(최종 전송 지점). 요청 예산·승인도 여기서.
- **11/11 결정 — 탐색과 진단의 경로 분리, 원본 능력 보존 우선.** 탐색(크롤링·브라우저 정찰)은 E②를 거치지 않고 가벼운 탐색 경계(승인 origin·경로, 리다이렉트 재검사, 내부망·메타데이터 차단, 시간·요청·동시성 상한)만 지난다. 진단 요청만 E②를 거친다. 탐색·진단 성능을 깎는 통제는 줄인다. 아래 11/05 결정의 "E② 하나로"는 진단 요청에 적용한다. 진행 순서·담당 세부는 이동찬이 이 문서에 따로 반영한다.
- **11/05 결정 — 12/18 필수, 프록시를 실제 통제 경계로.** 원본 Planner·Worker 루프와 Bash 도구는 유지하고, 엔진의 진단 요청이 대상에 닿는 길을 E② 집행 프록시 하나로 만든다(11/11부터 진단 요청에 적용, 원본 엔진의 대상 요청은 1회차 측정에서 96%가 Bash의 curl). 환경변수가 아니라 실행 환경(망)에서 우회를 막고, HTTPS는 TLS 검사 경로로 보며 검사 실패 시 차단한다. 지원 안 하는 도구·프로토콜은 명시적으로 차단·제외하고, 검증한 범위만 통제했다고 말한다.
  - 문구: **승인한 대상·범위·허용 메서드·예산에 따라 요청을 통제하고, 관측 가능한 대상 상태의 변화를 별도로 측정한다.** 상태 변경 자동 판별은 주장하지 않는다.
  - 정책 차단은 대상 응답과 분리한 신뢰된 실행 결과로 워커에 전달하고, 반복 거부는 최소 E① 연결로 프로그램이 재시도·예산·종료를 관리한다.
  - 세부(호출 귀속·TLS·결과 형식·수용 시험)는 E② 프록시 통제 초안(#189)과 공통 계약(#183) 개정에서 정한다. 등록 GET 통합 결과와 원본 루프를 통제한 통합 진단 결과는 따로 보고한다.
  - 공식 비교의 개선 후 엔진은 E②를 켠다(배치·측정은 평가 프로토콜 §2·§8).
- **11/11 결정 — 브라우저 크롤링의 쓰기는 탐색 시작 전 승인 한 번으로 정한다.** 읽기만 승인하면 GET·HEAD만 보내고 쓰기는 발견 기록으로 남긴다. 쓰기까지 승인하면 승인된 메서드의 쓰기를 건별 확인 없이 보낸다. 탐색 경계가 대상·경로·메서드·상한을 집행하고(11/11 경로 분리, E②의 요청별 감사 구조는 쓰지 않음) DELETE와 위험 경로 차단은 유지한다. 공식 E② 정책과 공식 비교 회차에는 적용하지 않는다. 브라우저 수용시험은 전용 정책으로 평가 경로에서 이 규칙을 시험한다. 시험 기준은 [탐색 경계·보존 수용시험](evaluation/browser-acceptance.md)에 있다.

### E③ 구조화 증거 판정 (오라클) — **Go 확정**
- **포크 당시 문제:** 재검증 저장이 판정값+설명·증거 문자열 검사에 의존했다(finding_retests.go:192는 당시 참조). 현재 지원되는 [E③ 구조화 증거 판정](contracts/e3-oracle.md)과 최초 확정 저장 경계가 구현돼 있으며, 유형별 필수 증거·정상 대조가 부족하면 UNDECIDABLE로 남긴다. 일반 HTTP 후보나 미지원 유형까지 자동 확정한다고 확대하지 않는다.
- **Go로 구현.** abc2lab-dast의 `oracle.py`(~130줄 순수 함수) = **Go 구현의 설계 스펙**, abc2lab-dast 테스트 = **Go 테스트 스펙**으로 이식. (사이드카 미채택 — 커널이 작아 Go 포팅이 사이드카 운영보다 쉽고, E²와 밀착, 단일 바이너리가 온프레 배포에 유리)

### 얇은 IDOR 통합 경로 (E②·E③ 통합 테스트, Phase 2 초기)
- 경로: 테스트 계정 A의 비민감 자료 → B 접근 시도 → 전송 정책(E②) 확인 → 표식·기대권한 비교(E③) → 판정 → 감사 기록.
- 정책과 오라클이 실제로 연결되는지 확인하는 walking skeleton. **초기 조회(읽기) 한정**, 상태변경은 별도 승인 시험환경. destructive-last ≠ 실행 허가.
- **11/04 결정 — IDOR은 원본과의 수치 비교가 아니라 "원본에 없는 검증 기능 추가"로 제시한다(최민준).** 단계: 1단계 운영자 수동 세션·등록 자원·GET 2회로 수평 IDOR 1건을 끝까지(조회 → 판정 → 저장 → 표시) / 1.5단계 LLM이 로그인을 명령하고 프로그램이 비밀을 채워 보내고 신원을 확인(E② 기능 필요) / 2단계 LLM이 후보를 제안하고 프로그램이 검증·승인.
- **11/05 결정 — 쓰기 IDOR은 12/18 범위에 넣되, 시간이 부족하면 먼저 뺀다.** E②의 승인된 쓰기가 필요하다.

### E① 종료·재계획 / E④ 중복·재사용 (효율, 이후)
- E① planner에 '검사완료·발견없음'/'증거부족'/'정책상 검증불가' 명시 처리(planner.go:303).
- E④ 계정·자원·조건·목적 기준 dedup + 관찰 재사용(상태변경 시 무효화)(planner.go:335).
