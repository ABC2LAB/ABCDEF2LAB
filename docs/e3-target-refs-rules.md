# E③ 세대·인스턴스 참조 규칙안 — 리셋·인스턴스 교체

- 상태: 제안(2026-11-19, 최민준). 리뷰 이동찬. [E③↔E② v3 계약](contracts/e3-e2-v3-journal-contract.md) §10 "송신 활성화 전 확정 필수" 3번(§6 리셋·인스턴스 교체 규칙)에 대한 안이다.
- 범위: `generation_ref`·`instance_ref`를 언제 바꾸고 언제 같은 값으로 두는지. 발급 시점(실행 시작, `runs/<job>/e3-target-refs.json` 동결)과 변경 검사(확정 단계 시작 때 리셋 게이트가 다시 계산해 다르면 `start_refused`·`target_changed`), "모르면 새로 발급"(`gen-x-`·`inst-x-`)은 #761 그대로 둔다.
- 코드: `cmd/first-controlled-diagnosis/product_e3_target_refs.go`. 송신 경로(제품 Host·v3 Recorder·E③ 목적 송신)는 건드리지 않는다.

## 1. 원칙

1. 서버가 **확인한** 대상 상태만 같은 참조의 근거가 된다. 확인할 수 없으면 기존 참조를 재사용하지 않는다(모르면 새로 발급).
2. 대상이 바뀌었는데 같은 참조가 남는 경우가 없어야 한다. 반대로 바뀌지 않았는데 참조가 바뀌는 것(보수적 오판)은 허용한다. 그 대가는 확정 단계가 시작하지 않는 것(`target_changed`)이지 거짓 CONFIRMED가 아니다.
3. "모름"을 `gen-x-`로 발급하면 그 회차의 확정 단계는 늘 `target_changed`로 멈춘다(#761). 그래서 "이어졌는지 모름"과 "지금 상태를 모름"을 구분한다. 지금 상태를 모르면 `gen-x-`·`inst-x-`이고, 회차 사이 연속성을 모르는 것은 아래 §3처럼 값만 회차마다 다르게 한다.

## 2. 서버가 변화를 알아채는 신호

| 변화 | 서버가 보는 것 | 바뀌는 참조 |
|---|---|---|
| 대상 재승인·철회·만료 | 대상 기록의 승인 판·승인 시각·상태(철회·만료면 세대를 모름) | 세대(→ 인스턴스) |
| 우리 확정 쓰기가 대상에 남음 | 쓰기 기록(쓰기 줄 참조·회차·시각). 기록하고 나서 보낸다(#738) | 세대 |
| 대상 리셋 | 운영자의 리셋 확인 기록(`POST /api/product/targets/{id}/reset-confirmation`: 확인자·시각, 진술 문장 필수, 남은 확정 쓰기가 있을 때만, 실행 중이면 `reset_run_active`로 거부) | 세대 |
| 접속 주소·포트·TLS 키 | 대상 기록의 고른 IP·주소 집합·포트·TLS 공개 키(SPKI). E²는 실행 내내 그 IP(`ConnectIP`)와 키(`TLSSPKISHA256`)로만 연결한다 | 인스턴스 |
| **회차 경계**(이 안에서 더함) | 그 회차의 job | 세대·인스턴스 둘 다 |

실행 중에 대상이 다른 IP나 다른 TLS 키로 바뀌면 E²가 그 연결을 받지 않는다. 그래서 응답이 없고(결과 불명·실패) CONFIRMED가 나올 수 없다.

## 3. 회차 사이에는 재사용하지 않는다

회차와 회차 사이에 대상이 이어졌는지 서버는 증명할 수 없다.

- 운영자가 리셋 확인 없이 대상을 되돌릴 수 있다(상태 변경 재현 전에는 대상을 리셋한다, CLAUDE.md 규칙 6. 연습 대상은 새 컨테이너로 띄운다).
- 같은 IP·같은 TLS 키로 인스턴스를 다시 만들면 §2의 어떤 신호도 바뀌지 않는다.
- 다른 회차의 진단 Worker가 승인된 쓰기 메서드로 대상 상태를 바꿨을 수 있다(자동 모드 쓰기, C21). 이 쓰기는 확정 쓰기 기록에 없다.

그래서 세대 digest 재료에 회차(job)를 더한다. 같은 대상 상태여도 회차가 다르면 세대가 다르고, 인스턴스는 세대를 품으므로 같이 다르다. 둘 다 "아는" 참조라 확정 단계는 그대로 돈다. 한 회차 안에서는 같은 job으로 다시 계산하므로, 상태가 같으면 같은 참조이고 변경 검사도 그대로다.

이 참조를 회차 사이에 비교하는 곳은 지금 없다. 접근통제 지도·판정 기록은 한 회차(task) 결속 안에서만 맞댄다. 앞으로 회차를 넘어 관찰을 재사용하려면(E④) 이 규칙에서는 늘 "다른 세대"로 보이므로, 재사용 쪽이 따로 연속성 근거(리셋 확인 직후 회차 등)를 세워야 한다.

## 4. 한 회차 안의 한계와 왜 거짓 CONFIRMED가 아닌가

한 회차 안에서, 같은 IP·같은 TLS 키로, 운영자 확인 없이 인스턴스를 다시 만들면 서버는 알 수 없다(참조가 그대로다). 이 경우에도 CONFIRMED가 거짓으로 나오지 않는 이유:

- 확정 단계는 회차마다 새 표식(난수)으로 자기 객체를 만들고 곧바로 A가 읽고 B가 읽는다. 그 사이에 인스턴스가 바뀌면 객체가 없어서 조회가 정상 응답이 아니거나 표식이 없다. 그래서 CONFIRMED가 아니다.
- 다른 회차나 바뀌기 전 인스턴스의 객체는 표식이 달라 증거가 되지 않는다.
- 신원(A·B가 서로 다른 주체인지)은 확정 단계를 시작할 때마다 다시 확인한다.

남는 것은 "판정이 어느 인스턴스에서 나왔는지" 기록이 덜 정확해지는 것이다. 판정 자체는 거짓이 되지 않는다.

## 5. 후속 제안(이 안에서 구현하지 않음)

- **인스턴스 식별 값**: 대상이 부팅·인스턴스 식별 값을 주면(예: 응답 JSON의 칸 하나), 선언의 선택 칸으로 그 경로·칸을 받는다. 확정 단계 시작·끝에 E²가 읽어 대조하면 §4의 한계를 줄인다. 대상으로 보내는 목적 요청이 필요하다. 그래서 E② 송신 경로(이동찬 몫)와 같이 정한다.
- **전송 계층 신호**: TLS 세션 재개 실패처럼 연결 쪽에서 인스턴스 교체를 알 수 있는 신호도 E² 몫이다.

## 6. 바뀌는 것

- 동결 파일 판 `e3-target-refs/v2`, digest 영역 `e3-target-generation/v2`·`e3-target-instance/v2`. v1 파일은 읽지 않는다. 그래서 바꾸기 전에 시작한 회차는 확정 단계 결속이 비어 `disabled`·`binding_invalid`로 꺼진다(보수적).
- `issueTargetRefs(target, job, random)`, `currentTargetRefs(target, job)`, `productTargetGeneration(rec, reset, job)`. 변경 검사는 결속의 `job_ref`로 다시 계산한다. 회차를 모르면(빈 job) 세대를 모른다.

## 7. 시험

- `TestProductTargetRefsNotReusedAcrossRuns`
  - 같은 대상 상태에서 두 회차가 서로 다른 세대·인스턴스를 받고, 둘 다 아는 참조다.
  - 같은 회차에서 다시 계산하면 같고 변경 검사가 통과한다.
  - 앞 회차 참조를 다음 회차 결속에 실으면 `target_changed`다.
  - 회차를 모르면 세대를 모른다.
- `TestProductTargetRefsChangeWithTarget`(#761, 회차를 고정해 그대로): 승인·쓰기·리셋 확인·주소·포트·TLS 키가 바뀌면 참조가 바뀐다.
- `TestReadTargetRefsStrict`: v1 동결 파일을 읽지 않는다.
