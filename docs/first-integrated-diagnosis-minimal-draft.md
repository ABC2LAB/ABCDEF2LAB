## 1. 목적과 완료 기준

첫 회차에서 연결을 확인할 경로는 다음과 같다.

`실제 LLM 도구 호출 → 프로그램의 등록 자원·세션 재검증 → 지원 E② 조회 전송 → 감사 마감 → E③ 판정 → revision·finding 저장 → 기존 결과 조회`

이 경로의 연결 실패와 모델의 도구 선택 실패를 구분하기 위해, 운영자가 LLM 없이 같은
검증 경로를 직접 호출하는 사전 점검도 제안한다. 수동 호출도 프로그램의 재검증·E②·감사·E③·저장을
그대로 거치며 별도 승인을 받은 새 회차로 실행한다. 수동 점검과 실제 LLM 회차가 대상 요청 2회를
공유하거나 자동으로 이어 실행되는 구성은 제안하지 않는다.

**이동찬 담당 준비 완료**는 기동기·실제 권위 공급자·서버 조립 구현과 검증이 끝나,
다른 담당자의 실제 산출물을 약속한 계약으로 연결하면 첫 통합 진단을 시작할 수 있는 상태다.
다른 담당자의 구현 대기와 실제 첫 진단 실행·결과 확인은 이 준비 완료 기준에서 제외한다.
합친 뒤 이동찬 소유의 필수 공급부를 추가로 구현해야 한다면 준비 완료로 세지 않는다.

첫 회차는 공개 연습 대상 Juice Shop v15.0.0의 **비평가·조회 중심 통합 확인**으로 제안한다.
`EvalRunID`는 비우며, 이 회차를 공식 baseline 비교나 로컬 모델 충분성의 근거로 계산하지 않는다.

### M01. 운영·기동·종료 감독

- 이동찬의 이번 실험 운영 겸임 방침은 §5에서 채택했다. 실제 머신의 운영 권한과 기동·종료 책임 이행은 착수 전에 확인한다.
- 새 전용 실행 환경에서 시작하고 예약 실행·자동 재시작을 비활성화한다. API listener는 loopback에 연결한다.
- 기동기는 실제 작업·worker·chat·자식 실행을 추적하고, 신규 실행 차단과 종료 대기를 수행한다.
- `StartControlledReadAssembly` 호출 전에 실제 작업·queue·trigger의 정지와 신규 실행 차단을 확립한다.
  빈 DB나 단일 HTTP 전송기의 inflight=0만으로 전체 작업 종료를 증명하지 않는다.
- 종료는 신규 실행 차단 → 실행·자식 drain → 감사·저장 결과 확인 → 공급자 lease·자원 해제 순서로 조립한다.
  timeout이면 미완료 상태와 소유권을 유지한다. 결과 불명인 저장을 새 실행으로 자동 재시도하지 않는다.

### M02. 신뢰 기동기 내부의 실제 권위 공급자

현재의 typed 조립 경계를 사용해 다음을 실제로 공급·검사하도록 구현한다. 아래는 채택한 구현 범위이며 실제 공급부 검증은 착수 조건으로 남는다.

- 장기 root FD, 배타 writer·배치/복원 근거, 실제 자식 추적과 취소 수명
- 등록된 namespace·instance·store epoch와 불변 key identity/version의 실제 결속
- 실제 checkpoint·revision·descriptor 공급부 및 실행별 publisher
- 정확한 request·Expected에 결속되고 Source → Prepare → 저장 반환까지 유지되는 finalization lease

파일 존재·권한 비트·동일한 참조 문자열·고정 성공 callback으로 이 권위를 대신하지 않는다.
설치/초기 등록은 운영자가 명시적으로 수행하며, 기동 중 새 디렉터리·빈 DB·새 epoch를 자동 승인하지 않는다.
필수 자료 누락·권위 회수는 신규 실행과 발급을 차단한다. 이미 알려진 저장 성공과 결과 불명은 구분한다.
모델·일반 API 입력은 이 권위를 발급하거나 키·저장소 관리 자격을 획득하지 못해야 한다.

**§5에서 채택한 단계적 수용 범위는 주경로 연결 확인이다.** 같은 프로세스의 공급자로 실제 SQL
내구성 ACK와 전송·판정·저장 연결은 확인할 수 있지만, 별도 프로세스·UID의 독립 감사 저장
서비스와 권한 분리를 검증한 것으로 계산할 수 없다.
이 회차의 SQL ACK는 실제 실행 DB의 저장 성공 확인이며, CPD01이 요구하는
별도 저장 서비스의 독립 내구성 ACK를 뜻하지 않는다.

[감사 경계의 CPD01·CPD02](contracts/e2-audit-journal.md)는 별도 수용 항목으로 유지한다.
[호스트 인증 초안의 AH01~06](contracts/audit-state-host-auth-proposal.md)을 확정·구현 완료로 승격하지 않는다.
독립 감사 서비스·인증·권한 분리는 후속 수용에서 실제 환경의 증거로 확인한다.

### M03. DB와 보호 경로

- 첫 회차 전용 PostgreSQL 16 DB를 하나 사용하고 필요한 core·감사 checkpoint·evidence revision schema를 명시적으로 준비한다.
  key registry를 같은 DB에 둘지와 필요한 schema·GRANT는 실제 공급부 연결 때 확인한다.
- 설치용 계정은 migration·초기 설정에 사용하고, 실행용 계정에는 필요한 권한만 부여한다.
  실행용 계정을 superuser나 전체 테이블 소유자로 두지 않는 안을 권장한다.
- `DataDir`, `KeyDir`, `StateDir`, `SnapshotDir`, journal·descriptor 경로를 설정에 명시한다.
  키는 `DataDir` 밖에 두고, 역할별 소유권과 디렉터리 0700·비밀 파일 0600 조건을 확인한다.
  경로·파일 권한만으로 M02의 신뢰가 성립한다고 보지는 않는다.
- state root와 공급자가 보유한 root가 같은 배치를 가리켜야 한다. 기동 중 누락 경로를 자동 생성해 통과시키지 않는다.
- 첫 회차 중 장애·재시작이 생기면 회차를 중단하고 근거를 보존한다.
  재개·복구는 연속성 확인 없이 진행하지 않으며, 새 회차는 명시 승인과 대상 reset 뒤 별도로 시작한다.

PostgreSQL 객체 소유자는 자신의 권한을 다시 부여할 수 있으므로 설치·실행 역할 분리 시
소유권도 함께 확인한다. [PostgreSQL 16 권한 문서](https://www.postgresql.org/docs/16/ddl-priv.html)

### M04. 첫 회차 승인과 한도

계정 A의 비민감 객체 하나에 대해 owner A 조회와 cross B 조회를 한 번씩 수행한다.
A/B 모두 해당 **시험을 실행할 승인**이 있어야 하며, 앱에서 B가 그 객체를 읽어도 되는지는
별도의 KG 정책과 실제 관찰로 판정한다. GET 자체를 비변경성의 근거로 쓰지 않는다.

정확한 origin·접속 IP·URL·계정 참조·자원 승인·응답 투영을 설정으로 등록한다.
로그인·계정 준비·reset/health는 **진단 회차 시작 전**, 별도 승인된 fixture 절차로 완료하고
그 실제 근거와 요청 수를 전달받는다. 아래 2회는 해당 승인된 진단 전송의 상한이며
LLM API 호출 수나 fixture 준비 요청 수가 아니다. fixture 준비를 진단 중에 다시 실행하지 않는다.

| 설정 | 채택 초기값 | 착수 전 확인 |
|---|---|---|
| 대상 요청 상한 | `VerifyRead`의 owner GET 1회 + cross GET 1회, 성공 시 정확히 2회 | 거부·중단 때는 0~2회일 수 있음. 부족한 요청을 자동 보충하거나 새 회차로 재시도하지 않음 |
| 별도 대상 health GET | 진단 회차 중 0회 | 아래 health 경계와 실제 송신 집계를 확인 |
| 요청 간 최소 간격 | 500ms | 대상 승인 조건과 충돌하지 않는지 확인 |
| 대상 요청 timeout | 10초 | 환경 지연과, 관측 기반 health 정책을 켠 경우 해당 임계치 제약 확인 |
| 승인 유효기간 | 준비 완료 후 최대 15분 | 실제 세션·승인 중 가장 빠른 만료 적용 |
| 응답 크기 상한 | 1MiB | fixture의 실제 응답 크기 확인 |
| 종료 대기 | 60초 | 초과하면 미완료·자원 보유 상태 유지 |
| 자동 재시도·리다이렉트 추적 | 자동 재시도·추적 비활성 | 리다이렉트 응답은 거부·기록. 지원 경로에서 재시도·바인딩 이후 새 최종 URL이 생기면 전송 전에 대상 origin을 다시 검사 |
| 공유예산 | 첫 회차에서 명시적 비활성 | 승인/발급 실패를 `CumulativeBudget=nil`로 숨기지 않음 |
| 평가 연결 | `EvalRunID=""` | 비평가 결과를 공식 평가 회차로 승격하지 않음 |

숫자는 §5에서 채택한 **미실측 초기 한도**다. 승인자가 확인한 값을 실제 설정에 전부 명시하고,
코드 기본값을 승인으로 해석하지 않는다. 앱 URL·계정·표식·포트는 코드에 하드코딩하지 않는다.

### 도구 입력과 전송 전 재검증

아래는 **연결 시 수용할 제안 조건**이며 새 도구 schema나 구현 완료를 뜻하지 않는다.

- 모델이 전달할 값은 등록된 조회 자원 참조와 owner/cross 계정 label로 한정한다.
  실제 JSON 필드명은 연결 담당 리뷰에서 확정한다. 원시 URL·인증 헤더·쿠키·토큰·키·승인 권위는 받지 않는다.
- 프로그램이 같은 실행의 `Resources`·`Sessions`에서 참조를 다시 해석하고, 허용 계정 조합·검증된 신원·만료·
  `Accounts`·`ReadOnly` 승인·KG 문맥을 대조한다. task·run·intent와 정확한 origin/IP/URL·GET·승인 범위도
  신뢰된 설정에 결속한다. 미등록·불일치·만료 입력은 **대상 전송 전에 거부**한다.
- LLM이 도구를 호출하지 않거나 잘못된 참조를 내면 미실행으로 남긴다. 전송 일부만 끝나거나 관찰이 부족하면
  해당 거부·실패·UNDECIDABLE 사유를 남기며, 미실행을 “취약점 없음”으로 기록하지 않는다.
- 운영자의 수동 trigger도 이 재검증 경로로만 연결한다. 우회 전송이나 프로그램의 자동 승인 발급 경로를 만들지 않는다.

### 두 요청과 health의 경계

첫 회차 진단 중 별도의 대상 health GET은 0회로 채택했다. fixture 준비의 health 확인은
회차 시작 전에 끝내고 근거를 인계한다. 서버·DB 자체의 준비 점검은 대상 앱 HTTP 요청과 구분한다.
[현재 E② health 중지 정책](contracts/e2-http-health-stop.md)은 전송기의 실제 요청을 수동적으로 관측하며
추가 probe를 만들지 않는다. 이 정책을 켜더라도 관측 대상은 위 owner/cross 두 요청뿐이며, 표본을 채우기 위한
추가 전송은 허용하지 않는다. 정책을 끄면 health 판정도 수행했다고 기록하지 않는다.

`VerifyRead` 경로와 실제 송신 집계에서 owner GET 1회 + cross GET 1회, 별도 health·retry·redirect 요청 0회를
확인하는 것을 수용 조건으로 둔다. 두 요청 안에서 지원할 수 없는 준비·검증 단계가 있으면 회차를 시작하지 않고
구성안을 다시 검토한다. 이 문서 작성만으로 해당 계측·수용시험을 통과했다고 주장하지 않는다.

## 3. 첫 회차에서 확인할 범위와 후속 항목

| 첫 회차 확인 대상 | 등록된 조회 경로의 E② 집행, 실제 owner/cross 관찰, journal·동기 SQL ACK·마감, E③ 판정·revision·저장·기존 조회의 같은 실행 결속 |

| 독립 감사 권한 분리 | 별도 서비스·실제 주체/권한·회수·복원 근거와 CPD 수용시험 뒤 확인. 이번 구성만으로 완료 주장 금지 |

| 이후 개발 | E① 종료·재계획, E④ 중복·재사용, 공식 반복 평가, 공유예산 활성화는 해당 후속 계획에서 진행 |

실제 LLM 호출 없이 실행한 합성 시험과 실제 첫 진단은 구분한다.
이 문서 작성 시점에 위 수용시험이나 실제 회차를 완료했다고 기록하지 않는다.

초기 로컬 기준 모델(검증 전)과 개선 순서는 [LLM 도입·개선 계획](llm-adoption-and-improvement-plan.md)을 참조한다.
로컬 기준 모델 선정만으로 준비 완료가 되지 않으며, RAG·파인튜닝·학습용 GPU를 M01~M04나 아래 착수 조건에 추가하지 않는다.

## 4. 실제 입력과 담당자 협의

세부 항목의 단일 대장은 [첫 회차 입력·공급 주체 대장](contracts/first-idor-host-inputs.md)이다.
아래 표는 기존 담당 경계에 따른 확인 창구이며 새로운 발급 권한이나 담당 확정을 뜻하지 않는다.

| 준비물 | 확인 창구 | 통합에 필요한 실물 |
|---|---|---|
| 기동기·호스트 권위·서버 metadata·DB/state | 이동찬, 실험 운영 역할 | 실제 typed 공급자·배치/키·epoch 근거·기동/종료 handle·보호 경로 |
| 승인된 A/B 계정·세션·조회 자원 | 최민준이 fixture를 준비하며 실제 승인/인증 주체와 이동찬이 인계 확인 | 신원 확인 상태·만료·정확한 시험 승인·`Accounts`/`ReadOnly`·E② snapshot. 실제 자료는 준비·검증 대기 |
| 동결 KG·정책·표식 | 1단계 실제 reader = [fixture 레지스트리 #193](https://github.com/ABC2LAB/ABCDEF2LAB/pull/193) resolver(최민준, #193). 이경준 KG 계약 정합 리뷰·내용 digest/generation 결속 저장 확인, 윤재상 보조, 최민준 의미 검토 | 실제 reader·snapshot/version/digest·정책·표식의 같은 문맥 |
| 비평가 대상·fixture/reset | 윤재상, 최민준 계약 확인 | 실제 instance와 reset/health 성공 뒤 발급된 준비 묶음·generation |
| 모델/profile·접속 | 이동찬·모델 운영 역할, 최민준 조건 확인 | 기존 선택을 반영한 실제 profile·접속·샘플링·보호된 키 공급 경로 |

### fixture 인계와 결과 격리

최민준이 준비할 A/B fixture 범위는 다음과 같다. 담당 방침 채택은 별도의 실행 승인이나
자격 자료가 이미 준비됐다는 뜻이 아니다. 실제 reset/health·generation 발급 책임은 기존 입력 대장을 따른다.

- A 소유 객체에 canary를 미리 심는 작업은 별도 승인된 fixture 준비 절차에서 수행한다.
  진단 E② 경로에서는 setup POST를 허용하지 않는다. 최종 reset·준비 묶음·KG snapshot·canary가 같은 세대를
  가리킴을 확인하고 인계한다. canary 준비 뒤 reset이 바뀌면 자료를 재검증하며 오래된 표식을 재사용하지 않는다.
- A/B 세션·토큰은 0600의 보호된 비밀 파일로 인계하고, 문서·모델·로그에는 보호 참조만 사용한다.
  신원 확인 상태·만료와 `Accounts`/`ReadOnly`를 포함한 시험 승인은 E② snapshot으로 전달한다.
- 비평가 객체는 운영자가 앱에서 직접 확인해 선택한다. GT·풀이·챌린지 해결 상태를 선택·탐색·판정 입력으로 주지 않는다.

`EvalRunID=""`로 저장한 비평가 결과는 기존 운영 결과 조회에만 사용하고, 공식 평가 회차로 승격하지 않는다.
[평가 판정 페이지 제안](contracts/verdict-record-page-api-proposal.md)의 `run_id` 필수·비평가 issuance 제외와
[판정 레코드 계약](contracts/verdict-record.md)을 따른다. 빈 Go 참조가 DB의 비평가 `eval_run_id=NULL`로
저장되는 경계까지 확인해야 하며, 문자열이 비었다는 사실만으로 export/scorer 격리가 입증되지는 않는다.
다음은 **착수 전 확인할 수용시험이며 아직 미실행**이다.

1. 비평가 저장 행이 정확한 task·실행의 기존 결과 조회에 남고, 평가 회차로 재결속되지 않는지 확인한다.
2. 비평가 행이 verdict-page 평가 export에 포함되지 않는지, 평가 모드의 누락된 `eval_run_id`가 거부되는지 확인한다.
3. scorer가 비평가 결과를 공식 지표에 합산하지 않는지 실제 수집 경로와 함께 확인한다.
   export/scorer 연결이 아직 없다면 이 검증은 미완료로 남긴다.

우리가 준비한 비밀값·키·비밀번호·쿠키·토큰 원문은 문서·모델 입력·공유 로그에 넣지 않는다.
확인 기록에는 보호 경로·참조·유효기간과 검증 결과를 사용한다.
평가 정답·풀이·챌린지 해결 상태는 탐색·판정 입력으로 제공하지 않는다.

## 5. 팀 리뷰와 착수 조건

2026-11-05 팀 합의: **M01~M04를 아래대로 채택한다**(이동찬 안, 최민준·이경준 확인).
채택은 첫 회차의 운영·DB·한도 방침을 정한 것이며, 실제 준비 완료·권한 발급·진단 시작을 뜻하지 않는다(아래 착수 조건 1~4).

| 결정 | 결정 항목 | 채택 내용 | 준비·검증 담당 |
|---|---|---|---|
| M01 | 이동찬의 임시 운영 겸임과 단일 환경·실행·기동기 범위를 채택할까? | **채택.** 이동찬이 첫 실험 운영자를 겸임한다. 단일 격리 Linux 환경에서 서버 1개·동시 실행 1개로 제한하고 예약 실행·자동 재시작을 끈다 | 이동찬: 기동 전 검사와 실행 종료·drain·감사 마감 확인 |

확인 창구는 채택한 방침의 준비·검증 담당이다. 실제 운영 권한·DB 자격과 회차 승인은 아래 착수 조건에 따라 확인한다.

리뷰 결과는 항목별 채택/수정/보류, 근거, 확인 담당과 수용 범위를 남긴다.
개발 계획·기존 CPD/AH 계약에 반영할 변경은 해당 담당자 리뷰로 조율한다.

착수 전에는 다음을 확인한다.

1. M01~M04의 결론과 실제 운영·승인 역할을 확인한다.
2. 실제 기동기·권위 공급자와 입력 연결을 구현·검증한다. 누락 자료를 성공 callback으로 대체하지 않는다.
3. 팀원 산출물을 같은 실행 빌드에 결합하고, DB·보호 경로·필수 공급자·수명·설정의 기동 전 검사를 통과한다.
4. 실제 작업·예약 실행·trigger 정지와 신규 실행 차단을 확립한 뒤 승인된 한 회차를 시작한다.

최초 실제 진단의 실행·결과 대조는 위 준비 완료 이후의 통합 단계다.
문서 초안 작성·리뷰·코드 시험 통과만으로 진단 시작 가능이나 진단 완료를 선언하지 않는다.
